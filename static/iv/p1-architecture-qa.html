﻿# 系统架构 常见题目（附答案）

系统设计基础

1. 系统设计面试考察哪些核心维度？

答案：
- 需求分析：功能需求、非功能需求（QPS、存储量、延迟要求）
- 容量估算：DAU、读写比例、峰值 QPS、存储规模
- 高层架构：核心组件拆分、数据流向
- 数据库设计：数据模型、选型（SQL vs NoSQL）、索引
- 扩展性设计：水平/垂直扩展、缓存、分库分表
- 高可用设计：冗余、故障转移、监控告警

2. 什么是 CAP 定理？

答案：
分布式系统无法同时满足以下三点，最多满足两项：
- C（一致性 Consistency）：所有节点同一时刻数据一致
- A（可用性 Availability）：系统始终可响应请求
- P（分区容错性 Partition Tolerance）：网络分区时系统仍能工作

由于网络分区在生产环境不可避免，实际只能在 CP 和 AP 间取舍：
- CP 系统（如 Zookeeper、HBase）：保证一致性，牺牲部分可用性
- AP 系统（如 Cassandra、DynamoDB）：保证可用性，数据最终一致

3. 什么是 BASE 理论？

答案：
BASE 是 CAP 中 AP 方向的延伸，适用于高可用分布式系统：
- BA（Basically Available，基本可用）：核心功能可用，非核心可降级
- S（Soft State，软状态）：允许中间状态（数据同步中）
- E（Eventually Consistent，最终一致）：数据最终达到一致，允许暂时不一致

对比 ACID：ACID 是强一致性（数据库事务），BASE 是弱一致性（分布式系统）。

4. 水平扩展和垂直扩展的区别？

答案：
- 垂直扩展（Scale Up）：提升单机配置（CPU、内存、硬盘），简单但有上限，成本高
- 水平扩展（Scale Out）：增加服务器数量，理论上无上限，需要无状态架构支持

现代云原生系统优先水平扩展，通过无状态设计（Session 外置到 Redis）、负载均衡实现弹性扩容。

5. 什么是负载均衡？常见算法有哪些？

答案：
负载均衡将流量分发到多台服务器，避免单点压力过大。常见算法：
- 轮询（Round Robin）：依次分发，适合同构服务器
- 加权轮询：按服务器权重分发，适合异构服务器
- 最少连接（Least Connections）：分发给当前连接数最少的服务器
- IP 哈希（IP Hash）：同一 IP 总分发到同一服务器（有状态服务）
- 一致性哈希：节点增减时只迁移少量数据（适合缓存集群）

缓存策略

6. 缓存有哪些常见读写策略？

答案：
- Cache-Aside（旁路缓存）：应用直接管理缓存，读时先查缓存，未命中再查 DB 并回填；写时先更新 DB，再删除缓存。最常用。
- Write-Through：写操作同时写缓存和 DB，一致性好但写延迟高
- Write-Behind（Write-Back）：只写缓存，异步刷新到 DB，写性能好但有数据丢失风险
- Read-Through：缓存自动回填，应用只与缓存交互

7. 什么是缓存穿透、击穿、雪崩？

答案：
- 缓存穿透：查询不存在的 Key，每次都打到 DB。解决：空值缓存（短 TTL）或布隆过滤器
- 缓存击穿：热点 Key 过期瞬间，大量请求同时打到 DB。解决：互斥锁（只允许一个请求回填）或逻辑过期（异步刷新）
- 缓存雪崩：大量 Key 同时过期，DB 压力骤增。解决：随机 TTL 偏移、多级缓存、限流降级

8. Redis 适合哪些使用场景？

答案：
- 缓存：降低 DB 压力（最常用）
- Session 存储：分布式系统共享会话
- 分布式锁：SET key value NX PX timeout 实现互斥
- 限流：滑动窗口计数器
- 消息队列：List（LPUSH/BRPOP）或 Stream（持久化 MQ）
- 排行榜：ZSet 有序集合
- 发布订阅：Pub/Sub（不推荐，消息不持久化）

微服务架构

9. 微服务架构与单体架构的区别？

答案：
| 维度 | 单体架构 | 微服务架构 |
|------|---------|-----------|
| 部署 | 整体部署 | 独立部署 |
| 技术栈 | 统一 | 各服务自选 |
| 扩展 | 整体扩展 | 按服务扩展 |
| 故障影响 | 全局 | 局部隔离 |
| 复杂度 | 低（初期） | 高（分布式） |
| 适合阶段 | 初创、小团队 | 成熟、大团队 |

10. 微服务架构的核心挑战有哪些？

答案：
- 分布式事务：跨服务数据一致性（Saga/TCC）
- 服务发现：动态注册和发现（Consul、Nacos）
- 网络延迟：服务间 HTTP 调用比本地调用慢
- 分布式追踪：链路追踪（Jaeger、Zipkin）
- 运维复杂度：大量服务的部署、监控、日志聚合
- 数据管理：每个服务独立 DB，跨服务查询困难

11. 什么是 API 网关（API Gateway）？

答案：
API 网关是微服务的统一入口，承担以下职责：
- 路由转发：根据路径/域名路由到对应微服务
- 身份认证：统一 Token 验证，无需每个服务重复实现
- 限流熔断：保护后端服务
- 协议转换：HTTP → gRPC、REST → GraphQL
- 日志监控：统一记录请求日志
- API 聚合：合并多个服务的响应（减少前端请求数）

常见实现：Kong、AWS API Gateway、Nginx + Lua、ASP.NET Core Ocelot、Node.js BFF

12. 什么是服务注册与发现？

答案：
微服务实例启动时，向注册中心注册自己的地址；调用方查询注册中心获取目标服务的地址列表，再负载均衡选取一个调用。注册中心维护服务健康状态，自动剔除不健康实例。
- 常用工具：Consul、Nacos（阿里，支持配置中心）、Eureka（Netflix）、Etcd
- 两种模式：客户端发现（调用方自己查询+负载均衡）vs 服务端发现（负载均衡器查询）

13. 微服务间通信方式有哪些？如何选择？

答案：
- 同步通信：
- REST/HTTP：简单，生态好，适合跨语言、外部 API
- gRPC：高性能（二进制、HTTP/2 多路复用），强类型（Protobuf），适合内部高频调用
- 异步通信：
- 消息队列（Kafka、RabbitMQ）：解耦、削峰、最终一致，适合不需要即时响应的场景

选择原则：需要即时响应用 REST/gRPC；需要解耦/削峰用消息队列。

14. 什么是熔断器（Circuit Breaker）？

答案：
熔断器防止下游服务故障级联扩散。三种状态：
- Closed（关闭）：正常调用，统计失败率
- Open（打开）：失败率超阈值，直接拒绝请求（快速失败），等待冷却时间
- Half-Open（半开）：冷却后允许少量请求试探，成功则恢复关闭，失败则重新打开

实现：.NET 用 Polly，Java 用 Resilience4j，Node.js 用 opossum。

15. 什么是 Saga 模式？如何处理分布式事务？

答案：
Saga 将分布式事务拆分为一系列本地事务，每步成功才执行下一步，失败则执行补偿事务回滚。
- 编排式（Choreography）：各服务通过事件触发，无中心协调，适合简单流程
- 协调式（Orchestration）：有中心 Saga Orchestrator 协调步骤，逻辑清晰，适合复杂流程

示例：下单 → 扣库存 → 扣余额 → 通知，任一失败则触发补偿（恢复库存、退款）。

消息队列

16. 消息队列适合哪些场景？

答案：
- 异步解耦：发送方不需要等待接收方处理，如发送邮件通知
- 削峰填谷：突发流量缓冲（如秒杀），消费方按能力消费
- 事件驱动：业务事件通知（订单创建 → 通知多个下游服务）
- 顺序保证：Kafka 分区内消息有序
- 延迟队列：定时任务（如15分钟未支付自动取消）

常用：Kafka（高吞吐、持久化）、RabbitMQ（功能丰富、易用）、RocketMQ（阿里云）

17. Kafka 为什么吞吐量高？

答案：
- 顺序写磁盘：磁盘顺序 I/O 比随机 I/O 快 100 倍，Kafka 消息追加写
- 零拷贝（Zero Copy）：sendfile 系统调用直接内核态传输，减少 CPU 拷贝
- 批量发送：生产者批量打包消息，减少网络往返
- 分区并行：Topic 分多个 Partition，消费者组并行消费
- Page Cache：利用操作系统页缓存，减少磁盘 I/O

18. 消息队列如何保证消息不丢失？

答案：
从生产、存储、消费三个环节保证：
- 生产端：发送后等待 ACK 确认（同步发送或回调确认）
- 存储端：消息持久化到磁盘（Kafka 默认持久化），多副本复制
- 消费端：消费后手动 ACK，未 ACK 的消息重新投递；消费逻辑幂等处理（防重复消费）

微前端

19. 什么是微前端？核心价值是什么？

答案：
微前端将大型前端应用拆分为多个独立子应用，每个子应用可独立开发、部署、技术栈自选。核心价值：
- 独立部署：子应用单独发布，不影响其他应用
- 技术无关：不同子应用可用 React、Vue、Angular
- 团队自治：各团队独立开发，减少协作冲突
- 渐进迁移：老应用逐步拆分，无需大重构

20. 微前端的常见实现方案？

答案：
| 方案 | 原理 | 代表 | 优劣 |
|------|------|------|------|
| iframe | 天然隔离 | - | 隔离好但体验差（路由、弹窗、通信） |
| qiankun | JS 沙箱 + CSS 隔离 | 阿里 | 接入成本低，国内主流 |
| Module Federation | Webpack 运行时共享 | Webpack 5 | 共享依赖，无运行时框架 |
| single-spa | 路由注册 | single-spa | 基础框架，qiankun 基于它 |
| Web Components | 浏览器原生 | - | 天然隔离，兼容性一般 |
| NPM 包 | 构建时集成 | - | 最简单，但不独立部署 |

21. qiankun 的核心原理是什么？

答案：
- JS 沙箱：
- SnapshotSandbox：切换时快照/恢复 window 属性（不支持并发）
- ProxySandbox：用 Proxy 代理 window，每个子应用有独立的全局作用域（推荐）
- CSS 隔离：
- shadowDOM：浏览器原生隔离（兼容性问题）
- scoped：给所有 CSS 选择器加前缀（data-qiankun 属性）
- 生命周期：子应用需导出 bootstrap、mount、unmount 三个生命周期函数，主应用按需调用

22. 微前端如何实现跨应用通信？

答案：
- 全局状态（Props）：主应用通过 props 传递数据给子应用（适合父→子单向传递）
- CustomEvent：浏览器原生自定义事件，发布/订阅（适合兄弟应用）
- 共享 Store：主应用维护全局状态，通过 props 共享给子应用
- URL 参数/路由：通过 URL 传递状态
- localStorage/sessionStorage：同域下共享存储

23. 微前端样式隔离如何处理？

答案：
- CSS Modules：编译时给类名加哈希（Button_abc123），防止命名冲突
- BEM 命名规范：.app-name-component-element 约定命名
- CSS-in-JS：Styled-Components 生成唯一 className
- Shadow DOM：真正的 CSS 隔离（Web Components）
- qiankun scoped：自动给子应用 CSS 加属性选择器前缀
- CSS 变量命名空间：--app1-primary-color 防止全局变量冲突

BFF 与渲染模式

24. 什么是 BFF（Backend For Frontend）？

答案：
BFF 是专门为前端设计的后端服务，作为前端和微服务之间的适配层：
- 数据聚合：合并多个微服务的数据，减少前端请求次数
- 格式转换：将后端数据格式转为前端需要的结构
- 鉴权处理：统一处理 Token 验证
- 端适配：不同端（PC/Mobile/小程序）各有专属 BFF，返回适配数据

Node.js 天然适合做 BFF（I/O 密集、JSON 处理、前端团队熟悉）。

25. SSR、CSR、SSG、ISR 的区别？如何选型？

答案：
| 模式 | 全称 | 原理 | 优势 | 劣势 | 适用 |
|------|------|------|------|------|------|
| CSR | 客户端渲染 | 浏览器执行 JS 渲染 | 交互体验好 | 首屏慢、SEO 差 | 管理后台、内部系统 |
| SSR | 服务端渲染 | 服务器生成 HTML 返回 | 首屏快、SEO 好 | 服务器压力大 | 电商、新闻、SEO 要求高 |
| SSG | 静态生成 | 构建时生成 HTML | 极快、CDN 友好 | 数据静态、需重新构建 | 博客、文档、营销页 |
| ISR | 增量静态再生 | 后台定时/按需重新生成 | 兼顾静态速度和动态数据 | 实现复杂 | 产品详情、内容频繁更新 |

Next.js 支持所有四种模式，可以按页面混用。

26. 什么是 Server Components（React Server Components）？

答案：
RSC 是 React 18+ 引入的新渲染模式，服务端组件在服务器执行，客户端组件在浏览器执行：
- Server Components：直接访问数据库/文件系统，不发送 JS 到客户端，无 State/Effect
- Client Components：有交互（useState、useEffect），需要在浏览器运行（加 'use client'）

优势：零 Bundle 大小（服务端组件不打包到客户端）、直接数据获取、流式 HTML 传输。Next.js 13+ App Router 默认使用 RSC。

DDD 领域驱动设计

27. 什么是 DDD？核心思想是什么？

答案：
DDD（Domain-Driven Design）是以业务领域为核心驱动软件设计的方法论。核心思想：
- 统一语言（Ubiquitous Language）：开发和业务使用同一套术语，减少理解偏差
- 领域模型：用代码精确表达业务概念（实体、值对象、聚合）
- 限界上下文（Bounded Context）：划定业务边界，不同上下文内的同一词汇含义不同

适用：复杂业务域（电商、金融、ERP），不适合 CRUD 简单业务。

28. DDD 的核心构件有哪些？

答案：
- 实体（Entity）：有唯一标识的业务对象（如 Order，有 orderId）
- 值对象（Value Object）：无唯一标识、通过属性定义（如 Money、Address），不可变
- 聚合（Aggregate）：一组相关实体和值对象的边界，有聚合根（Aggregate Root）作为唯一入口
- 领域服务（Domain Service）：不属于某个实体的业务逻辑
- 仓储（Repository）：聚合的持久化接口（隐藏数据库细节）
- 领域事件（Domain Event）：领域中发生的重要业务事件（如 OrderPlaced）

29. 什么是 CQRS？

答案：
CQRS（Command Query Responsibility Segregation）将读（Query）和写（Command）分离：
- Command（命令）：修改状态，不返回数据（如 PlaceOrder、UpdateUser）
- Query（查询）：只读数据，不修改状态（如 GetOrderById、ListProducts）

分离后可以：读库和写库独立优化、读库可做视图聚合（读性能）、写库专注业务规则（写正确性）。常与 Event Sourcing 结合使用。

30. 什么是 Event Sourcing？

答案：
Event Sourcing 不存储当前状态，而是存储所有历史事件序列，当前状态由事件回放得出。
- 优势：完整审计日志、可时间回溯、事件可发布给其他系统
- 劣势：查询复杂（需物化视图）、事件 Schema 演化困难

示例：银行账户不存 balance = 100，而存 [Deposit(50), Deposit(80), Withdraw(30)]，回放得到 100。

前端架构模式

31. 大型前端项目如何组织架构？

答案：
常见分层架构（以 React 项目为例）：

src/
├── app/           # 路由、全局 Provider
├── features/      # 按功能模块（Feature-Sliced Design）
│   ├── orders/
│   │   ├── api/       # API 请求（React Query/SWR）
│   │   ├── model/     # 状态管理（Zustand/Redux Slice）
│   │   ├── ui/        # 组件
│   │   └── lib/       # 工具函数
├── shared/        # 跨模块共享
│   ├── ui/        # 通用组件（Button、Modal）
│   ├── lib/       # 通用工具
│   └── api/       # HTTP 客户端配置
└── entities/      # 业务实体（User、Product 类型和基础操作）

核心原则：高内聚低耦合，按功能而非技术类型分包。

32. 什么是状态管理？如何选型？

答案：
- 组件状态（useState/useReducer）：局部状态，不需要共享时首选
- Context API：主题、语言、用户信息等低频全局状态
- Zustand：轻量，无样板代码，适合中小型项目
- Redux Toolkit：功能完整，RTK Query 内置数据获取，适合复杂状态
- Jotai/Recoil：原子化状态，细粒度订阅，适合高频更新
- React Query/SWR：服务端状态（缓存、刷新、乐观更新），替代大部分 Redux 数据获取场景

原则：服务端状态用 React Query/SWR，客户端状态用 Zustand/Context。

.NET 微服务架构

33. .NET 微服务常用的架构组件有哪些？

答案：
- ASP.NET Core：Web API 框架
- Ocelot：.NET API 网关（路由、限流、鉴权）
- Polly：弹性策略（重试、熔断、超时、降级）
- MediatR：CQRS + 中介者模式实现
- gRPC：高性能内部服务通信
- Entity Framework Core：ORM，支持多数据库
- Health Checks：AddHealthChecks() 内置健康检查
- Serilog/Seq：结构化日志
- OpenTelemetry：分布式追踪和指标

34. ASP.NET Core 如何实现水平扩展？

答案：
- 无状态设计：不使用 InMemory Session，改用 Redis 或 JWT
- 分布式缓存：IDistributedCache + Redis，不用内存缓存
- 数据保护：DataProtection Keys 存 Redis/Azure Blob（多实例共享加密密钥）
- SignalR 扩展：AddStackExchangeRedisBackplane() 让多实例 WebSocket 消息同步
- Docker + Kubernetes：容器化部署，Pod 水平扩展（HPA 自动伸缩）
- 健康检查：/health 端点供 K8s readiness/liveness 探针使用
