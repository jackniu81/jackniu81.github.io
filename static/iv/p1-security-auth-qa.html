安全与认证 常见面试题（附答案）

认证与授权基础

1. 认证（Authentication）和授权（Authorization）的区别？

答案：

  • 认证（AuthN）：验证"你是谁"，如用户名+密码登录、指纹识别
  • 授权（AuthZ）：验证"你能做什么"，如检查用户是否有管理员权限

流程：先认证（确定身份），再授权（检查权限）。常见错误：将二者混淆，403 Forbidden 是授权失败，401 Unauthorized 是认证失败（未登录或 Token 无效）。

2. Cookie-Session 和 Token 认证的区别？

答案：

维度 Cookie-Session Token（JWT）
存储 Session 存服务端，Cookie 存 SessionId Token 存客户端（localStorage/Cookie）
扩展性 多实例需共享 Session 存储（Redis） 无状态，天然支持水平扩展
安全性 SessionId 被盗可通过服务端失效 Token 被盗无法主动失效（除非加黑名单）
跨域 Cookie 跨域受限 请求头 Bearer Token，跨域友好
适用 传统 Web、对安全要求高 SPA、移动端、微服务

JWT

3. JWT 的结构是什么？如何工作？

答案： JWT（JSON Web Token）由三部分组成，. 分隔：

Header.Payload.Signature
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMiLCJleHAiOjE3MDAwMDB9.abc123
  • Header：算法和类型（{"alg":"HS256","typ":"JWT"}），Base64URL 编码
  • Payload：声明（Claims），如 sub（用户ID）、exp（过期时间）、自定义字段，Base64URL 编码（非加密，可被解码）
  • Signature：HMAC(Header + "." + Payload, 密钥) 防止篡改

工作流程：登录 → 服务端生成 JWT → 客户端存储 → 每次请求携带（Authorization: Bearer <token>） → 服务端验证签名

4. JWT 的优势和劣势？

答案： 优势：

  • 无状态，服务端不存储，天然支持水平扩展
  • 跨域友好（请求头传递）
  • Payload 携带信息，减少数据库查询
  • 跨服务共享（多个服务用同一密钥验证）

劣势：

  • 无法主动失效：Token 发出后到过期前无法撤销（用户改密码、注销后旧 Token 仍有效）
  • 体积较大：比 SessionId 大
  • 密钥泄露：所有 Token 失效，需轮换密钥

5. 如何解决 JWT 无法主动失效的问题？

答案：

  • Token 黑名单：注销时将 Token 存入 Redis 黑名单（jti 声明），验证时检查黑名单（引入服务端状态）
  • 短过期时间 + 刷新 Token：Access Token 5-15 分钟过期，Refresh Token 长期有效，过期后用 Refresh Token 换新 Access Token；安全问题时撤销 Refresh Token
  • 版本号（Token Version）：用户改密码时递增版本号，Token 中携带版本号，不一致则拒绝（需数据库查询）

6. Access Token 和 Refresh Token 的区别？

答案：

  • Access Token：短期有效（分钟级），用于访问 API，存在内存（不存 localStorage，防 XSS）
  • Refresh Token：长期有效（天/周级），只用于换取新 Access Token，存 HttpOnly Cookie（防 XSS）

Refresh Token 轮换：每次使用 Refresh Token 换 Access Token 时，同时颁发新的 Refresh Token，旧的失效（检测令牌重用攻击）。

OAuth2 与 OIDC

7. 什么是 OAuth2？解决什么问题？

答案： OAuth2 是授权框架，解决"第三方应用代表用户访问受保护资源"的问题，不涉及用户认证（只是授权）。

场景：使用微信登录某 APP，APP 不需要知道你的微信密码，只需要微信授权访问你的头像和昵称。

四个角色：

  • Resource Owner（资源所有者）：用户
  • Client（客户端）：第三方 APP
  • Authorization Server（授权服务器）：颁发 Token（如微信授权服务器）
  • Resource Server（资源服务器）：提供受保护资源（如微信 API）

8. OAuth2 的四种授权模式？

答案：

  • Authorization Code（授权码模式）：最安全，适合有服务端的 Web 应用。用户授权后，客户端获得授权码，再用授权码换 Token（Token 不经过浏览器）
  • Authorization Code + PKCE：授权码+代码挑战，适合 SPA 和移动端（无服务端）
  • Client Credentials（客户端凭证）：机器对机器（M2M），如后端服务调用 API，无用户参与
  • Device Code（设备码）：适合无浏览器设备（智能电视、CLI 工具）

⚠️ Implicit（隐式模式）已废弃，Token 直接返回给浏览器不安全，用 PKCE 替代。

9. 什么是 OIDC？与 OAuth2 的关系？

答案： OIDC（OpenID Connect）是基于 OAuth2 的认证层，在 OAuth2 授权的基础上增加了用户身份认证。

区别：OAuth2 解决授权（能做什么），OIDC 解决认证（你是谁）。

OIDC 在 OAuth2 基础上新增：

  • ID Token：JWT 格式，包含用户身份信息（sub、name、email 等）
  • UserInfo 端点：获取更多用户信息
  • 标准 Claims：统一用户信息字段

常见提供商：Google、Apple、Microsoft（Azure AD）、Keycloak、Auth0

常见 Web 攻击与防御

10. 什么是 XSS（跨站脚本攻击）？如何防御？

答案： XSS 攻击者向网页注入恶意 JS，在用户浏览器中执行，窃取 Cookie、伪造请求。

三种类型：

  • 存储型：恶意脚本存入数据库，所有用户看到时触发（最危险）
  • 反射型：恶意脚本在 URL 参数中，点击链接触发
  • DOM型：前端 JS 不安全操作 DOM（如 innerHTML = location.hash）

防御：

  • 输出编码：HTML 输出时转义特殊字符（< → &lt;），使用模板引擎（React JSX 默认转义）
  • 禁止 innerHTML：改用 textContent，必须使用时用 DOMPurify 清洗
  • HttpOnly Cookie：防止 JS 读取 Cookie
  • CSP（内容安全策略）：限制可执行的脚本来源
  • 输入验证：服务端过滤危险标签

11. 什么是 CSRF（跨站请求伪造）？如何防御？

答案： CSRF 攻击者诱导用户访问恶意页面，该页面自动发送携带用户 Cookie 的请求（浏览器自动带 Cookie），冒充用户操作。

<!-- 攻击者的恶意页面 -->
<img src="https://bank.com/transfer?to=attacker&amount=1000">

防御：

  • CSRF Token：服务端生成随机 Token 放入表单/请求头，服务端验证（Cookie 无法跨域读取，但 CSRF Token 在请求体/Header 中）
  • SameSite Cookie：SameSite=Strict/Lax 阻止跨站 Cookie 发送（现代浏览器默认 Lax）
  • Origin/Referer 检查：服务端验证请求来源域名
  • 双重 Cookie 验证：请求同时携带 Cookie 和请求参数中的 Token（跨域无法读 Cookie）

12. 什么是 SQL 注入？如何防御？

答案： 攻击者在输入中注入 SQL 语句片段，改变查询逻辑。

-- 攻击输入: ' OR '1'='1
SELECT * FROM users WHERE name = '' OR '1'='1' -- 返回所有用户

防御：

  • 参数化查询（Parameterized Query）：使用 ? 占位符，ORM 默认处理（最有效）
    cmd.CommandText = "SELECT * FROM users WHERE id = @id";
cmd.Parameters.Add("@id", userId);
  • ORM：EF Core、Sequelize 等默认参数化
  • 输入验证：类型检查、长度限制
  • 最小权限原则：DB 账号只授予必要权限（不用 root）

13. 什么是点击劫持（Clickjacking）？如何防御？

答案： 攻击者将目标网站用透明 iframe 嵌入，诱导用户点击看不见的按钮（如"确认转账"）。

防御：

  • X-Frame-Options 响应头：DENY（禁止嵌入）或 SAMEORIGIN（只允许同源嵌入）
  • CSP frame-ancestors：Content-Security-Policy: frame-ancestors 'none'（更现代的方式）

14. 什么是供应链攻击（Supply Chain Attack）？前端如何防御？

答案： 攻击者通过污染 npm 包、CDN 资源等依赖链，将恶意代码注入到目标项目中。典型案例：event-stream 包被劫持、colors.js 恶意更新。

防御：

  • 锁定版本：使用 package-lock.json/pnpm-lock.yaml 锁定精确版本
  • npm audit：定期检查已知漏洞（npm audit）
  • Subresource Integrity（SRI）：CDN 资源加 integrity 哈希校验
    <script src="https://cdn.com/lib.js" integrity="sha256-xxx" crossorigin="anonymous"></script>
  • 最小权限：只安装必要依赖，减少攻击面
  • 依赖扫描：CI 中集成 snyk、dependabot 自动检测漏洞

HTTPS 与 TLS

15. HTTPS 的工作原理？

答案： HTTPS = HTTP + TLS 加密。核心步骤：

  1. 握手阶段：协商加密算法、交换密钥（非对称加密）
  2. 数据传输：使用握手协商的对称密钥加密数据（对称加密速度快）
  3. 证书验证：验证服务器证书是否由可信 CA 颁发（防中间人攻击）

16. TLS 握手流程？

答案： TLS 1.3 握手（简化版，只需 1-RTT）：

  1. 客户端发送支持的加密套件、随机数、密钥协商参数
  2. 服务端选择加密套件、发送证书、返回密钥协商参数
  3. 客户端验证证书，双方根据密钥协商参数计算出对称密钥
  4. 之后用对称密钥加密传输

TLS 1.3 相比 1.2：减少了一次 RTT、移除了不安全算法、支持 0-RTT 恢复会话。

17. HTTP 常见安全响应头有哪些？

答案：

# 强制 HTTPS（1年内不允许 HTTP 访问）
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

# 防 XSS（现代浏览器用 CSP 替代）
X-XSS-Protection: 1; mode=block

# 防点击劫持
X-Frame-Options: DENY

# 防 MIME 嗅探
X-Content-Type-Options: nosniff

# 内容安全策略
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-xxx'

# 控制 Referrer 信息
Referrer-Policy: strict-origin-when-cross-origin

密码安全

18. 密码如何安全存储？

答案： 绝对不能：明文存储、MD5/SHA1 哈希（可被彩虹表破解）、自研加密算法

正确做法：使用慢哈希算法 + 盐：

  • bcrypt：内置盐，工作因子可调（推荐，前端/Node.js）
  • Argon2：内存密集型，最安全，抗 GPU 破解（推荐，2019年后新项目）
  • PBKDF2：FIPS 认证，合规场景
// C# BCrypt
string hash = BCrypt.Net.BCrypt.HashPassword(password, workFactor: 12);
bool valid = BCrypt.Net.BCrypt.Verify(password, hash);

19. 什么是彩虹表攻击？加盐如何防御？

答案： 彩虹表是预计算的哈希表（密码→哈希值），可快速反查哈希对应的明文。

加盐（Salt）：在密码哈希前拼接一段随机字符串，使相同密码产生不同哈希，使彩虹表失效（bcrypt/Argon2 自动处理加盐）。

bcrypt("password123", salt="abc") = "$2b$12$abc...hash1"
bcrypt("password123", salt="xyz") = "$2b$12$xyz...hash2"  // 相同密码，不同哈希

API 安全

20. 什么是速率限制（Rate Limiting）？如何实现？

答案： 限制单位时间内的请求次数，防止暴力破解、DDoS、爬虫。常见算法：

  • 固定窗口：每分钟最多 100 次，简单但有边界突破问题
  • 滑动窗口：基于 Redis 有序集合实现，平滑限流
  • 令牌桶：以固定速率填充令牌，突发流量可消耗积累的令牌（推荐）
  • 漏桶：严格匀速，不允许突发

ASP.NET Core 8+ 内置 Rate Limiting：

builder.Services.AddRateLimiter(options => {
    options.AddFixedWindowLimiter("api", o => {
        o.PermitLimit = 100;
        o.Window = TimeSpan.FromMinutes(1);
    });
});

21. 什么是 CORS？如何正确配置？

答案： CORS（跨源资源共享）是浏览器安全策略，阻止不同源的 JS 请求。

正确配置原则（避免常见错误）：

// ❌ 错误：生产环境允许所有来源 + 携带凭证
app.UseCors(x => x.AllowAnyOrigin().AllowCredentials()); // 不合法，浏览器会报错

// ✅ 正确：明确指定允许来源
builder.Services.AddCors(options => {
    options.AddPolicy("production", policy => {
        policy.WithOrigins("https://app.example.com")
              .AllowCredentials()
              .WithMethods("GET", "POST", "PUT", "DELETE")
              .WithHeaders("Authorization", "Content-Type");
    });
});

注意：AllowAnyOrigin() 和 AllowCredentials() 不能同时使用（浏览器安全限制）。

22. 什么是 CSP（内容安全策略）？

答案： CSP 通过 HTTP 响应头限制页面可加载的资源来源，有效防御 XSS：

Content-Security-Policy:
  default-src 'self';                 # 默认只允许同源
  script-src 'self' 'nonce-abc123';  # 脚本只允许同源和带 nonce 的内联
  style-src 'self' https://fonts.googleapis.com;
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';             # 禁止被嵌入

nonce：每次请求生成随机值，内联脚本需携带正确 nonce 才能执行，防止注入的内联脚本运行。

.NET 安全实践

23. ASP.NET Core 中如何实现 JWT 认证？

答案：

// Program.cs
builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options => {
        options.TokenValidationParameters = new TokenValidationParameters {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            ValidIssuer = config["Jwt:Issuer"],
            ValidAudience = config["Jwt:Audience"],
            IssuerSigningKey = new SymmetricSecurityKey(
                Encoding.UTF8.GetBytes(config["Jwt:Key"]!))
        };
    });

// Controller
[Authorize]
[HttpGet("profile")]
public IActionResult GetProfile() {
    var userId = User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
    return Ok(userId);
}

24. ASP.NET Core 中如何实现基于角色/策略的授权？

答案：

// 角色授权
[Authorize(Roles = "Admin,Manager")]
public IActionResult AdminAction() { ... }

// 策略授权（更灵活）
builder.Services.AddAuthorization(options => {
    options.AddPolicy("RequireAdmin", policy =>
        policy.RequireRole("Admin").RequireClaim("department", "IT"));

    options.AddPolicy("MinAge18", policy =>
        policy.Requirements.Add(new MinAgeRequirement(18)));
});

// 自定义需求
public class MinAgeHandler : AuthorizationHandler<MinAgeRequirement> {
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext ctx, MinAgeRequirement req) {
        var birthDate = ctx.User.FindFirst("birthdate");
        if (birthDate != null && CalculateAge(birthDate.Value) >= req.MinAge)
            ctx.Succeed(req);
        return Task.CompletedTask;
    }
}

25. 前端如何安全存储 Token？

答案：

存储位置 XSS 风险 CSRF 风险 推荐场景
localStorage ❌ 高（JS 可读） ✅ 无（需手动添加 Header） 不推荐
sessionStorage ❌ 高（JS 可读） ✅ 无 不推荐
Cookie（HttpOnly） ✅ 安全（JS 不可读） ❌ 有（需加 SameSite） ✅ 推荐
内存（变量） ✅ 安全（刷新消失） ✅ 无 Access Token 推荐

最佳实践：

  • Access Token → 内存变量（useState）
  • Refresh Token → HttpOnly + SameSite=Strict Cookie
  • 页面刷新时用 Refresh Token 换取新 Access Token
