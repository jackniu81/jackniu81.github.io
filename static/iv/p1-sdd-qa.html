SDD（规格驱动开发）面试题（附答案）

基础概念

1. 什么是 SDD（Spec-Driven Development）？

答案：
SDD（规格驱动开发）是一种以规格文档（Spec）为核心驱动软件开发全流程的方法论。与传统 TDD（测试驱动）不同，SDD 在写代码和测试之前，先由 AI 生成可机读的需求规格，再基于规格生成实施计划，最后执行实现。

核心理念：
- 让 AI 先"理解需求"，再"生成代码"
- 规格是 AI 和人类之间的合约
- 通过强制规格-代码-测试的可追溯性保证质量

与传统方式的区别：

对比维度 传统开发 TDD SDD
起点 直接写代码 先写测试 先写规格
AI 角色 代码补全 实现使测试通过 全流程驱动（规格→计划→实现）
文档 事后补充 测试即文档 规格作为源头文档
可追溯性 弱 中 强（FR→代码→测试矩阵）

2. SDD 的核心工作流是什么？

答案：
SDD 的完整工作流分为三个阶段：

阶段一：一次性知识库构建
- 运行 /create-pod-knowledge 分析代码库，生成 AI 可读的知识库（ai/knowledge/）

阶段二：规格交付循环（每个 JIRA 任务）
1. /create-specs <JIRA-ID> — 从 JIRA 生成规格文档
2. /create-plan <JIRA-ID> — 从规格生成实施计划
3. /execute <JIRA-ID> — 执行实现（TDD + 提交 + MR）
4. /wrap-up <JIRA-ID> — 合并后收尾（发布 Confluence 文档）

阶段三：定期维护
- /update-knowledge — 将已交付规格和新文档批量集成回知识库

3. SDD 中的 ai/knowledge/ 目录包含什么？

答案：
ai/knowledge/ 是 SDD 的核心知识库，包含 AI 可读的项目规格：

文件 内容
POD.md 执行级摘要：目的、子域、核心能力、业务实体、主要流程（必须存在）
functional-spec.md 功能规格
technical-spec.md 技术规格
data-model-spec.md 数据模型规格
api-spec.md API 规格
integration-spec.md 集成规格（内部 + 外部）
security-spec.md 安全规格
deployment-spec.md 部署规格
nfr-spec.md 非功能需求规格
CHANGELOG.md 知识库每次变更的审计记录

根目录还会生成 AGENTS.md（AI 行为约束）和 LEARNINGS.md（经验积累）。

4. SDD 中的 Spec（规格文档）应该包含哪些内容？

答案：
一份合格的 SDD 规格文档包含：

  • 功能需求（FR）：用户视角、技术无关、可测试的需求描述
  • 验收标准（AC）：每条 FR 对应的可验证标准
  • 成功标准：整体功能的量化验收指标
  • 作用域：明确包含什么、不包含什么
  • 开放问题：未解决的模糊点（必须在 /create-plan 前全部解决）
  • 自动解决的假设：AI 自动填补的假设，附上依据

质量要求：
- 所有 FR 必须可测试
- 不能泄露实现细节（不写 DB 名、框架名、基础设施指标）
- 每条 FR 必须有来源（JIRA 原文或代码证据）
- 无孤立需求（每条 FR 都在作用域内）

核心命令详解

5. /create-pod-knowledge 命令的核心作用是什么？

答案：
/create-pod-knowledge 是 SDD 的一次性启动命令，作用是将项目的人类文档和代码库转换为 AI 可高效读取的结构化知识。

执行内容：
1. 分析 ai/raw/ 目录下的原始文档（设计文档、API 文档、会议记录等）
2. 静态分析代码库结构、依赖关系、核心流程
3. 生成 POD.md 和 8 个详细规格文件
4. 生成 AGENTS.md（AI 约束规则）和 LEARNINGS.md

关键特点：每个项目只运行一次；之后通过 /update-knowledge 保持更新。

何时重新运行：代码库发生重大架构变更时。

6. /create-specs 命令的"递归自答澄清"机制是什么？

答案：
递归自答澄清（Recursive Self-Answering Clarification）是 /create-specs 的核心质量机制，用于在生成规格前自动解决需求中的模糊之处。

工作流（3 次迭代循环）：

第1轮：识别 JIRA 中的模糊点 → 查询 POD 知识库 → 尝试解答
第2轮：对未解决问题 → 分析代码库证据 → 再次尝试解答
第3轮：对仍未解决问题 → 评估业务影响 → 记录假设或保留为开放问题

上限规则：
- 超过 5 个开放问题时，按影响力排序保留前 5 个
- 其余标记为 [AUTO-RESOLVED: OVERFLOW]，附上解决假设

目的：减少人工往返确认，让 AI 在开始编码前就对需求有清晰认知。

7. /create-plan 的"开放问题硬关卡"是什么？

答案：
硬关卡（Hard Gate）是 /create-plan 在生成计划前的强制检查：如果规格中还有任何未解决的开放问题或未确认的假设，计划生成直接阻断（Block）。

检查项：
- specs.md 中是否有未解决的 [OPEN QUESTION]
- 是否有未验证的假设（无代码或文档依据的假设）
- [AUTO-RESOLVED] 标记的假设是否被人工确认

为何重要：
- 在模糊需求上生成的计划必然是错误的
- 提前暴露问题比在实现阶段修复成本低 10 倍
- 强制人工确认保证了人类对最终交付的知情权

8. /execute 命令完整执行什么流程？

答案：
/execute <JIRA-ID> 是 SDD 中耗时最长的命令，完整的实施生命周期：

Step 1 — 实施前检查
- 扫描规格和计划中的占位符、未解决问题、可追溯性缺口
- 任何问题都阻断执行

Step 2 — 准备
- 将规格文件附加到 JIRA
- 在所有受影响的代码仓库和 ai/ 仓库创建 develop-{JIRA-ID} 分支
- 将 JIRA 状态转换为"开发中"

Step 3 — TDD 实现
- 先写测试（Red）→ 实现使测试通过（Green）→ 重构（Refactor）
- 构建验证 → 跨项目验证 → 自我代码审查
- 维护任务进度清单（T-01、T-02...）

Step 4 — 推送与 MR
- 提交并推送所有受影响的分支
- 为每个受影响的源项目 + ai/ 仓库各创建一个 GitLab MR
- 生成包含可追溯矩阵的 change-summary.md

Step 5 — MR 审查修复（重新进入时）
- 获取所有未解决的 MR 评论
- 对每条评论分析并实现修复，或提供拒绝理由
- 构建、推送、回复评论

9. /wrap-up 命令做什么？什么时候运行？

答案：
/wrap-up <JIRA-ID> 是 SDD 的合并后收尾命令，在所有 MR 合并后运行。

执行内容：
1. 验证：确认所有 MR 都已合并（未合并则阻断）
2. 清理：删除所有 develop-{JIRA-ID} 特性分支
3. JIRA 更新：发布编码摘要到 JIRA，添加 AI-Delivered 标签，转换状态为 Complete
4. Confluence 发布：生成并发布完整的功能文档页面（强制步骤，缺少凭据则提示）

注意：/wrap-up 不更新 ai/knowledge/ 知识库。知识库更新需要单独运行 /update-knowledge。

10. /update-knowledge 的两种触发源是什么？

答案：
/update-knowledge 监听两种输入：

触发源 1 — 已交付的规格：
- 扫描 ai/specs/*/，找到有 change-summary.md 但无 .knowledge-integrated 标记的目录
- 将这些已实现的规格中的新知识集成到 ai/knowledge/

触发源 2 — 新的或修改的原始文档：
- 扫描 ai/raw/** 目录
- 使用 SHA-256 哈希对比 ai/knowledge/.raw-integrated.log 检测变更
- 将新增或修改的人类文档集成到知识库

任一触发源都可单独触发运行。更新内容包括 POD.md、所有 8 个规格、AGENTS.md、LEARNINGS.md，以及向 CHANGELOG.md 追加条目。

AI 模型选择策略

11. SDD 中哪些步骤适合使用 Claude Sonnet（开启扩展思考）？

答案：
Claude Sonnet + 扩展思考（Extended Thinking）适用于需要深度推理和严谨分析的步骤：

推荐步骤：
- /create-specs：递归澄清循环需要反复推敲需求逻辑，识别隐含矛盾，评估假设质量
- /create-plan：宪法/治理合规检查需要逐条比对，跨工件一致性验证需要深度推理

原因：
- 扩展思考让模型在生成最终答案前进行"内部草稿"式推理
- 对于识别规格中的逻辑漏洞、模糊约束、遗漏边界条件，思考过程明显提升准确性
- 递归澄清本身就是一个多层推理链，扩展思考天然契合

12. SDD 中哪些步骤适合使用 Claude Opus（不开启思考）？

答案：
Claude Opus（无扩展思考）适用于需要大上下文理解和综合代码生成的步骤：

推荐步骤：
- /create-pod-knowledge：需要同时处理大量原始文档和代码库文件，Opus 更大的知识广度和上下文理解能力更有优势
- /execute：实际编写代码、理解跨文件依赖、生成 MR 描述和 change-summary，需要原始的代码生成能力而非反复推敲
- /wrap-up：撰写 Confluence 文档、JIRA 摘要，是综合信息的输出任务，不需要深度推理

原因：
- Opus 在不开启思考时速度更快，适合大批量生成场景
- 代码生成任务的质量瓶颈通常在"知识广度"而非"推理深度"
- 扩展思考的 token 成本高，用在不需要反复推敲的任务上是浪费

13. Sonnet with thinking vs Opus without thinking：成本相同时如何选择？

答案：
两者价格相近时，核心决策标准是任务性质：

任务性质 选择 原因
分析、推理、识别矛盾 Sonnet + 思考 思考过程提升推理质量
生成、综合、代码实现 Opus（无思考） 更强的知识广度和生成能力
大上下文（>100K token） Opus（无思考） 更好的长文档理解
复杂约束检查 Sonnet + 思考 思考链帮助遍历所有约束

SDD 实践建议：

create-specs   → Sonnet + 思考  (规格质量是核心)
create-plan    → Sonnet + 思考  (架构决策需要推理)
create-pod-knowledge → Opus    (大量文档/代码分析)
execute        → Opus           (代码生成为主)
wrap-up        → Opus           (综合输出)
update-knowledge → Opus        (批量集成)

规格质量与最佳实践

14. 什么是"实现泄漏"（Implementation Leakage）？为何要避免？

答案：
实现泄漏是指规格文档中出现了具体实现细节，例如数据库表名、框架 API、Redis key 命名、Kafka topic 名等。

示例：

❌ 泄漏的规格：
"系统应将用户数据存储到 Cassandra 的 user_profile 表"

✅ 正确的规格：
"系统应持久化用户个人资料，支持按用户 ID 查询，响应时间 < 50ms"

为何避免：
- 规格是需求，不是设计；实现细节属于 plan.md 的工作
- 绑定实现细节使规格难以在技术栈变更时复用
- AI 生成计划时会依赖规格，实现泄漏会限制 AI 的方案选择空间
- 违反 SDD 的"技术无关、用户视角"原则

15. SDD 中的"可追溯矩阵"是什么？

答案：
可追溯矩阵（Traceability Matrix）是 SDD 的质量保证核心，记录了每条功能需求（FR）→ 对应文件变更 → 对应测试用例的映射关系。

示例：

FR 文件变更 测试用例
FR-01: 用户可按价格区间过滤商品 PriceFilter.cs, FilterMapper.cs PriceFilter_with_valid_range_returns_products
FR-02: 价格区间为空时返回所有商品 PriceFilter.cs PriceFilter_with_empty_range_returns_all

作用：
- 确保没有遗漏实现（每条 FR 都有代码）
- 确保没有遗漏测试（每条 AC 都有测试用例）
- 代码审查时 reviewer 可以对照矩阵检验完整性

16. SDD 中 AGENTS.md 的作用是什么？

答案：
AGENTS.md 是放在工作区根目录的 AI 行为规范文件，定义了AI Agent 在该项目中必须遵守的约束和惯例。

典型内容：
- 技术栈约束（使用的语言、框架、版本）
- 代码风格规范（命名惯例、文件组织）
- 禁止行为（如：禁止直接修改数据库 schema）
- 测试要求（覆盖率目标、测试框架）
- 分支和提交规范

与 Cursor Rules 的区别：
- AGENTS.md 是 SDD 框架内的标准文件，面向所有支持的 AI 工具
- Cursor Rules（.cursor/rules/）是 Cursor IDE 专有的规则文件
- 两者功能类似，AGENTS.md 更具普适性

17. SDD 中的 CONSTITUTION.md 是什么？

答案：
CONSTITUTION.md（位于 ai/harness/）是 SDD 框架的治理宪法，定义了整个开发团队的核心原则、质量门禁和功能开发标准。

核心内容：
- 团队的架构原则（如：微服务边界、数据所有权）
- 质量门禁（代码覆盖率、性能指标、安全标准）
- 功能开发标准（feature flag 使用规范、API 向后兼容要求等）
- 合规要求（数据隐私、审计日志）

何时被使用：/create-plan 在生成计划时会读取 CONSTITUTION.md，对规格进行合规检查，违反核心原则则阻断计划生成。

注意：技术栈对齐检查在 AGENTS.md 中，不在 CONSTITUTION.md 中。

18. change-summary.md 包含什么内容？

答案：
change-summary.md（位于 ai/specs/{JIRA-ID}/）是每次 /execute 后生成的交付总结：

  • MR 链接：所有已创建的 GitLab MR URL
  • 可追溯矩阵：FR → 文件变更 → 测试用例的完整映射
  • 任务进度清单：T-01、T-02... 每个实现任务的完成状态
  • 已测试的场景：覆盖的测试用例列表
  • 已知限制：实现中的已知边界或遗留问题

用途：
- MR reviewer 的参考材料
- /wrap-up 生成 Confluence 文档的数据源
- /update-knowledge 将已实现功能集成回知识库的依据

工作流与协作

19. SDD 与 TDD（测试驱动开发）有什么本质区别？

答案：

维度 TDD SDD
起点 失败的测试 AI 可读的规格
驱动力 让测试通过 实现规格中的 FR
需求来源 开发者自行理解 从 JIRA + 知识库提炼
AI 角色 辅助编写代码 全程驱动（分析→规格→计划→实现→文档）
文档 测试即文档 规格 + Confluence 文档
可追溯性 测试覆盖率 FR-代码-测试三层矩阵

关键点：SDD 包含 TDD，/execute 内部就是以 TDD 方式实现规格（先写测试，再实现）。

20. 什么是 POD（Project-Oriented Development）？

答案：
POD（Project-Oriented Development）是 SDD 框架中的项目组织单元，代表一个具有清晰业务边界的代码仓库或服务。

POD 的核心要素（定义在 POD.md）：
- Purpose：该 POD 解决什么业务问题
- Sub-domain：属于哪个业务子域
- Capabilities：提供哪些核心能力
- Business Entities：操作的核心业务实体
- Primary Flows：主要业务流程

实践意义：
- AI 在处理任何任务前先读取 POD.md，快速建立项目背景
- 减少 AI 对项目架构的猜测，提高首次生成的准确率
- 新团队成员通过 POD.md 快速上手项目

21. SDD 适合什么规模的团队和项目？

答案：
最适合场景：
- 团队规模 3-10 人的中型项目
- 需求来源明确（有 JIRA 等工单系统）
- 代码库有一定复杂度（跨文件、跨模块交互）
- 团队希望将 AI 用于整个开发流程，而非仅代码补全

不太适合场景：
- 个人 Side Project（流程太重）
- 极小型 MVP（无需规格文档）
- 纯前端静态页面（逻辑简单，SDD 收益低）
- 探索性研究项目（需求本身未定义）

扩展性：
- 大型团队（20+ 人）可将 SDD 用于模块级而非全项目级
- 与现有 Scrum/Kanban 工作流兼容

22. SDD 的知识库（ai/knowledge/）应该放在哪里？

答案：
ai/knowledge/ 目录通常放在一个独立的子模块仓库（git submodule），而非主代码仓库中。

推荐结构：

主代码仓库 (unified-deals)
└── ai/ (submodule → ai-knowledge 仓库)
    ├── knowledge/        # 知识库规格
    │   ├── POD.md
    │   ├── functional-spec.md
    │   └── ...
    ├── specs/            # 每个 JIRA 的规格和计划
    │   └── UD-123/
    │       ├── specs.md
    │       ├── plan.md
    │       └── change-summary.md
    ├── raw/              # 原始人类文档
    └── harness/          # CONSTITUTION.md 等框架文件

好处：
- 知识库变更与代码变更分开 review
- 知识库可被多个仓库共享
- /wrap-up 会为知识库单独创建 MR

进阶问题

23. 如何处理 SDD 规格与实际代码不一致的情况？

答案：
规格-代码不一致是 SDD 中的常见问题，处理原则：

类型一：规格正确，代码有误
- 修改代码使其符合规格
- 更新 change-summary.md 中的任务状态

类型二：代码正确，规格有误（需求理解偏差）
- 人工更新 specs.md 中的相关 FR/AC
- 记录修改原因
- 重新运行受影响的 /create-plan 步骤

类型三：规格过时（需求已变更）
- 创建新的 JIRA 任务描述变更
- 运行 /create-specs 生成变更规格
- 不直接修改旧规格

预防：在 MR 代码审查时，要求 reviewer 对照 change-summary.md 的可追溯矩阵检查。

24. SDD 中的"破坏性命令被阻断"（Destructive Command Blocked）是什么保护机制？

答案：
SDD 框架对某些高风险命令有内置保护，在特定条件下会阻断执行：

常见阻断场景：

场景 阻断原因
/wrap-up 时有 MR 未合并 防止遗漏代码导致分支删除后丢失变更
/create-plan 时有开放问题 防止在模糊需求上生成错误计划
/execute 时规格有占位符 防止执行不完整的规格
在非 develop 分支运行 /update-knowledge 防止知识库被特性分支的未经验证内容污染

设计思想：SDD 宁愿"提前失败、明确失败"，也不要"悄悄生成错误结果"。

25. SDD 的 LEARNINGS.md 存什么内容？

答案：
LEARNINGS.md（位于工作区根目录）是一个经验积累文件，记录项目开发过程中发现的规律、陷阱和改进建议。

典型内容：
- 某类任务的最佳实现模式（如："所有外部 API 调用需要熔断器"）
- 踩过的坑及解决方案（如："Cassandra 写入超时需设置 ConsistencyLevel.ONE"）
- AI 常见误判的场景（如："AI 会错误地复用旧的 DTO，需要在规格中明确"）
- 规格写作的注意事项（项目特有的领域知识）

更新时机：/update-knowledge 运行时自动更新；开发人员也可手动追加。

作用：让 AI 在未来任务中避免重复犯同类错误，是 SDD 的"项目级记忆"。

26. 如何评估一个 SDD 实施是否成功？

答案：
SDD 实施成功的衡量维度：

过程指标：
- 规格通过 8 点质量检查清单的比例（目标 >90%）
- 开放问题在进入 /create-plan 前的解决率（目标 100%）
- 可追溯矩阵的完整率（每条 FR 都有对应测试）

质量指标：
- MR 中与"需求理解偏差"相关的审查评论数量（目标趋近 0）
- 规格-代码不一致导致的返工次数
- 生产环境 bug 中"规格遗漏场景"占比

效率指标：
- 从 JIRA 任务到 MR 提交的周期时间
- 代码审查通过率（一次通过 vs 多轮返修）

文档指标：
- Confluence 文档的自动生成覆盖率
- 知识库更新的及时性

27. SDD 框架的 ai/raw/ 目录放什么文件？

答案：
ai/raw/ 存放人类编写的原始文档，是 SDD 知识库的原始素材来源：

典型文件：
- 产品需求文档（PRD）
- API 接口文档（OpenAPI/Swagger）
- 架构设计文档（Architecture Decision Records, ADR）
- 会议记录（技术评审、Grooming 会议记录）
- 现有系统的技术说明书
- 数据字典

注意：
- ai/raw/ 中的文件不直接被 AI 在任务执行中读取，而是先经过 /create-pod-knowledge 或 /update-knowledge 转换为结构化知识
- /update-knowledge 使用 SHA-256 哈希追踪文件变更，只处理新增或修改的文件

28. SDD 如何与 GitLab CI/CD 集成？

答案：
SDD 在 CI/CD 层面的集成点：

代码仓库层：
- 每个受影响项目都有独立的 develop-{JIRA-ID} 分支和 MR
- ai/ 知识库仓库有单独的 MR，与代码 MR 并行审查

CI/CD 流水线：
- /execute 完成后会检查各仓库的 CI/CD Pipeline 状态
- Pipeline 失败时，AI 会分析失败原因并修复
- change-summary.md 中记录每个 MR 的 Pipeline 状态

合规检查：
- 可在 MR Pipeline 中加入规格格式验证
- 可验证 change-summary.md 中可追溯矩阵的完整性

建议集成：
- 在 Pipeline 中运行 dotnet test / npm test 确保所有测试通过
- 可通过 MR Label（如 AI-Delivered）过滤 AI 生成的变更用于单独追踪

29. SDD 中 AI 的"自我代码审查"（Self-Review）机制如何工作？

答案：
/execute 在提交代码前会进行一轮 AI 自我审查：

检查内容：
1. 规格对齐：每条 FR 是否都有对应实现
2. 测试覆盖：每条 AC 是否都有对应测试用例
3. 代码质量：是否符合 AGENTS.md 中的编码规范
4. 边界条件：是否处理了所有边界情况
5. 错误处理：是否有适当的异常处理和日志
6. 潜在 Bug：是否存在明显的逻辑错误
7. 安全性：是否有输入验证缺失等安全问题
8. 实现泄漏：新代码是否引入了不该在规格层出现的耦合

工作方式：AI 模拟一个资深工程师视角逐项检查，发现问题则在提交前自动修复，无法自动修复的问题记录到 change-summary.md 的"已知限制"中。

30. 如何从现有项目迁移到 SDD 工作流？

答案：
迁移路径（渐进式）：

第一步：建立知识库
- 收集已有文档到 ai/raw/
- 运行 /create-pod-knowledge 生成初始知识库
- 人工审查 POD.md 和 8 个规格，修正不准确的描述

第二步：试点新需求
- 选择 1-2 个中等复杂度的新功能需求作为试点
- 走完完整的 SDD 流程（specs → plan → execute → wrap-up）
- 评估规格质量和代码生成准确率

第三步：团队培训
- 培训团队如何审查 specs.md（而非直接看代码）
- 建立规格审查流程（POD Lead 负责确认开放问题）
- 制定 AGENTS.md 中的团队规范

第四步：全面推广
- 所有新需求走 SDD 流程
- 历史缺陷修复可选择性使用（简单缺陷可跳过规格步骤）
- 定期运行 /update-knowledge 保持知识库最新

注意：存量代码无需重构，SDD 主要针对新增功能。
