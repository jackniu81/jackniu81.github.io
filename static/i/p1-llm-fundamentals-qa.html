LLM 基础原理面试题（附答案）

面向 AI 工程师、前端/全栈工程师转 AI 方向的必备基础。覆盖大模型原理、训练、推理、评估等核心概念。

Transformer 与注意力机制

1. Transformer 架构的核心是什么？

答案： Transformer 是目前所有主流大语言模型（GPT、Claude、Gemini）的底层架构，由 Google 2017 年论文《Attention is All You Need》提出。

核心组成：

  • 自注意力机制（Self-Attention）：让每个 token 都能"看到"序列中所有其他 token，捕捉长距离依赖
  • 前馈神经网络（FFN）：每层的非线性变换，存储大量知识
  • 层归一化（Layer Norm）：稳定训练
  • 位置编码（Positional Encoding）：注入序列位置信息（Transformer 本身无顺序感知）

编码器-解码器 vs 仅解码器：

架构代表模型特点
Encoder-OnlyBERT双向注意力，适合理解任务（分类、NER）
Decoder-OnlyGPT、Claude单向（因果）注意力，适合生成任务
Encoder-DecoderT5、BART适合翻译、摘要等 seq2seq 任务

2. 什么是自注意力（Self-Attention）机制？

答案： 自注意力让模型计算序列中每个 token 与其他所有 token 的"相关性分数"，再加权聚合。

计算流程：

  1. 每个 token 生成三个向量：Q（Query）、K（Key）、V（Value）
  2. 计算注意力分数：score = softmax(Q · K^T / √d_k)
  3. 加权求和：output = score · V

直觉理解：

  • Q："我在找什么？"
  • K："我能提供什么？"
  • V："我的实际内容是什么？"
  • 某个 token 的最终表示 = 所有 token 内容的加权平均，权重取决于相关性

多头注意力（Multi-Head Attention）：

  • 并行运行多个注意力"头"，每个头学习不同的关注模式
  • 如：一个头关注语法依赖，另一个关注语义关系

时间复杂度：O(n²)，n 为序列长度，这是长上下文的主要瓶颈。

3. 什么是 KV Cache？它如何加速推理？

答案： KV Cache（键值缓存）是 LLM 推理时的核心优化技术。

问题背景：生成第 n 个 token 时，需要计算前 n-1 个 token 的 K、V 向量，但这些向量在前面步骤中已经计算过。

KV Cache 原理：

  • 将历史 token 的 K、V 向量缓存在内存（GPU HBM）中
  • 生成新 token 时只需计算该 token 的 Q，与缓存的 K、V 做注意力

效果：

  • 推理速度提升数倍（避免重复计算）
  • 代价：显存占用随序列长度线性增长
  • 长上下文（1M tokens）KV Cache 需要大量显存

与 Prompt Caching（API 层缓存）的区别：

  • KV Cache：模型推理引擎内部优化，用户不感知
  • Prompt Cache：API 服务商缓存用户请求的前缀，降低 Token 计费成本

Tokenization（分词）

4. 什么是 Token？与字符有何不同？

答案： Token 是 LLM 处理文本的基本单位，不等于字符或单词。

常见分词器：

  • BPE（Byte-Pair Encoding）：GPT 系列使用，将高频字节对合并为单个 token
  • SentencePiece：Gemini、LLaMA 等使用，语言无关
  • WordPiece：BERT 使用

Token 数量估算：

文本Token 数（GPT-4o）
1 个英文单词~1.3 tokens
1 个汉字~1.5 tokens（比英文多）
1 行代码~10-20 tokens
1 页文档（~500 词）~700 tokens

为什么重要：

  • API 按 token 计费，token 数 = 成本
  • Context window 限制是 token 上限，不是字数/字符数
  • 中文 token 效率低于英文（同等内容中文消耗更多 token）

5. 什么是 Embedding（嵌入向量）？

答案： Embedding 是将文本（或其他数据）映射到高维连续向量空间的技术，语义相似的文本在向量空间中距离更近。

在 LLM 中的角色：

  1. 输入嵌入：将 token id 转换为稠密向量作为模型输入
  2. 输出表示：最后一层的向量表示用于检索、分类等任务

Embedding 应用场景：

  • 语义搜索：将文档和查询都转为向量，找最相似的文档
  • RAG（检索增强生成）：将知识库向量化，检索相关片段
  • 分类任务：用 embedding 作为分类器输入
  • 去重检测：计算文本相似度

主流 Embedding 模型：

模型厂商向量维度特点
text-embedding-3-largeOpenAI3072综合性能强
text-embedding-3-smallOpenAI1536性价比高
voyage-3Voyage AI1024代码和技术文档优化
nomic-embedNomic768开源，可本地运行

相似度计算：通常用余弦相似度（Cosine Similarity）：

from sklearn.metrics.pairwise import cosine_similarity
sim = cosine_similarity([vec_a], [vec_b])[0][0]  # -1 到 1

模型参数与生成控制

6. Temperature（温度）参数的作用是什么？

答案： Temperature 控制 LLM 输出的随机性（创造性）。

原理：在 softmax 计算中对 logits 除以 Temperature：

P(token) = softmax(logits / temperature)

Temperature 值的影响：

Temperature特点适合场景
0（或极小值）总选概率最高的 token，完全确定性代码生成、数学计算、数据提取
0.3-0.7均衡，略有随机性问答、总结、翻译
0.8-1.0较高随机性，输出多样创意写作、头脑风暴
> 1.0极高随机性，可能乱码实验性场景

实践建议：

  • 代码生成：temperature = 0
  • 一般对话：temperature = 0.7（多数 API 默认值）
  • 创意写作：temperature = 0.9-1.0

7. Top-P 和 Top-K 是什么？与 Temperature 如何配合？

答案： 三个参数都用于控制 LLM 的采样策略：

Top-K：只从概率最高的 K 个 token 中采样。

  • 如 Top-K=50，从概率最高的 50 个 token 中随机选一个
  • 优点：避免采样到极低概率的 token
  • 缺点：固定截断，不够灵活

Top-P（核采样，Nucleus Sampling）：从累积概率超过 P 的最小集合中采样。

  • 如 Top-P=0.9，选取概率累计到 90% 的 token 集合
  • 优点：动态调整候选集大小，适应不同分布
  • 实践中比 Top-K 更常用

配合使用建议：

# OpenAI 推荐：只调其中一个，不要同时调
# 代码任务
{"temperature": 0, "top_p": 1}

# 创意任务
{"temperature": 0.9, "top_p": 0.9}

8. 什么是 max_tokens？与上下文窗口的关系是什么？

答案：

  • Context Window（上下文窗口）：模型一次能处理的最大 token 数，包含输入+输出
  • max_tokens：API 调用时限制输出的最大 token 数

关系：

输入 tokens + 输出 tokens ≤ Context Window

示例：Claude Opus 4（200K 上下文）

  • 输入 190K tokens（大量代码和文档）
  • max_tokens = 8192（输出最多 8K tokens 的回答）
  • 总计 198K，未超 200K 限制

实践影响：

  • max_tokens 设太小 → 回答被截断
  • 输入太长 → 超出窗口，需要截断文档

训练方式

9. 什么是预训练（Pre-training）？

答案： 预训练是 LLM 的第一阶段训练，在海量无标注文本上进行自监督学习。

训练目标：

  • 语言模型（Causal LM）：给定前文，预测下一个 token（GPT 系列）
  • 掩码语言模型（MLM）：随机掩掉 token，预测被掩部分（BERT）

规模：

  • 数据量：万亿级 tokens（GPT-4 估计 ~13 万亿 tokens）
  • 参数量：千亿级（GPT-4 估计 ~1.8 万亿参数 MoE）
  • 计算：数百万 GPU 小时，成本数亿美元

预训练使模型获得：语法、事实知识、逻辑推理、代码理解等通用能力。

10. 什么是 Fine-tuning（微调）？有哪些主要方法？

答案： Fine-tuning 在预训练模型基础上，用特定任务数据进一步训练，使模型适应特定场景。

主要方法：

1. 全量微调（Full Fine-tuning）

  • 更新所有参数
  • 效果最好，但成本高，需要大量 GPU

2. LoRA（Low-Rank Adaptation）（最常用）

  • 在原始权重旁添加低秩矩阵，只训练新增部分
  • 参数量减少 90%+，效果接近全量微调
  • 适合消费级 GPU（RTX 3090/4090）

3. QLoRA（量化 + LoRA）

  • 将原始权重量化为 4-bit，显著降低显存需求
  • 可在单张 24GB GPU 上微调 70B 参数模型

4. PEFT（Parameter-Efficient Fine-Tuning）

  • LoRA 的泛化概念，包含 Adapter、Prefix Tuning 等

Fine-tuning vs RAG 如何选择：

场景推荐
教模型新的输出格式/风格Fine-tuning
知识频繁更新RAG（无需重新训练）
需要引用来源RAG
私有领域专业知识（相对固定）Fine-tuning 或 RAG 结合
快速原型验证RAG

11. 什么是 RLHF（基于人类反馈的强化学习）？

答案： RLHF（Reinforcement Learning from Human Feedback）是让 LLM 学习人类偏好的训练技术，是 ChatGPT 能"对齐"人类意图的关键。

三步流程：

Step 1：SFT（监督微调）

  • 用高质量的人工编写示例微调模型，让模型会"正常回答"

Step 2：训练奖励模型（Reward Model）

  • 人工标注者对同一问题的多个回答排序
  • 训练一个打分模型（奖励模型），学习人类偏好

Step 3：PPO 强化学习

  • 用奖励模型的打分作为奖励信号，用 PPO 算法优化 LLM
  • LLM 学会输出奖励分更高（更符合人类偏好）的回答

RLHF 的演进：

  • RLHF（标准版，复杂，需要 PPO）
  • DPO（Direct Preference Optimization）：更简单，直接优化偏好，无需奖励模型，Llama 3 等使用
  • RLAIF（AI 反馈的强化学习）：用 AI 代替人类打分（Claude 的 Constitutional AI）

幻觉与可靠性

12. 为什么 LLM 会产生幻觉（Hallucination）？如何减少？

答案： 幻觉是 LLM 生成看似可信但实际错误的内容，是当前 LLM 的核心挑战。

根本原因：

  • LLM 是概率预测器，不是"知识库"——输出是最高概率的 token 序列
  • 训练数据中的错误/噪声
  • 训练数据截止日期后的知识盲区
  • "Lost in the Middle"：长上下文中间部分注意力下降

幻觉类型：

类型示例
事实错误错误的历史日期、人名
不存在的引用编造论文标题和 DOI
代码幻觉调用不存在的 API 方法
数值错误数学计算错误

减少幻觉的策略：

  1. RAG：用检索到的真实文档作为上下文，让模型"有据可查"
  2. 要求引用来源："请引用具体来源，如果不确定请说不知道"
  3. Temperature = 0：降低随机性，减少随意猜测
  4. 二次验证：让 LLM 检查自己的输出
  5. 工具调用：计算、查询等任务交给工具而非 LLM

13. 什么是 Grounding（接地）？

答案： Grounding 是将 LLM 的输出锚定到可验证的事实来源，防止幻觉的技术。

主要形式：

  • RAG（检索接地）：从文档检索事实，让 LLM 基于文档回答
  • 工具调用接地：计算交给计算器，搜索交给搜索引擎
  • 实时搜索接地：Perplexity、Grok、Bing Chat 的搜索增强模式
  • 引用验证：要求 LLM 为每个声明提供可验证的来源

效果对比：

  • 无 Grounding：GPT 回答关于某项目的问题，可能编造不存在的功能
  • 有 RAG Grounding：GPT 基于项目文档回答，可追溯到原文

RAG 高级

14. RAG 的检索质量如何优化？

答案： RAG（检索增强生成）的质量瓶颈往往在检索环节，而非生成。

分块策略（Chunking）：

策略优点缺点
固定大小（512 tokens）简单，实现快可能截断句子
递归分割（按段落/句子）保持语义完整性块大小不均
语义分块按语义边界切分需要额外模型
父子分块小块检索，大块输入实现复杂

检索策略：

  • 稠密检索（Dense）：纯向量相似度，捕捉语义
  • 稀疏检索（BM25）：关键词匹配，精确词汇
  • 混合检索（Hybrid）：两者结合，效果最佳（当前最佳实践）

重排序（Reranking）：

  1. 先检索 Top-50 候选
  2. 用 Cross-Encoder 模型对候选重新精排
  3. 取 Top-5 注入 LLM
  • 常用重排器：Cohere Rerank、BGE-Reranker

Embedding 选择：不同文档类型选专用 Embedding：

  • 代码：voyage-code-2
  • 多语言：multilingual-e5-large
  • 通用：text-embedding-3-large

15. 什么是 GraphRAG？与传统 RAG 有何不同？

答案： GraphRAG（Microsoft 2024 年提出）将知识图谱与 RAG 结合，解决传统 RAG 在跨文档推理上的弱点。

传统 RAG 的问题：

  • 每次检索独立的文档片段
  • 无法理解文档间的关系
  • 全局性问题（"整个语料库的主题是什么？"）回答差

GraphRAG 流程：

  1. 从文档中抽取实体和关系（如：人物、组织、事件及其关系）
  2. 构建知识图谱（图数据库）
  3. 检索时沿图的关系路径检索，捕获跨文档联系
  4. 对图进行社区摘要，支持全局性查询

适合场景：

  • 法律文档分析（合同关系、条款引用）
  • 医学知识库（疾病-症状-治疗关系）
  • 企业知识图谱（组织架构、流程依赖）

工具：微软 GraphRAG 开源库、Neo4j + LangChain

AI 系统设计

16. 如何设计一个生产级 RAG 系统？

答案： 一个完整的生产级 RAG 系统包含以下模块：

用户查询
    ↓
[查询预处理]
  - 查询改写（HyDE / 多查询扩展）
  - 意图分类（是否需要检索）
    ↓
[检索层]
  - 混合检索（向量 + BM25）
  - 重排序（Reranker）
  - 引用追踪
    ↓
[生成层]
  - 上下文注入（Prompt 构建）
  - LLM 生成（带 Citation）
  - 输出过滤（Guardrails）
    ↓
[评估层]
  - 检索质量指标（召回率、精确率）
  - 生成质量指标（忠实度、相关性）
  - Langfuse / LangSmith 追踪

关键技术选型：

组件推荐方案
向量数据库Pinecone（云托管）/ Milvus（自部署）
Embeddingtext-embedding-3-large / voyage-3
重排器Cohere Rerank 3
框架LangChain + LangGraph
评估Ragas（自动化指标）+ Langfuse（追踪）

Ragas 评估指标：

  • Faithfulness（忠实度）：回答是否仅基于检索内容，不捏造
  • Answer Relevancy（回答相关性）：回答是否回应了问题
  • Context Recall（上下文召回）：检索到的文档是否包含答案所需信息

17. LLM 在生产环境中有哪些常见挑战？如何应对？

答案：

挑战描述应对策略
延迟大模型推理慢（1-30 秒）流式输出（SSE）、缓存常见问答、选小模型
成本Token 消耗大Prompt 压缩、Prompt Caching、路由到便宜模型
幻觉输出错误信息RAG、Grounding、输出验证
安全Prompt Injection、有害内容Guardrails AI、LlamaGuard
一致性相同问题输出不同答案Temperature=0、结构化输出
长上下文退化中间内容注意力弱关键信息放首尾，RAG 精准检索
速率限制API 调用频率限制并发控制、指数退避重试、多账号负载均衡

LLM 路由（Model Routing）：

  • 简单问题 → 便宜快速的小模型（GPT-4o-mini、Gemini Flash）
  • 复杂推理 → 强力大模型（Claude Opus 4、GPT-5）
  • 工具：RouteLLM、LiteLLM（统一多模型 API）

18. 什么是 Guardrails（护栏）？如何实现 AI 安全？

答案： Guardrails 是防止 AI 系统输出有害、错误或不合规内容的保护机制。

输入护栏（Input Guardrails）：

  • Prompt Injection 检测：识别恶意指令（如"忽略之前的指令"）
  • 敏感词过滤：阻止涉及 PII（个人信息）的输入
  • 话题限制：只允许与业务相关的问题

输出护栏（Output Guardrails）：

  • 有害内容过滤：暴力、歧视等内容检测
  • 格式验证：确保输出符合预期 schema
  • 事实一致性：检查输出是否与上下文一致

主流工具：

  • Guardrails AI：Python 库，声明式定义护栏规则
  • LlamaGuard（Meta）：专门训练的安全分类模型
  • NeMo Guardrails（NVIDIA）：基于对话流的护栏框架
  • Azure AI Content Safety：微软云端内容安全服务

代码示例（Guardrails AI）：

from guardrails import Guard
from guardrails.hub import ToxicLanguage, ValidJson

guard = Guard().use(ToxicLanguage(threshold=0.5)).use(ValidJson())

result = guard(
    llm_api=openai.chat.completions.create,
    prompt="用户问题：...",
    model="gpt-5"
)
