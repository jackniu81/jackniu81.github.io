一、性能指标体系

核心网页指标（Core Web Vitals）

指标全称含义目标值
LCPLargest Contentful Paint最大内容绘制< 2.5s
INPInteraction to Next Paint交互到下次绘制< 200ms
CLSCumulative Layout Shift累计布局偏移< 0.1
注：INP 于 2024-03-12 正式替代 FID（First Input Delay）成为三大 CWV 之一。FID 只测首次交互的输入延迟，INP 覆盖页面整个生命周期内点击/触摸/键盘交互的全流程（输入延迟 + 处理 + 呈现延迟），取近似最差值，更能反映真实响应性。2026 年监控体系应全部以 INP 为准，FID 仅作历史对比。

其他重要指标

  • FCP（First Contentful Paint）：首次内容绘制，< 1.8s 为良
  • TTFB（Time To First Byte）：首字节时间，< 800ms 为良
  • TTI（Time To Interactive）：可交互时间，越短越好
  • TBT（Total Blocking Time）：总阻塞时间，< 200ms 为良

测量工具

  • Lighthouse（Chrome DevTools / CI 集成）
  • WebPageTest（真实网络多地测试）
  • Chrome DevTools Performance（运行时分析）
  • PerformanceObserver API（线上真实用户监控 / RUM）

三、网络传输优化

1. 减少 HTTP 请求数

  • 合并 CSS/JS 文件（构建工具自动处理）
  • 使用 CSS Sprite 或 SVG Symbol 合并图标
  • 内联关键 CSS（Critical CSS）
  • HTTP/2 多路复用下适度拆包（避免过大 bundle）

2. 减小传输体积

  • Gzip / Brotli 压缩：文本资源（HTML/CSS/JS）压缩率 70%+ ，Nginx 配置 gzip on; brotli on;
  • JS Tree Shaking：移除未使用代码，Rollup/Vite 默认开启
  • 代码压缩 Minify：Terser（JS）、cssnano（CSS）
⚠️ 过时/存疑标注（2026-09 核实）：Vite / Rollup 构建链默认使用 esbuild 压缩 JS（速度比 Terser 快一个数量级），只有在 build.minify: 'terser' 显式配置时才走 Terser；webpack 5 生产模式下也可通过 swc-minify / esbuild loader 替代 Terser。cssnano 仍是 PostCSS 体系主流选择。
  • 图片优化：
    • 使用现代格式：WebP（比 JPEG 小 25-35%）、AVIF（更小）
    • 合理压缩：imagemin、sharp
    • 响应式图片：<img srcset> 按屏幕分辨率加载合适尺寸
    • SVG 替代位图（图标/简单图形）

3. 缓存策略

# HTML 入口文件 - 每次验证（保证拿最新）
Cache-Control: no-cache

# 带 hash 指纹的静态资源 - 长期强缓存
Cache-Control: max-age=31536000, immutable

# API 接口 - 按业务决定
Cache-Control: no-store  # 或 max-age=60
  • Service Worker 缓存：离线可用，精细控制缓存策略
  • CDN 缓存：静态资源分发到用户最近节点

4. 减少 DNS 查询 / 连接建立时间

<!-- DNS 预解析 -->
<link rel="dns-prefetch" href="//api.example.com">
<!-- 提前建立 TLS 连接 -->
<link rel="preconnect" href="https://cdn.example.com" crossorigin>

5. 资源预加载

<!-- 关键资源提前加载（字体、首屏图、关键 CSS） -->
<link rel="preload" href="/fonts/main.woff2" as="font" crossorigin>
<link rel="preload" href="/hero.webp" as="image">
<!-- 预取下一页可能需要的资源（子资源级，低优先级） -->
<link rel="prefetch" href="/next-page.js">

🆕 6. Speculation Rules API：prefetch / prerender 下一页

2024-2025 年投入产出比最高的 LCP 优化手段之一。通过 JSON 规则让浏览器推测性地预取（prefetch）甚至预渲染（prerender）用户即将访问的文档（整页导航，而非单个子资源）：

<script type="speculationrules">
{
  "prerender": [
    {
      "where": {
        "and": [
          { "href_matches": "/*" },
          { "not": { "href_matches": "/logout" } },
          { "not": { "selector_matches": ".no-prerender" } }
        ]
      },
      "eagerness": "moderate"
    }
  ],
  "prefetch": [
    { "urls": ["/next-page"], "eagerness": "conservative" }
  ]
}
</script>
<!-- 也可通过 Speculation-Rules 响应头引用外部 JSON 文件 -->
  • 三档激进度 eagerness：conservative（悬停/按下时）、moderate（悬停 200ms 左右）、eager（立即，匹配即预取）。
  • 与旧 <link rel="prefetch"> 的区别：link 预取只拉子资源进 HTTP 缓存、不执行 JS；Speculation Rules 的目标是文档 URL，prerender 会在不可见的后台标签页中完成 HTML 解析、子资源加载、JS 执行与布局，激活时近乎"瞬开"，LCP 可降到接近 0。旧的 Chrome 专属 <link rel="prerender"> 已废弃并被其取代。
  • 实测收益：Ray-Ban 移动端 LCP 4.69s → 2.66s；Cloudflare Speed Brain（2024-09 起默认注入规则）报告命中预取的页面 LCP 下降约 45%。
  • 风险与费用：预渲染会产生真实的后台流量（CPU、内存、带宽）与 JS 副作用（分析埋点、广告请求可能提前触发），必须排除登出、加购、支付等有副作用的 URL；建议对高置信度导航（结算按钮、搜索结果首条）用 prerender，低置信度大范围覆盖用 prefetch。
  • 支持度（2026-09 核实）：Chrome/Edge 109+，覆盖全球约 79% 流量；尚未进入 Baseline——Firefox 对 prefetch 持正面立场但未发布，Safari 26.2 仍在 flag 后。按渐进增强使用，不支持的浏览器自动忽略，无需 polyfill。

🆕 7. fetchpriority：资源优先级提示

fetchpriority 用于微调同一类型资源内部的获取优先级（high / low / auto），典型用法是给 LCP 图片提权：

<!-- LCP 图片：提权，常与 preload 二选一或组合使用 -->
<img src="/hero.avif" fetchpriority="high" alt="...">
<!-- 首屏不可见的第三方脚本/图片：降权，避免与关键资源抢带宽 -->
<script src="/analytics.js" fetchpriority="low" async></script>
  • 与 preload 的取舍：preload 解决的是"发现晚"（浏览器要解析 CSS/JS 后才知道资源存在，如背景图、字体）；fetchpriority 解决的是"优先级不对"（资源已被早早发现，但排在其他资源后面）。LCP 元素是 HTML 中直接可见的 <img> 时，加 fetchpriority="high" 往往比 preload 更合适，二者叠加反而浪费——先用 DevTools Network 面板确认瓶颈再决定。
  • 滥用 high 会让优先级提示失效；同一页面提权资源控制在极少数。
  • 支持度（2026-09 核实）：Baseline 2024 新可用（Chrome 101、Safari 17.2、Firefox 132，2024-10 起全主流浏览器支持），可直接生产使用。Next.js <Image priority> 底层即自动加该属性。

🆕 8. bfcache（前进后退缓存）

bfcache 把整个页面（JS 堆 + DOM）整体冻结在内存中，用户点前进/后退时瞬时还原，是"免费"的导航性能：

// 1) 检测页面是否从 bfcache 还原
window.addEventListener('pageshow', (e) => {
  if (e.persisted) {
    // 从 bfcache 恢复：重新挂监听、刷新实时数据，不要重复初始化
  }
});

// 2) 线上归因：为什么没有命中 bfcache（Chrome 125+）
const navEntry = performance.getEntriesByType('navigation')[0];
console.log(navEntry.notRestoredReasons);
// 常见 reason：'unload-handler'、'cache-control-no-store'、
// 'related-active-contents'、'internal-error' 等，含 iframe 级递归结构
  • 最常见的禁用原因：注册了 unload 监听器。卸载清理请改用 pagehide / visibilitychange（发送埋点用 navigator.sendBeacon）。Chrome 已在 2025-2026 年逐步移除 unload：对头部站点从 Chrome 135 开始、对全部站点按 1%→100% 灰度至 Chrome 154（2026-09-22）全量，现在不清理就是线上隐患。
  • 设置 Cache-Control: no-store 的文档无法进入 bfcache；WebSocket / WebRTC 长连接、IndexedDB 事务未结束等也会阻止。
  • notRestoredReasons API（挂在 PerformanceNavigationTiming 上）Chrome/Edge 125+ 可用，Firefox/Safari 尚未支持（非 Baseline），是目前线上统计 bfcache 命中率与阻塞归因的唯一手段；DevTools 的 Application → Back/forward cache 可做实验室复现。

🆕 9. 缓存新实践：stale-while-revalidate 与 Service Worker 现状

# 优先用缓存立即响应，后台静默拉新版本，下次访问生效
Cache-Control: max-age=0, stale-while-revalidate=86400
  • stale-while-revalidate 已被所有现代浏览器支持，适合更新频繁但可接受一版延迟的 API/HTML/JSON，是 SWR / React Query 等库 HTTP 层的天然搭档。
  • Service Worker 并未被淘汰（2026-09 核实）：网传"Chrome 移除 Service Worker / InstallEvent"不属实——Service Workers 规范 2026-04 仍在推进 W3C 候选推荐，Chrome 反而新增了 Service Worker Static Routing API（install 阶段用 event.addRoutes() 声明哪些请求直接走网络或缓存、绕过 SW 启动开销），解决 SW 拖慢导航关键路径的老问题。
  • 但 SW 的使用定位在收缩：纯静态资源缓存优先交给 HTTP 缓存 + CDN + 103 Early Hints；SW 主要用于离线能力、后台同步、推送、精细的网络回退策略。引入前先评估维护成本（更新失效、Quota 淘汰、调试复杂度）。

四、JavaScript 优化

1. 代码分割（Code Splitting）

// 路由级分割 - React
const Dashboard = React.lazy(() => import('./Dashboard'));

// 条件加载
if (user.isPremier) {
  const { PremierFeature } = await import('./PremierFeature');
}
  • 入口分割：每个路由独立 chunk
  • 动态导入：按需加载非首屏功能
  • 第三方库分包：vendor chunk 单独分离，利用浏览器缓存

2. 减少主线程阻塞

  • 长任务拆分：将耗时任务拆为 <50ms 的小任务

``javascript // 统一的让出函数：scheduler.yield() 不可用时降级 setTimeout function yieldToMain() { if ('scheduler' in globalThis && 'yield' in globalThis.scheduler) { return globalThis.scheduler.yield(); // 延续任务排在队首，恢复快 } return new Promise((resolve) => setTimeout(resolve, 0)); // 排到队尾 } // 按 50ms 时间预算切片，而非"每处理 N 个"（单条耗时不均时 N 不可靠） async function run(hugeList) { let deadline = performance.now() + 50; for (const item of hugeList) { processItem(item); if (performance.now() >= deadline) { await yieldToMain(); // 让浏览器响应交互 deadline = performance.now() + 50; } } } ``

兼容性（2026-09 核实）：scheduler.yield() Chrome/Edge 129+、Firefox 142+，Safari 至 26.x 仍未支持，非 Baseline，必须特性检测降级；scheduler.postTask()（user-blocking / user-visible / background 三档优先级）支持度相同，可用 scheduler-polyfill 补齐。
  • Web Worker：CPU 密集型计算放后台线程（图像处理、数据加密）
  • 避免不必要的 polyfill：@babel/preset-env 按 browserslist 精确 polyfill

3. 渲染性能优化

  • 防抖（debounce） 处理输入、搜索事件
  • 节流（throttle） 处理 scroll、resize 事件
  • 虚拟列表（Virtual Scroll）：只渲染可视区域内的列表项（react-virtual、vue-virtual-scroller）
  • 避免强制同步布局：读写 DOM 属性要分离，不要在循环中交替读写

🆕 5. INP 优化实战：输入延迟、处理与呈现三段

INP = 输入延迟（Input Delay）+ 事件处理（Processing）+ 呈现延迟（Presentation Delay），逐段治理：

阶段常见元凶手段
输入延迟别的长任务占着主线程scheduler.yield()/postTask 切片（见第 2 节）、非关键初始化 requestIdleCallback
事件处理同步重渲染、大列表 diff、同步 localStorage先同步给出视觉反馈，重活延后；useDeferredValue/startTransition（React 18+）
呈现延迟强制同步布局、DOM 过大、样式重算读写分离、避免在 RAF 回调里读 offsetHeight、控制 DOM 节点规模
// RAF 优化输入延迟：连续输入时把"更新 UI"收敛到下一帧，
// 并用 isInputPending（Chromium）在长循环中主动让道
while (workLeft && !navigator.scheduling?.isInputPending?.()) {
  doChunkOfWork();
}
  • 交互反馈原则：点击后 100ms 内必须有视觉响应（loading 态、乐观更新），数据结果再异步追上。
  • React 19 已将 View Transitions 与自动 memoization（React Compiler）纳入，startTransition 仍是把非紧急更新移出 INP 关键路径的首选 API。

🆕 6. 第三方脚本治理

第三方脚本（分析、广告、客服、A/B）通常是长任务与 INP 劣化的最大来源。web.dev 推荐的治理顺序：盘点 → 延迟 → 隔离 → 验证。

<!-- 1) 能异步就异步，非关键脚本延迟到空闲或交互后再加载 -->
<script src="/analytics.js" defer></script>
<button id="chat">客服</button>
<script>
  // 2) Facade 模式：用静态占位图/按钮代替真实三方组件，交互时才加载
  document.getElementById('chat').addEventListener('pointerenter', () => {
    const s = document.createElement('script');
    s.src = 'https://third-party-chat.example/widget.js';
    document.head.appendChild(s);
  }, { once: true });
</script>
  • Partytown（@builder.io/partytown）：通过在 Web Worker 中跑一个 DOM 代理层，把 jQuery 时代的同步三方脚本移出主线程，主线程只接收必要的 DOM 操作回放，适合无法改造的遗留三方脚本；注意它是"反向代理 DOM"的权衡方案，依赖 DOM 时序的脚本（部分广告、reCAPTCHA）可能不兼容，需逐个验证。
  • 其他手段：iframe 三方组件加 loading="lazy"、沙箱化；Tag Manager 中清理过期标签；用 WebPageTest 的 "Individual Assets" / DevTools Network 按域名统计第三方耗时占比。
  • 预算建议：第三方 JS 总量纳入第十章性能预算，典型阈值移动端 < 100KB（gzip 后）。

🆕 7. 长任务可观测：Long Animation Frames（LoAF）

旧的 Long Tasks API 只能告诉你"有个任务超过 50ms"，无法归因；LoAF 以"帧"为单位，给出该帧的 blockingDuration、renderStart、styleAndLayoutStart 以及具体脚本归因数组（脚本 URL、函数名、执行各阶段耗时）：

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    for (const script of entry.scripts) {
      // script.invoker / script.sourceURL / script.duration / script.executionStart
      console.log(script.sourceURL, script.duration, script.invoker);
    }
  }
}).observe({ type: 'long-animation-frame', buffered: true });
  • 是 INP 线上归因的核心工具：web-vitals v4 在 INP 上报中直接携带关联的 LoAF 条目，Sentry / DebugBear / SpeedCurve 等 RUM 均已接入。
  • 注意跨域脚本需带 crossorigin="anonymous" 且服务端返回 CORP/Timing-Allow-Origin，否则只能看到 URL 拿不到函数级信息。
  • 支持度（2026-09 核实）：Chrome/Edge 123+（2024-03），全球约 75% 流量可采；Firefox/Safari 尚无，非 Baseline。采集侧做好特性检测，降级时继续用 longtask + Event Timing（event/first-input entryType）组合。

1. 减少回流和重绘

/* 用 transform 替代 top/left 做位移动画 */
/* 不好 */

/* 好 */

  • CSS Modules / Scoped CSS：避免全局样式污染
  • Tailwind CSS Purge：构建时删除未用的工具类

  • 避免通配符 * 选择器

🆕 5. content-visibility：跳过离屏内容渲染

对长页面中屏外的大区块（长列表的后续项、Tab 未激活面板、折叠区），浏览器可直接跳过其布局与绘制：

.article-section {
  content-visibility: auto;
  /* 必须给占位尺寸，否则跳过渲染时高度塌缩、滚动条跳动（影响 CLS） */
  contain-intrinsic-size: auto 600px;
}
  • contain-intrinsic-size: auto <length> 中的 auto 表示"曾渲染过就记住真实尺寸"，回退到给定估值，滚动反复经过时更稳。
  • 典型收益：含海量 DOM 的文档/商品流页面初始渲染提升数倍；浏览器还会在跳过/恢复时触发 contentvisibilityautostatechange 事件，可据此暂停区块内 canvas/视频/轮播。
  • 注意：不要用在首屏或 LCP 候选元素上；打印、页内查找仍可访问被跳过内容（与 display:none 不同）。
  • 支持度（2026-09 核实）：Baseline 2024 新可用（Chrome 85、Safari 18、Firefox 125，2024-09 起全主流浏览器支持）。

🆕 6. View Transitions API 与感知性能

视图过渡把"内容突变"变成浏览器合成线程上的快照动画，不改变真实加载速度，但显著降低感知延迟，是 2024-2026 年原生 App 级体验的关键 API：

// SPA（同文档）：包裹一次 DOM 更新即可
function spaNavigate(updateDOM) {
  if (!document.startViewTransition) return updateDOM(); // 渐进增强
  document.startViewTransition(() => updateDOM());
}
/* MPA（跨文档）：整站一行开启，原生支持前进/后退 */
@view-transition { navigation: auto; }

/* 自定义共享元素动画 */
::view-transition-old(root) { animation: fade-out 0.2s ease; }
::view-transition-new(root) { animation: fade-in 0.3s ease; }
  • 支持度（2026-09 核实）：同文档（SPA）过渡 Chrome 111、Safari 18、Firefox 144（2025-10-14），至此达到 Baseline 新可用；跨文档（MPA）过渡 Chrome/Edge 126、Safari 18.2 可用，Firefox 尚未发布。不支持的浏览器直接跳为普通导航，可安全按渐进增强上线。React 19.2 已内建 View Transitions 支持（Next.js 16 跟进），不再需要 Framer Motion 等库承担路由转场。
  • 性能注意：动画只动 opacity / transform（走合成层）；给参与过渡的元素显式设置 view-transition-name，避免大面积同名快照导致内存翻倍；过渡期间避免同步强制布局。

八、服务端与网络层优化

1. 服务端渲染（SSR）

  • Next.js / Nuxt：服务端直接返回完整 HTML，显著提升 FCP 和 LCP
  • 流式渲染（Streaming SSR）：边渲染边传输，React 18 / Next.js App Router 支持
  • 静态生成（SSG / ISR）：预生成 HTML，CDN 分发，TTFB 最低

2. HTTP/2 / HTTP/3

  • 确保服务器开启 HTTP/2（新语法：http2 on;，旧写法 listen 443 ssl http2 在 Nginx 1.25+ 已弃用）
  • HTTP/3 / QUIC 对弱网环境效果显著

🆕 3. HTTP/3（QUIC）部署与 0-RTT

HTTP/3 已从"未来技术"变为默认配置：Cloudflare 数据 2025-10 全球采用率约 35%，Chrome、Edge、Firefox、Safari 均已原生支持。

  • 核心收益：1-RTT 合并传输+TLS 握手；QUIC 流级独立丢包恢复，消除 HTTP/2 的 TCP 队头阻塞；基于 Connection ID 的连接迁移（Wi-Fi ↔ 5G 切换不断连）；弱网/高丢包场景比 HTTP/2 快 30% 以上。
  • 0-RTT：回访用户首个数据包即可携带请求，再省一个 RTT；但存在重放攻击面，只能用于幂等/GET 请求，敏感端点需在应用层通过 Early-Data 请求头拒绝。
# Nginx 1.25+（主线版 1.25.0 起内置，稳定版 1.26+；需编译带 --with-http_v3_module）
server {
    listen 443 ssl;
    listen 443 quic reuseport;   # UDP 443，防火墙必须放行 UDP
    http2 on;
    http3 on;
    ssl_protocols TLSv1.3;       # HTTP/3 强制 TLS 1.3
    ssl_early_data on;           # 开启 0-RTT（推荐配合 OpenSSL 3.5.1+）
    # 告知浏览器该源支持 HTTP/3，缺少此头浏览器会一直走 HTTP/2
    add_header Alt-Svc 'h3=":443"; ma=86400' always;
}
  • 零成本方案：Cloudflare / Fastly 等 CDN 面板一键开启，边缘对客户端讲 HTTP/3，回源仍走 HTTP/1.1/2 即可；Caddy 默认开箱即启用 HTTP/3。

4. 服务端压缩

# Nginx 配置
gzip on;
gzip_types text/plain text/css application/json application/javascript;
gzip_min_length 1024;

# Brotli（需额外模块）
brotli on;
brotli_comp_level 6;
  • 静态资源建议构建时用最高级别 Brotli 预压缩（.br 文件 + gzipstatic/brotlistatic），运行时再实时压缩兼顾老客户端。
  • 新动向：Content-Encoding: zstd（RFC 8878）Chrome/Edge/Firefox 已支持，压缩率与速度优于 gzip，可作为 Brotli 之外的观察项。

5. 资源 Preload / Push

  • HTTP/2 Server Push（已逐渐被 103 Early Hints 替代；Chrome 从未默认启用推送，实际已名存实亡）
  • 103 Early Hints：在主响应前预先推送资源预加载指令

🆕 6. 103 Early Hints 生产落地

当源站首字节慢（SSR 查库、边缘回源）时，服务器先返回 103 携带关键子资源的 Link 头，让浏览器在等待 HTML 期间并行开始拉 CSS/字体/图片，把服务端思考时间"藏"进资源加载：

HTTP/1.1 103 Early Hints
Link: </styles/main.css>; rel=preload; as=style
Link: </hero.avif>; rel=preload; as=image; fetchpriority="high"
  • 浏览器支持（2026-09 核实）：Chrome/Edge 从 123 起默认启用（iframe 内除外），Safari 17+、Firefox 120+ 支持，可安全上线。
  • 服务端/CDN：Nginx 1.29.0（2025-06）新增 early_hints 指令，可自动把 PHP/上游返回的 103 透传或按配置生成；Cloudflare 对 HTML 响应自动生成 Early Hints（含识别到的关键资源）；Node.js 18+ 可在框架（Fastify/Hono）中直接 response.writeEarlyHints()。
  • 注意 Early Hints 只提示子资源，不替代 preload；文档级预取用 Speculation Rules（见第三章第 6 节）。

九、React / Vue 框架层优化

React 优化

// 1. memo 防止不必要的子组件渲染
const Child = React.memo(({ data }) => <div>{data}</div>);

// 2. useMemo 缓存计算结果
const sorted = useMemo(() => items.sort(compareFn), [items]);

// 3. useCallback 缓存函数引用（给子组件传函数时）
const handleClick = useCallback(() => { ... }, [dep]);

// 4. 列表必须有稳定的 key
{list.map(item => <Item key={item.id} {...item} />)}

// 5. 动态导入路由
const Page = lazy(() => import('./Page'));

Vue 优化

<!-- 1. v-once：静态内容只渲染一次 -->
<StaticComponent v-once />

<!-- 2. v-memo：缓存子树，仅依赖变化时更新 -->
<li v-for="item in list" :key="item.id" v-memo="[item.selected]">

<!-- 3. shallowRef / shallowReactive：浅层响应，减少 Proxy 开销 -->
const bigData = shallowRef(largeObject);

<!-- 4. computed 有缓存，避免模板中调用函数 -->
const sorted = computed(() => list.value.slice().sort());

🆕 React 19 / Next.js 15-16 性能要点（2026-09 核实）

  • Server Components 削减客户端 bundle：数据获取与重型逻辑留在服务端，下发的只有渲染结果，大型交互库（图表、Markdown）只在需要 "use client" 的边界引入，是当前 React 体系最结构性的 JS 体积优化。
  • PPR（Partial Prerendering，部分预渲染）：同一页面静态外壳即时下发 + <Suspense> 内动态部分流式补全，结束了 SSG 与 SSR 的二选一。Next 14 实验性引入、Next 15 继续打磨；Next 16（2025-10-21 发布）中 PPR 随 Cache Components 稳定：开启 cacheComponents: true 即默认 PPR，旧的 experimental.ppr / experimental.dynamicIO 标志已移除，改用 "use cache" 指令做组件/函数级缓存。
  • React Compiler 在 Next 16 稳定：编译期自动 memo 化，可逐步移除手写 useMemo/useCallback/React.memo，减少漏 memo 导致的重渲染（INP 收益），但仍需先治理昂贵渲染而非盲目依赖编译器。
  • React 19.2：useEffectEvent()、<Activity>（隐藏而非卸载路由、保留状态）与 View Transitions 集成；Next 16 还带来增量 prefetch、布局去重等导航优化。
  • 升级注意：Next 16 默认动态渲染（缓存全部显式 opt-in）、next/image 默认值变化、Turbopack 成为默认构建器，迁移前对照官方 upgrade guide 评估缓存语义变化。
