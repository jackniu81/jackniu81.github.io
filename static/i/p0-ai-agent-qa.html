AI Agent 工程师面试题（基础概念 + LangChain / LangGraph / Deep Agents 实战，附答案）

一篇覆盖：Agent / ReAct / 记忆 / RAG / Function Calling / 多 Agent / A2A 等通用概念，以及主流框架的编码能力与工程决策（代码手写、机制原理、排错与方案设计）。

一、基础概念

1. 什么是 AI Agent？它与普通 LLM 聊天有什么区别？

答案： AI Agent（智能体）是一种能够感知环境、自主规划、调用工具并执行动作以实现目标的 AI 系统。与普通 LLM 聊天不同，Agent 具备自主决策、多步执行、工具调用的能力。

对比维度普通 LLMAI Agent
交互方式单轮/多轮对话自主规划、多步执行
工具使用无可调用外部工具、API、数据库
记忆能力有限上下文窗口持久记忆（短期+长期）
自主性被动回答主动规划和行动
任务复杂度简单、单步复杂、多步、长周期

2. AI Agent 的四大核心组件是什么？

答案：

  • 感知（Perception）：接收用户输入、环境状态、工具返回结果
  • 规划（Planning）：分解任务、制定执行计划（如 ReAct、Chain-of-Thought）
  • 记忆（Memory）：存储上下文（短期）和知识（长期），支持跨步骤推理
  • 行动（Action）：调用工具、执行代码、调用 API、操作文件等

3. 什么是 ReAct 架构？

答案： ReAct（Reasoning + Acting）是一种 Agent 推理框架，让 LLM 交替进行思考（Thought）和行动（Action）：

Thought: 我需要搜索今天的天气
Action: search_web("今天北京天气")
Observation: 晴天，25°C
Thought: 已获得结果，整理回答
Action: 返回结果给用户

这种模式使 LLM 的推理过程透明、可调试，是目前最主流的 Agent 模式之一。LangGraph 手写实现见第 23 题。

4. Agent 的规划模式有哪些？

答案：

  • ReAct：思考与行动交替，动态规划，适合未知环境
  • Plan-and-Execute：先整体规划，再逐步执行，适合复杂任务
  • Reflection：执行后自我反思，迭代改进，提升输出质量
  • Self-Ask：将复杂问题分解为子问题逐步回答
  • Tree of Thoughts（ToT）：并行探索多个推理路径，选最优解

6. 🆕 什么是 Context Engineering？为什么 2025 年后它比 Prompt Engineering 更常被提起？

答案：

Context Engineering（上下文工程）是指系统性地设计和管理进入模型上下文窗口的全部信息：系统提示、工具定义、检索结果、历史消息、子代理回传、scratchpad 内容等。2025 年中由 Tobi Lütke（6/19）、Harrison Chase（6/23）、Andrej Karpathy（6/25）等人在公开讨论中带火，Anthropic 于 2025 年末发表《Effective Context Engineering for AI Agents》。

与 Prompt Engineering 的关系：上下文工程是超集——prompt 只是上下文中的一个可控片段。Agent 是多轮、自主、带工具的，真正决定成败的往往不是某一句 prompt，而是每一步"上下文里到底有什么"。

核心做四件事：

动作手段典型实现
写（Write）让 Agent 把中间产物外写scratchpad、todo 清单、虚拟文件（Deep Agents）
选（Select）每步只加载当前需要的内容JIT 检索、按需加载工具、动态 few-shot
压缩（Compress）上下文逼近窗口时摘要/裁剪compaction、滑窗、对话摘要（经验阈值约 70% 窗口占用即触发）
隔离（Isolate）把高噪音子任务关进独立上下文子代理（Manus 总结为 reduce / offload / isolate 三策）

为什么必须做：研究表明长上下文下所有模型都会出现性能衰减——Chroma 的 Context Rot 实验中 18 个模型全部随上下文长度衰减；"Lost in the Middle" 证明位于中间位置的信息利用率最低。Anthropic 总结四类上下文失败：poisoning（污染/投毒）、distraction（干扰）、confusion（混淆）、clash（指令冲突）。2025-09-29 Claude Code 推出 context editing（自动写文件、压缩对话），是该理念落地的代表。

7. 🆕 Anthropic《Building Effective Agents》提出了哪几种工作流模式？

答案：

Anthropic 于 2024-12-19 发表该文，首先区分两个概念：

  • Workflow（工作流）：LLM 与工具按预定义的代码路径编排，流程确定；
  • Autonomous Agent（自主智能体）：模型自己决定路径、动态调用工具，流程开放。

基本构件是"增强型 LLM"（带工具调用、检索、结构化输出的单次模型调用）。五种工作流模式：

模式结构适用场景
Prompt Chaining多个 prompt 串行，前一步输出喂下一步可拆成固定子任务（生成→校对→翻译）
Routing分类后分流到不同处理链客服意图分流、模型分级路由（见第 22 题）
Parallelization并行调用后聚合：sectioning（分片）/ voting（投票）多维度同时评审、多次投票降方差
Orchestrator-Workers主模型动态拆任务、派给 worker任务子项预先未知（如跨多文件代码修改）
Evaluator-Optimizer生成→评审→按意见修订循环翻译、代码、写作等可反复打磨的任务

核心建议：先用最简方案（单次增强 LLM → 再加工作流 → 最后才考虑完全自主 agent）；框架会增加抽象成本，能不引入就不引入。Orchestrator-Workers 与 Deep Agents 的规划 + 子代理机制一脉相承（见第 35 题）。

二、记忆、RAG 与知识

8. Agent 的记忆系统如何设计？

答案： Agent 记忆分为三类：

  • 短期记忆（In-context Memory）：当前对话的上下文，存在 LLM 的 context window 中，不持久
  • 长期记忆（External Memory）：持久化存储，通过向量数据库（RAG）或数据库检索，跨会话保留
  • 工作记忆（Working Memory）：当前任务执行中的中间状态、变量、步骤结果

工程实现上，短期记忆对应 LangGraph 的 state + checkpointer（第 24 题），长期记忆对应跨 thread 的 Store / RAG 知识库。

9. 什么是 RAG？与 Agent 有何关系？

答案： RAG（Retrieval-Augmented Generation，检索增强生成）是将外部知识库与 LLM 结合的技术：

  1. 将文档分块，向量化后存入向量数据库
  2. 用户提问时，检索相关文档片段
  3. 将检索结果注入 LLM prompt 生成回答

在 Agent 中，RAG 通常作为长期记忆工具，Agent 可以决定是否调用 RAG 检索来补充知识。

10. 常见向量数据库有哪些？

答案：

  • Chroma：轻量级，本地部署，适合原型和小型项目
  • Pinecone：云托管，高性能，适合生产环境
  • Milvus：开源，高性能，支持大规模向量检索
  • Weaviate：开源，支持混合检索（语义+关键词）
  • FAISS：Facebook 出品，纯本地，适合离线场景

11. 🆕 Agent 的长期记忆基建有哪些方案？和直接做 RAG 有什么区别？

答案：

代表方案（截至 2026-09）：

项目技术路线特点
Mem0向量 + 图谱的 drop-in 记忆层接入简单，有 ECAI 2025 论文（arXiv:2504.19413）与 LoCoMo 基准
ZepGraphiti 时序知识图谱支持带时间维度的事实，官方称检索 <200ms（示例口径）
Letta（前身 MemGPT，UCB）OS 式 memory blocks，Agent 自编辑记忆显式区分核心记忆/归档记忆
LangMemLangChain 原生记忆模块与 LangGraph Store 深度集成

与纯 RAG 的关键区别：

  1. 写入侧做事实抽取与更新：不是原样存文档块，而是从对话中抽取"用户偏好/实体关系"，并处理更新与冲突（旧事实失效）；
  2. 时序与关系：支持"用户上个月在 A 团队、这个月换到 B 团队"这类带时间的事实，图谱维护实体关系；
  3. 召回侧个性化：按用户/会话作用域检索，而非全局相似度。

常用评测基准：LoCoMo、LongMemEval、BEAM。注意各厂商常引用自测分数，跨方案比较时以独立基准为准。

三、工具调用

12. 什么是 Function Calling / Tool Use？

答案： Function Calling 是让 LLM 能够决定"调用哪个工具、传入什么参数"的能力：

  1. 开发者定义工具的名称、描述和参数 schema（通常是 JSON Schema）
  2. LLM 根据用户意图选择合适的工具并生成调用参数
  3. 代码执行实际的工具调用，将结果返回给 LLM
  4. LLM 基于结果继续推理或生成最终回答
tools = [{
    "name": "get_weather",
    "description": "获取指定城市的天气",
    "parameters": {
        "type": "object",
        "properties": {
            "city": {"type": "string", "description": "城市名称"}
        },
        "required": ["city"]
    }
}]

不借助框架的手写调用循环与消息流转见第 20 题。

13. Agent 常见的工具类型有哪些？

答案：

  • 搜索工具：Google Search、Bing、SerpAPI、Tavily
  • 代码执行：Python Interpreter、Node.js 运行环境
  • 文件操作：读写文件、解析 PDF/Excel/Word
  • 数据库查询：SQL 查询、向量数据库检索
  • API 调用：REST API、GraphQL、第三方服务
  • 浏览器控制：Playwright、Puppeteer（用于 Web 自动化）
  • 计算器：数学计算，避免 LLM 幻觉

14. @tool 装饰器生成的工具，其 schema 从哪里来？怎么写复杂参数？

答案：

schema 来自三处的自动提取：函数名、docstring（作为工具描述）、类型注解 + Pydantic（作为参数 JSON Schema）。复杂参数用 Pydantic Model：

from pydantic import BaseModel, Field
from langchain_core.tools import tool

class RefundInput(BaseModel):
    order_id: str = Field(description="订单号，ORD- 开头")
    reason: str = Field(max_length=200, description="退款原因")
    amount: float | None = Field(default=None, description="金额，单位元")

@tool(args_schema=RefundInput)
def apply_refund(order_id: str, reason: str, amount: float | None) -> str:
    """提交退款。写操作，调用前必须先与用户确认金额与原因。"""
    ...

追问"如何提升工具调用准确率"的标准答案：动宾命名、docstring 写清何时用/何时不用、参数给示例与约束、工具数量控制在约 20 个以内、返回精炼结构化结果。

15. 🆕 OpenAI Responses API 与 Chat Completions、Assistants API 是什么关系？

答案：

Responses API 是 OpenAI 于 2025-03 推出的统一接口（POST /v1/responses），定位为 Assistants API 的替代者：

特性说明
有状态previousresponseid 串联多轮，store 控制是否服务端存状态
入参input（取代 messages）+ instructions（系统提示）
内置工具websearch、filesearch、codeinterpreter、computeruse，并可挂 MCP 服务器
强类型输出output items 列表，含 message / function_call / reasoning / compaction（状态压缩）等类型
结构化responses.parse() 直接返回经 schema 校验的对象
resp = client.responses.create(
    model="gpt-5",
    input="查一下今天北京天气并总结穿衣建议",
    tools=[{"type": "web_search"}],
    store=True,
)
print(resp.output_text)

迁移口径：Assistants API 已于 2025-08-26 弃用、2026-08-26 关闭；简单单轮/多轮对话继续用 Chat Completions 即可；需要内置工具与服务端状态管理的 Agent 场景用 Responses API。

四、框架与选型

16. 用一句话说清 LangChain、LangGraph、Deep Agents 的关系，并给出选型依据。

答案：

三者是分层依赖而非竞争关系：

  • LangChain：组件层——ChatModel、Tool、Prompt、Retriever、OutputParser 的统一抽象，LCEL 做线性编排。
  • LangGraph：编排层——在 LangChain 组件之上提供有状态的图（State/Node/Edge），解决循环、分支、持久化、人机协同。
  • Deep Agents：应用层——基于 LangGraph 预置了规划（todo）、子代理、虚拟文件系统、长短期记忆的"深度智能体"模板。

选型依据：

任务特征选择
单次调用 / 固定线性 RAGLCEL 或裸 SDK（OpenAI / Anthropic）
简单 ReAct 单 AgentLangChain create_agent
流程可画出确定流程图、需审批/回放/多 AgentLangGraph StateGraph
多角色对话协作、研究型分工AutoGen / CrewAI（或 LangGraph Supervisor）
只能描述目标、路径靠 Agent 自主探索的长任务Deep Agents

核心判断：固定流程用图，开放目标用深度智能体，线性任务别上框架。

17. AutoGen 和 CrewAI 分别是什么？适合什么场景？

答案：

AutoGen（微软出品）专注于多智能体对话协作，让多个 Agent 相互交流完成任务：

  • 每个 Agent 有独立角色（如 Planner、Coder、Reviewer）
  • Agent 之间通过消息传递协作
  • 支持人机混合（Human-in-the-loop）

CrewAI 是基于角色的多智能体框架，用船员（Crew）来比喻多个 Agent 分工协作：

  • Agent：有 role、goal、backstory，定义具体角色
  • Task：分配给某个 Agent 的具体任务
  • Crew：管理所有 Agent 和 Task 的编排器
  • Process：顺序或层级执行模式

与 LangChain 系的区别：LangChain/LangGraph 更侧重工作流编排和工具调用、可控性强；AutoGen / CrewAI 更侧重多 Agent 角色扮演与对话协作，适合"研究员 + 写作者 + 审核员"这类专业化分工场景。

⚠️ 过时/存疑标注（2026-09 核实）：AutoGen v0.4 已于 2025-01 完全重写（2025-01-14/17 发布），改为异步事件驱动的 Actor 模型，分层为 autogen-core / autogen-agentchat / autogen-ext，内置 OpenTelemetry，支持 Python + .NET。2025-10 微软宣布 Microsoft Agent Framework（MAF，合并 AutoGen + Semantic Kernel），其 1.0 于 2026-04-03 发布，AutoGen 随后进入维护模式。新项目选型应评估 MAF，而非直接上手旧 AutoGen；SDK 整体格局见第 19 题。

18. LangChain v1 之后有哪些重要的 API 变化？

五、LangChain 编码题

20. 手写一个带工具的 Agent（不使用 AgentExecutor），说明消息流转。

答案：

from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, ToolMessage
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询指定城市的天气。city 为城市名。"""
    return f"{city}：晴，25°C"

llm = ChatOpenAI(model="gpt-4o-mini").bind_tools([get_weather])
tools = {"get_weather": get_weather}

messages = [HumanMessage("北京天气如何？")]

for _ in range(10):                       # 最大步数，防死循环
    ai = llm.invoke(messages)
    messages.append(ai)
    if not ai.tool_calls:                # 无工具调用 = 终态
        break
    for call in ai.tool_calls:           # 执行所有请求的工具
        result = tools[call["name"]].invoke(call["args"])
        messages.append(ToolMessage(str(result), tool_call_id=call["id"]))

print(messages[-1].content)

消息流转是 Agent 的命门，必须能默写：

Human → AI(tool_calls) → Tool(tool_call_id 对应) → AI … → AI(无 tool_calls=终态)

两个高频扣分点：① ToolMessage 必须带 toolcallid 与请求一一对应；② 每轮要把 AI 消息和 Tool 消息都追加进历史，漏任一边模型都会报错。

21. LCEL 的 | 语法底层是什么？为什么它能免费获得流式/重试/并行？

答案：

| 调用的是对象的 or，把每个 Runnable 串成 RunnableSequence。LangChain 的组件（prompt、llm、parser、retriever）都实现了统一的 Runnable 接口（invoke / stream / batch / ainvoke / astream）。

因为接口统一，序列就能把能力整条链透传：

  • .stream()：逐段向前后传播，最后一个组件边产边出；
  • .batch() / .abatch()：自动并发执行多条输入；
  • .withretry()、.withconfig()：包裹在任意 Runnable 外层，不侵入业务代码。
chain = (prompt | llm | StrOutputParser()).with_retry(
    stop_after_attempt=3, wait_exponential_jitter=True
)

适用边界要能说清：LCEL 只擅长无环的线性/并行结构；一旦需要根据模型输出循环或回跳到前面节点，LCEL 表达不了，必须用 LangGraph。

22. 怎么做模型分级路由（省成本）？给出代码。

答案：

用 LCEL 的 RunnableBranch 按输入特征选择不同模型：

from langchain_core.runnables import RunnableBranch, RunnableLambda

mini = ChatOpenAI(model="gpt-4o-mini")
pro  = ChatOpenAI(model="gpt-4o")

def is_complex(msg: dict) -> bool:
    return any(k in msg["question"] for k in ("架构", "排查", "多步", "权衡"))

router = RunnableBranch(
    (is_complex, pro),
    mini,                       # 默认分支
)
chain = RunnableLambda(lambda x: x) | router | StrOutputParser()

工程上还会配合：意图识别用小模型 + withstructuredoutput、子 Agent 强制用便宜模型、超长固定前缀开 prompt caching、对每一步记账设预算。

六、LangGraph 编码题

23. 手写 StateGraph 版 ReAct，并解释 reducer 的作用。

答案：

from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition

class State(TypedDict):
    messages: Annotated[list, add_messages]

llm_tools = ChatOpenAI(model="gpt-4o-mini").bind_tools([get_weather])

def chat(state: State):
    return {"messages": [llm_tools.invoke(state["messages"])]}

g = StateGraph(State)
g.add_node("chat", chat)
g.add_node("tools", ToolNode([get_weather]))
g.add_edge(START, "chat")
g.add_conditional_edges("chat", tools_condition)   # 有 tool_calls→tools，否则→END
g.add_edge("tools", "chat")
app = g.compile()

reducer 是高频考点：节点返回的是"对 state 的更新"，Annotated[list, addmessages] 声明该字段用 addmessages 做追加合并（按消息 id 去重/更新），而不是默认的整体覆盖。若不写 reducer，第二个节点返回 {"messages": [...]} 会把整个列表替换掉，历史丢失。自定义场景常用 operator.add（列表拼接）或自己写 reducer 函数。

24. Checkpointer 解决什么问题？写一段"跨次请求保持记忆 + 恢复执行"的代码。

答案：

Checkpointer 在每个超步（super-step）后把 state 快照持久化，带来三个能力：同 thread 多轮记忆、进程重启后续跑、历史回放/分叉（time travel）。

from langgraph.checkpoint.memory import InMemorySaver  # 生产换 PostgresSaver

app = g.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "user-123"}}

app.invoke({"messages": [("user", "查 ORD-12345678")]}, cfg)
app.invoke({"messages": [("user", "它现在到哪了")]}, cfg)  # 自动带历史

snapshot = app.get_state(cfg)             # 当前状态快照
for hist in app.get_state_history(cfg):   # 全部历史，可回到任意步分叉
    ...

要点：thread_id 是会话隔离键，一个会话一个 thread；内存版只用于开发，生产必须用 Postgres 等持久实现，否则重启即失忆。

25. 什么是 Human-in-the-Loop？现场编码：给"退款"这类写操作加人工审批（interrupt）。

答案：

Human-in-the-Loop 是在 Agent 工作流中加入人工干预的机制：在关键决策节点暂停，等待人工确认后再继续；防止 Agent 执行高风险操作（删除数据、退款、发邮件）；也支持人工修正 Agent 的中间输出或补充信息。LangGraph 用 interrupt 原生实现。

from langgraph.types import interrupt, Command
from langchain_core.messages import AIMessage

def refund_node(state: State):
    payload = {"order_id": "ORD-12345678", "amount": 299.0}
    decision = interrupt({"ask": "确认退款 ¥299？", "payload": payload})
    if decision == "approve":
        apply_refund.invoke(payload)
        return {"messages": [AIMessage("退款已提交")]}
    return {"messages": [AIMessage("已取消退款")]}

调用方两次调用：

app.invoke(inputs, cfg)                       # 在 interrupt 处暂停，state 已落盘
app.invoke(Command(resume="approve"), cfg)    # 人工审批后恢复

关键区分（常追问）：让模型"先问一句用户"只是生成文本，请求结束状态即丢；interrupt 是真正暂停图执行并持久化，可以隔数小时、跨进程重启后用 Command(resume=...) 精确恢复。典型场景：高风险写操作、补信息、等待外部回调。

26. 条件边怎么写？tools_condition 内部判断逻辑是什么？

答案：

条件边接收一个返回"下一节点名"的路由函数：

def route(state: State) -> str:
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"
    return END

g.add_conditional_edges("chat", route, {"tools": "tools", END: END})

toolscondition 就是这个逻辑的预置版：检查最后一条 AIMessage 是否带非空 toolcalls，有则路由到工具节点名（默认 "tools"），否则路由到 END。注意第三个参数是返回值→真实节点名的映射，重命名节点时必须同步改映射。

答案：

stream_mode产出场景

updates每个节点本次的增量更新最常用，前端展示"当前执行到哪步/在干什么"

七、多智能体与互操作协议

28. 什么是多智能体系统？价值是什么？

答案： 多智能体系统由多个 AI Agent 组成，每个 Agent 有独立的角色和职责，通过协作完成复杂任务：

  • 分工：每个 Agent 专注于特定任务（规划、编码、测试、审查）
  • 并行：多个 Agent 同时处理不同子任务，提升效率
  • 检验：一个 Agent 验证另一个 Agent 的输出，减少错误

多 Agent 的核心价值是专职分工和上下文隔离；但要记住"单 Agent + 多工具够用，就不要上多 Agent"。

29. 多智能体有哪些架构模式？通信如何实现？

答案：

常见架构模式：

  • Supervisor（监督者模式）：一个主 Agent 负责协调分配任务给子 Agent
  • Peer-to-Peer / Network（点对点）：Agent 之间直接通信，无中心节点
  • Pipeline（流水线）：Agent 串行执行，上一个的输出是下一个的输入
  • Hierarchical（层级）：树形结构，高层 Agent 管理低层 Agent

通信方式：

  • 消息传递：Agent 发送/接收结构化消息（如 JSON）
  • 共享状态：通过共享数据库或内存（如 LangGraph State）交换信息
  • 工具调用：一个 Agent 以"工具"形式调用另一个 Agent
  • 事件驱动：通过消息队列（如 Kafka、RabbitMQ）异步通信

30. 多 Agent 的 Supervisor 模式如何实现？为什么默认不推荐 Network 模式？

答案：

from langgraph_supervisor import create_supervisor

sup = create_supervisor(

不默认用去中心化 Network 的原因：Agent 互相喊话会形成不可控的调用图，容易互相等待/死循环、token 与延迟随对话轮次膨胀、出错时难以定位是哪个 Agent 的决策、状态一致性难保证。只有确实需要对等协商且能接受这些代价时才用。

31. 什么是 OpenAI Agents SDK？

答案： OpenAI Agents SDK（2025 年发布）是 OpenAI 官方推出的轻量级 Agent 开发框架，前身为 Swarm。

核心概念：

  • Agent：有 instructions（角色描述）和 tools（工具列表）的 LLM 执行单元
  • Handoff（移交）：一个 Agent 将任务移交给另一个更专业的 Agent
  • Guardrails（护栏）：对 Agent 输入/输出进行验证的过滤器
  • Runner：协调 Agent 执行循环的调度器

代码示例：

from openai import OpenAI

    return f"{city} 今天晴天，25°C"

    name="天气助手",
    instructions="你是一个天气查询助手，帮用户查询城市天气。",

32. 什么是 Google ADK（Agent Development Kit）？

答案： Google ADK 是 Google 于 2025 年发布的开源 Agent 框架，专为构建可互操作的 AI Agent 设计。

核心特点：

  • 多 Agent 编排：原生支持层级化多 Agent 系统
  • A2A 原生集成：内置 Agent2Agent 协议支持

部署选项：Google Agent Engine、Cloud Run、GKE。

与 LangGraph 对比：ADK 更紧密集成 Google 生态（Gemini、Vertex AI），LangGraph 更通用、更成熟。

36. 子代理为什么能"节省主上下文"？什么时候该用？

答案：

上下文窗口是稀缺资源，且长上下文会稀释注意力、增加成本。子代理在独立上下文里完成高噪音工作（浏览几十个网页、跑若干 SQL、读多个文件），只把最终结论/摘要交回主 Agent，主上下文不被海量原始 observation 撑爆。

适用：子任务会产生大量中间内容、与主线决策弱相关；不适用：子任务结果就是最终答案主体、或需要与主流程反复细粒度交互——隔离反而丢信息。

37. Deep Agents 和裸 LangGraph 的代价分别是什么？如何决策？

答案：

  • 裸 StateGraph：开发量大，每个节点/分支都要自己设计，但可控性、可审计性、SLA 最强，适合企业交易流程。
  • Deep Agents：上手快、能自主探路，但 token 消耗高、执行路径不确定、难以给出强时效保证，且复杂工具环境下可能规划失焦。

决策口诀："人能画出确定流程图"用 LangGraph；"只能描述清楚目标"用 Deep Agents。 涉及钱、合规、不可逆操作的核心链路不应交给纯自主探索，应在 LangGraph 中显式约束并加 interrupt。

九、工程化与排错

38. Agent 跑到一半报 429 / 超时，如何保证不丢上下文？

答案：

关键认知：重试的单位是"一次 LLM 调用"，而状态都在 messages/state 里。做法：

  • 对模型调用加指数退避 + 抖动的重试（with_retry），读 retry-after，超阈值（如 5 分钟，配额耗尽）快速失败而非死等；
  • 重试时携带完整 messages，模型能基于已执行的工具结果从断点继续；
  • 在 LangGraph 中还有双保险：checkpointer 已把每步落盘，即使进程崩溃，用同 thread_id 重新 invoke(None, cfg) 即可从最后一个完成的超步恢复。

39. 如何保证模型输出一定是可解析的结构化数据？

40. 如何防止 Agent 失控（死循环 / 烧钱 / 误操作）？还有哪些高频故障？

答案： 一组组合拳：

  • recursion_limit 限制图最大超步数（默认 25，按业务收紧）；
  • 外层工具调用总预算、相同参数重复调用检测、整体超时；
  • 工具结果截断、工具数量精简，控制每轮 token；
  • 所有副作用写操作走 interrupt 人工确认；
  • 模型分级路由 + 子代理用小模型 + 固定前缀 prompt caching；
  • LangSmith/Langfuse 全链路 tracing，按 run 统计 token 与耗时定位热点。

41. 怎么做 Agent 的测试、评估与回归？

答案：

  • 节点纯函数化：节点 (state) → state_update，对其用构造的 state 做确定性单测；
  • 工具层：mock 外部 API，单独测参数解析与返回处理；
  • LLM 层不确定性：用两类手段——录制真实交互的轨迹（trajectories）做端到端回归，断言"调用了哪些工具、顺序、最终结果"；对语义判断用 LLM-as-Judge 打分而非精确匹配；
  • 结构化输出用 Pydantic 校验作为断言；用少量金标集在每次改 prompt/换模型后回归，防止"改好一个 case 改坏三个"。

评估指标：

  • 任务完成率：Agent 成功完成任务的比例
  • 步骤效率：完成任务所需的工具调用次数（越少越好）
  • 幻觉率：Agent 输出的错误信息比例
  • 工具调用准确率：选择正确工具的比例
  • 延迟与成本：Token 消耗、API 调用次数、P50/P95 响应时间

常用评估框架：LangSmith、Langfuse、Ragas、TruLens、Braintrust、Arize Phoenix。标准化基准见第 47 题。

43. 什么是 Prompt Caching（提示词缓存）？

答案： Prompt Caching 是大模型 API 的一项重要优化特性，将重复使用的上下文缓存在服务器端，显著降低成本和延迟。

工作原理：

  1. 首次请求：完整处理系统提示和文档上下文（正常计费）
  2. 后续请求：相同前缀部分从缓存读取（仅收取少量缓存读取费用）
  3. 缓存 TTL：通常 5 分钟（Anthropic），部分厂商支持更长 TTL

成本对比（Anthropic 示例）：

类型价格
普通输入 Token$3 / 1M tokens
缓存写入$3.75 / 1M tokens（首次）
缓存读取$0.30 / 1M tokens（后续），节省 90%
❌ 更正（2026-09 核实）：下文代码使用的 claude-opus-4-5 型号真实存在（2025-11-24 发布），但上表 $3 / $3.75 / $0.30 实际是 Sonnet 4.x 档价格（输入 $3 的 1.25 倍写入、0.1 倍命中），并非 Opus 价格。Opus 4.5 / 4.6 / 4.7 / 4.8 / 5 定价均为 $5 输入 / $25 输出；5 分钟缓存写入 $6.25、1 小时缓存写入 $10、缓存命中 $0.50（每 1M tokens）。当前旗舰为 Opus 5（2026-07-24 发布；另有 Opus 4.8 2026-05-28、Opus 4.6 2026-02-05；Sonnet 5 为 $2 / $10）。缓存现有 5 分钟与 1 小时两档 TTL。以上价格仅为示例、截至 2026-09，以 platform.claude.com 官网为准。

使用场景：

  • 系统提示较长（1000+ tokens）的 Agent
  • RAG 检索结果作为固定上下文
  • 代码库分析（将代码文件缓存，多次查询）

代码示例（Anthropic）：

client.messages.create(
    model="claude-opus-4-5",
    system=[{
        "type": "text",
        "text": "你是代码审查专家...",
        "cache_control": {"type": "ephemeral"}  # 标记缓存
    }],
    messages=[{"role": "user", "content": "审查这段代码"}]
)

OpenAI 缓存：GPT-4o 自动缓存超过 1024 tokens 的前缀，无需手动标记。注意缓存要求前缀完全一致，所以要把固定内容（角色提示、工具定义、资料）放在前面，易变内容放后面。

⚠️ 过时/存疑标注（2026-09 核实）："GPT-4o 自动缓存超过 1024 tokens 前缀"的说法已过时——gpt-4o 系列自 2026-02-13 起退役；自动前缀缓存是 OpenAI 平台级特性，迁移 gpt-5 系列后仍适用，但免费缓存的 token 阈值与覆盖模型会调整，以官方文档为准。

44. 生产部署 Agent，你会给出怎样的架构清单？

45. 排查"模型该调工具却直接瞎答"，你的排查顺序是什么？

答案：

  1. 看 工具描述：是否说清了触发时机，名字是否直观；
  2. 看 参数 schema：描述、示例、必填项是否完整，模型是否因不知怎么填参数而放弃；
  3. 看 工具数量与冲突：是否太多、有无功能重叠导致选择困难；
  4. 看 system prompt：是否明确授权/鼓励使用工具，有无冲突指令；
  5. 看 模型能力：小模型 function calling 能力弱，换更强模型验证；
  6. 看 上下文：决策所需信息是否已在历史里（已在上下文就不必调工具）；
  7. 用 LangSmith trace 确认模型实际收到的 tools 定义和返回的 tool_calls，定位是"没选工具"还是"选了但参数错/被代码拦截"。

49. 🆕 语音 Realtime Agent 的架构要点是什么？

答案：

OpenAI Realtime API 时间线：gpt-4o-realtime-preview（2024-12-17）→ gpt-realtime GA（2025-08-28）→ gpt-realtime-mini（2025-10-06，示例口径，以官网为准）。

三种接入方式：

方式延迟量级（示例）场景
WebRTC客户端约 100ms浏览器 / App 直连媒体面
WebSocket服务端约 200ms后端编排、对接业务系统

安全要点：前端绝不嵌入 sk- 密钥，由后端签发短时有效的 ephemeral key。

架构四要点：

  1. VAD 与 turndetection：none（自行管理）/ servervad（按静音切分）/ semantic_vad（按语义判断话说完没有）；

  3. 流式：音频边采边发、输出边收边播，避免攒整句；
  4. 音频工程：回声消除、降噪、抖动缓冲。

路线对比：端到端 S2S 模型延迟低、语气自然，但可控性弱；传统 STT → LLM → TTS 级联链路慢但每环可替换、可插工具与护栏。生产常见混合：S2S 为主，关键交易节点降级为级联以便加校验。

51. 🆕 长时间运行的 Agent 任务如何保证可靠性？

答案：

长任务（数分钟到数小时）的核心敌人：进程崩溃、网络抖动、副作用重复执行、预算失控。

  1. Durable Execution（持久化执行）：工作流状态事件溯源、可回放恢复——Temporal / Restate / DBOS 是这一派代表；Vercel AI SDK 7 的 WorkflowAgent 提供同范式；LangGraph 用 Postgres checkpointer，崩溃后 invoke(None, cfg) 从最后超步恢复（见第 24、38 题）；
  2. 任务队列 + 异步化：请求只负责入队，结果通过 SSE / WebSocket / webhook 回推；
  3. 重试语义：指数退避 + 抖动重试瞬时错误；至少一次投递下用幂等键（idempotency key）/ 去重表保证副作用只生效一次；跨多步的写操作用补偿事务（saga）回滚；
  4. 预算护栏：recursion_limit、每工具调用次数与 token 预算、整体超时与熔断；
  5. 降级路径：超预算或连续失败后保存现场、转人工或发通知，而不是无限重试。

一句话：把"内存里跑的 agent 循环"当成"随时会崩溃的分布式系统"来设计。

十、综合设计题

52. 设计一个电商客服 Agent：查单、退款、转人工。请给出技术选型与关键流程。

答案：

选型：核心链路路径确定且含风险操作 → LangGraph，不用纯 Deep Agents。

节点设计：

START → 意图识别(structured_output)
          ├─ 查单 → order_query(tool) → 生成回复 → END
          ├─ 退款 → 信息补全 → refund_review(interrupt 人工审批)
          │             ├─ approve → apply_refund(tool) → END
          │             └─ reject  → 取消回复 → END
          └─ 其他/超步数/超预算/连续失败 → human_handoff → END

工程要点：

  • 意图识别与工单字段用 gpt-4o-mini + withstructuredoutput（示例，2026 年应换现役小型号），复杂沟通才升级旗舰模型；
  • Postgres checkpointer，thread_id 即会话 ID，支持跨轮/跨重启续跑；
  • 退款金额、原因必须 interrupt 确认；节点重试 + 失败统一兜底转人工；
  • recursion_limit 与 token 预算触发自动转人工；
  • LangSmith tracing + 金标轨迹集做回归；工具最小权限（退款接口限单用户、限金额）。

53. 设计一个"自动生成竞品分析报告"的系统，该用 Deep Agents 吗？如何控成本与质量？

答案：

适合用 Deep Agents：目标明确但路径开放（搜什么、读几篇、如何组织无法预先画死）。

  • 规划：让 Agent 先生成 todo（竞品维度、信息源清单）并展示，便于纠偏；
  • 子代理隔离：每个竞品/每个维度派独立子代理检索，只回传结构化摘要，保护主上下文；
  • 文件系统：原始资料与各章节草稿落虚拟文件，最终汇总，支持长任务和续写；
  • 质量：末尾加一个 reviewer 角色（结构化打分 + 引用核查，事实必须能在文件资料中找到出处），不达标带着意见回到 writer 修订（有限次数的反思循环）；
  • 成本：检索/摘要子代理用小模型，仅主编排与终审用旗舰模型；设总 token 预算与最大轮次；固定的角色提示与资料前缀开 prompt caching；
  • 交付：流式产出过程步骤（updates）让用户看到进度，报告以 Markdown/文件形式交付并附引用列表。

54. 如果团队已有 Java/Node 技术栈，引入 Python 写 Agent 框架如何与主系统集成？

答案：

不要为了用框架把业务搬进 Python，采用边界化集成：

  • 把 Agent 做成独立服务（FastAPI / LangGraph Platform），主系统通过 HTTP/SSE 或消息队列调用，按会话传 thread_id；
  • Agent 需要的业务能力（查单、退款）由主系统以工具 API / MCP Server 暴露，Agent 侧只做编排，不直连核心数据库；
  • 鉴权、限流、审计放在 API 网关层统一处理；
  • JS/TS 团队也可评估 LangChain.js / LangGraph.js，核心概念（Runnable、StateGraph、checkpointer）一一对应，减少语言切换成本；
  • 工具协议尽量走 MCP 标准化，使同一套工具能被不同语言、不同 Agent 复用。

56. 如何设计一个高质量的 Prompt？

答案： 好的 Prompt 应包含以下要素：

1. 角色定义（Role）：You are an expert ...
2. 任务描述（Task）：Your goal is to ...
3. 上下文（Context）：Given the following information ...
4. 约束条件（Constraints）：You must only ..., avoid ...
5. 输出格式（Output Format）：Respond in JSON with fields ...
6. 示例（Few-shot）：Example input/output

常用技巧：

  • Chain-of-Thought：要求模型"step by step"思考
  • Self-consistency：多次采样取最优
  • Structured Output：用 JSON Schema 强约束输出而非文字要求（第 39 题）

58. 什么是 Computer Use（计算机使用）Agent？

答案： Computer Use 是 Anthropic 于 2024 年底推出的能力，允许 AI Agent 直接控制计算机桌面（鼠标、键盘、屏幕截图）来完成任务。

工作原理：

截图 → 视觉理解 → 决策（点击/输入/滚动）→ 执行 → 截图（下一步）

当前主要产品：

  • Claude Computer Use：Anthropic API，开发者可集成
  • OpenAI Operator：面向消费者，操作网页完成任务（预约、购物等）
  • Google Project Mariner：Chrome 插件形态的浏览器 Agent
⚠️ 过时/存疑标注（2026-09 核实）：产品清单需更新——OpenAI Operator 已并入 ChatGPT Agent、独立入口 2025-08-31 关闭（见第 57 题）；Google Project Mariner 已演化为 Gemini 2.5 Computer Use（2025-10）。此外，视觉/截图派之外，DOM/可访问性树路线（Playwright MCP、browser-use、Stagehand 等）在工程界已成为主流补充，两条路线的工程对比详见第 50 题。

与 Playwright/Selenium 的区别：

维度传统 Web 自动化Computer Use

适用范围仅 Web 应用任何桌面/Web 应用

稳定性高仍在改善中
