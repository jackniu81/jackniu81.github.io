一、基础认知与工程范式

1. 什么是 AI Agent？它和普通 LLM 聊天、传统 AI 应用的区别是什么？ ｜必刷 ｜基础

答案： 一句话定义：Agent = 模型 + 工具集 + 运行循环 + 当前状态。

  • 模型负责理解目标、分析当前局面、决定下一步；
  • 工具集负责提供外部能力（搜索、数据库、文件系统、业务 API）；
  • 运行循环负责让系统不是只回答一次，而是能"想一步、做一步、看结果、再决定下一步"；
  • 当前状态负责保存消息、工具返回、中间结论。

与传统 AI 应用的对比：

维度 普通 LLM / 传统 AI 应用 AI Agent
交互方式 单轮请求 → 单轮结果 围绕目标持续决策、多步执行
决策 被动回答 / 规则驱动 主动规划、动态选择工具
工具 无或固定 动态选择和调用
状态 无 有消息历史与任务状态
任务 简单、单步、路径已知 复杂、多步、路径依赖中间结果

关键判断：不是所有 AI 应用都该叫 Agent。固定表单生成、固定知识问答、固定流程审批，用普通链路或 Workflow 就够了；只有路径不固定、需要根据中间结果继续选工具或改路线时，Agent 才真正合适。

另外要澄清一个常见误区：很多人把"长期记忆、复杂规划、多智能体协作"当成 Agent 的必备条件——不是。能做到"理解目标 → 决定是否调工具 → 拿到结果再继续判断"，就已经是 Agent 了；记忆、规划、反思、多智能体是往上叠的扩展能力。

追问：单工具助手算不算 Agent？ ｜ 构建复杂 Agent 最主要的挑战是什么？ ｜ 为什么说很多 Agent 不是能力不够，而是状态、边界、治理没设计好？

2. Agent 的四大核心组件是什么？工程上真正要控制的是哪几件事？ ｜必刷 ｜中等

答案： 经典四组件（适合打底）：

  • 感知 Perception：接收用户输入、环境状态、工具返回结果；
  • 规划 Planning：分解任务、制定执行计划（ReAct、Plan-and-Execute 等）；
  • 记忆 Memory：短期上下文 + 长期知识，支撑跨步骤推理；
  • 行动 Action：调用工具、执行代码、调 API、操作文件。

但工程落地时，更值钱的说法是"要控制五件事"：

  1. 目标和职责：一个 Agent 解决什么问题，尽量单一，别什么都做；
  2. 工具边界：只暴露完成任务真正需要的能力，不给模型一把通吃的权限；
  3. 状态设计：任务进展、中间结论、消息历史放在哪里，要显式设计；
  4. 停止条件：什么时候继续、什么时候澄清、什么时候转人工、什么时候结束，不能模糊；
  5. 治理能力：日志、Trace、重试、超时、审计、人工接管都要补齐。

一句话：Agent 设计的重点不是"堆更多能力"，而是围绕模型、工具、循环、状态四条主线，把系统做得更可控、可追踪、能稳定交付结果。

追问：这四组件分别对应 LangGraph 里的什么？（模型=节点里的 LLM 调用，工具=ToolNode，循环=边与条件边，状态=State + checkpointer） ｜ 记忆放在哪一层？（见第 43、44 题）

3. 什么是 ReAct 架构？它解决了什么问题？ ｜高频 ｜基础

答案： ReAct = Reasoning + Acting，让模型交替进行思考和行动，典型形态是 Thought → Action → Observation 循环：

Thought: 我需要先查今天的天气
Action: search_web("今天北京天气")
Observation: 晴天，25°C
Thought: 已获得结果，整理回答
Action: 返回结果给用户

它解决的是"一次性生成搞不定多步决策和外部信息依赖"的问题：模型先做当前判断，再决定调用什么工具，然后根据工具返回更新判断，直到任务完成。同时推理过程透明、可调试。

一个重要补充：现代 Tool Calling Agent 不一定把 Thought 明文输出。真实代码里更常见的是 AIMessage.tool_calls → 工具执行 → ToolMessage → 下一轮。所以更准确的理解是：ReAct 是一种工作机制，不是一个固定 Prompt 模板。

代价也要说清：链路更长、成本更高、调试更复杂，不是所有场景都值得上完整循环。LangGraph 手写实现见第 80 题。

4. Chain-of-Thought 是什么？它和 ReAct 有什么区别？ ｜高频 ｜基础

答案： CoT（思维链）是让模型"一步一步想"——把中间推理显式展开再给结论，靠的是模型内部已有的知识和计算，典型收益在数学、逻辑、多跳推理类题目上；常见变体有 self-consistency（多次采样投票取多数）、ToT（树状展开多路径）。

区别在一句话：CoT 只"想"，ReAct 会"做"。

CoT ReAct
信息来源 模型参数内的知识 外部工具实时获取
是否能改变环境 否 是（可以调 API、写数据）
幻觉风险 高（推理链可能自圆其说地编） 低（有 Observation 纠偏）
成本 一次调用，便宜 多轮循环，贵
适用 算术、逻辑、需要展示推导 需要查事实、操作外部系统

所以：只靠模型内部推理就能解题，CoT 够了；需要外部事实或多步动作，才升级到 ReAct。 实践中两者常叠加——ReAct 的 Thought 阶段本身就是一次 CoT。

5. Agent 的规划模式有哪些？各自的适用边界是什么？ ｜高频 ｜中等

答案：

  • ReAct：思考与行动交替、动态规划。适合路径未知、强依赖外部反馈的任务。缺点是没有全局视野，容易局部绕圈。
  • Plan-and-Execute：先整体规划出步骤清单，再逐步执行（执行器常用小模型）。适合长任务、需要看得见进度的场景；缺点是计划会过期，中间变化要能重新规划。
  • Reflection / Evaluator-Optimizer：生成 → 评审 → 按意见修订的循环。适合有明确质量标准的任务（代码、翻译、写作）；需要评审信号足够可靠，否则只是自我复读。
  • Self-Ask：把复杂问题拆成子问题逐个解答再汇总。适合多跳问答。
  • Tree of Thoughts（ToT）：并行探索多条推理路径并回溯搜索。适合搜索空间大的推理题，成本高，工程上少用。
  • Orchestrator-Workers：主模型动态拆任务、派给 worker。适合子项数量预先未知的任务（见第 8 题）。

选型心法：规划模式的价值随"任务长度 × 不确定性"上升，成本也同步上升。能用一次增强 LLM 调用解决的，别加规划。

追问：Deep Agents 的 todo 清单属于哪一种？（Plan-and-Execute 的工程化版本，见第 96 题） ｜ 怎么防止 Agent 规划失焦、无限重规划？（步数与预算上限 + 显式完成条件，见第 103 题）

6. Agentic AI 与传统 AI 的区别是什么？ ｜中频 ｜基础

答案：

传统 AI Agentic AI
决策方式 规则驱动或单次推理 自主规划、多步推理
目标 完成单一预定任务 自主达成复杂长期目标
适应性 固定流程 动态适应环境变化
工具使用 无或固定 动态选择和调用工具
失败处理 报错终止 重试、换路径、降级、求助人工
代表 图像识别、推荐系统 Devin、Manus、Claude Code

补一句工程视角：Agentic AI 的难点不在"模型会不会想"，而在长链路的可控性——状态怎么存、什么时候停、错了怎么回滚、成本怎么兜住。这也是为什么 2025-2026 的重心从"能力"转向"harness 与治理"（见第 14 题）。

7. Workflow 和 Agent 的分界线在哪？什么时候工作流比 Agent 更合适？ ｜必刷 ｜中等

答案： Anthropic 的定义最清晰：

  • Workflow（工作流）：LLM 与工具按预定义的代码路径编排，流程由开发者写死，确定可审计；
  • Autonomous Agent（自主智能体）：模型自己决定路径、动态决定用什么工具、什么时候结束，流程开放。

判断口诀：人能不能提前画出确定的流程图。 能画出来 → Workflow；画不出来（下一步依赖中间结果）→ Agent。

工作流更合适的场景：业务步骤固定、输出格式明确、要求强可控与易审计——分类、摘要、内容审核、报告生成、表单填充、固定审批链。这类任务用工作流能清楚定义节点职责、失败重试、人工介入点和 SLA。Agent 更适合开放任务和动态决策，代价是延迟、成本、不确定性、调试难度全都上升。

另一个高频追问点：Workflow 里哪些节点该交给 LLM？ 答案是"语义判断和文本生成"的节点（意图分类、抽取、改写、总结），而"精确计算、查表、校验、权限判断"应该用代码规则，不要用模型。

8. Anthropic《Building Effective Agents》提出了哪五种工作流模式？ ｜必刷 ｜中等

答案： 该文（2024-12-19）首先区分 Workflow 与 Autonomous Agent（见第 7 题），基本构件是增强型 LLM（带工具调用、检索、结构化输出的单次模型调用），然后给出五种工作流模式：

模式 结构 适用场景
Prompt Chaining 多个 prompt 串行，前一步输出喂下一步 可拆成固定子任务（生成→校对→翻译）
Routing 分类后分流到不同处理链 客服意图分流、模型分级路由（见第 77 题）
Parallelization 并行调用后聚合：sectioning（分片）/ voting（投票） 多维度同时评审、多次投票降方差
Orchestrator-Workers 主模型动态拆任务、派给 worker 子任务数量预先未知（如跨多文件代码修改）
Evaluator-Optimizer 生成→评审→按意见修订循环 翻译、代码、写作等可反复打磨的任务

核心建议：先用最简方案——单次增强 LLM → 再加工作流 → 最后才考虑完全自主 agent；框架会增加抽象成本，能不引入就不引入。

Orchestrator-Workers 与 Deep Agents 的"规划 + 子代理"、Evaluator-Optimizer 与 Reflection 模式都一脉相承（见第 96、5 题）。

9. 什么时候该用 Prompt、RAG、微调、Workflow、Agent？ ｜必刷 ｜中等

答案： 最稳的判断方式，是先看问题到底缺知识、缺行为，还是缺流程能力：

  • 模型本来就会，只是任务没描述清楚 → Prompt；
  • 缺私有知识、最新知识、外部知识 → RAG；
  • 缺稳定行为（固定格式、语气、分类习惯）→ 微调；
  • 流程固定、节点明确、要稳定和可审计 → Workflow；
  • 路径不固定、需要边做边决定下一步、动态调工具 → Agent。

压缩成一句话：

手段 解决的问题
Prompt 任务表达
RAG 知识来源
微调 行为稳定
Workflow 固定流程
Agent 动态决策

真实项目通常不会一开始就说"必须做 Agent"。大部分需求先用 Prompt + RAG + Workflow 就能覆盖，只有在任务开放度高、工具选择依赖中间结果、流程没法提前写死时，Agent 的价值才真正体现。

追问：为什么很多项目不一开始做微调？（数据、算力、回滚成本、模型迭代会让微调贬值） ｜ 预算有限先做哪个？（先 Prompt + RAG，它们可回滚、可评测、见效快）

10. RAG 和微调（SFT）的核心区别是什么？能不能一起用？ ｜必刷 ｜中等

答案： RAG 解决"知识从哪里来"，微调解决"模型应该怎么表现"。

RAG 不改模型参数，运行时把相关资料检索出来交给模型生成，所以适合时效性强、更新频繁、需要可溯源的知识；微调会改模型参数，更适合提升输出风格一致性、结构化能力、分类能力或领域行为稳定性。

对比要点：

RAG 微调
改什么 上下文 参数
更新成本 重建索引即可 重训 + 重新评测 + 发版
可溯源 有引用 无
适合 事实、文档、私有数据 格式、风格、语气、判别任务
失效场景 检索不准就答不对 知识过期、幻觉依旧存在

它们当然可以一起用，很多企业项目就是这么落地的：产品政策靠 RAG 保持最新，回复格式和字段输出靠微调或结构化输出保证稳定。注意微调不会给模型新知识，硬塞事实反而容易诱发幻觉。

追问：为什么不优先做续训（继续预训练）？（算力门槛、数据配比、灾难性遗忘、性价比远低于 RAG） ｜ 什么场景适合 RAG + 微调组合？（领域术语/格式行为不稳 + 知识高频更新）

11. Token 和上下文窗口是什么？它们在工程上意味着什么？ ｜高频 ｜基础 ｜腾讯一面

答案： Token 是模型处理文本的基本计量单位，不等于"字数"或"单词数"——模型看到的不是原始文本，而是 tokenizer 切出来的一串 token。上下文窗口则是单次推理最多能看到多少 token 的上限，工程上说的 8K / 32K / 128K，本质是"系统提示 + 历史对话 + 检索结果 + 用户问题加起来最多塞多少 token"。

工程意义很直接：

  • 窗口决定你能不能做长文问答、多轮对话、大段 RAG 上下文拼接；
  • token 越多成本越高、延迟越高（且多数厂商按输入分档计价，长上下文更贵）；
  • 超出窗口的内容会被截断或进不了模型，不是塞得越多越好（长上下文还有注意力衰减问题，见第 30 题）。

换算口径必须说清 tokenizer（详见下方更正）：

❌ 更正：原答案给的"1 个中文字符约 0.6 token、128K ≈ 二十万中文字符"是低估口径（旧版词表 + 极简文本的理想值）。实测更稳妥的说法是：

  • 同一句 45 字中文，cl100k_base（GPT-4 早期）切出约 57 token（≈1.27 token/字），o200k_base（GPT-4o 及之后）约 37 token（≈0.82 token/字），同一文本差约 1.5 倍；
  • 中文类语料的 token/字符均值约 1.48，英文与代码约 0.315，差约 4.7 倍；
  • 国产模型自有词表（Qwen / DeepSeek 等）普遍约 0.6~1 token/字；
  • 因此"1 汉字 ≈ 11.5 token（新词表 0.60.8）"，128K 大约对应 8~16 万汉字，而不是二十万。 结论：任何换算都必须指明是哪个 tokenizer，估算留 30% 余量，真实对账一律以目标模型的 tokenizer 或 API 返回的 usage 字段为准。另外，模型换代常伴随分词器升级，同一文本的 token 数会变（部分换代涨幅可达三成），旧系数不能沿用。

还有一个容易被忽略的点：标称窗口 ≠ 有效窗口。2026 年旗舰模型普遍宣传 1M token 上下文，但公开模型卡里的长文检索测试显示，同一模型在 128K 与 1M 位置上的准确率可以差出几十个百分点。所以窗口大小只是上限，能不能"用满"要靠检索与压缩来保证（见第 13、31 题）。

追问：如果上下文被截断了你优先怎么处理？（先砍低信号内容 → 摘要压缩 → 检索式补充，见第 44 题） ｜ 怎么估算一个 Agent 会话的 token 成本？（按步数 × 每步上下文重传量算，不是只算用户输入）

12. 大模型应用上线前你最关心哪些工程指标？ ｜高频 ｜中等 ｜腾讯一面

答案： 从五个维度看：

维度 指标
效果 准确率、忠实度、任务完成率、引用正确率
性能 首 token 延迟（TTFT）、端到端延迟、P95/P99
成本 token 消耗、检索成本、工具调用成本、单任务平均成本
稳定性 超时率、错误率、重试率、降级命中率
治理性 日志、Trace、Prompt 版本、索引版本、权限审计

如果是 RAG / Agent 项目，还会额外看：检索召回质量、工具调用成功率、人工兜底比例、badcase 回灌效率——这些才是真正影响线上体验的。

运维指标的完整分层见第 119 题，评测方法见第 113、115 题。

追问：怎么设计降级策略？（缓存 → 规则链路 → 小模型 → 兜底话术 + 转人工） ｜ 成本超预算先优化哪一层？（先上下文与检索层，再模型路由，最后才是换供应商，见第 121 题） ｜ Prompt / 模型 / 索引怎么做回滚？（三者一起版本化 + 灰度，见第 20 题）

13. 什么是 Context Engineering？为什么 2025 年后它比 Prompt Engineering 更常被提起？ ｜必刷 ｜较难 ｜2026 新增

答案： Context Engineering（上下文工程）指系统性地设计和管理进入模型上下文窗口的全部信息：系统提示、工具定义、检索结果、历史消息、子代理回传、scratchpad 内容等。2025 年中由 Tobi Lütke、Harrison Chase、Andrej Karpathy 等人公开讨论带火，Anthropic 随后发表《Effective Context Engineering for AI Agents》。

与 Prompt Engineering 的关系：上下文工程是超集——prompt 只是上下文里一个可控片段。Agent 是多轮、自主、带工具的，真正决定成败的往往不是某一句 prompt，而是每一步"上下文里到底有什么"。

核心做四件事：

动作 手段 典型实现
写（Write） 让 Agent 把中间产物外写 scratchpad、todo 清单、虚拟文件（Deep Agents）
选（Select） 每步只加载当前需要的内容 JIT 检索、按需加载工具、动态 few-shot
压缩（Compress） 逼近窗口时摘要 / 裁剪 compaction、滑窗、对话摘要（经验阈值约 70% 窗口占用即触发）
隔离（Isolate） 把高噪音子任务关进独立上下文 子代理（Manus 总结为 reduce / offload / isolate 三策）

为什么必须做：长上下文下所有模型都会出现性能衰减——Chroma 的 Context Rot 实验中 18 个模型全部随上下文长度衰减；"Lost in the Middle" 证明中间位置的信息利用率最低。Anthropic 总结四类上下文失败：poisoning（污染/投毒）、distraction（干扰）、confusion（混淆）、clash（指令冲突）。2025-09-29 Claude Code 推出 context editing（自动写文件 + 压缩对话），是该理念落地的代表。

追问：上下文工程会不会取代 prompt 工程？（不会，是包含关系，见第 14 题的三代范式） ｜ 你的项目里具体怎么落地？（工具分层暴露、检索精排后只留 Top-K、历史摘要、子代理只回传摘要、固定前缀缓存）

14. 什么是 Harness Engineering？它和 Prompt / Context Engineering 是什么关系？ ｜必刷 ｜较难 ｜2026 新增

答案： Harness（脚手架 / 挽具）指模型之外的一切运行装置：工具与权限、上下文装配策略、执行循环、验证与反馈信号、沙箱、重试与回滚、评测与可观测。Harness Engineering 就是把这些设计成工程系统。

时间线（可作为"是否跟进前沿"的证据）：

  • 2026-02-05 Mitchell Hashimoto（Terraform 作者）给出定义；
  • 2026-02-11 OpenAI Ryan Lopopolo 发表《Harness engineering: leveraging Codex in an agent-first world》：一个 3 人团队从 2025-08 底的空仓库开始，5 个月产出约 100 万行代码、约 1500 个 PR，应用逻辑、测试、CI、文档、可观测几乎零手写；结论是"早期慢不是模型能力不足，而是环境定义不充分"；
  • 2026-04 Birgitta Böckeler 在 martinfowler.com 提出 harness 的两类部件：guides（前馈引导：规范、AGENTS.md、示例、约束解码） 与 sensors（反馈传感：lint、测试、覆盖率、类型检查、CI 信号）；
  • 2026-09-02 Google Shir Meir Lador 称其为编程 Agent 最重要的趋势，并给出基于 ADK 2.0 的最小实现。

三代范式是嵌套而非替代：

范式 关注 回答的问题 时期
Prompt Engineering 告诉模型什么 怎么说清楚任务 2022-2024
Context Engineering 模型看到什么 每一步上下文里放什么 2025
Harness Engineering Agent 能做什么、做错怎么办 怎么让它在真实系统里不出事 2026 起

常见公式：Agent = Model + Harness。同一个模型换一套 harness，基准分数能差出几十个点（跨论文比较要先对齐评测协议，见第 115 题）。

追问：AGENTS.md 起什么作用？（把项目约定、构建命令、测试方式、边界规则固化成前馈引导，让 Agent 不必每次猜） ｜ 只有大模型团队才需要 harness 吗？（任何把 Agent 接进真实系统的团队都需要，因为它本质是可观测 + 可回滚 + 权限边界）

15. Vibe Coding 和 Agentic Engineering 有什么区别？ ｜中频 ｜基础 ｜2026 新增

答案： Vibe Coding 由 Andrej Karpathy 于 2025-02 提出：完全交给模型、顺着感觉走、不怎么细看代码的编程方式。它描述的是"人有多放手"。

Agentic Engineering（也叫 agentic coding）是刻意配置 harness 的工程实践：定义清晰的目标、边界、验证信号、权限和回滚路径，让 Agent 在受控环境里自主完成任务（Claude Code、Codex CLI、Devin 这类产品的正确用法）。

两者的区别不在"用不用 AI"，而在有没有刻意设计约束与反馈：

维度 无约束 Vibe Coding Agentic Engineering
规格 一句话让它写 先有任务拆解与验收标准
验证 跑起来看着对 测试 / lint / CI / 覆盖率做传感器
权限 全给它 沙箱 + 最小权限 + 人审写操作
代码归属 生成即接受 评审、重构、可回滚
曲线 起步极快 → 中期混乱 → 后期崩盘 起步稍慢（环境定义成本）→ 持续变快

面试里最讨喜的说法：Vibe Coding 适合原型和一次性脚本；进入长期维护的真实代码库，就必须转成 agentic engineering，也就是把 harness 补齐。

二、Prompt、结构化输出与护栏

16. System Message 和 User Message 应该怎么分工？ ｜必刷 ｜基础

答案： System 放稳定约束，User 放动态任务。

  • System：角色、目标、边界、安全规则、输出格式要求、工具使用规范——这些应该尽量稳定、少改；
  • User：用户当次任务、输入数据、补充上下文、个性化要求。

这样拆分的好处：结构清晰、便于版本管理，也更适合模板化、灰度和评测。全混在一段 prompt 里，后面排查效果波动会非常困难。

工程上还有两个附带收益：

  1. 缓存友好——固定前缀（System + 工具定义 + 资料）放前面、易变内容放后面，才能命中 prompt caching（见第 122 题）；
  2. 安全分层——很多注入防御依赖"指令层与数据层不同权"，把外部内容当数据而不是指令（见第 108 题）。

17. 如何设计一个高质量的 Prompt？ ｜高频 ｜基础

答案： 六要素结构（Role / Task / Context / Constraints / Output / Few-shot）：

1. 角色定义（Role）：You are an expert ...
2. 任务描述（Task）：Your goal is to ...
3. 上下文（Context）：Given the following information ...
4. 约束条件（Constraints）：You must only ..., avoid ...
5. 输出格式（Output Format）：Respond in JSON with fields ...
6. 示例（Few-shot）：Example input/output

常用技巧：

  • CoT：要求"step by step"思考（复杂推理题有效，见第 4 题）；
  • Self-consistency：多次采样取最优，降方差；
  • Structured Output：用 JSON Schema 强约束输出，而不是文字要求"请返回 JSON"（见第 21 题）；
  • 正反例：给"什么是错的"往往比抽象要求更有效；
  • 明确拒答与澄清策略：说清"信息不足时应该问，而不是猜"。

另外三个实操细节：把长约束拆成编号列表（比长段落更易遵循）、把格式要求放在结尾附近（开头也行，但别埋在中部）、few-shot 示例的分布要覆盖边界情况。

18. 在 Prompt 工程里，如何系统优化提示词并把准确率做上去？ ｜高频 ｜中等

答案： 不该把 Prompt 优化理解成"反复手改几句提示词"，而是一个小型工程闭环。核心不是玄学技巧，而是任务拆解、样例驱动、评测回归、边界收敛：

  1. 先定义任务边界：什么叫答对、什么叫答错、哪些情况必须拒答或澄清；
  2. 输入分层：稳定规则放 System，动态任务放 User；
  3. 先修大问题再修措辞：如果本质是缺知识、缺工具、缺流程，不要靠 Prompt 硬抬效果；
  4. 用样例和反例：few-shot、反例约束、输出格式示例，通常比抽象要求更稳定；
  5. 结构化约束：能用 schema / parser / structured output 的地方，不要只写"请返回 JSON"；
  6. 建 badcase 集：把线上错例沉淀成固定评测集，每次改 Prompt 都跑回归，而不是靠体感判断"好像更准了"；
  7. 版本与灰度：Prompt、模型版本、温度、输出格式一起管理，避免改了一个点却查不清影响。

务实补一句：所谓"准确率 > 95%"必须绑定具体任务（分类、抽取、格式生成、客服问答），它不是通用承诺值。真正的目标是"某个具体任务在固定评测集上稳定达标"，而不是追一个脱离场景的数字。

追问：Prompt 怎么改都上不去，如何判断该切 RAG / Tool / Workflow / 微调？（看缺口是知识、执行能力、行为还是流程，见第 9 题） ｜ badcase 集怎么建才有用？（按失败类型分层采样 + 标注修复状态 + 每次上线前必跑） ｜ 线上效果突然下降怎么归因？（见第 150 题）

19. Prompt 工程的边界是什么？为什么不能把一切问题都交给 Prompt？ ｜中频 ｜基础

答案： Prompt 是"任务表达和约束手段"，它解决不了知识缺失、复杂状态管理、强执行需求三类问题：

  • 资料太多 → 靠塞上下文会出现成本高、噪声多、丢关键信息 → 转 RAG；
  • 多步复杂流程全靠 Prompt 硬编排 → 变成不可维护的长指令 → 转 Workflow / LangGraph；
  • 需要稳定调用外部系统 → 应该走 Tools / Function Calling，而不是让模型在文本里"假装调用了接口"。

合理分工：Prompt 负责表达规则，RAG 负责补知识，Tools 负责执行能力，Graph / Workflow 负责流程控制。

再加一条容易被忽视的边界：Prompt 是"概率性约束"，不是硬保证。真要"必须是这个格式"要靠 schema / 约束解码（见第 22 题），真要"不许越权"要靠权限和沙箱，而不是写一句"你不能删数据"。

20. 如何做 Prompt 版本管理与回归？ ｜中频 ｜中等

答案： Prompt 进入生产环境后，就不能当成"临时改改的字符串"，要当配置资产 / 代码资产管理。通常同时管四样东西：

  • Prompt 模板本身：System、User 模板、few-shot 示例、输出格式要求；
  • 运行参数：模型名、模型版本、temperature、top_p、max_tokens；
  • 评测集：固定 golden questions、典型 badcase、失败样例；
  • 发布信息：模板版本号、发布时间、负责人、灰度范围、回滚版本。

更稳的做法：

  1. Prompt 和代码一起版本化，或放进配置中心统一管理；
  2. 每次改 Prompt 都跑固定回归集，不只看主观感觉；
  3. 记录模板 hash、模型版本与关键参数，避免"明明没改 Prompt，效果却变了"时查不清；
  4. 上线前灰度 + 抽样人工复核，高风险链路保留快速回滚能力。

一个常被忽略的点：换底层模型后，旧 Prompt 不一定还保持原效果（换代模型 + 分词器变化都会影响表现）。所以回归的对象不是"这段 Prompt 对不对"，而是"Prompt 与当前模型组合起来还稳不稳"。

追问：golden set 怎么建？（覆盖高频意图 + 边界 + 历史 badcase，每类若干条，标注期望断言） ｜ Prompt、模型、索引三者同时变更时怎么回滚？（三者打同一 release tag，按 tag 整体回滚，禁止只回滚一项）

21. 结构化输出有哪些常见做法？各自优缺点是什么？ ｜必刷 ｜中等

答案： 从 Model I/O 主线看，可分成"后处理解析"和"前约束生成"两类：

做法 定位 优点 缺点
纯 Prompt 约束 直接要求按 JSON 返回 最简单、起步快、通用 多说一句话、少个逗号程序就崩，稳定性最差
Output Parser StrOutputParser / JsonOutputParser / PydanticOutputParser 契合 prompt | model | parser 链路，解耦 仍是"模型已输出，我再转"，错了只能重试
Structured Output with_structured_output(TypedDict / Pydantic / JSON Schema) 输出前先定 schema，模型按结构生成并自动解析，约束力强 依赖平台能力，复杂 schema 成本高
Function / Tool Calling 结构化输出的一种特例 生成调用意图 + 参数，有协议级契约 只覆盖"要调工具"的场景

细分 schema 选型：TypedDict 适合字段固定但不追求强运行时校验；Pydantic 适合类型、范围、必填项严格的业务；JSON Schema 适合跨语言跨系统共享协议。

生产上的优先顺序：

  1. 能用原生结构化输出就优先用；
  2. 需要强校验时优先用 Pydantic 一类 schema；
  3. 即使模型已经结构化输出，也要补业务校验、缺省值处理、失败重试。

❌ 更正：原答案有一句自相矛盾的表述——"通常会优先采用只保证'返回合法 JSON'的模式，因为前者更接近'按 schema 生成'"。逻辑是反的。正确说法：平台支持更强的结构化输出时，应优先用原生结构化输出 / schema 约束；JSON Mode 只保证"是合法 JSON"，并不保证符合你的字段与枚举，很多时候只是"长得像 JSON"。

一句话收口：Prompt 只能"尽量要求它长成这样"，Parser 与 Structured Output 才是在把模型输出真正接进程序系统。

22. JSON Mode、Structured Outputs、约束解码三者有什么区别？ ｜高频 ｜较难 ｜2026 新增

答案： 按"约束力从弱到强"排：

层级 保证什么 实现方式 失败模式
JSON Mode 输出是语法合法的 JSON 采样时限制为 JSON token 序列 字段缺、枚举值错、类型错、字段名幻觉
Structured Output（schema 引导） 输出符合给定 schema function calling / JSON Schema 约束生成，服务端校验 复杂嵌套 schema 表现下降；深层可选字段仍可能缺
约束解码 / Grammar（GBNF、outlines、vLLM guided decoding） 输出逐 token 都在语法允许集合内 推理引擎用有限状态机 / 文法屏蔽非法 token 需自托管引擎与文法；文法设计不当会过度限制语义

工程要点：

  • 调第三方 API：优先 response_format / json_schema（strict）或 function calling；OpenAI 的 strict 模式会做 schema 强制，但复杂 schema（大量 union / 深层可选）支持有限，常见做法是把 schema 拍平、字段名简单化、枚举用 Literal。
  • 自托管推理：可以直接上约束解码（vLLM 的 guided decoding / SGLang 的文法约束），确定性最强，代价是要维护文法和吞吐。
  • 无论哪一层都要补业务校验：schema 只能保证"形状对"，不能保证"值合理"（比如金额是负数、日期是 2050-13-40）。所以典型链路是 structured output → Pydantic 校验 → 一次自动修复重试 → 兜底降级。
class Ticket(BaseModel):
    category: Literal["billing", "tech", "other"]
    priority: int = Field(ge=1, le=5)
    summary: str

structured = llm.with_structured_output(Ticket)
ticket = structured.invoke("我付了钱但没开通，很急")   # -> Ticket 实例

23. Function Calling 和"让模型输出 JSON 再自己解析"有什么区别？ ｜中频 ｜中等

答案： 表面上都像"输出结构化结果"，但稳定性和工程边界差别很大：

  • 输出 JSON + 自解析：在 Prompt 层提要求。简单、通用、起步快，但模型多说一句自然语言、少一个字段、类型写错，程序端就要自己兜底；
  • Function Calling：协议级结构化输出。模型不是随便返回一段文本，而是明确返回工具名 + 参数，宿主按约定解析和执行，可靠性通常更高。

生产上的判断：

场景 选择
只是抽字段、轻量结构化返回，平台原生能力有限 JSON + parser
要进入真实工具调用、外部系统编排、有副作用 原生 Function Calling / Tool Use

更关键的区别在职责边界：JSON 解析是"你让模型尽量长成这个格式"；Function Calling 是"模型和宿主之间有一层明确契约"。契约越清楚，后面的校验、审计、重试、观测越好做。

追问：平台没有原生 FC 时怎么把 JSON 方案做稳？（few-shot 示例 + 停止序列 + JSON 修复解析 + 一次重试 + schema 校验） ｜ 为什么生产更推荐原生 Tool Calling？（见第 47 题的链路职责划分）

三、RAG 与检索基础设施

24. 请描述一个完整的 RAG 流水线。 ｜必刷 ｜中等

答案： 完整 RAG 分索引阶段和检索阶段：

索引：文档加载 → 清洗 → 切块 → 向量化 → 写入向量库（+ 元数据）
检索：接收问题 → query 改写 → 召回（稠密/稀疏/混合）→ 重排过滤 → 上下文组装 → 生成 → 引用/脱敏/格式化

工程上真正难的通常不是"把模型接起来"，而是三件事：

  1. 文档是否被正确解析（PDF、扫描件、表格、图文混排）；
  2. 切块是否保留语义（太大噪声多，太小丢上下文）；
  3. 检索结果是否真的对当前问题有帮助（召回准不准、排序对不对、噪声多不多）。

线上效果差，大多数时候卡在这三层，而不是卡在最后一轮生成。

四代 RAG 的演进脉络可以顺手带一句：Naive RAG（top-k 拼上下文）→ Advanced RAG（预处理/混合检索/rerank/后处理）→ Modular & Agentic RAG（检索成为可决策的模块）→ Graph RAG（引入实体关系与多跳）。

追问：chunk 应该怎么切？（见第 26 题） ｜ metadata 应该存哪些字段？（见第 26、35 题） ｜ 为什么要加 rerank？（见第 28 题）

25. 什么是 RAG？它和 Agent 是什么关系？ ｜必刷 ｜中等

答案： RAG（Retrieval-Augmented Generation，检索增强生成）是把外部知识库与 LLM 结合的技术：文档分块向量化入库 → 提问时检索相关片段 → 注入 prompt 生成回答。它解决的是"知识从哪里来、能不能溯源、能不能低成本更新"。

在 Agent 里，RAG 通常扮演可被调用的知识工具 / 长期记忆载体：Agent 决定要不要查、查什么、查几轮。两者的关系不是替代而是嵌套——Agent 是决策循环，RAG 是循环里的一个能力环节。RAG 接入 Agent 的三种接法见第 32 题，Agentic RAG 见第 33 题。

一个常见误区：RAG 不是安全层。知识库文档本身也可能带恶意指令，把"检索到的内容"当"可信提示词"是很危险的（见第 108 题）。

26. 文本切块应该怎么设计？有哪些常见坑和新做法？ ｜高频 ｜中等

答案： 切块的目标不是"切得均匀"，而是尽量保留对检索有意义的语义单元。通常结合固定长度、段落边界、标题层级和重叠窗口来设计：太大噪声多、命中不准；太小丢上下文，检索回来也答不了。手册、FAQ、制度文档、图文混排 PDF 不能只按字符数切，要结合版面结构、标题、表格和语义边界。

常见坑：

  • 切块过碎，语义被截断；
  • 忽略标题层级，chunk 里丢失"这段属于哪一节"的上下文；
  • 重叠（overlap）不足，边界信息丢失；
  • 纯 OCR 文本脏乱不清洗（页眉页脚、水印、断行）；
  • 表格被打散成几段残缺文本；
  • 多个主题塞进一个 chunk，导致向量语义污染。

两个 2025-2026 已被验证有效的做法：

做法 出处 / 时间 原理 收益与代价
Contextual Retrieval Anthropic，2025-09 入库前让 LLM 为每个 chunk 生成一句"本片段在整个文档中的背景说明"并前置拼接，配合 prompt caching 摊薄成本 检索失败率显著下降（官方口径：结合 BM25 + rerank 时最高降约 49%）；代价是索引阶段多一次 LLM 调用
Late Chunking 2024 末提出，2025 广泛采用 先把整篇文档送入 embedding 模型拿到 token 级向量，再按切块边界做 mean pooling 每块天然带全文上下文；在 BeIR 类基准上约 +3~3.6%；依赖能输出 token 级向量的模型

metadata 至少建议存：来源文件、文档 ID 与版本、章节标题路径、页码/坐标、权限与租户标签、更新时间、内容类型（正文/表格/图注）。这些字段决定了后面能不能做权限过滤、增量重建和引用溯源（见第 35 题）。

追问：chunk_size 和 overlap 怎么定？（没有普适值，用你自己的评测集扫参：常见起点 256512 token、overlap 1020%，看召回质量和上下文组装成本） ｜ 结构化文档怎么办？（按结构块切，见第 34 题）

27. RAG 效果不好时，你会怎么排查？ ｜必刷 ｜中等

答案： 按检索前 / 检索中 / 检索后三层展开：

层 检查项
检索前 query 是否表达清楚，要不要改写、拆问、补历史上下文
检索中 切块质量、Embedding 选型、索引参数、top_k、过滤条件、rerank 是否合理
检索后 拼给模型的上下文是否过长/噪声多、关键信息是否被淹没、生成提示是否要求"无依据就拒答"

企业知识库还要额外查：文档质量、版本是否最新、权限过滤是否误伤。

区分"召回问题"还是"生成问题"的方法很实用：把 gold 文档人工塞进上下文再跑一次——如果塞对了就能答对，问题在检索；如果塞对了还答错，问题在生成/提示。

很多所谓"模型不聪明"的问题，最后都能定位到文档解析脏、chunk 太碎、召回噪声大或上下文组装差。

追问：top_k 是不是越大越好？（不是，受 Lost in the Middle 与成本限制，通常召回 2050 → rerank 后取 38） ｜ 什么是 Lost in the Middle？（见第 30 题）

28. 混合检索、重排序、查询改写分别解决什么问题？ ｜高频 ｜中等

答案： 三者解决三个层次的问题：

手段 解决的问题 常见做法
查询改写 用户问题不像检索语句 指代消解 / 补全历史、多查询（multi-query）、拆子问题、HyDE（先假想答案再拿它去检索）
混合检索 只靠稠密向量会漏关键词命中 向量召回 + BM25/稀疏召回，用 RRF（倒数排名融合）或加权分数合并
重排序 rerank 召回了一批候选但顺序不够准 Cross-Encoder 精排：Cohere Rerank、BGE-Reranker、ColBERT（晚交互，性价比好）

真实项目里，制度、产品参数、订单字段、错误码这类知识关键词常常非常重要，只靠 dense retrieval 不够。比较稳的组合是：query 改写 + 稠密检索 + 稀疏检索 + rerank，再结合 metadata 过滤收口。

Rerank 放在哪一层：放在召回之后、上下文组装之前——召回追求覆盖率（多召回），rerank 追求精度（精选 Top-K），最后只让高信号片段进窗口。

成本要如实说：混合检索 + rerank 会比单路向量检索贵（多一次稀疏查询和 N 次 cross-encoder 打分），但通常比"把 top_k 拉到 50 全塞进长上下文"便宜，因为省的是更贵的生成 token。

追问：稠密和稀疏的区别与 2026 年的新变化？（见第 29 题） ｜ Adaptive RAG 是什么？（先判问题难度，简单问题不检索、单跳检索一次、复杂问题才多轮检索——把"要不要查"变成一个路由决策）

29. 稠密检索和稀疏检索怎么选？为什么 2026 年 BM25 又回潮了？ ｜高频 ｜较难 ｜2026 新增

答案：

稀疏检索（BM25 / TF-IDF） 稠密检索（Embedding + ANN）
匹配依据 词频与逆文档频率，字面命中 语义向量距离，"意思接近"
优势 专有名词、型号、错误码、代码标识符、人名精确命中强；可解释；索引便宜 同义改写、跨语言表达、模糊意图更鲁棒
短板 同义词、换说法就召不回；跨语言弱 稀有 token 容易被"平滑"掉；幻觉式近邻；需 GPU/推理成本
典型失败 "服务器型号 R740xd"被写成"这台机器"就查不到 把"禁止删除数据库"和"如何删除数据库"判成近邻

为什么 2026 年 BM25 重新被重视：

  1. 有研究在大规模、深层嵌套语料（如 28 层层级文档）上发现，纯稠密检索明显劣于 BM25，差距可达近 20 个百分点——层级越深、专有术语越多，字面命中越关键；
  2. 企业 RAG 的语料以"制度 + 参数表 + 工单 + 错误码"为主，恰恰是稀疏检索的主场；
  3. 长上下文与 GraphRAG 的成本压力下，"便宜且确定性强的召回路径"性价比凸显；
  4. 主流向量库（Qdrant、Milvus、ES/OpenSearch、pgvector）都把 sparse vector / 全文检索做成一等公民，混合检索的接入成本大幅下降；Learned sparse（SPLADE）作为折中方案也在普及。

工程结论：默认就该做混合检索 + rerank，把"要不要稀疏"当默认而不是优化项；只有在纯语义改写型任务（跨语言、口语化问答）里才考虑只上稠密。

追问：RRF 融合怎么算？（对各路结果按排名取 1/(k+rank) 求和，k 常取 60，不需要统一分数尺度） ｜ learned sparse 和 BM25 怎么选？（SPLADE 效果通常更好但要额外维护模型与索引体积，BM25 零模型成本、可解释）

30. 什么是 Lost in the Middle？对 RAG 设计有什么启示？ ｜高频 ｜中等

答案： Lost in the Middle 指：上下文一长，模型往往更容易利用开头和结尾的信息，而把中间那部分关键证据"看见了但没用好"（U 型性能曲线，原始论文来自 Liu et al., TACL 2024）。

启示很直接：不是把更多 chunk 塞进上下文就一定更好。中间噪声太多，真正关键的证据反而更容易被淹没。工程处理：

  1. 先做 rerank 和过滤，再决定谁能进上下文；
  2. 尽量减少低价值片段，别把"可能相关"都塞进去；
  3. 重要证据优先放前面（或把结论前置），必要时先做摘要；
  4. 复杂问题采用分阶段检索，而不是一次性把大段材料全塞进去。

可以结合第 13 题的 Context Rot 一起说：长上下文不等于高质量上下文，RAG 的核心仍然是"把最有用的证据放到最容易被模型用到的位置"。

31. 有了超长上下文模型，还需要 RAG 吗？ ｜必刷 ｜中等

答案： 多数场景仍然需要，因为**"能塞进去"和"应该塞进去"完全不是一回事**。

超长上下文确实让长文理解、少量文档内推理更方便（2026 年旗舰普遍宣传 1M token），但企业场景里常见的问题不是"窗口不够大"，而是：

  • 知识总量太大，没法每次都全塞；
  • 长上下文的成本和延迟都显著更高（输入按 token 计费，且很多厂商对超长输入有分档溢价）；
  • 标称窗口 ≠ 有效窗口：公开模型卡的长文检索测试显示同一模型在 128K 与 1M 位置准确率能差几十个点（见第 11、30 题）；
  • 权限过滤、租户隔离、版本控制不能靠窗口硬塞解决；
  • 审计和引用追溯更适合通过检索链路来做。

合理理解：长上下文扩大了可处理范围，但没有消灭检索的价值。 它更适合少量长文档分析、上下文整合和复杂推理；RAG 更适合海量知识缩圈、权限过滤、证据引用和持续更新。

一句话：长上下文不是 RAG 的替代品，更接近 RAG 的补充能力。（常见组合：RAG 先缩圈到 Top-K，再用长窗口承载这些证据 + 多步推理。）

32. RAG 应该如何接入 Agent 执行链路？ ｜高频 ｜中等

答案： 不能只理解成"先查一遍资料再回答"，更稳的做法是把检索能力做成 Agent 可按需调用的一环。三种接法：

接法 说明 适用
前置检索 问题一进来先统一检索，把证据交给 Agent 继续规划 明确的问答型请求、单轮知识库场景；延迟可控、流程简单
按需检索 把 Retriever / Search 封成 Tool，Agent 在需要事实依据时主动调用 多步任务、并非每步都需要资料；推荐作为主线
后置校验 先生成结果，再用检索做证据核对或引用补全 作为增强，不适合主链路——增加延迟，且一旦前面跑偏，后面修正成本更高

真实项目通常"按需检索为主，前置检索为辅"：很多步骤是规划、路由、参数确认或工具执行，不需要查知识库，做成可调用能力能减少无效检索。

追问：什么情况下该从"一次检索"升级成"多轮检索 + 中途补检"？（badcase 集中在证据不足、多跳、需要交叉验证时 → Agentic RAG，见第 33 题）

33. 什么是 Agentic RAG？它和"一次检索后直接生成"有什么区别？ ｜中频 ｜较难

答案： 传统 RAG 是固定流水线：先检索一次，再把结果交给模型生成。Agentic RAG 是闭环过程：模型 / Agent 根据当前进展决定要不要检索、检索什么、是否改写 query、是否继续补检，甚至在证据不足时主动回头重查。

最大区别不在"有没有检索"，而在于检索是否被当成一个动态决策过程来管理：

传统 RAG Agentic RAG
流程 固定、可预测 动态、依中间结果
成本 / 延迟 可控 显著更高
适合 单轮问答、标准知识库 复杂问题、多跳证据、需自检补检
风险 召回一次不到位就答错 可能变成"更贵的随机游走"

工程上不会一上来就Agentic RAG，先看 badcase 是否真的集中在这几类：一次检索经常拿不到足够证据；问题需要拆问 / 多轮求证 / 多源交叉验证；生成前需要判断"该查知识库、查网页还是查业务系统"。

如果真要落地，必须同时补上步数上限、预算限制、失败退出条件和可观测性。

34. 复杂文档 RAG 或多模态 RAG 应该怎么做？ ｜中频 ｜较难 ｜2026 新增

答案： 最大的坑是把 PDF、扫描件、表格、图片、网页全都当"普通纯文本"处理。更稳的做法是把解析层单独看待：

  1. 先做版面分析、OCR、表格提取、标题层级恢复，而不是一开始就按字符切块；
  2. chunk 尽量按结构块切——标题、段落、表格、图注各成单元，不要把一张表切成几段残缺文本；
  3. metadata 保留页码、章节标题、文档版本、来源文件、坐标或结构位置，方便引用和追溯；
  4. 查询时走多路召回：文本召回、表格召回、图片说明召回，再统一重排和组装；
  5. 表格建议额外存"表格的自然语言摘要 + 结构化行列"双份，兼顾语义召回与精确取数；
  6. 图片 / 图表用 VLM 生成描述文本入库（多模态 embedding 是另一条路线，跨模态检索更直接但对模型和成本要求更高）。

如果是企业知识库，复杂文档 RAG 往往比"模型选型"更影响上限——解析错了、表格碎了、图文对应关系丢了，后面再强的模型也很难补回来。

追问：为什么设备手册、制度 PDF 特别难做 RAG？（双栏排版、页眉页脚污染、跨页表格、大量图示与编号引用、版本多且权限复杂） ｜ OCR 准确率和最终问答效果是什么关系？（不是线性关系：OCR 错在关键数字/型号上是致命的，错在正文虚词上影响很小，所以要按字段重要性看） ｜ 多模态 RAG 什么时候值得上？（图 / 表承载了不可替代的信息时才上，纯装饰性图片直接丢）

35. 为什么企业项目里的 RAG 必须重视权限、版本和引用？ ｜中频 ｜中等

答案： 因为企业知识不是"能查到就行"，而是"要查对、查对权限范围、还能追溯来源"。

  • 权限：向量检索必须做租户隔离、角色过滤、文档级或段落级权限控制，不能把安全寄希望于模型"自觉不回答"。工程上一般在检索层过滤（metadata filter / 集合隔离）而不是生成层事后拦截；常见难点是源系统 ACL 变更后的同步——用权限位图、行级安全（RLS）或按用户/角色分集合等方式。
  • 版本：索引和源文档要可追踪，文档更新后要知道哪些向量需要增量重建；要能回滚到旧索引（蓝绿双集合 + 别名切换是常见做法）。
  • 引用：答案不能回溯到原文片段时，业务方很难建立信任，也不利于审计和复盘。引用要能落到具体文档 + 页码/章节 + chunk_id。

所以企业里 RAG 不只是检索效果问题，更是数据治理问题。

追问：如何避免用户问到权限外文档？（召回时就按 user_id/role 过滤 + 向量库层隔离 + 不把敏感内容写进共享摘要） ｜ 知识更新时怎么兼顾一致性与成本？（增量 upsert + 软删除旧版本 + 定时全量校对）

36. 什么是向量数据库？和传统数据库有什么区别？主流产品怎么选？ ｜高频 ｜基础

答案： 向量数据库是专门面向"相似度检索"的存储系统，保存向量、原始内容和元数据，支持近邻搜索、过滤和召回。传统数据库擅长精确过滤、事务和结构化查询；两者不是替代而是分工：结构化条件走关系库，语义召回走向量库，再通过 metadata 把两边结合起来。

只用 MySQL 当然也能存 Embedding，但数据量一上来，ANN 索引、混合检索、大规模召回都会低效，工程复杂度明显上升。

主流产品盘点（选型看"团队现有技术栈 + 规模 + 合规"，不看热度）：

产品 定位 适用
pgvector Postgres 扩展 中小规模、已有 PG、想少一个组件、需要强事务与行级权限；运维最简单
Qdrant 开源，Rust，性能/性价比好 中型生产，支持 payload 过滤、稀疏向量、量化
Milvus 开源，分布式，云原生 大规模（亿级）、多集合、高并发
Pinecone 托管 SaaS 不想自运维、海外业务、快速上线
Weaviate 开源，内置模块化向量化与混合检索 想一站式做混合检索
ES / OpenSearch 搜索引擎带向量能力 已有 ES 且本来重度依赖全文检索
Chroma / FAISS 轻量 / 纯库 原型、本地、离线实验；不适合多副本在线服务

一个常见追问：已经有 ES 了还需要专门的向量库吗？ 回答思路是看规模与延迟要求：千万级以内、混合检索为主，ES 足够；高 QPS、大向量、低延迟、需要 GPU 索引与量化时，专业向量库更合适。

37. Embedding 是什么？它在应用开发里最核心的价值是什么？ ｜高频 ｜基础

答案： Embedding 把文本、图片等原始内容变成固定长度的向量，让"语义关系"尽量映射成"空间关系"——把"意思接近"变成"距离接近"，程序才能做相似度计算。

最核心的价值不只是"把文本编码成数字"，而是让系统第一次具备了按语义检索的能力：语义搜索、相似匹配、去重、聚类、推荐、RAG 召回。放到 RAG 里，Embedding 决定的是"问题和知识能不能在向量空间里正确相遇"——选错了，后面的向量库、重排、Prompt 只能在一个偏掉的召回基础上做优化。

两个必须强调的工程细节：

  1. 建库和查询用同一套 Embedding 模型，这是底线——不然要么维度对不上，要么维度一样但相似度没有意义（换模型必须重建索引）；
  2. Embedding 只是"把文本变成稠密向量"这一层，真正检索时往往还要和标量字段过滤、稀疏检索配合，不能把它理解成检索系统的全部。

38. 如何选择合适的 Embedding 模型？评估它好坏看什么？ ｜高频 ｜中等

答案： 不要先看榜单，先看自己的知识类型和检索目标，再反推选型。先看三件事：

  • 语言与领域适配：中文、英文、多语言、代码、法律、金融，适合的模型可能完全不同；中文场景优先看 C-MTEB / 自有样本；
  • 建库与查询一致性：同一套模型，必要时保留模型版本号以支持双索引；
  • 成本与延迟：不是维度越高越好、不是模型越大越好，要看知识库规模和查询量能不能撑住。

真正评估时分三层看，而不是只盯一个榜单分数：

层 看什么
检索层 相关片段有没有更容易被召回、坏例子有没有减少、重排前后差距大不大（nDCG@k、Recall@k、MRR）
业务层 最终答案的忠实度、引用准确性、任务完成率有没有变好（RAGAs / DeepEval 类）
工程层 延迟、成本、接入复杂度、向量存储体积能不能接受

还要补两句：

  • Embedding 选型不是孤立问题，它会和切块策略、索引参数、混合检索、rerank 一起决定上限；
  • 公开榜单（MTEB / C-MTEB）只能做初筛，真正决定要不要上线的是你自己的知识样本和 badcase。

更稳的做法：先选 2~3 套候选模型跑通，再在自己的知识库样本上小规模对比，看召回质量、最终回答质量、成本延迟，最后再定。

39. 近似检索（ANN）和精确检索怎么权衡？ ｜中频 ｜中等

答案： 精确（暴力）检索把查询向量和库里每一个向量都算一遍，结果确定但成本高、延迟高；ANN 用索引换速度——HNSW（图索引，召回高、内存大）、IVF（倒排聚类，可配 PQ 量化省内存）、DiskANN（磁盘友好）等，牺牲一点精确度换吐量与响应速度。所以大部分线上系统优先用 ANN。

工程上不是二选一，而是看业务：

场景 建议
高风险检索、数据量不大、结果一致性要求极高 精确或更保守的索引参数（高 ef/高 nprobe）
通用知识问答、商品搜索、海量文档召回 ANN + rerank 做精度补偿
成本敏感、内存受限 标量/二进制量化 + 精排拉回精度

关键参数要会说：HNSW 的 M 与 ef_construction（建索引时定）、ef_search（查询时可调，越大越准越慢）；IVF 的 nlist 与 nprobe。调优的本质是召回率 vs 延迟的曲线，拿自己的评测集扫参，不要背固定值。

40. GraphRAG、LightRAG 适合什么场景？和传统向量 RAG 怎么选？ ｜中频 ｜较难 ｜2026 新增

答案： 先说两个基础判断题：

  • 什么场景下知识图谱比纯向量检索更有价值？ 当问题核心不只是"语义相似"，而是"实体关系、路径推理、多跳关联、结构化约束"时——设备故障排查、商品属性关联、组织关系、法规条文引用、依赖链分析。只靠向量容易召回到"语义接近但关系错误"的内容。工程上把它理解成增强而不是替代：向量负责语义召回，图谱负责结构化约束、实体消歧和关系推理。
  • GraphRAG 适合什么？ 实体关系密、需要多跳推理、社区摘要（全局性问题如"这批文档主要在讨论什么主题"）、结构化约束强的场景。

2025-2026 的演进主要在于降成本：

方案 特点
GraphRAG（微软） 效果开创者，但索引要逐实体抽取 + 社区摘要，token 成本高，适合一次性建库、反复回答全局问题
LightRAG（港大，EMNLP 2025） 双层检索（低层实体关系 / 高层主题），支持 local/global/hybrid/mix 四种模式与多模态；v1.5 引入多模态 + 四种分块 + 角色 LLM。索引成本比 GraphRAG 低很多（官方口径约三个数量级）、检索更快，35k+ stars
LazyGraphRAG（微软） 思路是"用轻量 LLM 标注代替预先详细摘要"，把索引成本降到传统 GraphRAG 的约 0.1%，查询时才按需深入
KAG / nano-GraphRAG KAG 强调逻辑形式与知识对齐；nano 系列适合学习与小规模落地

落地路径通常是：先用传统向量 RAG 打底 → badcase 明显集中在多跳关系、实体消歧、结构约束时再引入图谱增强 → 真正上线时常常是"向量召回 + 图谱召回 + 融合重排"一起做。只有问题核心在关系结构上时，图谱路线的收益才会大于复杂度。

追问：图谱更新和维护成本会不会太高？（会，实体抽取与消歧质量直接决定上限；要评估源数据变更频率与抽取成本） ｜ 多路召回比纯图谱主路更现实吗？（在大部分企业混合场景下是的）

41. RAG 系统在实际部署中面临哪些挑战？ ｜高频 ｜较难

答案： 难点不在"能不能检索"，而在"从索引到回答的完整链路能不能长期稳定运行"。拆成六类：

侧 挑战
数据侧 文档解析质量、切块策略、表格与 PDF 处理、知识更新时效
检索侧 Embedding 选型、召回质量、混合检索、重排效果、metadata 过滤
生成侧 上下文组装、引用溯源、忠实度控制、拒答策略
治理侧 权限隔离、版本管理、引用可追溯、知识回滚
评测侧 badcase 建设、离线评测与在线指标闭环
工程侧 延迟、成本、缓存、可观测、索引重建与线上运维

面试里更稳的答法不是只说"部署会有很多工程问题"，而是明确讲出：RAG 是一条从数据接入、索引构建、检索召回到生成回答的完整链路，任何一层出问题，最终答案都会出问题。

追问：知识库频繁更新时怎么处理索引重建与版本回滚？（增量 upsert + 双集合别名切换 + 旧版本保留一个回滚窗口） ｜ 查询慢卡在哪个环节？（分段计时：向量化/召回/rerank/组装/生成，rerank 与生成为最常见热点，见第 120 题）

42. RAGFlow、Dify 还是自研链路？开源 RAG 平台怎么选？ ｜中频 ｜中等

答案： 不要答成"谁更强"，而要答成"当前知识库场景更需要什么"：

重点 推荐方向
文档导入、解析、切块、检索与 RAG 编排体验 RAGFlow 这类专项平台更有吸引力（深度文档解析是它的长板）
多类 Agent、工作流、插件生态、业务 API 编排 Dify / Coze 边界更宽
深度定制、复杂状态治理、合规审计、内部系统耦合 自研代码链路（LangChain/LangGraph + 自建检索）更稳

真正选型时优先看四类因素：文档导入与解析质量、权限与多租户能力、对接业务系统的方便程度、二次开发空间。很多项目不是卡在"能不能做 RAG"，而是卡在"解析质量稳不稳、权限做不做得住、后续能不能接进企业系统"。

追问：平台转自研的迁移边界怎么划？（把检索、权限、评测三层抽成独立服务，平台只做上层编排；迁移时先换编排层不动数据层）

四、记忆与上下文管理

43. 上下文窗口、短期记忆、长期记忆分别是什么关系？ ｜必刷 ｜中等

答案：

  • 上下文窗口：模型单次推理能看到的内容上限，是昂贵的计算资源；
  • 短期记忆（In-context / Session Memory）：会话或线程级状态，当前对话上下文，不持久；
  • 长期记忆（External Memory）：跨会话保留的用户或任务信息，落在数据库/向量库/图谱，按需检索；
  • 工作记忆（Working Memory）：当前任务执行中的中间状态、变量、步骤结果。

工程上不能把这三者混为一谈：窗口不能无限塞历史；短期记忆保留当前任务相关的历史、摘要、线程状态；长期记忆更适合存偏好、画像、历史结论和可复用事实，按需检索，不应该每次全量放进 prompt。

成熟系统的典型形态：窗口里只放高信号上下文，短期记忆保证当前线程不断档，长期记忆通过数据库或向量库按需召回。

对应到 LangGraph：短期记忆 = State + checkpointer（按 thread_id，见第 82 题），长期记忆 = Store（跳 thread、按 namespace/key）或 RAG 知识库。

追问：记忆和 RAG 的区别？为什么说记忆不是训练模型？Redis 适合做什么？（均见第 46 题） ｜ 上下文被截断时选滑窗、摘要还是检索式补充？（见第 44 题）

44. 如何为 Agent 设计短期与长期记忆系统？超长多轮对话怎么既不断档又省 token？ ｜高频 ｜较难

答案： 先把记忆拆两层，不然很容易把所有信息都塞进上下文，最后又贵又乱：

  • 短期记忆：解决"当前会话/线程不断档"，核心是 读历史 → 拼进提示 → 调模型 → 写回历史；
  • 长期记忆：解决"跳会话保留偏好、画像、历史结论、可复用事实"，核心是"存结构化信息，按需召回"，而不是每轮全量塞 prompt。

技术落地：短期常见做法是把消息历史或线程状态持久化到内存、Redis 或 checkpointer，再通过 MessagesPlaceholder 或图状态在下一轮重新注入；长期更适合放在数据库、向量库，关系很重要的场景里放进知识图谱。

在 LangChain / LangGraph 体系下要能讲清两套定位：

方案 定位 适合
RunnableWithMessageHistory + BaseChatMessageHistory 对话历史注入 聊天助手、轻量多轮问答
LangGraph persistence / checkpointer 线程级状态持久化（图在每一步的快照） 复杂 Agent、图编排、断点恢复、人机协同
Store / 向量库 / DB 跳线程长期存储，按需检索 偏好、画像、历史结论

超长多轮对话的四种常见手段（必须能说差异）：

  1. 滑动窗口：只保留最近 N 轮原文，简单直接，但容易丢早期约束；
  2. 周期性摘要：每隔几轮把历史压成结构化总结，保留目标、已确认事实、待办和偏好；
  3. 检索式补充：旧对话写入向量库或长期存储，按当前问题召回相关片段，而不是把所有旧消息都塞回窗口；
  4. 结构化记忆槽：城市、会员等级、偏好、关键状态这类固定信息直接落键值或数据库，不让模型每次"回忆"。

所以记忆系统不是"历史保存得越多越好"，而是要区分：什么该原样保留，什么该摘要，什么该结构化，什么该按需检索。

追问：四种手段怎么组合？（近期原文 + 中段摘要 + 远期检索 + 关键槽位直存，是生产常见四合一） ｜ 摘要会丢信息怎么办？（摘要只作为补充索引，关键事实另入结构化字段）

45. Agent 的长期记忆基建有哪些方案？ ｜高频 ｜较难 ｜2026 新增

答案： 代表方案（截至 2026-10）：

项目 技术路线 特点

46. 记忆和 RAG 的区别是什么？记忆算训练吗？Redis 在记忆里适合做什么？ ｜高频 ｜基础 ｜2026 新增

答案： 三个追问都有标准答法：

1）记忆 vs RAG：形式上都是"存下来、检索回来"，区别在写入侧与作侧：

RAG（知识库） 记忆
写入 文档原样切块入库 从对话中抽取事实，处理更新与冲突（旧事实失效）
内容 领域知识、文档 用户偏好、实体关系、历史结论
时序 一般不管 要区分"上月在 A 团队、本月在 B 团队"
检索 全局相似度为主 按用户/会话作用域检索，带个性化
质变 知识库更新即可答新内容 写错会持续误导后续所有会话

2）记忆不是训练：记忆只改上下文内容，不改参数，因此可随时增删、可解释、可按用户隔离；微调才改参数，贵、慢、难回滚、无法按用户区分。面试里能把这句说清就赢一半。

3）Redis 的定位：适合做短期记忆 / 会话缓存——按 session_id 存最近 N 轮消息、TTL 自动过期、低延迟高并发；也能做语义缓存（向量相似度检索）与频控。不适合做长期记忆主存储（语义检索、事实抽取、时间推理不是它的主场），长期记忆还是向量库 / 图谱 / 关系库更合适。

追问：记忆该存哪些字段？（user_id/namespace、事实内容、类型标签、时间戳与有效期、来源会话、置信度） ｜ 如何防止用户 A 的记忆泄到用户 B？（命名空间硬隔离 + 检索时强制带作用域过滤 + 写入时禁存敏感原文）

五、工具调用与 Function Calling

47. Function Calling 的基本原理是什么？消息是怎么流转的？ ｜必刷 ｜中等 ｜腾讯一面

答案： 核心分工一句话：模型负责决策，程序负责执行。

完整链路：

  1. 宿主程序把工具的 name、description、参数 schema（通常是 JSON Schema）一起发给模型；
  2. 模型判断要不要调用工具，如果要，先返回结构化的 tool_calls，而不是直接给最终自然语言；
  3. 宿主程序读取 AIMessage.tool_calls，真正去执行 Python 函数、HTTP API、数据库查询或业务服务；
  4. 程序把执行结果封成 ToolMessage（带 tool_call_id）再交回模型；
  5. 模型基于工具结果生成最终答复。

消息流转是 Agent 的命门，必须能默写：

Human → AI(tool_calls) → Tool(tool_call_id 一一对应) → AI … → AI(无 tool_calls = 终态)

所以 Function Calling 不是模型自己去调 API，它只是生成"调用哪个工具、传什么参数"的结构化意图。真正的鉴权、参数校验、超时、幂等、重试和安全控制，全部在宿主程序这一层。

工程补一句：Function Calling 解决的是"模型如何表达调用意图"，不解决"工具是否安全、是否允许调用、调用失败怎么兜底"。

追问：为什么生产更推荐原生 Tool Calling？（协议级契约，见第 23 题） ｜ 工具执行失败怎么处理？（见第 55 题）

48. Tool、Function Calling、Agent 三者是什么关系？ ｜必刷 ｜基础

答案： Tool 是能力单元，Function Calling 是调用机制，Agent 是把模型、工具、状态和决策流程组织起来的运行模式。

  • Tool 解决"能做什么"；
  • Function Calling 解决"怎么发起结构化调用"；
  • Agent 解决"如何围绕目标多轮地决定要不要调用、调用谁、调用几次"。

所以 Tool 不等于 Agent，单次 Tool Calling 也不一定等于 Agent。真实项目里很多需求只需要 Tool Calling（意图识别 + 调一个工具 + 结果整合），不一定要上完整 Agent；只有任务需要多步规划、反复决策和状态推进时，Agent 才值得引入。

Agent 决定调用与否的那个字段就是 finish_reason / 有无 tool_calls：无工具调用即视为终态（见第 47、51 题）。

追问：单工具助手算不算 Agent？（看是否有循环与状态推进，不看工具个数） ｜ Tool 设计的最小粒度应该是什么？（见第 52 题）

浏览器控制 Playwright、Puppeteer、browser-use
计算与校验 计算器、单位换算、正则校验（避免 LLM 幻觉）

面试里比背名字更重要的是：按"读/写、可逆/不可逆"给工具分级。只读工具可以直接给模型用；写操作工具（发消息、下单、退款、改数据）必须加确认、幂等与审计（见第 83、107 题）。

追问"如何提升工具调用准确率"的标准答案：

  1. 动宾命名（get_weather 而不是 weather），名字即可读；
  2. docstring 写清何时用 / 何时不用（包括反例）；
  3. 参数给描述、示例与约束（枚举用 Literal，范围用 Field(ge=, le=)）；

51. 现场手写一个带工具的 Agent（不用 AgentExecutor）。 ｜必刷 ｜中等

答案：

from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, ToolMessage
from langchain_core.tools import tool

@tool
def get_weather(city: str) -> str:
    """查询指定城市的天气。city 为城市名。"""
    return f"{city}：晴，25°C"

llm = ChatOpenAI(model="gpt-5-mini").bind_tools([get_weather])
tools = {"get_weather": get_weather}

messages = [HumanMessage("北京天气如何？")]

for _ in range(10):                       # 最大步数，防死循环
    ai = llm.invoke(messages)
    messages.append(ai)
    if not ai.tool_calls:                # 无工具调用 = 终态
        break
    for call in ai.tool_calls:           # 执行所有请求的工具
        result = tools[call["name"]].invoke(call["args"])
        messages.append(ToolMessage(str(result), tool_call_id=call["id"]))

print(messages[-1].content)

两个高频扣分点：

  1. ToolMessage 必须带 tool_call_id，与请求一一对应；
  2. 每轮要把 AI 消息和 Tool 消息都追加进历史，漏任一边模型都会报错。

加分点：工具名不存在时要拒绝执行（防工具幻觉）；call["args"] 要过 Pydantic 校验而不是直接 ** 展开；工具执行要有超时与异常捕获，失败时把错误作为 observation 回传而不是直接抛异常。

注：示例中的 gpt-5-mini 是现役型号占位写法；旧版示例里的 gpt-4o / gpt-4o-mini 自 2026-02-13 起陆续退役，新代码应改用现役型号。init_chat_model("provider:model") 的用法本身不变，迁移通常只需改模型字符串。

52. 设计 Tool 时最值得重视的工程原则是什么？ ｜高频 ｜中等

答案： 四点：单一职责、明确 schema、可观测、可失败。

  • 单一职责：一个 Tool 只做一件清晰的事，避免"大而全万能工具"；
  • 明确 schema：让模型更稳定地理解参数含义，不依赖它猜；
  • 可观测：每次调用都能追踪请求、参数、耗时、结果和错误；
  • 可失败：必须有超时、异常码、重试策略和降级逻辑，而不是假设一定成功。

如果 Tool 要连业务系统，还要加权限校验、幂等控制和审计日志。因为工具一旦从"查天气"变成"发消息、下工单、写数据库"，风险等级就完全不同了。

追问：Tool 粒度多细算合适？（以"业务动作"为粒度，而不是以"底层 API"为粒度——模型擅长选意图，不擅长拼参数链路） ｜ 写操作工具怎么设防？（interrupt 人审 + 幂等键 + 作用域限制，见第 83、104 题）

53. 什么是"工具幻觉"？工程上怎么缓解？ ｜高频 ｜中等

答案： 工具幻觉指：模型调用了不存在的工具、传了不合理的参数，或者在只该读数据时却试图触发写操作。在工具数量多、描述模糊、schema 不清晰时特别常见——模型有时不是"不会用工具"，而是"对工具边界理解错了"。

兜底措施：

  1. 工具注册表白名单：不存在的工具名直接拒绝；
  2. schema 强校验：参数类型、必填项、枚举值运行时校验，不信任模型返回；
  3. 工具集收敛：按场景暴露最小工具集，别让模型在几十个相近工具里乱猜；
  4. 描述治理：工具名、description、参数说明里明确读写边界和适用场景；
  5. 高风险确认：发消息、写数据库、发工单、下单类副作用动作必须审批或二次确认；
  6. 失败反馈：把错误原因回传给模型，让它有机会修正，但要限制重试次数防死循环。

一句话：Tool Calling 不是"接上就行"，而是要让模型"调得准、调得住、调错了也出不了大事"。

54. 工具很多时，如何控制上下文长度和调用稳定性？ ｜中频 ｜较难

答案： 工具一多，问题不再是"会不会调工具"，而是"会不会在一堆相似工具里选错、调错、越调越乱"。四类做法：

做法 说明
分层暴露 先按业务域拆成搜索类、数据类、执行类、写操作类，不要一次把所有工具塞给同一个 Agent
动态选择 先做 Tool Retrieval 或路由，只把 Top-N 个最相关工具描述放进当前上下文，而不是全量列出
工具聚合 把过细的底层 API 封装成更高层的业务动作，减少模型在几十个相近函数里猜名字
描述治理 工具名、description、参数说明里明确"什么时候用、什么时候不用、有没有副作用"

再往前走一步：生产里可以把"工具选择"本身做成独立阶段（先意图分类或子域路由，再进入具体工具调用）。既控上下文长度，也降工具幻觉和误调用概率。

一句话：工具多不是问题，关键是别让模型在一个没有层次的工具海里盲选。

追问：优先做路由还是先改工具粒度？（先改粒度与描述，成本最低；工具数仍爆炸时再上 Tool Retrieval） ｜ Tool Retrieval 和知识检索有什么区别？（检索对象是工具 schema/描述，召回后注入的是 tools 字段而不是上下文文本） ｜ MCP 工具一多同样有这个问题（见第 65 题）

55. 工具调用失败了怎么办？返回内容过长、多工具依赖顺序又怎么处理？ ｜高频 ｜较难 ｜2026 新增

答案： 这三问是 2026 年面试里考得最实的工具细节题。

1）失败后的四级策略（优先级从上到下）：

  1. 重试：只对瞬时错误重试（超时、429、5xx），指数退避 + 抖动；参数错不盲重试；
  2. 修正参数重试：把结构化错误码和原因作为 observation 回传给模型，让它自己改参数再调（限次，通常 ≤ 2）；
  3. 换工具 / 降级：主工具不可用时走备用数据源，或降级为"缓存 / 规则 / 人工"；
  4. 上抛与止损：仍失败就终止当前分支，记录现场并转人工，不要继续消耗上下文。

关键设计：错误返回给模型的应该是可行动的结构化信息（{"error_code": "INVALID_DATE", "hint": "需要 YYYY-MM-DD"}），而不是一大段 Python traceback。

2）返回内容过长：这是上下文膨胀的头号杀手。常用手段：

  • 工具层先做结果裁剪：只返结构化摘要 + 必要字段，支持 limit / fields 参数；
  • 分页或字段选择，让模型按需再拉；
  • 落文件只回路径：超长 observation 写入文件/虚拟文件系统，上下文里只留句柄与摘要（Manus、Deep Agents、Claude Code 都是这个思路）；
  • 截断时显式标注 ...(已截断，共 N 条)，避免模型把部分结果当全量下结论。

3）多工具顺序与依赖：

  • 能并行的就并行：独立查询（同时查天气和查新闻）一轮内并发发出，省掉串行延迟；
  • 有依赖的要拆成多步，前一步输出作为参数契约进入下一步（先查 user_id 再查订单）；常见做法是用结构化状态或 schema 存中间产物，而不是靠模型"记得上一步说了什么"；
  • 依赖关系能写进流程的别交给模型：固定顺序用 Workflow / LangGraph 边定义（见第 7、81 题），只把真正需要临时决策的部分留给 Agent；
  • 副作用工具要特别注意幂等与执行次数（重试不能重复下单，见第 104 题）。

追问：怎么防止模型拿到工具结果后乜二次编造？（要求只引用字段值、带来源、生成后做一致性校验，见第 110 题） ｜ 工具描述怎么写模型才不选错？（见第 50、54 题）

六、协议层：MCP、A2A 与 Agent Skills

56. 什么是 MCP？它解决的核心问题是什么？ ｜高频 ｜中等 ｜腾讯一面

答案： MCP（Model Context Protocol）由 Anthropic 于 2024-11-25 发布，是一套开放标准，用来规范 AI 应用如何以统一方式连接外部工具、资源和提示模板——常被比喻成"工具侧的 USB-C"。

它解决的不是"模型能不能调工具"，而是"不同 AI 应用怎样用统一方式接外部能力"。MCP 统一的是模型本身之外的部分：Host、Client、Server 之间发现、暴露和调用能力的方式。

参与角色：

  • Host：真正跑模型的应用（IDE、Claude Desktop、自研 Agent）；
  • Client：Host 内部的连接器，一个 Server 对应一个 Client，保持 1:1 隔离；
  • Server：对外暴露 Tools / Resources / Prompts 的服务进程。

企业关心 MCP 的理由很实在：一次暴露、多处复用、统一 schema、降低接入成本——内部把业务系统封装成 MCP Server 后，Cursor、Claude、自研 Agent 都能直接用，不必每个应用写一套集成。

治理进展：MCP 已于 2025-12-09 捐赠给 Linux Foundation 旗下新成立的 Agentic AI Foundation（AAIF）（由 Anthropic、Block、OpenAI 联合发起，创始项目含 MCP、goose、AGENTS.md）。

57. MCP 和 Tool / Function Calling / RAG / Agent 怎么区分？ ｜高频 ｜中等

答案： 四句话分工：

概念 解决什么
Tool / Function Calling 模型如何表达"我要调用哪个工具、传什么参数"
RAG 模型如何拿到外部知识
Agent 谁来规划、决策、调用这些能力
MCP 这些外部能力如何被标准化暴露和接入

和 Function Calling 的关系是上下层而不是替代：Function Calling 更靠近模型决策（怎么表达调用意图），MCP 更靠近生态接入和协议标准化（能力从哪里来、怎么发现）。真正落地时，Agent 完全可以在 MCP 暴露的能力之上继续用 Function Calling 做调用决策。

和 RAG 的区别：MCP 不是一种检索算法，它可以把检索能力做成一个 MCP Server（如知识库检索、向量库查询），但 RAG 本身的切块/召回/重排优化与 MCP 无关。

58. MCP 是如何做到跨平台兼容的？ ｜中频 ｜中等

答案： 本质上来自"统一协议，而不是统一实现"：不同平台、不同语言、不同宿主程序，只要都遵循同一套消息结构（JSON-RPC 2.0）、能力暴露方式和调用约定，就能在协议层互通。客户端不需要为每个外部系统写一套私有接入方式，服务端也能按标准暴露能力。

所以 MCP 的价值不在于它绑定了某个技术栈，而在于把接入差异收敛成了统一的协议面。类比：MCP 之于 AI 应用，相当于 LSP 之于编辑器与语言服务器、USB-C 之于设备接口。

工程上还要补一句：兼容的是协议面，不是体验面——鉴权方式、部署形态、工具质量、安全边界都仍需自己做治理（见第 61、65 题）。

59. MCP 协议的主体内容是什么？原语是怎么演进的？ ｜中频 ｜中等

答案： 按四层讲最清楚：

  1. 参与角色：Host、Client、Server；
  2. 能力类型：Tools、Resources、Prompts；
  3. 通信机制：能力发现、请求、响应、错误、通知；
  4. 传输方式：stdio、Streamable HTTP 等承载协议的通道。

三类原语的控制权归属要分得清：

原语 谁控制 含义
Tools model-controlled 模型可自动决定要不要调用的动作
Resources application-driven 由宿主决定如何纳入上下文的资料
Prompts user-controlled 可复用的提示/工作流模板（斜杠命令类）
客户端侧原语：Sampling（服务器反过来请求宿主生成）、Roots（宿主告知可操作目录范围）；后来新增 Elicitation（elicitation/create，服务器向用户弹结构化表单收集输入）。

规范按日期版本演进：2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 → 2026-07-28（当前最新版）。原语与特性的时间线：

  • 2025-03-26：OAuth 2.1 授权框架、Streamable HTTP 取代旧 HTTP+SSE；
  • 2025-06-18：Elicitation、structuredContent、resource_link，并取消 JSON-RPC 批处理；
  • 2025-11-25：Elicitation 增加 URL 模式、扩展与实验性特性框架成型；
  • 2026-07-28：史上最大修订，全面无状态化（见第 60 题）。

和 OpenAPI / Function Calling 的区别：Function Calling 只是单次请求里的工具 schema；OpenAPI 描述 HTTP 接口但没有会话/资源/提示协商；MCP 是有生命周期、可发现、双向通信的协议（只是 2026 版把"会话"从协议层拿掉了，见下一题）。

60. MCP 2026-07-28 新版规范改了什么？为什么去掉会话？ ｜必刷 ｜较难 ｜2026 新增

答案： 2026-07-28 是 MCP 第五版规范，被称为"史上最大修订"，主题是全面无状态化（stateless）——目标是让 MCP 能直接跑在普通 HTTP 负载均衡、Serverless 和企业网关上，而不是还得维持粘性会话。

删除 / 移除：

  • 移除协议级会话概念与 Mcp-Session-Id 头；不再要求服务端维护会话表；
  • 删除 initialize / notifications/initialized 握手；
  • 取消 JSON-RPC batch（2025-06-18 已删）；服务端不得主动向客户端发请求（要反 ask 只能走 Sampling / Elicitation 等声明式原语）。

新增 / 替代：

  • 版本与能力协商从"握手"改为每个请求自带：在 _meta 里带 io.modelcontextprotocol/protocolVersion、clientCapabilities（clientInfo 可选）；
  • 新增必须实现的 server/discover 方法，返回 supportedVersions / capabilities / instructions / ttlMs / cacheScope，把"一次性发现"变成可缓存的查询；
  • 结果对象必须带 resultType（如 "complete"），流式/不完整结果能被显式标识；
  • 新错误码：-32602 Invalid params、-32020 HeaderMismatch、-32021 MissingRequiredClientCapability**、**-32022` UnsupportedProtocolVersion（下文简写，实际名为 HeaderMismatch / MissingRequiredClientCapability / UnsupportedProtocolVersion）；
  • 引入版本化扩展框架（Extensions），官方示例：MCP Apps（服务端渲染交互界面）与 Tasks（长任务轮询）；
  • 强化 OAuth 2.0 / 2.1：明确服务器作为资源服务器的元数据发现、resource indicator、PKCE；
  • stdio 三条硬规矩：消息不得内嵌换行、stdout 只放协议消息、日志一律走 stderr（否则换行分帧会被破坍）。

收益实测（官方示例口径）：同一个工具调用的握手路径从 7 条消息 / 837 字节 降到 2 条消息 / 257 字节，下行流量约省 69%。

为什么去会话：有状态设计下，服务端必须记住"这个 session 里已经初始化过了、已打开哪些资源流"，导致必须粘性路由 + 内存状态 + 重启丢会话，这三点在云原生环境里都是成本。无状态后，每个请求自带版本与能力，任意实例都能服务，缓存、重试、水平扩展都回到普通 HTTP 那一套。

追问：旧客户端怎么兼容？（靠版本协商与 server/discover 的 supportedVersions，服务端可同时声明多个版本） ｜ 无状态后长任务怎么办？（Tasks 扩展 + 轮询，或自己接消息队列） ｜ stdio 为什么还留着？（本地工具首选：零网络攻击面、无需鉴权、由客户端拉起子进程）

61. MCP 的传输方式怎么选？鉴权怎么做？ ｜高频 ｜较难

答案： 两种官方传输：

传输 形态 要点
stdio 客户端拉起本地子进程，换行分隔 JSON-RPC 无网络攻击面、无需鉴权，适合本地工具；严格 stdout/stderr 分离
Streamable HTTP 单端点：POST 请求 + 可选 GET/SSE 流 取代旧的 HTTP+SSE；本地部署必须绑 127.0.0.1 并校验 Origin 防 DNS rebinding；远端走 OAuth 2.1

选型一句话：本地单人工具用 stdio，需要多用户/跨网络/可观测用 Streamable HTTP（2026 版无状态化后，后者部署明显变简单，见第 60 题）。

鉴权实践（按优先级）：

  1. 远程服务用 OAuth 2.1（授权码 + PKCE），服务器实现为资源服务器，通过 RFC9728 元数据发现、RFC8707 resource indicator 定位受众；
  2. 企业内部可用网关代理鉴权（mTLS / JWT），但不要把长期 API Key 写进客户端配置；
  3. 服务器侧必须做调用者身份→工具权限的映射（不是"能连上就能调所有工具"），并按用户做数据作用域过滤；
  4. 写操作额外加二次确认/审批（见第 83、107 题）。

62. MCP 服务器开发流程是什么？ ｜中频 ｜中等

答案： 典型流程：

  1. 明确能力边界：要暴露的是工具、资源还是提示模板（对应不同控制权，见第 59 题）；
  2. 定义输入输出 schema 和错误处理方式：参数、返回结构、错误码、能否分页/裁剪；
  3. 选择传输方式：stdio 或 Streamable HTTP；
  4. 实现服务端逻辑，补齐鉴权、日志、超时、异常处理；
  5. 客户端联调：注册、发现、调用、真实模型下的选择准确率测试。

工程上最容易被忽略的是能力边界和错误处理。MCP Server 不是简单把现有 API 套一层壳，而是要把能力设计成真正适合模型消费的接口：名字可读、描述说清何时不用、返回精炼结构化摘要（同第 50、52 题的原则）。

追问：怎么测 MCP Server 质景？（官方 Inspector / 客户端手工验证 + 自己搭一套"该调/不该调"用例集，看工具选择准确率与参数合法率）

63. Agent 应该如何接入 MCP 工具？ ｜中频 ｜中等 ｜腾讯一面

答案： 核心是把 MCP 暴露的能力纳入自己的工具注册与调度体系：

  1. 发现 MCP Server 暴露的工具/资源（2026 版走 tools/list + server/discover）；
  2. 把能力转换成 Agent 能消费的工具描述与 schema（填进模型的 tools 字段）；
  3. 执行时由模型决定何时调用，宿主负责真正发起 MCP 请求；
  4. 把结果回传给 Agent，进入下一轮决策。

真正的关键不在"接通"，而在"接通之后仍然可控"：权限映射、超时、失败重试、观测、审计。多服务器场景下工具名要加命名空间前缀（避免两个 Server 同名工具造成歧义），工具总量大时要做 Tool Retrieval（见第 54 题）。

高频追问：MCP 在你的架构里是只做权限检查，还是会和环境级安全沙箱一起工作？——标准答案是职责分层：MCP / Tool 负责"能不能调"，沙箱负责"即使调了也跑不出边界"，两者不可互替（见第 105、106 题）。如果只有 MCP 没有隔离，一旦模型被注入，文件与命令仍可造成真实破坏。

64. MCP 的流式与并发怎么保证？ ｜中频 ｜较难

答案： 流式（SSE）的价值：结果边产生边返回，而不是等整次调用结束才一次性返回。三个直接收益：降首包延迟、支持长任务中途进度回传（减少"卡死感"）、更利于宿主做取消/超时/部分结果处理。对研究型任务尤其重要。

并发不是协议单方面决定的，要看"协议层 + 服务层 + 工具层"一起设计：

  • 协议层：每个请求有唯一 id，避免响应错配（注意 JSON-RPC batch 已取消，并发靠多请求并行而不是打包）；
  • 服务层：服务端要支持并行处理而非串行阻塞，2026 无状态后可直接交给普通负载均衡；
  • 工具层：超时、限流、优先级、幂等；
  • 客户端：正确管理多请求上下文与背压。

补一句：如果底层工具本身很慢，协议再好也救不了——先去看工具层的瓶颈。

65. MCP 有哪些安全风险？怎么防御？ ｜必刷 ｜较难

答案： 2025-2026 集中暴露的典型威胁：

威胁 说明
Tool poisoning 工具描述里藏恶意指令，模型读到就执行（Invariant Labs，2025-04）
Rug pull 工具描述/行为上线后被悄悄篡改，客户端缓存的 schema 已不是当前版本
间接参数注入 工具返回内容里带指令，或参数被拼接后直接进 shell/SQL
slopsquatting 幻觉包名抢注（Seth Larson 命名）。USENIX Security 2025 论文：19.7% 样本引用幻觉包、43% 可每次复现，抢注的 huggingface-cli 曾获约 3 万下载
无鉴权公网暴露 Trend Micro 2025 年发现 492 个无鉴权暴露在公网的 MCP 服务器；另有恶意 MCP 代理包 RCE、Kaspersky 2025-09 报告相关攻击活动
SDK / 注册表缺陷 OX Security 报告 MCP SDK 缺陷波及约 1.5 亿次下载的包；11 个知名注册表里 9 个接受恶意条目
供应链投毒 2026-03 LiteLLM 生态发生投毒事件（示例，截至 2026-10）

防御按六层落地：

  1. allowlist：工具/服务器白名单，新工具默认不可信；
  2. 锁定与哈希校验：锁版本、记录工具描述哈希，变更就告警（防 rug pull）；
  3. 把所有工具返回内容一律当不可信数据处理（与第 108 题间接注入同一套防护）；
  4. 最小权限 + 作用域：只读优先、按用户隔离、限额；
  5. 沙箱执行：容器 + 网络隔离 + 域名 allowlist（见第 106 题）；
  6. 写操作人审 + 全量审计日志。

另可提一句：OWASP 已经有 MCP Top 10（2025） 与 Agentic Skills Top 10（AST 2026） 专项清单（见第 107、69 题），以及 Agent Skills 生态也出现了恶意 skills 攻击现象。

66. 有哪些热门的 MCP 工具？ ｜低频 ｜基础

答案： 集中在几类（面试里更重要的不是背全名字，而是知道为什么流行——它们覆盖了 Agent 最常见的外部能力需求）：

  • 浏览器自动化：Playwright MCP（微软，走可访问性树，见第 138 题）；
  • 数据与后端：数据库类（Postgres / Supabase）、电子表格；
  • 文件与代码：本地文件系统、GitHub、代码库检索；
  • 搜索与知识：网页搜索（Tavily 等）、知识库检索；
  • 办公与设计：Notion、Slack、Figma、Canva、Cloudflare 等厂商官方 Server；
  • 开发与可观测：Sentry、Ramp 类业务系统。

值得补的洞察：MCP 生态里"工具多"很快就不是卖点了，治理（鉴权、审计、版本、质景评分）才是——这也是企业关心 MCP 目录与签名/认证机制的原因。

67. 什么是 A2A 协议？现在发展到什么阶段了？ ｜高频 ｜较难 ｜2026 新增

答案： A2A（Agent2Agent） 是 Google 于 2025-04-09 发布的开放标准，解决不同框架、不同厂商的 AI Agent 之间的互操作问题（MCP 管 Agent ↔ 工具，A2A 管 Agent ↔ Agent）。

关键时间线：

  • 2025-06-23 捐赠给 Linux Foundation；IBM 的 ACP 于 2025-06 合并入 A2A；
  • v1.0.0 于 2026-03-12 发布（首个生产稳定版），v1.0.1 约 2026-05；
  • 2026-08-27 加入 Agentic AI Foundation（AAIF） Growth Stage；150+ 组织参与，TSC 覆盖 AWS、Cisco、Google、IBM Research、Microsoft、Salesforce、SAP、ServiceNow 八家；
  • SDK：Python / JS / Java（1.0.0.Final GA 2026-06-10）/ Go / .NET；平台集成：Azure AI Foundry / Copilot Studio（2025-12）、AWS Bedrock AgentCore（2025-11）、Semantic Kernel。

v1.0 四大主题（能说出这四个就是真的跟进过）：

  1. 多协议绑定：JSON-RPC 2.0 / gRPC / HTTP+JSON（REST）三者平等，同一语义三种载体；
  2. 版本协商：A2A-Version Header；
  3. 签名 Agent Card：密码学身份，解决"这个 Agent 到底是谁发布的"；
  4. 零信任安全模型：不假设内网可信，能力与权限声明化。

核心概念：Agent Card（能力名片，供发现与路由）、Task（有状态、可长时间运行的工作单元，支持流式更新与推送通知）、Artifact（产出物）、Message/Part（多模态内容块）。典型流程：

用户请求 → Orchestrator Agent →（A2A 委托）→ Research Agent / Writing Agent
                                                  ↓（通过 MCP 调用工具）
                                       搜索、数据库、文件系统

意义：A2A + MCP 构成了 AI Agent 的完整协议栈，类比 HTTP（应用层）+ TCP（传输层）。

68. A2A 和 MCP 的区别是什么？什么时候真的需要多智能体？ ｜高频 ｜中等 ｜腾讯一面

答案： MCP 更关注"模型和外部能力怎么接"，A2A 更关注"Agent 和 Agent 之间怎么协作"。

维度 MCP A2A
通信对象 Agent ↔ Tool（工具） Agent ↔ Agent（智能体）
通信方向 Agent 主动调用工具 Agent 委托另一个 Agent
标准化内容 工具 schema、资源接口 Agent 发现、任务委托、结果返回
发起方 Anthropic（现 LF/AAIF） Google（现 LF/AAIF）
抽象层次 能力接入层 代理协作层

❌ 更正：原表里"发起方"这一行出现了两次，实际第一行内容应为"通信方向"（主动调用 vs 委托），第二行才是协议发起方（MCP=Anthropic，A2A=Google）。上表已改正。

什么时候需要多智能体：如果系统只是需要接搜索、数据库、文件系统，MCP 的价值更明显；只有已经演化出多个角色明确、职责分离的 Agent（规划、检索、执行、审阅各自独立），A2A 或多智能体编排才有意义。多智能体不是越早越好：单 Agent 能清晰处理时，多智能体只会增加通信、调试和治理成本。拆分划算的信号：职责边界清晰、单 Agent 的 prompt 已经过载、流程确实需要角色分治（见第 87-89 题）。

追问：Supervisor 和 Handoff 怎么选？（见第 89、92 题） ｜ 多智能体最常见的失败点？（目标漂移、死循环互等、上下文不一致、错误传播、成本膨胀） ｜ A2A 与 LangGraph 这类应用内编排框架的边界？（LangGraph 管一个应用内部的图与状态，A2A 管跳应用/跳厂商的委托，两者不重叠）

69. 什么是 Agent Skills / SKILL.md？为什么说它是 2026 年的新标准？ ｜必刷 ｜基础 ｜2026 新增

答案： Agent Skills 是 Anthropic 于 2025-12-18 发布的开放标准（agentskills.io），用可移植的文件目录把"领域知识 + 操作规程"交给 Agent。

一个 Skill 就是一个目录，核心是 SKILL.md：

---
name: pdf-form-fill
description: 用于读取 PDF 表单并填写字段。当用户要求“填表/提交表单”时使用；仅阅读合同时不要用。
---

正文工作流：1) 先提取字段清单 → 2) 向用户确认 → 3) 写入表单 → 4) 导出并校验

目录可附带 scripts/（可执行脚本）、references/（长文档按需加载）、assets/（模板与素材）。

最关键的设计是渐进式披露（progressive disclosure），分三层加载：

层级 加载内容 成本
L1 元数据 name + description（frontmatter，description 上限 1024 字符） 常驻，极小
L2 正文 SKILL.md 全文 被触发时才读
L3 附属 scripts / references / assets 真正需要时才读或执行

这正好回应了上下文工程的核心矛盾：知识想常驻但窗口不够（见第 13 题）。description 写得好不好直接决定"该用时不被错过、不该用时不被误触"，写法与工具描述同源。

为什么是"新标准"：已被 40+ 客户端采纳（GitHub Copilot、VS Code、Cursor、OpenAI Codex、Gemini CLI、Goose、OpenCode、Roo Code、Amp、Factory、Kiro、Mistral Vibe、Spring AI、Databricks、Snowflake 等），anthropics/skills 仓库约 149k stars；2026 年又补上了企业管理员控制（集中分发/禁用/审计）与合作伙伴技能目录（Atlassian、Canva、Cloudflare、Figma、Notion、Ramp、Sentry）。

安全提醒：Skill 里可以带可执行脚本，也能指示 Agent 做什么，本质上是一个"能影响行为的代码包"——已出现恶意 skills 攻击现象，所以也要白名单 + 审计 + 版本锁定（对应 OWASP Agentic Skills Top 10，见第 65、107 题）。

追问：Skills 和 MCP 什么关系？（不冲突：MCP 管"外部能力接入"，Skills 管"流程知识注入"；一个 Skill 可以调用 MCP 工具） ｜ 和 AGENTS.md / rules 文件的区别？（AGENTS.md 是全仓常驻，Skills 是按需加载的能力包）

70. Skill、Tool、独立 Agent 的边界在哪里？什么时候该拆成 Skill 而不是再开一个 Agent？ ｜高频 ｜较难 ｜2026 新增

答案： 三者是不同粒度的能力封装：

Tool Skill Agent
本质 一个可调用函数 一段可复用的操作规程/知识 一个有自主循环的执行体
谁控制执行 宿主代码 模型按文档执行 模型自己规划与决策
状态 无（单次调用） 无自主状态（寄生于宿主 Agent） 有（自己的上下文与任务状态）
上下文成本 一段 schema 按需加载（渐进式） 独立窗口，只回传摘要
适合 确定性的原子动作 固定套路的领域流程 开放目标、多步探索

决策口诀：

  • 能写成一个函数的，不要做成 Skill（Skill 不会增加新能力，只是把行为知识化）；
  • 流程可预测、只需套 SOP 的，用 Skill（比拆一个 Agent 便宜：没有额外推理循环、没有跨 Agent 传递损耗）；
  • 子任务高噪音、需要独立探索、会撑爆主上下文的，才拆子 Agent（见第 97 题）。

换句话说：Skill 解决"怎么做才对"，子 Agent 解决"在哪里想"。 2026 年的普遍教训是多 Agent 滥用：拆 Agent 带来通信成本、一致性难题和调试黑盒，而很多场景用一个带完整 SOP 的 Skill 就能解决。

七、框架与编排：LangChain / LangGraph / Deep Agents

71. 用一句话说清 LangChain、LangGraph、Deep Agents 的关系，并给出选型依据。 ｜必刷 ｜中等

答案： 三者是分层依赖而非竞争关系：

  • LangChain：组件层——ChatModel、Tool、Prompt、Retriever、OutputParser 的统一抽象，LCEL 做线性编排；
  • LangGraph：编排层——在 LangChain 组件之上提供有状态的图（State/Node/Edge），解决循环、分支、持久化、人机协同；
  • Deep Agents：应用层——基于 LangGraph 预置了规划（todo）、子代理、虚拟文件系统、长短期记忆的"深度智能体"模板。

选型依据：

任务特征 选择
单次调用 / 固定线性 RAG LCEL 或裸 SDK（OpenAI / Anthropic）
简单 ReAct 单 Agent LangChain create_agent
流程可画出确定流程图、需审批/回放/多 Agent LangGraph StateGraph
多角色对话协作、研究型分工 AutoGen / CrewAI（或 LangGraph Supervisor）
只能描述目标、路径靠 Agent 自主探索的长任务 Deep Agents

核心判断：固定流程用图，开放目标用深度智能体，线性任务别上框架。

72. LangChain 在今天的价值是什么？为什么不是直接手写 SDK 就够了？ ｜高频 ｜中等

答案： LangChain 的价值不在于"能不能调模型"，而在于把模型输入输出、Prompt、Parser、Retriever、Tools、Memory、Callbacks 等常见能力统一成了一套可组合接口。

如果只做一个最小 Demo，手写 SDK 当然可以。但一旦进入多模型接入、链式编排、结构化输出、可观测和长期维护阶段，统一抽象会明显降低代码分散度。它真正解决的是"应用层编排和生态整合"问题，而不是"替你发一个 HTTP 请求"。

也要诚实说出它的代价：抽象层带来调试成本（报错看不到底层）、版本迭代快（旧 API 大量废弃）、容易诱导新手把简单问题复杂化。所以"什么时候不用 LangChain"也是合格答案：需求单一、厂商固定、流程线性时，直接裸 SDK 更便宜。

73. 各类 Agent 开发框架应该如何选取？ ｜高频 ｜中等

答案： 框架选型不看热度，看任务复杂度、团队能力、交付要求：

目标 选择
快速原型、生态丰富、常见组件齐全 LangChain
显式状态、循环、条件路由、人机协同、多智能体 LangGraph
低代码、快速验证业务流程 Coze / Dify
系统边界简单、需求非常明确 直接手写 SDK
多角色对话协作 AutoGen / CrewAI / MAF
绑定某家模型生态且要轻 各家官方 SDK（见第 91 题）

成熟的回答不是简比较"哪个最好"，而是说明"什么场景下用什么更划算"，并能给出替代方案和迁移路径：能说出指标（交付周期、可观测粒度、故障定位成本、人员上手时间）比能背名字更值钱。

追问：用什么指标判断这次选型成功？（上线周期、故障定位时长、单位任务成本、回归覆盖率） ｜ 平台转代码框架的迁移边界？（把工具、检索、权限抽成独立服务，只换编排层）

74. LangChain 1.0 / LangGraph 1.0 之后有哪些重要的 API 变化？ ｜必刷 ｜中等 ｜2026 更新

答案： 关键节点：LangChain 1.0.0 与 LangGraph 1.0.0 于 2025-10-17 同日发布（PyPI 可验证），之后 1.0.1（10-20）→ 1.1.0（2025-11-24）→ 1.3.x（2026-08），仓库描述改为 "The agent engineering platform"。主要变化：

  • 模型按 provider 分包：from langchain_openai import ChatOpenAI，旧的 langchain.chat_models 入口废弃；
  • Agent 统一为 create_agent：from langchain.agents import create_agent；旧的 initialize_agent、AgentExecutor、各堆 AgentType 枚举全部废弃；
  • 中间件（middleware）体系：1.0 把 Agent 循环开放为可钩入点（before_model / after_model / wrap_tool_call 等），用于上下文压缩、护栏、人工审批，而不必自己重画图；
  • 高层快捷 API：init_chat_model("openai:gpt-5") 按 "provider:model" 字符串实例化，便于切换厂商；
  • 消息与状态：消息类型统一走 langchain_core.messages；状态更新走 LangGraph 的 reducer 机制（见第 80 题）；
  • LangGraph 1.1（2026-03）：类型安全增强、事件流、checkpoint 性能优化；
  • 可观测性：统一为 LangSmith v2 环境变量（LANGSMITH_TRACING=true，旧版为 LANGCHAIN_TRACING_V2）。

面试要点：能说出"Chain/AgentExecutor 那套老 API 已被 LCEL + LangGraph（以及 create_agent）取代"即可看出是否持续跟进版本。

75. 用 LangChain 开发一个 Agent，有哪两条路线？ ｜高频 ｜中等

答案：

  • classic 路线（理解原理用）：模型、工具、Prompt、create_tool_calling_agent(...)、AgentExecutor(...) 一层层组起来；
  • 1.x 路线（生产首选）：直接用 create_agent(...)，背后由基于 LangGraph 的运行时驱动循环、状态和工具调用，支持 middleware、checkpointer、HITL。

不管哪条路线，底层都是同一条主线：

  1. 先定义 Tools，把外部能力封成清晰的能力单元；
  2. 选择 LLM，并让模型知道可调用的工具 schema；
  3. 设计 Prompt，明确角色、工具使用规则、停止条件和输出边界；
  4. 形成"模型决策 → 工具执行 → 结果回传 → 继续或结束"的闭环。

面试里真正加分的不是背 API 名，而是能说清 Agent 为什么会调用工具、什么时候停、失败了怎么兜底（见第 47、51、103 题）。

76. LCEL 的 | 语法底层是什么？为什么它能免费获得流式/重试/并行？ ｜高频 ｜中等

答案： | 调用的是对象的 __or__，把每个 Runnable 串成 RunnableSequence。LangChain 的组件（prompt、llm、parser、retriever）都实现了统一的 Runnable 接口（invoke / stream / batch / ainvoke / astream）。

因为接口统一，序列就能把能力整条链透传：

  • .stream()：逐段向前后传播，最后一个组件边产边出；
  • .batch() / .abatch()：自动并发执行多条输入；
  • .with_retry()、.with_config()：包裹在任意 Runnable 外层，不侵入业务代码。
chain = (prompt | llm | StrOutputParser()).with_retry(
    stop_after_attempt=3, wait_exponential_jitter=True
)

它的价值不只是写法短，而是让顺序链、分支链、并行链、函数链能用同一种接口去拼装、调试和替换——做日志、流式、批处理、回调和局部替换时可维护性明显更好。

适用边界必须说清：LCEL 只擅长无环的线性/并行结构；一旦需要根据模型输出循环或回跳到前面节点，LCEL 表达不了，必须用 LangGraph（见第 78 题）。

77. 怎么做模型分级路由（省成本）？ ｜高频 ｜中等

答案： 用 LCEL 的 RunnableBranch 按输入特征选择不同模型：

from langchain_core.runnables import RunnableBranch, RunnableLambda

mini = ChatOpenAI(model="gpt-5-mini")
pro  = ChatOpenAI(model="gpt-5")

def is_complex(msg: dict) -> bool:
    return any(k in msg["question"] for k in ("架构", "排查", "多步", "权衡"))

router = RunnableBranch(
    (is_complex, pro),
    mini,                       # 默认分支
)
chain = RunnableLambda(lambda x: x) | router | StrOutputParser()

工程上还会配合：意图识别用小模型 + with_structured_output、子 Agent 强制用便宜模型、超长固定前缀开 prompt caching、对每一步记账设预算。

完整的路由三层设计（意图路由 / 复杂度路由 / 成本路由）见第 121 题，与意图识别的区别见第 112 题。

78. LangGraph 相比普通 Workflow 或链式调用，最大的价值是什么？ ｜必刷 ｜中等

答案： LangGraph 最大的价值是把复杂流程中的状态、节点、边和循环显式表达出来，让大模型驱动的动态流程真正可设计、可追踪、可恢复。

普通链式调用适合简单串行，Workflow 适合固定路径，而 LangGraph 更适合：分支、循环、人工中断、状态持久化、多 Agent 协作。它不是"换一种写法"，而是把复杂控制流从隐式逻辑变成显式图结构。

当你发现系统开始出现这些问题时，LangGraph 的优势就出来了：要不要继续查？什么时候结束？失败后从哪里恢复？状态怎么跳轮保留？

代价也要说：图本身有学习曲线和维护成本，节点粒度拆不好会变成"什么都塞一个节点"的黑盒；简单线性任务用它属于过度设计（见第 71、73 题）。

79. LangGraph 里 State、Node、Edge 分别代表什么？ ｜高频 ｜基础

答案： State 是共享状态，Node 是处理逻辑，Edge 是流转规则。

  • State 决定图里"大家共同操作的上下文"是什么（TypedDict / Pydantic + reducer）；
  • Node 决定每一步具体做什么（调模型、查库、执行工具），本质是 (state) → state_update 的函数；
  • Edge 决定执行完当前节点后去哪里，可以是固定边（add_edge）或条件路由（add_conditional_edges）。

真实项目里，LangGraph 设计得好不好，往往取决于 State 是否清晰、Node 粒度是否合理、Edge 条件是否可解释。很多图写得难维护，不是因为图本身复杂，而是把太多隐式逻辑塞进了一个节点。

80. 现场手写 StateGraph 版 ReAct，并解释 reducer 的作用。 ｜必刷 ｜中等

答案：

from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode, tools_condition

class State(TypedDict):
    messages: Annotated[list, add_messages]

llm_tools = ChatOpenAI(model="gpt-5-mini").bind_tools([get_weather])

def chat(state: State):
    return {"messages": [llm_tools.invoke(state["messages"])]}

g = StateGraph(State)
g.add_node("chat", chat)
g.add_node("tools", ToolNode([get_weather]))
g.add_edge(START, "chat")
g.add_conditional_edges("chat", tools_condition)   # 有 tool_calls→tools，否则→END
g.add_edge("tools", "chat")
app = g.compile()

reducer 是高频考点：节点返回的是"对 state 的更新"而不是整个新状态。Annotated[list, add_messages] 声明该字段用 add_messages 做追加合并（并按消息 id 去重/更新），而不是默认的整体覆盖。若不写 reducer，第二个节点返回 {"messages": [...]} 会把整个列表替换掉，历史丢失。自定义场景常用 operator.add（列表拼接）或自己写 reducer 函数（如取最大值、合并 dict）。

加分点：并行分支同时更新同一个 key 时，必须有 reducer，否则报 InvalidUpdateError；这就是 LangGraph 把"并发写入语义"显式化的地方。

81. 条件边怎么写？tools_condition 内部判断逻辑是什么？ ｜高频 ｜基础

答案： 条件边接收一个返回"下一节点名"的路由函数：

def route(state: State) -> str:
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"
    return END

g.add_conditional_edges("chat", route, {"tools": "tools", END: END})

tools_condition 就是这个逻辑的预置版：检查最后一条 AIMessage 是否带非空 tool_calls，有则路由到工具节点名（默认 "tools"），否则路由到 END。

注意第三个参数是返回值 → 真实节点名的映射，重命名节点时必须同步改映射（否则会出现"路由函数返了 tools 但图里没有这个节点"的经典型报错）。路由函数也可以返回列表，实现并行扇出（fan-out）。

82. Checkpointer 解决什么问题？写一段"跨次请求保持记忆 + 恢复执行"的代码。 ｜必刷 ｜中等

答案： Checkpointer 在每个**超步（super-step）**后把 state 快照持久化，带来三个能力：同 thread 多轮记忆、进程重启后续跑、历史回放与分叉（time travel）。

from langgraph.checkpoint.memory import InMemorySaver  # 生产换 PostgresSaver

app = g.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "user-123"}}

app.invoke({"messages": [("user", "查 ORD-12345678")]}, cfg)
app.invoke({"messages": [("user", "它现在到哪了")]}, cfg)  # 自动带历史

snapshot = app.get_state(cfg)             # 当前状态快照
for hist in app.get_state_history(cfg):   # 全部历史，可回到任意步分叉
    ...

要点：

  • thread_id 是会话隔离键，一个会话一个 thread（多用户场景下这同时是安全边界，必须服务端生成、不能信客户端传入）；
  • 内存版只用于开发，生产必须用 Postgres/Redis 等持久实现，否则重启即失忆；
  • 恢复执行用 invoke(None, cfg)（见第 101 题）；
  • Checkpointer（thread 内） vs Store（跨 thread）：前者是会话级快照，后者是长期记忆（见第 43、44 题）。

追问：checkpoint 会不会涨得很大？（会，消息列表不压缩时线性增长；需要配清理/摘要策略，见第 44 题）

83. 什么是 Human-in-the-Loop？现场编码：给"退款"这类写操作加人工审批。 ｜必刷 ｜中等

答案： HITL 是在 Agent 工作流中加入人工干预的机制：关键决策节点暂停、等待人工确认后再继续；防止 Agent 执行高风险操作（删数据、退款、发邮件），也支持人工修正中间输出或补信息。LangGraph 用 interrupt 原生实现。

from langgraph.types import interrupt, Command
from langchain_core.messages import AIMessage

def refund_node(state: State):
    payload = {"order_id": "ORD-12345678", "amount": 299.0}
    decision = interrupt({"ask": "确认退款 ¥299？", "payload": payload})
    if decision == "approve":
        apply_refund.invoke(payload)
        return {"messages": [AIMessage("退款已提交")]}
    return {"messages": [AIMessage("已取消退款")]}

调用方两次调用：

app.invoke(inputs, cfg)                       # 在 interrupt 处暂停，state 已落盘
app.invoke(Command(resume="approve"), cfg)    # 人工审批后恢复

关键区分（常追问）：让模型"先问一句用户"只是生成文本，请求结束状态即丢；interrupt 是真正暂停图执行并持久化，可以隔数小时、跨进程重启后用 Command(resume=...) 精确恢复。典型场景：高风险写操作、补信息、等待外部回调。

工程细节：恢复时传入的可以是字符串，也可以是 dict（Command(resume={"approved": True, "operator": "zhang"})）；审批请求要落库（带超时与升级链路），否则 interrupt 会无限挂起；审批人看到的 payload 要包含可决策的信息（金额、用户、历史相似案例）。

84. LangGraph 的流式有哪几种 stream_mode？分别用在什么场景？ ｜高频 ｜中等

答案：

stream_mode 产出 场景
values 每个节点后的完整 state 调试、要看全局最新状态
updates 每个节点本次的增量更新 最常用，前端展示"当前执行到哪步/在干什么"
messages LLM 的 token 级分片 + 元数据 聊天打字机效果
custom 节点内主动推送的业务进度 "正在检索知识库"类自定义事件
debug 含检查点/任务调度的详细事件 深度排错

可传列表同时订阅多种：stream_mode=["updates", "messages"]，配合异步 SSE/WebSocket 推给前端。

LangGraph 的流式不只是"模型 token 一点点吐出来"，更重要的是把整张图的执行过程流出来——这是它比单纯 SDK 流式更好用的地方（对应第 85 题的"可观察"）。

85. LangGraph 的进阶特性里，最有工程价值的是哪四类？ ｜中频 ｜较难

答案： 流式处理、持久化、时间回溯、子图——四句口诀：流式解决可观察，持久化解决可恢复，时间回溯解决可复盘，子图解决可维护。

  • 流式：五种 stream_mode（见第 84 题）；
  • 持久化：checkpointer 是线程内、会话内的短期记忆，按 thread_id 保存图状态，用于断点恢复、人机协同、多轮任务承接；跨线程跨会话的长期信息走 Store；
  • 时间回溯（Time-Travel）：get_state_history + 从任意 checkpoint 分叉重跑。排障价值极大：很多复杂 Agent 不是最后结果错了，而是中间某一步状态被污染了；
  • 子图（Subgraphs）：把"检索子图""审批子图""报告生成子图"独立封装，主图只做更高层编排；好处是复用、隔离命名空间、团队并行开发；注意父子图的 state key 要显式映射，子图自己的 checkpointer 会形成嵌套 checkpoint。

四个一起上，LangGraph 才真正像生产基础设施，而不只是一个能跑通的 Demo 图。

86. Checkpoint、HITL、Time-Travel 在面试里怎么讲得更工程化？ ｜中频 ｜较难

答案： 这三个概念适合放在一起讲，因为它们共同解决的问题是：复杂 Agent 不是"能跑起来"就够了，还要能停、能看、能批、能继续。

能力 一句话定位
Checkpoint 负责可恢复：长任务、断点续跑、失败重放
HITL 负责可控制：支付、删改数据、对外发送前的确认权
Time-Travel 负责可复盘：排障、调试、重跑特定阶段

这三个能力放在一起，面试官通常会感觉你理解的不是"图会不会画"，而是"系统上线以后怎么治理"。

追问：哪些节点一定会加人工审批？（不可逆副作用：退款/下单/删数据/对外发消息/改权限；以及低置信度的高风险判断） ｜ 什么时候时间回溯从调试利器变成生产必需？（需要事故回溯与合规审计、需要 A/B 重放同一起点、需要"修正某一步后继续跑"的业务流程时）

87. 什么是多智能体系统？它的真实价值是什么？ ｜高频 ｜基础

答案： 多智能体系统由多个 AI Agent 组成，每个有独立角色和职责，通过协作完成复杂任务：

  • 分工：每个 Agent 专注特定任务（规划、编码、测试、审查）；
  • 并行：同时处理不同子任务，提升效率；
  • 检验：一个 Agent 验证另一个的输出，减少错误；
  • 上下文隔离（最重要的一个）：每个子任务有自己的窗口，不被主线噪声干扰（见第 97 题）。

但要记住反面："单 Agent + 多工具够用，就不要上多 Agent"。拆分的三个划算信号：职责边界清晰、单 Agent 的 prompt 已经过载、流程确实需要角色分治（见第 68 题）。

88. 多智能体有哪些架构模式？通信如何实现？ ｜高频 ｜中等

答案： 架构模式：

  • Supervisor（监督者）：一个主 Agent 负责协调分配任务给子 Agent；
  • Network / Peer-to-Peer：Agent 之间直接通信，无中心节点；
  • Pipeline（流水线）：串行执行，上一个输出是下一个输入；
  • Hierarchical（层级）：树形结构，高层 Agent 管理低层 Agent；
  • Swarm / Handoff：无固定主管，当前 Agent 把控制权交给下一个（OpenAI Agents SDK 模式，见第 92 题）。

通信方式：

方式 实现
消息传递 结构化消息（JSON）、A2A（跨应用）
共享状态 共享 State / 数据库（LangGraph 同图内首选）
工具调用 一个 Agent 以"工具"形式调用另一个 Agent（最简单、最可控）
事件驱动 消息队列（Kafka、RabbitMQ）异步通信

选型建议：能用"Agent 当工具"就不要上自由对话——工具式调用天然有入参出参 schema、可超时、可重试、可观测；而"多个 Agent 在一个共享消息列表里聊天"最难治理。

89. Supervisor 模式怎么实现？为什么默认不推荐 Network 模式？ ｜高频 ｜中等

答案：

from langgraph_supervisor import create_supervisor

sup = create_supervisor(
    agents=[researcher_agent, writer_agent],
    model=ChatOpenAI(model="gpt-5"),
    prompt="你是主管，把任务分给调研员/写作者，全部完成后回复 FINISH。",
).compile(checkpointer=InMemorySaver())

主管 Agent 每轮决定"派给谁或结束"，子 Agent 作为被调度的节点，上下文由主管统一管理。

不默认用去中心化 Network 的原因：Agent 互相喊话会形成不可控的调用图——容易互相等待/死循环、token 与延迟随对话轮次膨胀、出错时难以定位是哪个 Agent 的决策、状态一致性难保证。只有确实需要对等协商且能接受这些代价时才用。

Supervisor 自己的坑也要说：主管成为瓶颈与单点（它误判则全盘错）、主管上下文容易被子 Agent 回传的长结果撑爆（所以只收摘要，见第 97 题）、多轮仲裁时任务目标漂移。应对：主管只做路由不写内容、子 Agent 输出强制 schema、给主管的上下文加预算与压缩、冲突时固定仲裁规则（优先级/人工）。

追问：子 Agent 冲突仲裁怎么做？（确定性规则优先，如"写操作以审阅意见为准、事实以检索为准"；仍冲突则升级人工）

90. AutoGen 和 CrewAI 分别是什么？现在该怎么选？ ｜高频 ｜中等

答案： AutoGen（微软）专注多智能体对话协作：每个 Agent 有独立角色（Planner / Coder / Reviewer），通过消息传递协作，支持人机混合。

CrewAI 是基于角色的多智能体框架，用"船员"比喻分工：Agent（role / goal / backstory）、Task（分给某 Agent 的任务）、Crew（编排器）、Process（顺序或层级执行）。

与 LangChain 系的区别：LangChain/LangGraph 更侧重工作流编排和工具调用、可控性强；AutoGen / CrewAI 更侧重多 Agent 角色扮演与对话协作，适合"研究员 + 写作者 + 审核员"这类专业化分工。

⚠️ 选型必读（截至 2026-10）：AutoGen v0.4 已于 2025-01 完全重写（改为异步事件驱动的 Actor 模型，分层 autogen-core / autogen-agentchat / autogen-ext，内置 OpenTelemetry，支持 Python + .NET）；2025-10 微软宣布 Microsoft Agent Framework（MAF，合并 AutoGen + Semantic Kernel），其 1.0 于 2026-04-03 发布，AutoGen 随后进入维护模式。因此：新项目选型应评估 MAF，而不是直接上手旧 AutoGen API；CrewAI 仍是独立活跃项目，上手快、适合角色化内容任务，但细粒度控制和持久化不如 LangGraph。

追问：什么时候用 CrewAI 而不是 LangGraph？（任务本质是"几个固定角色接力产出内容"且过控要求不高时用 CrewAI；需要审批、回放、强状态管控时用 LangGraph）

92. 什么是 OpenAI Agents SDK？ ｜中频 ｜基础

答案： 2025-03 发布、由 Swarm 演变而来的轻量 Agent 框架，四个核心概念：

  • Agent：有 instructions（角色描述）和 tools（工具列表）的 LLM 执行单元；
  • Handoff（移交）：一个 Agent 把任务移交给另一个更专业的 Agent（去中心化路由）；
  • Guardrails（护栏）：对输入/输出做验证的过滤器（可并行运行、触发则中断）；
  • Runner：协调 Agent 执行循环的调度器。
from openai import OpenAI
from agents import Agent, Runner, tool

@tool
def get_weather(city: str) -> str:
    return f"{city} 今天晴天，25°C"

weather_agent = Agent(
    name="天气助手",
    instructions="你是一个天气查询助手，帮用户查询城市天气。",
    tools=[get_weather],
)

result = Runner.run_sync(weather_agent, "北京今天天气怎么样？")
print(result.final_output)

与 LangChain 的区别：Agents SDK 更轻、官方支持、原生 Handoff，学习曲线低；LangChain/LangGraph 生态更广、跳厂商，持久化与人机协同更成熟（Handoff vs Supervisor 的选择见第 89、68 题）。

93. OpenAI Responses API 与 Chat Completions、Assistants API 是什么关系？ ｜中频 ｜中等

94. 什么是 Google ADK？ ｜中频 ｜基础

答案： Google 于 2025-04 发布的开源 Agent 框架，专为构建可互操作的 Agent 设计：

  • 多 Agent 编排：原生支持层级化多 Agent 系统（agent tree）；
  • A2A 原生集成：内置 Agent2Agent 协议支持（见第 67 题）；

  • 事件驱动：基于事件流的执行模型，天然支持流式；
  • 另有组件化工具（函数/检索/代码执行）、内置评估与开发 UI；ADK 2.0 进一步强调 harness 能力（见第 14 题）。

部署选项：Google Agent Engine、Cloud Run、GKE（也可本地跑）。与 LangGraph 对比：ADK 更紧密集成 Google 生态（Gemini、Vertex AI），LangGraph 更通用、更成熟。

95. Claude Agent SDK 和"harness"是什么关系？ ｜高频 ｜较难 ｜2026 新增

答案： Claude Agent SDK（2025-09-29 随 Sonnet 4.5 发布）与 Claude Code 同一套栈，可以把它理解成"把 Claude Code 的 harness 开放给你编程使用"：

  • agent loop：内置的"收集上下文 → 行动 → 验证"循环，不用自己写 while；
  • 工具与权限系统：工具级 allow/deny/ask 规则、hook（PreToolUse / PostToolUse 等）可在工具执行前后做硬拦截——这是把第 106、107 题的安全要求落到代码层的地方；
  • 子代理（subagents）：独立上下文，只回传摘要（见第 97 题）；
  • Skills / AGENTS.md / MCP：渐进式能力加载（见第 69 题）；
  • 上下文管理与 compaction：接近窗口限制时自动压缩；
  • 文件系统与 bash 作为通用工具：不靠几十个专用工具，而靠"读文件 + 写文件 + 执行命令"三个通用能力覆盖大多数任务。

面试里能讲出的关键点：它的默认设计哲学就是"harness-first"——把模型能力包在一个可控、可审计、可否决的执行壳里。这也解释了为什么 2026 年大家开始用"Model + Harness"而不是"Model + Prompt"来描述 Agent。

追问：和 LangGraph 怎么选？（Claude Agent SDK 开箱即用但绑 Anthropic 生态、图控制粒度不如 LangGraph；LangGraph 跳厂商、流程更显式但要自己搭护栏）

96. Deep Agents 内置了什么？现场写一个研究型深度智能体。 ｜必刷 ｜中等

答案： 内置四件套，免去自己在 LangGraph 里手搓：

  1. 规划：todo 清单工具，自主拆解并维护任务状态；
  2. 子代理（Subagents）：在隔离上下文中执行子任务，只回传摘要；
  3. 虚拟文件系统：跳步骤沉淀中间产物（草稿、数据、代码）；
  4. 分层记忆：thread 内短期记忆 + 跨 thread 的长期 Store。

2026 年的演进（能说出一两条就是跟进过）：v0.4（2026-02-10）集成沙箱执行包（不在宿主直接跑代码）、2026-03 自主上下文压缩（agent 自己决定何时写文件/压缩）；中间件体系包 MemoryMiddleware / SkillsMiddleware / SubAgent，权限模型 FilesystemPermission。

追问：四件套分别对应哪个工程问题？（规划→目标不漂移；子代理→上下文隔离；文件→中间产物不进窗口；记忆→长任务续做与个性化）

97. 子代理为什么能"节省主上下文"？什么时候该用？Deep Agents 与裸 LangGraph 的代价分别是什么？ ｜高频 ｜较难

答案： 为什么省上下文：上下文窗口是稀缺资源，长上下文会稀释注意力、增加成本（见第 13、30 题）。子代理在独立上下文里完成高噪音工作（浏览几十个网页、跑若干 SQL、读多个文件），只把最终结论/摘要交回主 Agent，主上下文不被海量原始 observation 撑爆。这就是上下文工程里的 isolate。

什么时候用：子任务会产生大量中间内容、且与主线决策弱相关。不适用：子任务结果就是最终答案主体、或需要与主流程反复细粒度交互——隔离反而丢信息。

两条路线的代价对比：

裸 StateGraph Deep Agents
开发量 大，每个节点/分支都要自己设计 小，开箱即用
可控性 最强，可审计、可给 SLA 路径不确定，难给强时效保证
token 成本 可控 高（规划 + 多子代理 + 文件操作）
适合 企业交易流程、合规链路 研究型、开放式长任务

决策口诀："人能画出确定流程图"用 LangGraph；"只能描述清楚目标"用 Deep Agents。 涉及钱、合规、不可逆操作的核心链路不应交给纯自主探索，应在 LangGraph 中显式约束并加 interrupt（见第 83 题）。

八、平台与系统集成

98. Coze / Dify 这类平台和 LangChain / LangGraph 的关系怎么理解？ ｜高频 ｜中等

答案： Coze / Dify 更偏应用层、低代码和可视化交付，LangChain / LangGraph 更偏代码级开发框架。它们不是谁替代谁，而是同一条 AI 应用链路上的不同层级：

  • Dify / Coze：快速把 Agent、RAG、Workflow 搭起来，方便业务侧验证、协作和交付；
  • LangChain：把 Prompt、Model I/O、Parser、Retriever、Tools 按代码方式组合；
  • LangGraph：状态显式、循环、条件路由、人机协同、多智能体等复杂编排。

真实项目里很常见的路径：先用平台验证业务价值，再把核心链路迁到代码框架；或者平台负责上层业务编排，底层复杂能力由自建服务承接。

追问：什么时候必须从平台出来？（需要自定义状态机/审批链、权限与企业系统深度耦合、评测与回滚需可控、流量上来后平台成本或延迟不可接受）

99. 用 Python 调用 Dify / Coze 工作流时，最值得关注哪些工程细节？ ｜中频 ｜中等

答案： 五类问题：鉴权、参数对齐、流式模式、超时限制、日志追踪。

Dify 工作流 API 重点字段：

  • Authorization: Bearer {api_key}；请求体的 inputs、response_mode、user。

两个极易踩坑的点：一是 API Key 和工作流是绑定关系，不是拿一个全局 key 到处用；二是长流程尽量用 streaming，因为 blocking 很容易被网关超时打断。做流式时，要能识别 SSE 流里的 workflow_finished 事件，并正确拿到最终 outputs。

Coze 要盯紧：workflow_id、app_id、parameters。其中 parameters 必须和工作流里定义的输入变量严格对齐——变量名一旦对不上，代码看起来能跑、请求也可能成功，但业务结果就是不对。流式处理时要能区分 PING / MESSAGE / DONE（或 SDK 里的 MESSAGE / ERROR / INTERRUPT 事件）。

工程总结清单：

  • 密钥、工作流、应用的绑定关系是否搞清楚；
  • 请求参数名是否和平台工作流输入严格一致；
  • 是不是默认用流式，而不是把长任务都压成阻塞式；
  • 平台日志、workflow_run_id、业务 request_id 是否串起来了；
  • 流程里有外部副作用时，是否做了幂等、重试和失败补偿（见第 104 题）。

这道题真正考察的不是"会不会发 POST 请求"，而是是否真正理解过平台 API 的真实调用链。

100. 团队已有 Java/Node 技术栈，引入 Python 写 Agent 如何与主系统集成？ ｜中频 ｜中等

答案： 不要为了用框架把业务搬进 Python，采用边界化集成：

  • 把 Agent 做成独立服务（FastAPI / LangGraph Platform），主系统通过 HTTP/SSE 或消息队列调用，按会话传 thread_id；
  • Agent 需要的业务能力（查单、退款）由主系统以工具 API / MCP Server 暴露，Agent 侧只做编排，不直连核心数据库；
  • 鉴权、限流、审计放在 API 网关层统一处理；
  • JS/TS 团队也可评估 LangChain.js / LangGraph.js，核心概念（Runnable、StateGraph、checkpointer）一一对应，减少语言切换成本；
  • 工具协议尽量走 MCP 标准化，使同一套工具能被不同语言、不同 Agent 复用（呼应第 149 题的"自研 MCP 与成熟框架相比的扩展性优势"）。

追问：跨语言调用的超时与重试怎么设计？（主系统只管入队 + 幂等键，Agent 侧自己控制循环预算，结果异步回调；避免上游超时重试导致下游重复执行副作用）

九、可靠性、安全与治理

101. Agent 跑到一半报 429 / 超时，如何保证不丢上下文？ ｜必刷 ｜中等

答案： 关键认知：重试的单位是"一次 LLM 调用"，而状态都在 messages/state 里。

  • 对模型调用加指数退避 + 抖动的重试（with_retry），读 retry-after；超阈值（如 5 分钟，配额耗尽）快速失败而非死等；
  • 重试时携带完整 messages，模型能基于已执行的工具结果从断点继续；
  • LangGraph 里还有双保险：checkpointer 已把每步落盘，即使进程崩溃，用同 thread_id 重新 invoke(None, cfg) 即可从最后一个完成的超步恢复（见第 82 题）。

两个补充：工具调用的重试要区分"幂等读"与"非幂等写"（见第 104 题）；如果失败源于上下文过长（而非限流），重试再多次也没用，要先压缩。

追问：429 和 5xx 的处理差异？（429 看 retry-after 并降并发；5xx 短退避重试后降级） ｜ 配额耗尽怎么办？（降级到备用模型/缓存/规则链路，并把任务入队延后执行）

102. 如何防止 Agent 失控（死循环 / 烧钱 / 误操作）？ ｜必刷 ｜中等

答案： 一组组合拳：

  1. recursion_limit 限制图最大超步数（默认 25，按业务收紧）；
  2. 外层工具调用总预算、相同参数重复调用检测、整体超时；
  3. 工具结果截断、工具数量精简，控制每轮 token；
  4. 所有副作用写操作走 interrupt 人工确认（见第 83 题）；
  5. 模型分级路由 + 子 Agent 用小模型 + 固定前缀 prompt caching；
  6. LangSmith/Langfuse 全链路 tracing，按 run 统计 token 与耗时定位热点。

其他高频故障及对策：

问题 对策
幻觉（编造信息） 引入 RAG、增加验证步骤、要求引用出处（见第 110 题）
上下文丢失（多步后忘早期信息） checkpointer 持久化、压缩/摘要历史
工具滥用（调不必要的工具） 优化工具描述、精简工具集（见第 54 题）
成本失控 控制 context window、小模型路由、预算告警
目标漂移 目标写进结构化 state 并每步对齐；定期回到 todo 清单
重复执行副作用 幂等键 + 去重表（见第 104 题）

103. 如何设计 Agent 的完成判断与终止条件，避免过早结束？ ｜高频 ｜较难

答案： Agent 的"结束"不能只靠感觉，也不能只看日志或一个宽泛的完成率分数。更稳的做法是设计显式完成条件，拆四层：

层 判断内容
任务层 是否达成用户目标，是否拿到了必须的产物或字段
工具层 关键工具调用是否成功，返回结果是否满足预期约束
状态层 当前 state 是否进入 done / failed / need_human 这样的终态
保护层 最大步数、超时、重复无进展次数、异常退出条件

如果链路里有 Supervisor 或监督节点，更适合把它当"辅助审查"和"异常兜底"，而不是唯一的结束依据。真正稳的方案是：只有当关键任务结果、工具返回和状态机条件都满足时，才允许进入最终答复节点；否则宁可继续执行、澄清或转人工，也不要过早把未完成结果返回给用户。

只靠监督节点统计完成率和查日志为什么不行？（慢、主观、易误判，且难以自动化回归）

工程做法：给每类任务定义必须产物清单（字段级，可用 Pydantic 校验）＋验收规则（测试通过、引用存在、金额一致），把它当成图的出口条件而不是"模型说自己完成了"。

104. 长时间运行的 Agent 任务如何保证可靠性？ ｜高频 ｜较难 ｜2026 新增

答案： 长任务（数分钟到数小时）的核心敌人：进程崩溃、网络抖动、副作用重复执行、预算失控。

  1. Durable Execution（持久化执行）：工作流状态事件溯源、可回放恢复——Temporal / Restate / DBOS 是这一派代表；Vercel AI SDK 7 的 WorkflowAgent 提供同范式；LangGraph 用 Postgres checkpointer，崩溃后 invoke(None, cfg) 从最后超步恢复；
  2. 任务队列 + 异步化：请求只负责入队，结果通过 SSE / WebSocket / webhook 回推；
  3. 重试语义：指数退避 + 抖动重试瞬时错误；至少一次投递下用幂等键（idempotency key）/ 去重表保证副作用只生效一次；跨多步的写操作用**补偿事务（saga）**回滚；
  4. 预算护栏：recursion_limit、每工具调用次数与 token 预算、整体超时与熔断；
  5. 降级路径：超预算或连续失败后保存现场、转人工或发通知，而不是无限重试。

一句话：把"内存里跑的 agent 循环"当成"随时会崩溃的分布式系统"来设计。

追问：幂等键怎么生成？（业务主键 + 操作类型 + 参数哈希，存库唯一约束；重复提交返回首次结果） ｜ Agent 场景的 saga 长什么样？（记录已完成步骤的逆操作，失败时按逆序补偿；补偿也失败就告警开人工工单）

105. Agent Infra 要准备哪些东西？Runtime、Sandbox、Kubernetes 调度怎么设计？ ｜高频 ｜较难 ｜2026 新增

答案： 2026 面试里"Agent Infra"已经是一个单独考点——它不是"部署一个 Web 服务"，而是为一个会自己发请求、会执行代码、会长时间占住资源的循环体准备基础设施。

层 要解决的问题 典型做法
Runtime 执行循环放在哪里 常驻 worker（长循环、内存态） vs 每次 invocation（隔离好、冷启代价）；LangGraph Platform / Temporal / 自建 FastAPI + 队列
状态与持久化 会话状态、断点恢复 Postgres checkpointer + 对象存储存产物；Redis 做热会话与频控
Sandbox 代码/命令/浏览器的隔离执行 容器或 microVM（gVisor / Firecracker）+ 只读根 + 网络策略；会话级复用 vs 任务级创建（成本与安全的权衡）
调度 长任务不堵占 worker 异步任务队列 + 优先级；CPU/GPU 与模型推理资源独立调度；背压与超时传播
可观测 过程不可见 OTel GenAI + trace_id 贯穿模型/工具/检索（见第 116、117 题）
成本与配额 烧钱不可控 按用户/租户记账、预算熔断、语义缓存与 Prompt 缓存
模型接入 厂商锁定与故障 OpenAI-compatible 网关 + 多活降级 + 超时重试（见第 123 题）

K8s 上的三个实操点：Agent 是 I/O 密集 + 长连接，CPU limit 意义不大、要调并发与连接数；SSE 长连接要关闭入口代理缓冲并调大超时；Sandbox 用 Job / Pod-per-session 并配自动回收与网络策略（NetworkPolicy 默认 deny）。

追问：为什么要区分 Runtime 和 Sandbox？（Runtime 跑"决策与编排"，Sandbox 跑"不可信代码/命令"；合在一起时一旦模型被注入就是宿主机沦陷）

106. 多用户场景下，如何为 Agent 做安全沙箱隔离？ ｜高频 ｜较难

答案： 如果 Agent 只是单机 Demo，很多风险不会暴露；一旦进入多用户场景，安全隔离就必须从"工具权限"上升到"执行环境隔离"。三层方案：

层 措施
环境层 Docker 或其他容器把每个任务或租户隔离，限制 CPU、内存、网络和文件系统访问范围
系统层 seccomp、AppArmor、只读根目录、临时工作目录、非 root 用户运行，避免直接碰宿主机
应用层 对工具、文件访问、系统命令、外部连接做白名单和审计，不让模型拿到裸权限

如果要执行代码、命令或读文件，通常不会只靠 Prompt 或业务代码做限制，而是把工作目录挂成最小权限空间，敏感目录不挂载，数据库密钥和主机凭据也不进容器。

职责分工要讲清：MCP 或 Tool 负责"能不能调"，沙箱负责"即使调了也跑不出边界"，两者职责不同，最好一起上（对应第 63 题的追问）。另外要按会话隔离临时目录与缓存，避免跨会话数据泄漏。

追问：能执行命令的 Agent 怎么防它 rm -rf 或删数据库？（不靠提示词：非 root + 只读挂载 + 命令白名单 + seccomp 屏蔽系统调用 + 数据库账号只给 SELECT）

108. Prompt Injection 是什么？为什么 RAG / Agent 场景更要小心？ ｜必刷 ｜中等

答案： 本质上是：不可信输入试图改写系统指令、诱导模型越权，或者让 Agent 执行原本不该执行的动作。

它不只来自用户直接输入，也可能藏在网页、PDF、知识库文档、邮件、工具返回甚至图片里。只要这些内容会被模型读到，就可能形成间接注入——所以在 RAG、浏览器 Agent、代码解释器这类会读外部内容的系统里，风险明显更高。

五层防护：

  1. 指令分层：System 放稳定规则，User 和外部文档都视作不可信输入，不能和系统约束同权；
  2. 内容隔离：检索片段、网页内容、用户上传文档只当"待分析材料"，不要默认它们能发新指令（可用分隔符/标签包裹并声明"以下为数据"）；
  3. 工具权限：所有写操作、危险操作都走白名单、schema 校验和最小权限，不让模型拿裸能力；
  4. 动作校验：关键输出做规则校验，关键动作做确认、审批或 HITL，不让一句恶意文本直接触发副作用；
  5. 观测与兜底：记录注入样例、失败轨迹和异常调用，及时加入评测集和拦截规则。

这里有一句特别关键：RAG 不是安全层，知识库文档本身也可能带恶意指令。 只要把"检索到的内容"直接当成"可信提示词"，系统就很危险。

追问：文档里写着"忽略之前所有指令"怎么处理？（它只是文本内容，不执行；内容级过滤器 + 工具白名单 + 写操作人审；把它加入注入样本集） ｜ 浏览器 Agent 怎么防页面里的隐藏提示词？（白色字/元数据/alt 里的指令：只取可访问性树的可见文本与必要属性，长度截断与模式过滤，并默认不可信） ｜ 为什么微调和对齐不能从根上解决 Prompt Injection？（对齐降低概率但不提供硬保证；只要模型能读入自由文本，就无法把"内容"与"指令"完全分开；真正的隔离靠权限与执行边界）

109. 如何确保 Agent 的行为安全、可控且符合人类意图？ ｜高频 ｜较难

答案： 不能只寄希望于模型本身"够聪明"或"已经对齐过"。模型层的 SFT、RLHF / RLAIF 只能提供基础安全边界，真正落地到应用时必须补应用层治理：

层 措施
模型与提示层 System 明确角色、边界、安全规则和拒答策略
工具与权限层 不给模型裸权限；Tool 做 schema 约束、鉴权、参数校验、最小权限暴露
执行与流程层 最大步数、超时、人工审批、转人工、失败兜底
观测与审计层 调用日志、trace、输入输出、关键决策点、人工复盘链路

再补一层生产视角的预算与熔断：最大工具调用次数、时间预算、token 预算、费用预算；连续失败停止、异常率告警、重复无进展退出。它们的价值不只是省钱，更重要的是把"模型可能一直试下去"的风险收住。

一句话总结：模型对齐解决"基础行为别太离谱"，应用治理解决"在你的业务系统里别出事"。 真正稳的 Agent 一定是"模型能力 + 权限边界 + 流程控制 + 人机协同"一起做，而不是只靠某一层。

110. 什么是幻觉？应用层应该怎么缓解？ ｜高频 ｜中等

答案： 幻觉不只是"完全胡说八道"，更常见的是"看起来很像真的，但细节、引用、时间点、权限范围或工具结果已经偏了"。

因此不应把幻觉当成单纯模型问题，而应视为一条链路上的系统问题。四层缓解：

  1. 知识层：用 RAG、外部检索、引用和无依据拒答，尽量让模型基于证据回答；
  2. 执行层：把计算、查库、发消息、查订单交给 Tool，不让模型纯文本瞎编结果；
  3. 约束层：结构化输出、schema 校验、关键字段规则校验、低温度策略，减少"格式对了但内容错了"；
  4. 治理层：badcase 回灌、人工抽检、线上监控和降级，别把"模型大概率没问题"当上线条件。

总结：幻觉很难被彻底消灭，工程目标不是"保证永不出错"，而是让它可发现、可限制、可回滚、可复盘。

追问：RAG 为什么不能消灭幻觉？（检索不准/不全时模型仍会补全；即使有参考也会改写错数值与时间） ｜ 什么叫"有引用但依然不忠实"？（引了真存在的段落，但结论并不由它支持——所以不能只校"引用存在"，要校"结论与证据一致性"，见第 113 题） ｜ 幻觉和 Prompt Injection 是一回事吗？（不是：前者是无恶意的生成偏差，后者是恶意指令诱导；但都靠"证据 + 校验 + 审计"兜）

111. 排查"模型该调工具却直接瞎答"，你的排查顺序是什么？ ｜高频 ｜中等

答案： 七步，从描述到 trace：

  1. 看工具描述：是否说清了触发时机，名字是否直观；
  2. 看参数 schema：描述、示例、必填项是否完整，模型是否因不知怎么填参数而放弃；
  3. 看工具数量与冲突：是否太多、有无功能重叠导致选择困难；
  4. 看 system prompt：是否明确授权/鼓励使用工具，有无冲突指令（如"直接回答不要反问"会被理解为不要调工具）；
  5. 看模型能力：小模型 function calling 能力弱，换更强模型验证；
  6. 看上下文：决策所需信息是否已在历史里（已在上下文就不必调工具，这有时候是正确行为）；
  7. 用 LangSmith trace 确认模型实际收到的 tools 定义和返回的 tool_calls，定位是"没选工具"还是"选了但参数错/被代码拦截"。

排查心法：先确认 tools 真的发出去了（bind_tools 忘了调、或被另一个分支绕过），再看描述与 schema，最后才看模型本身（见第 150 题的分层排障展示）。

112. 意图识别 / 任务路由应该怎么做？ ｜高频 ｜较难

答案： 先强调：这题和"模型路由"不是一回事——模型路由回答"这次用大模型还是小模型"（见第 77、121 题），意图识别/任务路由回答"这次请求到底该走 FAQ、RAG、Tool、Agent、Workflow，还是直接转人工"。

三层设计：

  1. 目标分类：先定义清楚系统有哪些路由终点（闲聊、FAQ、知识问答、查状态、执行动作、复杂任务、人工兜底）；
  2. 路由机制：高确定性场景先用规则和关键词兜底，模糊场景再用分类模型或 LLM 做语义判断（小模型 + with_structured_output）；
  3. 置信度治理：低置信度不强判，允许澄清、降级或转人工，别让系统带着误判继续往下跑。

工程上不会做"单层万能路由器"，而是多级路由：先业务意图路由（FAQ / RAG / Tool / Agent）→ 再子域路由（客服里再分订单、退款、工单、投诉）→ 最后模型路由（强模型还是轻模型）。好处是更容易治理、也更容易评测。

评估重点：路由准确率、低置信度占比、误路由成本、澄清命中率，以及每条路由分支的最终任务完成率。

追问：什么时候规则路由就够了？（意图集合小、表达模式固定、误路由代价低时；新业务上线先规则兜底再逐类换成语义路由） ｜ 一个问题同时像 FAQ 又像 Tool 调用怎么办？（优先可执行路径，因为 Tool 返回的是事实态；或先澄清一句；关键是两边都能兜住不要硬判） ｜ 如何避免错误路由把后续链路全部带偏？（低置信度多路并发取交集、出口处做一致性回归判断、允许中途重路由）

十、评测与可观测性

113. 你会如何评估一个 RAG 或 Agent 系统的效果？ ｜必刷 ｜较难

答案： 先拆成离线评测和在线评测，再把问题拆到具体层级，而不是只盯一个总分。

RAG 两层看：

  • 检索层：相关内容有没有被召回、引用片段对不对、badcase 卡在切块、召回、重排还是过滤（指标：Recall@k、nDCG、命中率）；
  • 生成层：答案是否忠实于证据、引用是否正确、无依据时能不能拒答、最终回答对业务有没有帮助（指标：faithfulness、answer relevance、引用正确率）。

Agent 两类评测：

  • 轨迹级（trajectory）：有没有选对工具、参数对不对、有没有无效循环、是不是过早结束；
  • 结果级（outcome）：最终任务有没有完成，输出质量和用户体验是否达标。

（更完整的三层划分 outcome / trajectory / process 见第 115 题。）

在线评测看用户满意度、转人工率、任务中断率、耗时、badcase 类型分布；对 Agent 还要看工具调用成功率、重试率、循环次数和人工兜底比例。

自动评测不要只押一种：把规则评测、LLM-as-a-judge 和人工抽检结合起来——规则和 LLM 评测适合放大规模、做回归，人工抽检负责兜住高风险误判和评价漂移。常用框架：LangSmith、Langfuse、Ragas、TruLens、Braintrust、Arize Phoenix、DeepEval。

最重要的是评测不能只告诉你"分数变低了"，而要能定位到底是哪一层出问题：召回差、上下文组装差、生成幻觉、工具失败、终止条件不合理，这些问题的修法完全不同。

推荐的闭环：先分层建指标 → 再沉淀 badcase → 最后让 badcase 反过来驱动 Prompt、检索、工具和流程迭代。

追问：RAGAS 适合做什么？（无参考的 RAG 三层指标：faithfulness / answer relevance / context relevance，适合快速回归） ｜ badcase 数据集怎么建？（按失败类型分层采样、标注定位到层、只进不出、每次改 prompt/换模型必跑） ｜ LLM-as-Judge 怎么防止它自己不准？（用固定 rubric + 少量人工金标集校准 + 双模型交叉 + 警惕长度/位置/自家模型偏置）

114. Agent 怎么测试、回归？和传统单元测试有什么不同？ ｜高频 ｜中等

答案： 不同在LLM 输出不确定，所以不能直接用相等断言。四类做法：

  1. 节点纯函数化：LangGraph 节点是 (state) → state_update，对其用构造的 state 做确定性单测（这一层应占大部分测试量）；
  2. 工具层：mock 外部 API，单独测参数解析与返回处理；
  3. LLM 层不确定性：用两类手段——录制真实交互的**轨迹（trajectories）**做端到端回归，断言"调用了哪些工具、顺序、最终结果"；对语义判断用 LLM-as-Judge 打分而非精确匹配；
  4. 结构化输出用 Pydantic 校验作为断言；用少量金标集在每次改 prompt/换模型后回归，防止"改好一个 case 改坏三个"。

补充实践：确定性参数（temperature=0、固定 seed、mock 时钟）、固定夹具（预置订单/用户）、失败样本回灌为回归用例、按"必须产物清单"写断言而不是比对整段文本（见第 103 题）。覆盖率方面，2026 年也开始出现"插桩式 Agent 测试"——用真实埋点看 Agent 到底走了哪条分支。

追问：模型输出文本变了会不会弄坏回归？（会，所以不断言整段文本，只断言关键字段与结构） ｜ 要不要用真模型跑 CI？（分层：PR 跑 mock，每夜跑真模型小样本，发布前跑全量金标集）

115. 衡量 Agent 能力有哪些主流基准？为什么单看任务完成率不够？ ｜高频 ｜较难

答案： 主流基准（下列数字均为公开报告值，会随模型迭代快速变化，仅作量级参考）：

基准 机构 / 时间 考察点
τ-bench Sierra，2024-06（arXiv:2406.12045） 零售/航空客服双控对话；按策略遵循 + 数据库终态打分；用 pass^k 衡量 k 次独立运行全部成功的可靠性

  • 浏览器/桌面任务注意视觉派与 DOM 派的成本差异（见第 138 题）；

116. 大模型应用的可观测性怎么做？ ｜中频 ｜中等

答案： 至少做到三件事：有日志、有指标、有 Trace——能看见请求怎么流过系统、每一步花了多久、失败在哪里、用了多少 token、最后输出了什么。

三个核心维度：

  • 追踪 Tracing：记录每一步执行（工具调用、LLM 请求、决策链路）；
  • 评估 Evaluation：自动或人工评估输出质量；
  • 监控 Monitoring：实时监控延迟、错误率、Token 消耗、成本。

具体上应打通 trace_id / request_id，把入口请求、Prompt 版本、模型版本、索引版本、检索结果、工具调用、异常信息、耗时和 token 用量串起来。用了 LangChain / LangGraph，还要重点关注节点流转、状态更新、人工中断点、重试次数和最终退出原因。

十一、部署、推理性能与成本

118. 生产部署 Agent，你会给出怎样的架构清单？ ｜必刷 ｜中等

答案：

  • 运行时：LangGraph Platform 或自建 FastAPI 服务；长任务异步执行，结果走 SSE/WebSocket 流式回推；
  • 持久化：Postgres 做 checkpointer 与 store，thread_id 绑定会话；密钥走环境变量/Secret Manager；
  • 可靠性：节点级重试与超时、失败分支降级到"道歉/转人工"、限流与配额熔断（长任务专题见第 104 题）；
  • 安全：工具最小权限、写操作审批、用户输入与工具返回的注入风险审查（见第 106-108 题）；
  • 可观测/成本：LangSmith tracing，监控任务完成率、工具成功率、P95 延迟、token/成本告警；
  • 质量：轨迹回放评测集、灰度发布与 prompt 版本管理、模型可热切换（init_chat_model 配置化）。

一句话：从 Demo 到生产，差的不是代码量，而是状态、权限、降级、观测、回滚这五件事。

119. Agent 部署和运维有哪些指标？ ｜高频 ｜中等

答案： 至少看五类：

类别 指标
效果 任务完成率、用户满意度、引用正确率
性能 首 token、端到端延迟、P95/P99
稳定性 调用成功率、超时率、重试率、失败率
成本 token 消耗、工具调用成本、单任务平均成本

如果是多工具、多步骤 Agent，还要看每一步的成功率和卡点分布，否则只能知道"最终失败了"，却不知道失败发生在哪一层（对应第 120 题）。

120. Agent 链路耗时很长时，如何定位性能瓶颈？ ｜高频 ｜较难

答案： 一条链路跑到几分钟，不能只说"模型太慢"，要先把耗时拆开：

层 看什么
模型层 单次推理时长、首 token 延迟（TTFT）、输出 token 长度（TPOT）
检索层 召回、重排、外部搜索、知识库请求耗时
工具层 API 延迟、浏览器动作、代码执行、等待外部系统返回
编排层 路由判断、Supervisor 判断、重复重试、串行等待
结果层 后处理、校验、存储、日志落盘

做法是给每一步打 trace 和 span，先看 wall time 花在哪，再决定是换模型、改链路、减少步骤，还是把串行改成并行。用了 LangGraph 还要看节点级耗时、是不是反复进入同一节点、有没有因为缺少明确完成信号而来回判断。

关键结论：很多五分钟任务最后不是卡在单次模型调用，而是卡在多步链路过长、工具等待、监督节点重复判断、中间没有明确成功信号导致反复检查。也就是说，性能问题很多时候不是"模型太慢"，而是状态流转和执行闭环没有设计好。

121. 控制大模型应用成本，你会优先从哪些层面下手？ ｜高频 ｜中等

答案： 从模型、上下文、检索、流程四层入手：

  • 模型层：高低配模型分层，大任务用强模型，小任务用轻模型（见第 77、121 题的路由）；
  • 上下文层：压缩 Prompt，减少无效历史，控制返回长度；
  • 检索层：优化召回和重排，减少无意义进窗内容；
  • 流程层：减少不必要的 LLM 调用次数，能规则化就不要全靠模型。

很多系统成本高，不是因为模型太贵，而是链路设计太浪费：无差别全量检索、过长历史拼接、多次重复调用大模型、工具失败后盲目重试。

可加的手段：

  1. 语义缓存：相似问题直接命中已有答案（用 embedding 相似度 + 阈值；注意失效策略与个性化场景不能串用户）；
  2. Prompt Caching（见第 122 题）；
  3. 预算记账：按任务/用户统计 token 与费用，对异常会话熍断；
  4. 工具结果截断 + 子代理用小模型（长 observation 是隐性大头，见第 55 题）；
  5. 自托管小模型承接简单流量（见第 123、124 题）。

追问：token 成本和工具成本哪个先优化？（先看"哪个占比大"：RAG 长文档场景先优上下文与缓存；工具重场景先并发化 + 超时 + 降级） ｜ 如何平衡成本与效果？（按路由分支分别看"每成功任务成本"，而不是平均成本）

122. 什么是 Prompt Caching？工程上怎么用好？ ｜高频 ｜中等

答案： Prompt Caching 把重复使用的上下文缓存在服务端，显著降低成本和延迟：

  1. 首次请求：完整处理系统提示和文档上下文（正常计费，并有写入溢价）；
  2. 后续请求：相同前缀部分从缓存读取（命中价通常只有输入的 1/10）；
  3. 缓存 TTL：Anthropic 现有 5 分钟与 1 小时两档（1 小时档写入更贵）。

使用场景：系统提示较长（1000+ tokens）的 Agent、RAG 检索结果作为固定上下文、代码库分析（将代码文件缓存后多次查询）。

client.messages.create(
    model="claude-sonnet-4-5",   # 型号仅为示例，以官方当前型号为准
    system=[{
        "type": "text",
        "text": "你是代码审查专家...",
        "cache_control": {"type": "ephemeral"}  # 标记缓存
    }],
    messages=[{"role": "user", "content": "审查这段代码"}]
)

OpenAI 侧：主流型号对足够长（经验阈值 ≥ 1024 token）的公共前缀自动缓存，无需手动标记。

缓存要求前缀完全一致，所以要把固定内容（角色提示、工具定义、资料）放前面，易变内容（用户问题、时间戳、会话参数）放后面。反面例子：在 System 里插一个"当前时间"会让整个前缀缓存失效。

❌ 更正：旧版答案把 $3 / $3.75 / $0.30 这张价目表标为 Opus 价格——它实际是 Sonnet 档（输入 $3，缓存写入为输入的 1.25 倍、命中为 0.1 倍）；Opus 档的输入/输出价明显更高（近年多为 $5 / $25，缓存写入与命中也相应上浮）。具体型号与价格一律以官方定价页为准，面试里背价格不如说清"倍数关系"：写入略贵于普通输入、命中约为一折、长 TTL 更贵。

⚠️ 两个提醒：① 旧版"GPT-4o 自动缓存 1024 token"的说法已过时——gpt-4o 系列自 2026-02-13 起陆续退役，自动前缀缓存是平台级特性，迁移新一代型号后仍适用，但免费缓存阈值与覆盖型号会变；② 换代分词器会改变同文本的 token 数（历史上有三成量级的变化），所以缓存命中率与成本估算系数不能沿用旧值。

123. 内网环境下怎么设计 Agent / RAG 系统？ ｜中频 ｜较难

答案： 核心不是"把公网方案照搬一遍"，而是先把 数据不出域、模型可控、依赖可替换、链路可观测 这几件事立住。按企业级部署思路拆三层：

层 内容
应用层 Dify、Coze 类平台的私有化版本，或自研后端；负责工作流、Agent 编排、权限和业务接口
推理层 用 Xinference / vLLM / Ollama 这类托管平台统一管理 LLM、Embedding、Rerank，对外暴露 OpenAI-compatible API
数据层 内网向量库、关系库、对象存储、知识库索引、日志与审计系统都在可控域内

关键点：

  • 模型接入统一：上层尽量都走兼容 API，方便替换在线模型、本地模型和不同推理引擎；
  • 网络和权限隔离：Agent 能访问哪些内网系统必须按最小权限开放，不让模型拿到一把通吃的内网钥匙；
  • 知识治理：文档解析、索引重建、版本回滚、租户隔离、引用追踪都要内建；
  • 可观测与审计：请求链路、工具调用、检索结果、模型版本、token 用量、异常告警能在内网闭环查看；
  • 降级能力：内网模型抖动时是否有缓存、规则链路、人工兜底或备用模型。

追问：为什么要把应用层与推理层解耦？（模型升级/换型不动业务代码；可并行跑多个引擎做 A/B；运维与扩缩容独立） ｜ 为什么 LLM、Embedding、Rerank 最好分开管理？（三者硬件画像完全不同：生成吃显存与 KV 缓存，Embedding/Rerank 吃吞吐与批处理；分开才能各自调优与降级） ｜ 不能访问公网搜索时动态信息怎么补？（内网新闻/工单/数据仓接入为检索源；定时同步外部摘要入库；或经审计的代理出口）

124. vLLM 为什么快？PagedAttention、Continuous Batching、Prefix Caching 分别解决什么？ ｜高频 ｜较难 ｜2026 新增

答案： vLLM 是当前开源推理引擎的事实标准（同类：SGLang、TensorRT-LLM、TGI），核心是把"一次性大请求"当成分页、连续、可复用的资源来管理。

技术 解决的问题 做法
PagedAttention KV Cache 内存碎片（传统预分配按最大长度，实际生成长度不可知） 把 KV 分块管理（约 16 token/块），按需分配，类似操作系统分页；消除 60-80% 碎片，显存利用率从约 60% 拉到 95%+，因此同卡能撑更高并发与更长上下文
Continuous Batching Static Batching 下"一条长回答堵住整批"（短请求要等长请求跑完才能入场） 以迭代为单位调度：某序列一结束就立即把槽位让给新请求，批内成员动态进出；吐量常见 2-5 倍 提升
Prefix Caching 多请求共享长前缀时重复计算 KV 命中相同前缀（System + 工具定义 + 资料）则直接复用 KV，与厂商 Prompt Caching 同效应但自控
RadixAttention（SGLang） 前缀复用的自动化 用基数树组织多轮/多分支共享前缀，对 Agent、少样本、多轮工具调用尤其友好
其他 单步更快 量化（GPTQ/AWQ/FP8）、张量并行、投机解码、Chunked Prefill、PD 分离

面试里能拿分的一句话：推理优化的主战场是显存与调度，不是算子——大模型推理是内存带宽墙，而不是算力墙。

追问：Agent 场景为什么特别需要 Prefix Caching？（每轮重传整个历史与工具定义，前缀重复度极高） ｜ 自托管还是调 API？（看流量规模、数据合规、定制需求；中等流量下自托管需叠加运维与 GPU 成本，不一定便宜）

125. 推理优化还有哪些常用手段？TTFT 和 TPOT 分别代什么？ ｜高频 ｜中等 ｜2026 新增

答案： 两个指标先定义清楚：TTFT（Time To First Token，首 token 延迟，主要受排队 + 预填充影响，决定"看起来响应快不快"）；TPOT（Time Per Output Token，逐 token 间隔，决定"打字机流不流畅"）。

常用手段按作用于哪一阶段分类：

手段 主要影响 适用场景
量化（INT8/INT4、GPTQ/AWQ/FP8） 降显存、提吐量，轻微质量损失 单卡放不下、成本敏感
KV Cache 量化 / 驱逐 长上下文与高并发下的显存 长窗口、多会话
投机解码（speculative decoding） 降 TPOT（小模型草拟 + 大模型验证） 输出长、延迟敏感
Chunked Prefill 长 prompt 不堵死解码请求 混合长输入短输出场景
PD 分离（Prefill/Decode 分开集群） 两类工作负载硬件画像不同，分开各自优化 大规模生产集群
FlashAttention 提升注意力计算效率与显存行为 基本已是默认
并行策略（TP/PP/EP） 多卡/多机扩展 超大模型
路由与缓存（语义/Prefix） 直接减少计算 高重复度流量（Agent/RAG）

补一句业务视角：用户感受到的"慢"很多时候不是 TPOT，而是排队与多步循环次数；所以先确认是推理层慢还是编排层慢（见第 120 题）。

126. Dense 和 MoE 模型有什么区别？工程上怎么选？ ｜中频 ｜中等 ｜2026 新增

答案：

  • Dense（稠密）：每次前向都激活全部参数；质量可预测，但推理成本与参数量成正比；
  • MoE（稀疏专家）：用路由器把 token 送给 Top-K（常为 2）个专家 FFN，总参数量很大但激活参数小，所以此单位成本能支撑更多知识；代表：Mixtral、DeepSeek、Qwen 部分型号。

工程影响：

维度 Dense MoE
显存占用 按激活参数 要装下全部专家参数（显存不省）
吐量/延迟 稳定 路由与专家并行带来调优复杂度，批小时长尾延迟明显
部署 简单 需要专家并行（EP）、all-to-all 通信与负载均衡策略
微调 直接 易出现路由坍塌/专家利度不均，常先冻路由或上 LoRA
能力 同等激活参数下知识量小于 MoE 知识/推理任务性价比高

选型一句话：自托管看显存与并发画像，调 API 基本无感。 面试里把"MoE 省的是计算不是显存"说清楚就能赢一半。

127. LoRA / QLoRA 和全参微调怎么选？ ｜高频 ｜中等 ｜2026 新增

答案： 先分清层次：LoRA / QLoRA 是"参数高效方法"（改哪些参数），DPO / GRPO 是"优化目标"（用什么损失）——两者不在同一层，可以组合（QLoRA+SFT、QLoRA+DPO、QLoRA+GRPO）。

LoRA 原理：冻结原权重 W，只训练低秩增量 ΔW = B·A，其中 A 为 d×r、B 为 r×d，r 常取 8~64。参数量降几个量级，显存与存储友好；训练后可合并进原权重，推理时零额外延迟（ adapter 不合并则多一层计算）。常见变体：QLoRA（4-bit 量化基座 + LoRA，单卡可训 7B~70B）、Adapter（串/并联小瓶颈层，推理有额外开销）、P-Tuning / Prefix Tuning（只训提示向量，可学习参数更少、效果波动更大）。

什么时候用 LoRA，什么时候全参：

场景 建议
领域术语/格式/风格适配、数据量千到万条、卡有限 LoRA / QLoRA
要改变模型能力本身、大量高质量数据、有算力 全参
多业务共享一个基座、按租户挂不同 adapter LoRA（一个基座 N 个 adapter 最好管理）
只是行为不稳、格式不对 先想结构化输出/提示，不一定要微调（见第 10 题）

坑：灾难性遗忘（混入一定比例通用数据）、训推不一致（模板/特殊 token/截断长度没对齐）、数据量少且单样时反而把噪声学得更狠。

框架：LLaMA-Factory（零代码/低代码常见首选）、trl（SFT/DPO/GRPO 全家桶）、verl（大规模 RL）；并行与显存：DeepSpeed ZeRO-1/2/3、FSDP、DDP、Megatron（TP/PP/EP）。ZeRO 的直觉：1 切优化器状态、2 再加梯度、3 连参数也切（通信递增，单卡显存递减）。

追问：蒸馏算不算微调？（算广义，用小模型学大模型输出/分布，属于"能力下沉降本"路线，不是给新知识） ｜ 微调后怎么评测？（固定业务金标集 + 通用能力回归，防止"专业变强、通用变傻"）

128. RLHF、PPO、DPO、GRPO 都是什么？怎么选？ ｜高频 ｜较难 ｜2026 新增

答案： 四个词分属两层：RLHF 是流程范式，PPO/DPO/GRPO 是具体优化算法。

方法 机制 需要什么 特点
RLHF（流程） SFT → 训奖励模型 RM → 用 RL（常用 PPO）优化策略，KL 约束防偏离 偏好对 + 奖励模型 + 4 个模型常驻（policy/ref/critic/RM） 效果好但工程最重、不稳定、显存成本高
PPO 裁剪目标的 on-policy RL，需 value 网络估计 advantage 同上 调参门槛高，易 reward hacking
DPO 直接把偏好对写进损失，跳过显式 RM 与采样 仅需偏好对，离线 简单便宜、好复现；与采样分布有 gap，强推理任务收益不如 RL 类
GRPO 同一 prompt 采一组样本，用组内相对得分归一化当 advantage，去掉 value 网络 可验证的奖励信号（规则/测试通过） 显存与算力省一大截，DeepSeek-RL 系代表；RL 基础方法
DAPO / GSPO / SPO 对 GRPO/PPO 的工程修补（ clipping、长尾稳定、off-policy 修正等） — 前沿调优话题，能说名字即可

选型建议：

  • 行为/格式/风格对齐 → DPO（最便宜、最易上线）；
  • 有客观对错的任务（数学、代码、工具调用成功率）想拉能力 → GRPO（奖励可验证，无需 RM）；
  • 有专业 RL 团队与算力、要精细控制人类偏好 → PPO/RLHF；
  • 应用工程师优先顺序：提示/结构化输出 → RAG → few-shot → SFT/LoRA → DPO → GRPO（成本与风险递增，能停在前面就停在前面）。

面试常见追问："为什么 R1 类方法能不用 RM？"——因为奖励来自可验证信号（答案格式/单元测试/数学校验），GRPO 用组内相对比较代替 critic，所以不需要学一个人类偏好模型。
