AI 编程工具使用技巧（附答案）

基础概念

1. 什么是 AI 编程助手？

答案： AI 编程助手是基于大语言模型的代码生成和辅助工具，能够理解自然语言需求，生成代码、解释代码、调试问题、重构代码等。代表产品有 GitHub Copilot、Claude Code、Cursor、Windsurf（2026 年已更名 Devin Desktop）等。

2. AI 编程工具的核心能力有哪些？

答案：

  • 代码生成：根据注释或自然语言生成代码
  • 代码补全：智能预测下一行
  • 代码解释：解释复杂代码逻辑
  • Bug 修复：定位和修复错误
  • 代码重构：优化代码结构
  • 测试生成：自动生成单元测试
  • 文档生成：生成代码注释和文档

3. 主流 AI 编程工具有哪些？

答案：

IDE / 编辑器类：

  • GitHub Copilot：微软出品，2026 年 6 月迁移至 AI Credits 计费，支持多种 IDE，企业生态最成熟
  • Cursor：AI-first IDE（基于 VS Code），Cloud/Background Agents 支持长期自主任务，2026 年最热门
  • Windsurf：Codeium 出品，已被 OpenAI 收购（2025），Cascade 引擎，将深度集成 GPT-5
  • Claude Code：Anthropic 出品，CLI + Desktop App，自主推理能力顶尖，SWE-bench 领先

Agent / 全自主类：

  • Devin（Cognition AI）：AI 软件工程师，独立完成编程任务，有独立沙盒环境
  • Jules（Google）：GitHub 原生 Agent，@Jules 分配任务，底层用 Gemini 2.5 Pro
  • Amazon Q Developer：AWS 生态专用，安全扫描 + 代码转换，企业合规强

通用辅助类：

  • ChatGPT / GPT-5：OpenAI，通用对话，可辅助编程和代码讲解
  • Gemini 2.5：Google，超大上下文（1M token），适合大代码库分析
❌ 更正（2026-09 核实）：Windsurf 从未被 OpenAI 收购。真实时间线：①2025 年 5 月 OpenAI 宣布以约 30 亿美元收购 Windsurf（前身 Codeium）；②2025 年 7 月 11 日交易告吹——微软依据投资协议可共享 OpenAI IP 而明确反对，叠加 CFIUS/监管不确定性；③Google 随即以约 24 亿美元达成非排他性技术授权 + 核心团队雇佣（CEO Varun Mohan、联合创始人 Douglas Chen 等加入 Google DeepMind），Google 不持股；④2025 年 7 月 14 日 Cognition AI（Devin 母公司）收购 Windsurf 剩余全部资产（产品、IP、350+ 企业客户），Windsurf 作为独立产品保留；⑤2026 年 6 月 2 日 Windsurf 正式更名为 Devin Desktop，Cascade 代理于 2026 年 9 月移除，由 Devin Local 取代。 另：Jules 底层模型 2025 年 11 月已升级为 Gemini 3 Pro（2026 年初切换 3.1 Pro）；通用对话模型 2026 年 9 月时点已迭代到 GPT-5.6 / GPT-6 Astra 与 Gemini 3.x。

提示词技巧

4. 如何写好 AI 编程提示词？

答案：

  • 明确需求：清晰描述要实现的功能
  • 提供上下文：说明技术栈、框架版本
  • 分步骤：复杂任务拆分为小步骤
  • 给出示例：提供输入输出示例
  • 指定约束：说明性能、安全等要求

示例：

// ❌ 不好的提示词
写一个函数

// ✅ 好的提示词
用 TypeScript 写一个函数，接收用户数组，返回年龄大于 18 的用户。
要求：使用 filter 方法，添加类型注解，处理空数组情况。

5. 如何让 AI 生成更准确的代码？

答案：

  • 提供类型定义：给出接口或类型
  • 说明边界条件：空值、异常情况如何处理
  • 指定代码风格：函数式/面向对象、命名规范
  • 要求测试用例：让 AI 同时生成测试
  • 迭代优化：先生成基础版本，再逐步优化

6. 如何用 AI 调试代码？

答案：

  • 提供完整错误信息：包括堆栈跟踪
  • 说明预期行为：期望的输出是什么
  • 提供相关代码：上下文代码片段
  • 描述复现步骤：如何触发错误

示例：

这段代码报错 "Cannot read property 'name' of undefined"
预期：从用户列表中获取第一个用户的名字
实际：users 可能为空数组
请帮我修复并添加空值检查

7. 如何让 AI 重构代码？

答案：

  • 说明重构目标：提高可读性/性能/可维护性
  • 指定模式：使用设计模式、函数式编程等
  • 保持功能不变：强调不改变原有逻辑
  • 要求测试覆盖：确保重构后功能正常

示例：

重构以下代码：
1. 提取重复逻辑为函数
2. 使用策略模式替代 if-else
3. 添加类型注解
4. 保持原有功能不变

工具对比

8. GitHub Copilot 的优势和劣势是什么？

答案： 优势：

  • 生态最成熟，支持 VS Code、JetBrains、Visual Studio 等主流 IDE
  • 企业合规友好，数据留存策略清晰
  • 代码补全速度快（Next Edit Suggestions）
  • 2026 年集成 GPT-5.x、Claude、Gemini 等多模型可选
  • PR Review 自动化，CI/CD 集成好

劣势：

  • 2026 年 6 月迁移至 AI Credits 按量计费，重度 Agent 用户成本可能上升
  • 自主 Agent 能力不如 Cursor Cloud/Background Agents
  • 深度推理不如 Claude Code

定价（2026）：

  • Copilot Pro：$10/月（含 AI Credits 额度）
  • Copilot Pro+：$39/月
  • Copilot Business：$19/用户/月
  • 超出额度按 token 按需计费

适合场景：企业统一部署、已深度集成 GitHub 工作流的团队

⚠️ 过时/存疑标注（2026-09 核实）：Copilot 已于 2026 年 6 月 1 日全量切换到 AI Credits 用量计费（替代 premium request）：1 AI credit = $0.01，按各模型公开 API 费率对输入/输出/缓存 token 计价。截至 2026-09 各套餐为：Free（有限额度）、Pro $10（含 1,000 credits）、Pro+ $39（3,900）、Max $100（10,000）、Business $19（1,900）、Enterprise $39（3,900）；代码补全（completion）与 Next Edit Suggestions 仍全部免费、不扣 credits；额度用尽后不再自动降级到便宜模型。

9. Claude Code 的优势和劣势是什么？

答案： 优势：

  • 深度推理能力顶尖（Claude Opus 4，SWE-bench 72.5%）
  • 跨文件、跨模块理解能力强
  • 原生 MCP 集成，可调用外部工具
  • Fork 模式：可拆分子任务给并行子 Agent
  • 2026 年新增 Desktop App（不再只是 CLI）
  • /design 技能：直接生成 UI 设计稿并实现
  • Remote Control：手机上远程启动开发机上的 Claude Code 会话

劣势：

  • 成本较高（按 token 计费）
  • 学习曲线陡峭（需熟悉命令行工作流）
  • 需要明确任务边界，否则可能过度修改

适合场景：架构重构、复杂 bug 追踪、技术债务清理、长期大型任务

⚠️ 过时/存疑标注（2026-09 核实）："Opus 4 / SWE-bench 72.5%"是 2025 年 5 月 Claude 4 发布时的数据。截至 2026-09，Claude Code 主力模型已迭代到 Sonnet 5（2026-06-30 发布，$2/$10、1M 上下文）与 Opus 4.8（2026-05-28 发布，SWE-bench Verified 88.6%、SWE-bench Pro 69.2%）；中间经历 Opus 4.5（2025-11）/4.6（2026-02，80.8%）/4.7 与 Sonnet 4.5（2025-09）/4.6（2026-02）。

10. Cursor 的优势和劣势是什么？

答案： 优势：

  • VS Code 体验，上手快，生态丰富
  • Cloud/Background Agents（2025 年 10 月起）：云端 Agent 可长期自主运行，无需本地开着电脑
  • Subscriptions：Agent 可订阅 PR、Slack 事件，自动被唤醒处理任务
  • /goal：设置长期目标（如"修复所有 flaky test"），Agent 持续工作直到完成
  • 子 Agent VM：并行子任务各自独立虚拟机，不互相干扰
  • Origin：内置 Git 托管，Agent 原生代码仓库
  • Builds：预热开发环境，Agent 启动快 3x

劣势：

  • 深度单步推理不如 Claude Code
  • Background/Cloud Agents 需要额外付费（按 credit/分钟计费）
  • 夹在 OpenAI/Anthropic 两大巨头之间，生存压力大

适合场景：日常开发、中大型项目、需要长期自主 Agent 运行的团队

⚠️ 过时/存疑标注（2026-09 核实）：2026 年 9 月 10 日 Cursor 进一步推出 Projects（协调者 agent + 云端子 agent 集群 + 跨会话共享上下文 + 事件订阅），上述 Cloud Agents、Subscriptions、/goal 等能力已被整合进 Projects 体系；另据公告，Cursor 对 OpenAI 模型的访问将于 2026 年 11 月 12 日终止，模型池转为 Anthropic、xAI、自研 Composer 与开源模型。

11. Windsurf 的优势和劣势是什么？

答案：

Windsurf 由 Codeium 公司开发。2025 年 OpenAI 宣布以约 30 亿美元收购 Codeium，Windsurf 归属 OpenAI。

优势：

  • Cascade 引擎，Agentic 自主能力强，端到端体验流畅
  • 快速原型开发，多文件编辑体验好
  • 未来将深度集成 GPT-5，模型能力大幅提升
  • 免费版仍可用

劣势：

  • 被 OpenAI 收购后未来方向不确定，插件生态较小
  • 社区相比 Cursor 小
  • 企业客户需重新评估数据归属（已变为 OpenAI 旗下）

适合场景：快速原型、MVP 开发、希望体验最新 OpenAI 模型的用户

❌ 更正（2026-09 核实）：本题关于归属的描述全部错误，详见第 3 题更正。准确时间线：OpenAI 2025 年 5 月签约、7 月告吹（微软反对 IP 共享 + CFIUS/监管不确定性）→ Google 约 24 亿美元非排他授权 + 挖走创始团队 → Cognition AI 2025 年 7 月 14 日收购 Windsurf 剩余资产并继续运营该产品 → 2026 年 6 月 2 日更名 Devin Desktop，深度集成 Devin Cloud/Devin Local（Cascade 于 2026 年 9 月移除）。Windsurf 从未归属 OpenAI，也从未"深度集成 GPT-5"。

12. 如何选择 AI 编程工具？

答案： 根据使用场景选择：

  • 日常开发：Cursor 或 Copilot
  • 复杂重构：Claude Code
  • 企业部署：GitHub Copilot（合规友好）
  • 快速原型：Windsurf（2026-06 起为 Devin Desktop）
  • 学习探索：ChatGPT 或免费工具

根据预算选择：

  • 免费：Windsurf/Devin Desktop Free、ChatGPT Free、Gemini CLI
  • 低成本：GitHub Copilot ($10/月)
  • 中等成本：Cursor ($20/月)
  • 按需付费：Claude Code（按 token，或含在 Claude Pro/Max 订阅中）

最佳实践

13. AI 生成的代码需要审查吗？

答案： 必须审查。AI 生成的代码可能存在：

  • 逻辑错误：不符合业务需求
  • 安全漏洞：SQL 注入、XSS 等
  • 性能问题：低效算法、内存泄漏
  • 代码风格：不符合团队规范
  • 过度工程：不必要的复杂度

审查要点：

  • 功能正确性
  • 边界条件处理
  • 错误处理
  • 性能影响
  • 安全性

14. 如何提高 AI 编程效率？

答案：

  • 熟悉快捷键：快速触发 AI 补全
  • 建立代码库：积累常用提示词
  • 分步骤执行：复杂任务拆分
  • 快速迭代：先生成基础版本，再优化
  • 结合搜索：AI + Google/Stack Overflow
  • 保持上下文：在同一会话中连续提问

15. AI 编程的局限性有哪些？

答案：

  • 理解业务逻辑：AI 不了解具体业务需求
  • 架构设计：复杂系统架构需要人工设计
  • 创新能力：AI 基于已有知识，难以创新
  • 调试复杂问题：深层次 bug 需要人工介入
  • 代码质量：可能生成冗余或低效代码
  • 安全意识：可能忽略安全最佳实践

16. 如何避免过度依赖 AI？

答案：

  • 理解原理：不要盲目复制代码
  • 手写核心逻辑：关键算法自己实现
  • 定期复习：回顾 AI 生成的代码
  • 保持学习：持续学习新技术
  • 代码审查：团队互相审查代码
  • 测试驱动：先写测试，再用 AI 实现

🆕 26. 编码 Agent 的沙箱与权限模型是怎么回事？--dangerously-skip-permissions 有什么风险？

答案： 自主 Agent 能读写文件、执行 shell、联网安装依赖，因此主流工具都用"权限模式 + 沙箱 + 执行环境"三层模型来约束：

1. 权限模式（每次动作要不要问你）

工具典型模式
Claude Codedefault（逐次确认）、acceptEdits（自动接受文件编辑）、plan（只读规划，审批后才动手）、auto（分类器模型自动审批，2026-03 推出）、dontAsk（只允许预批准工具）、bypassPermissions
Codex CLIread-only（只读）、workspace-write（仅工作区可写）、danger-full-access（无限制），--yolo 一键放开
CursorAgent 模式下的命令/文件编辑审批、YOLO/自动模式

--dangerously-skip-permissions（Claude Code）对应 Codex 的 --yolo：跳过所有权限提示，连受保护路径检查也跳过，只在删除根目录/家目录等极少数情况仍会拦截。

2. 沙箱（动作执行时能碰到什么）

  • 文件系统隔离：只能写工作目录，敏感路径（~/.ssh、.env）受保护
  • 网络隔离/出口白名单：默认禁网或只允许批准域名
  • OS 级强制执行：Claude Code 沙箱化 Bash 在 macOS 用 Seatbelt、Linux/WSL2 用 Landlock + bubblewrap，对子进程同样生效
  • 更强隔离：沙箱运行时、Dev Container、虚拟机，以及云端托管沙箱（Copilot coding agent 跑在 GitHub Actions VM、Codex/Cursor 后台 agent 跑在云端隔离 VM）

3. 真实事故与风险 Anthropic 自己的事故日志记录过：Agent 误解指令删除远程 git 分支、把工程师的 GitHub auth token 上传到内部计算集群、对生产数据库执行 migration。另有 NCC Group 2026 年 5 月白皮书指出：各工具沙箱默认开关不一、GUI/CLI 实现差异大，危险权限模式属于"按设计如此"的风险。

关键背景：Anthropic 数据显示用户会批准 93% 的权限提示——审批疲劳让"逐次确认"形同虚设，这也是 auto 模式（用分类器替代人审批）和默认沙箱出现的原因。

最佳实践：

  • 日常开发用 plan/default + 内置沙箱，不要在主力机上用 bypass/YOLO
  • 无人值守/CI 场景必须放进容器或 VM，配网络出口白名单，再考虑 skip-permissions
  • 用允许列表（allowlist）预批准只读命令，配置 protected paths
  • 警惕间接提示注入：README、Issue、网页里的"指令"可能劫持 Agent

🆕 27. 什么是 slopsquatting？如何防范 AI 推荐恶意依赖的供应链攻击？

答案： Slopsquatting（AI 抢注/幻觉包抢注） 一词由 Python 软件基金会驻场开发者 Seth Larson 提出，是 typosquatting（抢注拼错域名）的 AI 版：LLM 一本正经地推荐一个根本不存在的包名，攻击者提前在 npm/PyPI 上抢注该名字，植入恶意代码，等开发者或自主 Agent 自动安装。

规模（USENIX Security 2025 论文，arXiv:2406.10279）：

  • 分析 16 个代码模型生成的 223 万个代码样本，19.7% 含至少一个幻觉包名，共 205,474 个不同的假包名
  • 开源模型平均幻觉率 21.7%，商业模型 5.2%（CodeLlama 部分配置超 33%，GPT-4 Turbo 最低 3.59%）
  • 同一提示重跑 10 次，43% 的假包名每次都出现——幻觉可预测，攻击可规模化
  • 幻觉分三类：名称糅合（conflation）38%、近似拼写 13%、纯编造 51%；另有 8.7% 的 Python 幻觉名在 npm 上真实存在（跨生态误装）

已确认真实事件：

  • huggingface-cli（PyPI）：正确安装方式是 huggingface_hub[cli]，研究者抢注假名包后 3 个月内被下载超 3 万次（连阿里某公开仓库 README 都抄了错误命令）
  • react-codeshift（npm，2026-01）：jscodeshift 与 react-codemod 的幻觉糅合名，被发现时已有 237 个仓库引用；Agent Skills 市场也出现过 1,184 条恶意条目（ClawHub 投毒事件）

防护措施：

  1. 安装前核验：在官方注册表确认包存在、发布者身份、注册时间（刚注册+被 AI 频繁推荐 = 高危）
  2. Lockfile 固定版本 + 包哈希校验，CI 中强制
  3. 给 Agent 装依赖加门禁：人工审批或 allowlist，禁止 Agent 自行添加新依赖
  4. SBOM（软件物料清单）：AI 生成代码上线前盘点全部依赖
  5. 工具辅助：slopcheck（扫描文档/AGENTS.md/SKILL.md 中尚不存在的包名）、Socket.dev、Snyk
  6. 记住：AGENTS.md、SKILL.md、.cursorrules 本身也是攻击面，AI 会把其中的安装命令当作可信指令

35. 什么是 MCP（Model Context Protocol）？

答案： MCP（Model Context Protocol）是 Anthropic 于 2024 年底提出的开放标准协议，用于连接 AI 模型与外部数据源和工具。

核心设计：

  • 标准化接口：定义 AI 如何调用外部工具（文件系统、数据库、API、浏览器等）
  • 服务器/客户端架构：MCP Server 暴露工具，MCP Client（AI IDE）连接并调用
  • 可组合性：同一个 AI 可以同时连接多个 MCP Server

类比：MCP 对 AI 工具生态的意义，类似 USB-C 对硬件接口的统一作用。

37. 什么是 Cursor Rules（.cursor/rules）？如何使用？

答案： Cursor Rules 是存放在项目根目录下的规则文件，用于持久化约束 AI 的行为，让 AI 在整个项目中遵守特定规范。

位置：

  • 新版：.cursor/rules/ 目录下，每个 .mdc 文件是一条规则
  • 旧版：项目根目录 .cursorrules 文件

常见用法：

# 技术栈约束
- 使用 TypeScript，禁止 any 类型
- React 组件使用函数式，禁止 Class 组件
- 样式使用 TailwindCSS，禁止 inline style

# 代码风格
- 函数名使用 camelCase
- 组件名使用 PascalCase
- 注释用中文

# 特定框架规范
- API 调用统一使用 /services 目录下的封装
- 禁止直接在组件中写 fetch/axios

优势：避免每次对话重复说明背景，AI 始终按项目规范生成代码。

38. 什么是 "Vibe Coding"（氛围编程）？

答案： Vibe Coding 是 OpenAI 联合创始人 Andrej Karpathy 于 2025 年 2 月提出的概念，描述一种几乎完全依赖 AI 生成代码、开发者只负责描述意图和验收结果的编程方式。

核心特点：

  • 开发者用自然语言描述需求，不手写代码
  • 遇到 bug 直接把错误信息粘贴给 AI 让其修复
  • 不深究代码细节，只关注功能是否符合预期

适合场景：个人项目、原型验证、非核心业务快速实现

风险：

  • 难以维护不理解的代码
  • 安全漏洞难以察觉
  • 技术债务积累

结论：Vibe Coding 提升了个人开发效率，但在团队或生产代码中仍需工程师深度理解代码。2025 年下半年起业界以 Spec-Driven Development（规格驱动，见第 57 题）作为其"纠偏"方案。

40. 上下文窗口（Context Window）大小对 AI 编程有什么影响？

答案： 上下文窗口是模型一次能处理的 token 上限，直接影响 AI 对代码库的理解深度。

影响维度：

  • 文件数量：窗口越大，能同时参考的文件越多
  • 代码连贯性：大窗口让 AI 理解跨模块依赖关系
  • 长对话稳定性：长会话不会因窗口溢出而"失忆"

实际体验：

  • 16K 窗口：只能处理单文件、小函数
  • 128K 窗口：可处理中等项目（数十个文件）
  • 200K+ 窗口：可一次处理较大代码库，减少多轮对话
  • 1M 窗口（Gemini 2.5/3、Sonnet 5、Opus 4.6+）：可塞入整个中型项目

注意：大窗口不等于质量好，模型在窗口中间的内容上可能注意力下降（"lost in the middle" / context rot 问题）；2026 年的旗舰模型普遍引入了上下文压缩（context compaction）缓解长任务遗忘。

41. GitHub Copilot Workspace 是什么？

46. 什么是 AI 编程中的"幻觉"问题？如何应对？

答案： AI 幻觉（Hallucination）是指模型生成看似合理但实际错误的内容，在编程场景中危害尤大。

常见幻觉类型：

  • 不存在的 API：调用库中根本不存在的方法
  • 过时接口：使用已废弃的旧版 API
  • 错误的参数顺序：参数名正确但顺序错误
  • 假的包名：推荐根本不存在的 npm/pypi 包（supply chain attack 风险，见第 27 题 slopsquatting）
  • 错误的逻辑：代码运行不报错但结果不对

应对策略：

  1. 验证 API 存在性：查官方文档或 GitHub 源码
  2. 运行测试：不要只看代码，必须执行验证
  3. 指定版本：提示词中说明库版本，如 "React 18, Next.js 14"
  4. 二次确认：对关键逻辑用另一个模型或搜索引擎验证
  5. 避免依赖生僻库：优先推荐使用 AI 熟知的主流库

🆕 48. 什么是 Agent Skills？它和 MCP、自定义命令有什么区别？

答案： Agent Skills 是 Anthropic 于 2025 年 10 月 16 日推出的能力打包机制：一个文件夹 = 一项可复用专长，内含 SKILL.md（指令）、脚本和参考资源，Agent 在相关任务时自动发现并加载。2025 年 12 月 18 日 Agent Skills 作为开放标准发布（agentskills.io），可跨 Claude 应用、Claude Code、API 移植。

核心设计——渐进式披露（progressive disclosure）：

  1. 启动时只加载 SKILL.md 的 YAML frontmatter（name + description，每个约 100 token），装几十个 skill 也不占上下文
  2. 任务匹配时才加载 SKILL.md 正文
  3. 真正需要时再读目录里的参考文件/执行脚本
pdf-skill/
├── SKILL.md        # frontmatter + 流程指令
├── FORMS.md        # 按需读取的参考
└── scripts/
    └── fill_form.py  # 确定性脚本，比让模型生成 token 更可靠

🆕 49. 什么是 Subagents（子代理）/多代理并行编码？使用边界是什么？

答案： 子代理指主会话派生若干拥有独立上下文窗口的 Agent 并行干活，2025-2026 年成为主流 coding agent 的标配：

  • Claude Code：subagents（最多嵌套三层）、Fork 分叉会话；2026 年 2 月 Opus 4.6 推出 Agent Teams（研究预览）：一个主导 Agent 协调多个队友 Agent，演示案例是从零写出 10 万行、支持三种 CPU 架构并能启动 Linux 的 C 编译器
  • Cursor：Background/Cloud Agents 各自独立 VM；2026-09-10 发布 Projects，协调者 agent 调度云端子 agent 集群并维护共享上下文
  • OpenAI Codex：Ultra 模式用 subagents 并行加速；2026-09-10 Agents API 公测，提供沙箱、并行子 agent、可恢复会话
  • Kimi K2.5 等模型侧：Agent Swarm 可协调多达 100 个专用子 agent

适用任务：

  • 可天然并行的批量活：给多个模块补测试、跨包改名、依赖版本 sweep
  • 探索性研究：多个子 agent 分别读不同子系统再汇总
  • 上下文隔离：把"脏"探索丢给子 agent，主会话只接收结论，节省主上下文
  • 子 agent 可用便宜模型（如 GPT-5.4 mini / Haiku / Flash），降低 token 成本

使用边界（什么时候不该用）：

  • 子任务强耦合、共享可变状态时，合并冲突与不一致风险高
  • 需要统一架构决策的任务，必须由主 agent/人把控
  • 子 agent 产出仍需审查：并行放大产出速度，也放大返工面
  • token 成本与协调复杂度随子 agent 数量超线性增长，并非越多越好

50. 如何为 AI 提供高质量的代码上下文？

答案： AI 的输出质量高度依赖输入的上下文质量，"垃圾进垃圾出"在 AI 编程中同样适用。

高质量上下文包含：

  • 相关文件：手动 @引用关键文件（接口定义、工具函数、配置文件）
  • 类型定义：提供 TypeScript 接口/类型，让 AI 知道数据结构
  • 技术栈说明：框架版本、依赖库列表
  • 错误信息：完整的堆栈跟踪，而非截断的部分
  • 期望行为：描述"应该做什么"，而非只描述"现在不对"

避免：

  • 粘贴整个大文件（稀释有效信息）
  • 跨不相关话题混合在同一会话
  • 不说明已有代码约束就让 AI 自由发挥

51. 什么是 Memory Bank 模式？

54. 什么是 "Context Poisoning"（上下文污染）？如何预防？

答案： Context Poisoning 是指会话历史中的错误信息、过时假设或错误代码积累后，导致 AI 在后续回复中持续犯同类错误。

常见触发场景：

  • 会话初期 AI 生成了一个错误方案，后续问题都基于此展开
  • 粘贴了有 bug 的代码但未说明它是错误的
  • 长会话中早期的约束与后期需求冲突

预防策略：

  1. 开新会话：遇到方向偏差时，及时另开会话重新描述
  2. 显式纠正：明确告诉 AI "之前的方案不对，请忽略，重新考虑"
  3. 精简历史：不必要的早期消息不用保留
  4. 明确约束：在会话开始时明确不变的约束条件
  5. 使用规则文件：将核心规范放入 AGENTS.md / Cursor Rules，而非依赖会话记忆

🆕 56. 什么是编码 Agent 的上下文工程（Context Engineering）？

答案： 上下文工程指系统性地决定"把什么信息、在什么时候、以什么形式放进 Agent 的上下文"，2025-2026 年被认为比单次提示词技巧更决定 Agent 输出质量。主要环节：

1. 上下文从哪来

  • 显式引用：@文件/@符号、粘贴报错、拖拽截图
  • 隐式信号：当前打开的标签页、光标位置、最近编辑、git diff/历史
  • 仓库级检索：代码库索引

2. 代码库索引：混合检索是主流

  • Embedding 语义检索：按"意思"找代码，解决同义词问题
  • Keyword/BM25 关键词检索：按精确符号名找，解决语义检索"看着相关其实不对"
  • 实践中两者混合 + rerank 重排序；部分工具还叠加代码图谱（如 Cognition 的 Codemaps）分析调用关系
  • 为什么不能只靠 embedding：精确标识符（函数名、错误码）关键词检索更准；纯 embedding 在大型 monorepo 召回噪声大

3. 长任务与跨会话记忆

  • 规则文件：AGENTS.md / CLAUDE.md / .cursor/rules 提供稳定背景（第 47 题）
  • 记忆文件 / Memory Bank：任务进度、架构决策落盘（第 51 题）
  • Context Compaction（上下文压缩）：接近窗口上限时自动把历史总结成压缩块续跑，Opus 4.6、GPT-5.2-Codex 等 2026 年模型普遍支持
  • 云端共享上下文：如 Cursor Projects 的 shared-context 文件，多个本地/云端 agent 共同写入研究结论与项目知识

实践原则：

  • 小而准 > 大而全：无关文件会稀释注意力，整库粘贴效果常不如精选 5 个文件
  • 长任务主动让 Agent 写 checkpoint/进度文档，而不是依赖它"记得"
  • 警惕 context rot（超长上下文中段信息被忽略）与上下文污染（第 54 题）
  • 把确定性信息（命令、规范）放规则文件，把易变信息放任务文档

🆕 57. 什么是 Spec-Driven Development（规格驱动开发）？

答案： Spec-Driven Development（SDD）是 2025 年下半年针对 Vibe Coding 返工潮出现的工作流：先写结构化、可验证的规格（spec），人审批后再让 Agent 按规格写代码，规格贯穿计划、任务拆解、实现与验收全过程。核心洞察是：模型擅长模式补全但不会读心，"做个用户管理 API"背后藏着认证方式、错误格式、分页、限流等上千个未声明决策，必须显式化。

标准流程：

Requirements（需求 + 可测验收标准）
  → Design/Plan（技术方案：动哪些文件、什么架构）
  → Tasks（拆成可逐条审查的小步清单/checklist）
  → Implement（Agent 按任务清单顺序执行）
  → Verify/Converge（跑测试对照验收标准，不通过继续收敛）

代表工具：

工具形态特点
GitHub Spec Kit开源 CLI（2025-09 发布，2026 年 130K+ stars，38 种 agent 集成）Constitution（项目宪法级约束）→ /specify → /plan → /tasks → implement → converge，可离线/内网用，不绑定工具
Amazon KiroIDE（2025 年中）.kiro/specs/<name>/ 下生成 requirements.md、design.md、tasks.md 三件套
OpenSpec / BMAD / Tessl社区/商业方案Tessl 走最激进的 spec-as-source（只维护规格，代码全部再生成）

三种落地深度：

  • Spec-first：规格只为当前任务服务，代码落地后规格刻意过期——适合一次性原型
  • Spec-anchored：规格与代码并存、同步更新——有客户的生产系统推荐
  • Spec-as-source：只改规格、由 Agent 重新生成代码——愿景诱人但授权边界等实现决策全交给生成器，风险高

与规则文件的分工：AGENTS.md/CLAUDE.md 管"所有任务都要遵守的通用约束"，spec 管"这一个特性要实现什么行为"。规格是护栏不是保证：Agent 仍可能不遵守，关键验收标准必须能被测试/检查自动执行。

工程实践中的 Eval：

# 构建 Golden Set（黄金测试集）
eval_cases = [
    {
        "input": "修复这个 Bug：...",
        "expected_behavior": "函数返回正确结果",
        "evaluation_criteria": ["代码可运行", "测试通过", "逻辑正确"]

]

def evaluate_response(ai_output, expected):
    judge_prompt = f"""
    评估以下 AI 输出是否满足要求：
    输出：{ai_output}
    要求：{expected}
    评分（1-5）并说明理由：
    """
    return llm.generate(judge_prompt)

🆕 68. 深入评测基准：SWE-bench 分数为什么不等于实际体验？什么是 Terminal-Bench？

答案： SWE-bench Verified 的饱和：它从 500 个真实 GitHub Python 仓库 issue 中人工筛出，模型要产出能通过隐藏测试的补丁。头部成绩从 2023 年的约 3% 升到 2025 年中 Opus 4 的 72.5%，2026 年 7 月拥堵分数（congestion score）已达 93.9%——头部模型挤在同一区间，基准失去区分度。

三重结构性问题：

  1. 数据污染：OpenAI 2026 年 2 月宣布停止报告 SWE-bench Verified，理由是每个前沿模型都能逐字复现金标准补丁（题目仓库本就在训练语料里）；另有实验显示只给 issue 文本，模型就能凭记忆说出 63%-65% 要改的文件名
  2. 验证器噪声：DeepSWE 审计发现自动验证器错误率约 32%；OpenAI 对 138 个难题的审计中 59.4% 测试用例本身有缺陷
  3. 通过 ≠ 可合并：METR 人工复审发现约 50% "测试通过"的 PR 不会被真实维护者接受；任务分布也偏向"改 1-3 个文件、不到 20 行"的简单 bug

SWE-bench Pro 的挫折：Scale AI 2025 年 9 月推出更难、刻意使用强 copyleft 仓库防训练污染的 Pro（731 道公开题），但 OpenAI 2026 年 7 月 8 日审计发现约 30% 题目判分有误（自动流程标记 200 题、人工标记 249 题，主要是隐藏测试比题目要求更苛刻），并撤回了自己对该基准的推荐。

Terminal-Bench：2025 年 5 月推出（v2.0 共 89 题），不看补丁而是让 agent 在真实终端+容器里端到端完成任务（文件系统、进程、网络调试、多步 shell）。2026 年 5 月 v2.1 修补了其中 28 题。关键发现：同一个模型挂不同 harness（Claude Code/OpenHands/自研循环），分数可波动 30-50 个百分点——它测量的是"模型+外壳"的组合，不只是模型。2026 年 4 月 UC Berkeley 对 8 个主流 agent 基准的审计更显示它们全部可被技术性刷分（如注入 pytest hook 让全部测试报通过）。

新基准与实操建议：

  • 更难的新基准：SWE-bench Pro（修复后）、Frontier-Bench（2026-07，覆盖 ML/科研/运维/安全等 7 域，最高分仅 34.4%）、ARC-AGI-3
  • 公开榜单用于排除弱模型，不要用于在强模型间做 2-3 分的精细取舍——差距在基准自身误差线内（小于 5 分当平局）
  • 自建 eval：从本仓库已合并 PR/已修 bug 中抽 20-50 题做盲测，跑通自己的 CI，这是唯一包含"你的代码库、你的评审标准"的基准
  • 度量 agent 用 merge rate、返工率、cycle time 等结果指标（第 69 题）

🆕 69. 团队如何度量 AI 编程的落地效果？（采纳率、吞吐量与"生产率悖论"）

答案： 2025-2026 年的严肃研究表明，"采纳率高 = AI 有效"是错觉，团队需要一套配对了质量对冲指标的度量体系。

几个必须知道的反直觉数据：

  • METR 随机对照试验（2025 年，16 名资深开源开发者、246 个任务）：使用 AI 工具后任务反而慢了 19%；受试者事前预计快 24%、事后仍坚信自己快了 20%——感知与实际存在约 40 个百分点的鸿沟
  • LinearB 2026 年对 810 万个 PR 的统计：AI PR 接受率约 32.7%，人工 PR 为 84.4%；AI 代码等待评审的时间长 4.6 倍
  • Google DORA 2025 报告：80%+ 的人认为 AI 提升了生产力，但 AI 使用度与软件交付稳定性呈负相关；约 30% 的人不信任 AI 生成代码
  • Jellyfish 2026 数据：企业 AI 工具采纳率中位数 74%，但 AI 辅助代码占合并代码比例中位数只有 27%——买了 license ≠ 产生影响
  • 反面参照：GitHub 自家对照研究测得隔离任务场景快 55.8%——结论是"窄任务个人提效真实，但不等于团队吞吐提升"

不要只看的虚荣指标：license 激活数、补全采纳率（Copilot 类工具约 30% 的建议被接受，只度量"点了接受"）、PR 数量（AI 让 PR 产量暴涨，但评审产能没涨，瓶颈转移到 reviewer）。

推荐跟踪的四类指标：

  1. 生产合并的 AI 代码占比（production-merged，而非生成量/接受量）
  2. Cycle time（首个 commit 到合并的端到端时长，分团队对比）
  3. PR 评审等待时长 vs PR 数量（识别评审瓶颈）
  4. AI 代码返工率（rework/回滚/缺陷率，与人工 PR 对照）

配合 DORA（部署频率、变更前置时间、变更失败率、恢复时间）与 DX Core 4 / SPACE 框架使用。

配套做法：

  • AI 生成代码先过 AI 评审（Copilot code review、CodeRabbit 等）做第一道模式过滤，人集中审架构、安全、业务正确性
  • 关键路径（鉴权、支付、迁移）保持人工主导，建立 AI 代码事故复盘机制
  • 度量的单位是团队工作流而不是个人：Faros AI 对 1,255 个团队的研究发现个人产出（任务数 +21%、PR 数 +98%）与公司级交付改善之间没有显著相关——产出涨了，结果未必动
