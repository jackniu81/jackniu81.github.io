前端工程化 常见面试题（附答案）

版本核实日期：2026-09。当前主线版本：Vite 8.1（Vite 8 于 2026-03-12 发布）、Rolldown 1.0（2026-05）、Node 24 LTS、ESLint 10、Vitest 4、Rspack 2.x、Biome 2.x。

构建工具

1. Vite 和 Webpack 的核心区别是什么？

答案： 开发环境：Vite 利用浏览器原生 ESM，按需编译模块（秒级启动，不随项目大小增加）；Webpack 需要打包所有模块，项目大时启动几十秒。热更新（HMR）：Vite 只更新变化的模块，毫秒级；Webpack 需重新打包相关模块，较慢。生产构建：Vite 底层用 Rollup（Tree Shaking 更彻底）；Webpack 自有生态更成熟，插件生态更丰富。选型建议：新项目优先 Vite；现有 Webpack 大型项目迁移成本较高。

⚠️ 版本更新（2026-09 核实）：Vite 8（2026-03-12 稳定版）已将生产构建从 Rollup 切换为 Rust 编写的 Rolldown，开发期 esbuild 的角色也由 Rolldown + Oxc 接管，"dev esbuild / prod Rollup"双引擎成为历史架构；Rolldown 保持 Rollup 插件 API 兼容，多数 Vite 插件可直接使用。Vite 6/7 主线仍是 esbuild + Rollup，Vite 7 可通过 rolldown-vite 包可选切换。Vite 8 要求 Node 20.19+ 或 22.12+。

2. Vite 的开发原理是什么？

答案： ① 启动时只启动开发服务器，不打包，速度极快；② 浏览器发起模块请求时，Vite 按需编译对应文件（TS/JSX/Vue/Sass → 浏览器可运行 JS/CSS）；③ 利用浏览器 HTTP 缓存和强缓存区分源码模块和依赖（node_modules 用 esbuild 预打包为 ESM，缓存于 .vite）；④ HMR 通过 WebSocket 通知浏览器只替换变化的模块。

⚠️ 版本更新（2026-09 核实）："nodemodules 用 esbuild 预打包"在 Vite 6/7 主线仍是现状（这两版可安装 rolldown-vite 切换为 Rolldown 预览）；Vite 8 起依赖预打包（dep optimizer）已改用 Rolldown，TS/JSX 转换改用 Oxc，缓存目录仍是 nodemodules/.vite。optimizeDeps.esbuildOptions 保留并自动转换为 optimizeDeps.rolldownOptions，但已标记弃用。

3. 🆕 Vite 8 为什么切换到 Rolldown？rolldown-vite 是什么？

答案： 旧架构问题：Vite 长期使用双引擎——开发期 esbuild 负责依赖预打包与 TS/JSX 转换，生产期 Rollup 负责打包优化。两套转换管线、两套插件适配、大量胶水代码，导致 dev/prod 行为偶发不一致，且单一管线的能力（如全量打包、模块级持久缓存）难以实现。Rolldown 是 VoidZero（Evan You 创立）用 Rust 编写、底层基于 Oxc 的打包器，目标是"esbuild 级速度 + Rollup 插件 API 兼容"，官方基准比 Rollup 快 10-30 倍。 时间线：2024-04 首次发布 → 2025-05 rolldown-vite 技术预览（把 Vite 6/7 整体换成 Rolldown 的临时包，通过 npm alias "vite": "npm:rolldown-vite@x" 可选安装）→ 2025-12 Vite 8 beta 默认 Rolldown → 2026-03-12 Vite 8 稳定版，Rolldown 成为唯一默认打包器 → 2026-05 Rolldown 1.0 稳定。 Vite 8 现状：依赖预打包用 Rolldown、JS/JSX 转换与压缩用 Oxc（esbuild 配置项自动映射到 oxc 但已弃用）、CSS 压缩默认 Lightning CSS；多数 Vite 插件开箱即用；额外解锁了 advancedChunks 精细分包、模块级持久缓存、原生插件（hook filters）、原生 Module Federation，以及 Vite 8.1 的实验性 Bundled Dev Mode（大型应用开发期也打包，冷启动可快十余倍）。迁移建议：中小项目直接升 Vite 8（兼容层自动转换大部分配置）；插件重度依赖的大库可先停在 Vite 7 + rolldown-vite 灰度验证。注意 Vite 6/7 主线不是 Rolldown，面试时不要把路线图当成当时的现状。

4. 🆕 2026 年 Rspack、Turbopack、Vite（Rolldown）如何选型？

答案： 三者都是 Rust 系高性能打包工具，但定位不同：① Vite 8 + Rolldown：多框架通用（Vue/React/Svelte/Solid/Astro 等），开发期原生 ESM 按需编译 + 生产统一 Rolldown 打包，插件生态最广、周下载量最大，新项目的默认选择；② Rspack（字节跳动）：webpack API 兼容的替代品，配置结构、loader 与大部分 webpack 插件可复用，2025 年 1.0 GA，2026 年已发布 2.0/2.1，冷启动速度突出，适合存量 webpack 大型仓库低成本迁移；③ Turbopack（Vercel）：与 Next.js 深度绑定的增量打包器（函数级缓存、复用 SWC 转换），Next.js 15（2024-10）开发模式稳定，Next.js 16（2025-10）起 dev 与 next build 生产构建均稳定，并成为新项目默认打包器，但它基本不能脱离 Next.js 单独使用。 选型口诀：按"从哪里迁移"决定——webpack 存量项目 → Rspack；Next.js 项目 → 用内置 Turbopack；其他框架/全新项目 → Vite。Rspack（讲 webpack API）和 Rolldown（讲 Rollup API）是互补关系而非直接竞争。Parcel 仍在维护，但社区声量已明显落后。

5. 🆕 什么是 Vite 6 的 Environment API？解决什么问题？

答案： Vite 5 之前系统中只有两个隐式环境：client（浏览器）和可选的 ssr（Node）。现代应用往往同时运行在浏览器、Node SSR、Cloudflare workerd/Deno 等边缘运行时上，两套环境无法表达这种结构，框架作者只能写 hack 代码适配。Vite 6（2024-11）正式引入 Environment API：一个 dev server 内可存在多个相互独立的环境（共享 HTTP server、中间件、解析配置和插件管线，各自拥有模块图），每个环境连接自己的开发运行时——客户端由浏览器执行代码，其他环境由 Module Runner 拉取并执行 Vite 转换后的代码（如 workerd 经 miniflare 本地运行），使开发行为尽量对齐生产。 配置上通过 environments: { server: {}, edge: { resolve: { noExternal: true } } } 声明多个环境，未显式配置时继承顶层选项。Vite 5.1 的实验性 Vite Runtime API 在 Vite 6 演化为 Module Runner API。目标用户要分清：该 API 主要面向框架/库作者（Nuxt、SvelteKit、SolidStart 等）；普通 SPA/MPA 应用开发者完全无感知，配置和行为与 Vite 5 一致，不需要学习。该 API 在 Vite 6 发布时标记为实验性，后续大版本逐步稳定。

6. Webpack 的构建流程是什么？

答案： ① 读取 webpack.config.js 初始化配置；② 从 entry 开始递归分析依赖图；③ 对每个模块按 rules 配置调用对应 Loader 转换（如 Babel、CSS Loader）；④ 将模块转换结果合并为 Chunk；⑤ 通过 Plugin 在各生命周期钩子执行额外操作（如 HTML 生成、压缩）；⑥ 输出打包文件到 output 目录。

7. Loader 和 Plugin 的区别？

答案： Loader：文件转换器，在模块加载时转换文件内容（如将 .scss → CSS，.ts → JS），是单一职责的纯函数，按 use 数组逆序执行。Plugin：功能扩展，通过 Webpack 的 Tapable 钩子系统在构建各阶段插入逻辑，可访问完整的编译上下文（如生成 HTML 入口、提取 CSS 文件、定义全局变量）。Loader 处理文件级别，Plugin 处理构建流程级别。

8. 什么是 Tree Shaking？原理是什么？

答案： Tree Shaking 静态分析模块导入导出关系，移除未使用的代码（dead code elimination）。依赖 ES Module 的静态结构（import/export 是静态声明，构建时可分析），CommonJS 的动态 require 无法静态分析。要求：① 使用 ES Module；② 代码无副作用（package.json 中 "sideEffects": false，或指定有副作用的文件）；③ 生产模式（Rollup/Rolldown/Webpack 生产构建自动开启）。

9. 什么是代码分割（Code Splitting）？

答案： 将大 bundle 拆分为多个 chunk，按需加载，减少初始加载体积。三种方式：① 入口分割（多个 entry point）；② 动态导入（import('module') 返回 Promise，Vite/Webpack/Rspack 自动拆包）；③ SplitChunksPlugin（Webpack/Rspack 将公共依赖提取为独立 chunk）。常见策略：路由级分割（每个路由一个 chunk）+ 第三方库单独分包（vendor）。

10. 🆕 Vite 生产构建有哪些常用优化手段？

答案： ① 分包策略：Rollup 时代用 output.manualChunks 把 react/react-dom 等稳定大库拆成 vendor 包以利长缓存；Vite 8/Rolldown 中 manualChunks 对象形式已移除、函数形式弃用，推荐更精细的 output.advancedChunks.groups（类似 webpack splitChunks，用 name/test 声明分组），路由级 import() 仍自动拆包。② build.target：Vite 7 起默认 'baseline-widely-available'（Vite 7 约为 chrome107/safari16；Vite 8 升到 chrome111/edge111/firefox114/safari16.4），默认少转译、产物更小；要兼容更老浏览器再显式调低。③ modulepreload：默认 { polyfill: true } 自动注入 <link rel="modulepreload"> polyfill 并预加载动态 import 的依赖 chunk，库模式不注入，确认不需要可关闭（旧的 build.polyfillModulePreload 已弃用）。④ CSS 分包与压缩：CSS 默认按异步 chunk 做 code split（build.cssCodeSplit），Vite 8 起 CSS 压缩默认 Lightning CSS。⑤ 其他：Vite 8 JS 压缩默认走 Oxc；按需开 sourcemap；assetsInlineLimit 内联小资源；用 rollup-plugin-visualizer 分析包体；避免 barrel files（桶文件妨碍按需 Tree Shaking）；dev 期可用 server.warmup 预热高频文件。

11. 🆕 Vite 库模式、SSR 外部化和 d.ts 类型声明如何处理？

答案： 库模式（build.lib）：开发组件库/工具库时配置 lib: { entry, name, formats: ['es','cjs'], fileName }，产出多格式产物；库模式下 nodemodules 默认全部外部化、不注入 modulepreload polyfill、CSS 默认提取为独立文件。SSR 外部化：Vite 在 SSR 时默认外部化 nodemodules（ssr.external），因为 Node 可直接加载 CJS/ESM，避免重复打包；对只发布 ESM、含需转译新语法或有样式副作用的依赖，用 ssr.noExternal 强制纳入 Vite 管线打包（边缘运行时如 workerd 场景尤其常见，很多 SSR 报错都和 external/noExternal 配置有关）。类型声明：Vite 本身不生成 .d.ts（它只转译、不做类型检查），常见方案是 tsc --emitDeclarationOnly 单独产出声明，或用 vite-plugin-dts 插件自动生成、支持多入口与插入三斜线引用。发布前仍应跑 tsc --noEmit 保证类型无误。package.json 配合：用现代 exports 字段声明 import/require/types 条件导出，让不同环境解析到正确产物。

12. 🆕 Oxc 是什么？它在 Vite 中承担什么角色？

答案： Oxc（The JavaScript Oxidation Compiler）是 VoidZero 团队用 Rust 编写的 JS/TS 工具链合集，基于一套高性能统一 AST，包含 parser、resolver、transformer、minifier、linter（Oxlint）和 formatter（Oxfmt）。与其他工具的关系：① Rolldown 底层的解析与压缩就使用 Oxc；② Vite 8 中 TS/JSX 转换和 JS 压缩从 esbuild 切换为 Oxc transformer/minify（Vite 6.1 时 minify: 'oxc' 还是实验项，Vite 8 已成默认，esbuild 配置项自动转换但弃用）；③ Oxlint 对标 ESLint，2025 年发布 1.0、内置 650+ 条 Rust 原生规则，2026-03 推出兼容 ESLint 插件 API 的 JS Plugins（alpha），官方基准比 ESLint 快数十倍，已在 Preact、PostHog 等项目生产使用；④ Oxfmt（2026 年 beta）对标 Prettier；⑤ SWC 是另一套独立的 Rust 转译器（Next.js/Turbopack 生态使用），与 Oxc 是竞争关系；Biome 也是 Rust 实现但自带 AST 与 formatter，并不基于 Oxc。取舍：Oxlint 规则总量与插件生态仍不及 ESLint（框架自定义文件、类型感知规则在补齐），很多团队采用"Oxlint 跑绝大多数规则 + ESLint 兜底少量特殊规则"的过渡方案。

13. 🆕 Lightning CSS 是什么？与 PostCSS/Autoprefixer 什么关系？

答案： Lightning CSS 是 Rust 实现的 CSS 解析、转换与压缩一体化工具，速度远快于 JS 版 PostCSS 链，并内置按 browserslist 的语法降级（嵌套、color-mix()、逻辑属性等新特性自动改写）与高级压缩优化。Vite 中的集成：① css.transformer 可选 'postcss'（默认）或 'lightningcss'，开启后整条 CSS 处理管线（含 CSS Modules、@import 打包、降级）换成 Lightning CSS；② Vite 8 起 build.cssMinify 默认已是 'lightningcss'（仅压缩环节默认切换；想用回 esbuild 需自行安装 esbuild 并显式配置），而 transformer 在 Vite 8.1 仍处于"向默认切换推进中"的状态。与 PostCSS/Autoprefixer 是替代而非叠加关系：选择 lightningcss transformer 后 CSS 不再经过 PostCSS，Autoprefixer 的加前缀工作由 Lightning CSS 按 targets 自动完成；但大量 PostCSS 插件（Tailwind 的 PostCSS 插件、自定义插件链）在 Lightning CSS 下不可用，迁移前需要评估替代方案。

14. 🆕 esbuild 和 SWC 的定位是什么？为什么它们都不做类型检查？

答案： esbuild 是 Go 编写的一体化构建工具（打包 + 转译 + 压缩），Vite 6/7 用它做开发期转换和依赖预打包；SWC 是 Rust 编写的编译/转译库，Next.js（经 Turbopack）及大量 Babel 替代场景使用，也可配合其他打包器。二者核心定位都是"快速转译"：把 TS/JSX/新语法降级为可运行的 JS，不理解类型语义。不做类型检查的原因：转译是单文件、纯语法层面的工作，可高度并行、按需编译，契合 dev server 毫秒级响应；而类型检查需要整个程序的类型图（跨文件导入导出、泛型推断、声明合并），架构和成本完全不同，塞进转译管线会毁掉速度优势。因此 Vite 对 .ts 只 transpile（要求 isolatedModules: true，不支持 const enum 等需跨文件信息的特性），类型检查交给 tsc --noEmit（CI 中执行或单独开 tsc --watch）、IDE 或 vite-plugin-checker。2026 现状：Vite 8 中 esbuild 的转译/压缩角色已被 Oxc 取代（配置仍兼容），SWC 则继续在 Next.js/Turbopack 生态中使用。

15. 如何优化 Webpack 构建速度？

答案： ① 缩小查找范围：配置 resolve.extensions、resolve.alias、include/exclude Loader 范围；② 缓存：cache: { type: 'filesystem' } 开启持久缓存（Webpack 5），Babel Loader 开启 cacheDirectory；③ 多线程：thread-loader 或 happypack；④ 减少插件：生产才用的插件不要在开发环境运行；⑤ DllPlugin / 联邦模块：预编译不变的第三方库；⑥ 升级到 Webpack 5（内置持久缓存、更快的算法）。

⚠️ 版本更新（2026-09 核实）：第⑤点中的 DllPlugin 在 Webpack 5 持久缓存时代已基本淘汰。DLL 需要手动维护预编译清单、依赖升级后容易出现版本不一致问题，而 cache: { type: 'filesystem' } + Babel 缓存已能覆盖其收益，新项目不建议再引入。模块联邦（Module Federation）解决的是运行时跨应用共享模块，属于微前端架构需求，并不能用来给日常构建提速。若团队可更换工具链，Rspack 对 webpack 配置高度兼容，是更彻底的提速路径。

16. 什么是 Module Federation（模块联邦）？

答案： Webpack 5 引入，允许多个独立构建的应用之间共享模块，实现真正的微前端运行时共享。一个应用可以作为 Host（消费其他应用暴露的模块），也可以作为 Remote（暴露模块给其他应用使用）。共享依赖（如 React）只加载一次，无需重复打包。适合大型企业级微前端架构。

ℹ️ 补充（2026-09）：Vite 生态曾长期依赖社区的 vite-plugin-federation；Rolldown 已把 Module Federation 作为原生能力内建，Vite 8 项目做模块联邦不再必须借助社区插件。

包管理与依赖

17. package.json 中 dependencies 和 devDependencies 的区别？

答案： dependencies：生产运行所需的依赖（如 React、Axios），会打包进产物或随项目部署；devDependencies：只在开发时需要的依赖（如 Vite、TypeScript、ESLint、测试框架），不进入生产产物。npm install --production 只安装 dependencies。区分清楚可减小生产镜像体积，加快部署。

18. package-lock.json / pnpm-lock.yaml 的作用是什么？

答案： 锁文件精确记录每个依赖及其依赖的具体版本和完整性哈希（SHA），保证所有环境（本地/CI/生产）安装的依赖版本完全一致，避免"我这里没问题"的问题。必须提交到版本库。不同包管理器的锁文件格式不同，混用（如同时有 package-lock.json 和 yarn.lock）会导致混乱，应统一使用一种。

19. 什么是 peerDependencies？

答案： peerDependencies 声明插件/库对宿主环境的依赖要求，但不自动安装，由使用者手动安装兼容版本。如 React 插件库声明 "peerDependencies": { "react": ">=16.8.0" }，表示需要宿主项目提供 React，避免重复安装多个 React 实例。npm 7+ 自动安装 peer deps（之前版本只警告）。

20. 什么是 npm script 的 pre 和 post 钩子？

答案： 在 script 名称前加 pre 或 post 前缀，npm 会自动在对应脚本前后执行：

{
  "scripts": {
    "prebuild": "npm run lint",
    "build": "vite build",
    "postbuild": "npm run compress"
  }
}

执行 npm run build 时自动依次运行 prebuild → build → postbuild，适合串联步骤。

21. 🆕 Corepack 是什么？Node 25 之后包管理器安装有什么变化？

答案： Corepack 是 Node 官方附带的包管理器代理：在项目中直接运行 pnpm/yarn 时，它会读取 package.json 的 packageManager 字段（如 "packageManager": "pnpm@9.15.0"）自动下载并切换到对应版本，保证团队成员使用同一个包管理器版本，通过 corepack enable 启用。 版本变化（2026-09 核实）：Corepack 仅随 Node 14.19 到 Node 25 之前的版本分发；Node 25（2025-10 发布）起不再内置 Corepack，新环境要么 npm install -g corepack 单独安装，要么直接安装 pnpm/yarn，不能再假设 corepack 命令必然存在。包管理器侧，pnpm 11（2026-04）要求 Node 22+、改为纯 ESM 分发，store 索引改用 SQLite，并默认开启供应链安全策略（如新包发布 24 小时后才允许安装的 minimumReleaseAge、构建脚本白名单 allowBuilds）。当前 Node LTS 为 24，Node 20 已于 2026-04 EOL。团队实践建议：锁定唯一包管理器（packageManager 字段 + only-allow 类拦截脚本）、锁文件必提交。

代码质量

22. ESLint 的作用和配置方式？

答案： ESLint 是 JS/TS 静态代码分析工具，检查代码质量和风格问题，可自动修复部分问题（--fix）。配置文件（.eslintrc.json 或 eslint.config.js）中配置：parser（如 @typescript-eslint/parser）、plugins、extends（规则集，如 eslint:recommended、@typescript-eslint/recommended、plugin:react/recommended）、rules（自定义规则）。配合 VSCode ESLint 插件实现实时提示。

⚠️ 版本更新（2026-09 核实）：ESLint 9（2024-04）起 Flat Config（eslint.config.js）成为默认配置格式，旧 .eslintrc.* 同期被弃用；ESLint 10（2026-02 发布）已彻底移除 eslintrc 系统——.eslintrc.json、.eslintignore、ESLINTUSEFLAT_CONFIG、--env 等旧参数全部失效，Node 要求 20.19+/22.13+/24+。新项目应直接写 Flat Config（单一配置文件、插件直接 import、用 languageOptions 代替 parserOptions）： ``js // eslint.config.js import tseslint from 'typescript-eslint' export default [ { files: ['**/*.ts'], languageOptions: { parser: tseslint.parser }, rules: { 'no-unused-vars': 'error' } }, ] ` 旧仓库可用 npx @eslint/migrate-config .eslintrc.json` 自动迁移。ESLint 10 还改为从被检查文件所在目录向上查找配置，对 monorepo 多包不同规则更友好。

23. Prettier 和 ESLint 有什么区别？如何配合使用？

答案： Prettier 是代码格式化工具，只关注代码样式（缩进、引号、换行等），不做语义分析；ESLint 关注代码质量（未使用变量、潜在错误等），也有部分格式规则。配合使用：安装 eslint-config-prettier（关闭 ESLint 中与 Prettier 冲突的格式规则），eslint-plugin-prettier（将 Prettier 作为 ESLint 规则运行）。二者职责互补，不应重复配置格式规则。

24. Husky 和 lint-staged 如何配合使用？

答案： Husky：配置 Git hooks，在特定 Git 操作前自动执行脚本（如 pre-commit、commit-msg、pre-push）。lint-staged：只对本次提交（staged）的文件运行 lint/format，而非全量扫描（避免慢）。组合：提交前自动对变更文件运行 ESLint + Prettier，阻止不合规代码进入仓库，保证代码库质量。

# .husky/pre-commit
npx lint-staged
// package.json
"lint-staged": {
  "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
  "*.{css,md}": ["prettier --write"]
}
⚠️ 版本更新（2026-09 核实）：Husky v9（2024-01 发布，当前主线）初始化方式已变：使用 npx husky init（不再是 husky install 或 npx husky-init），package.json 中的 prepare 脚本简化为 "prepare": "husky"；v9 通过 git config 的 core.hooksPath 指向仓库内 .husky/ 目录，钩子文件是纯 shell（不再需要 . "$(dirname -- "$0")//husky.sh" 样板行），.husky/_/ 是自动生成的运行时目录，不要手改。上面示例中的纯命令写法本身即 v9 风格，可继续使用。

25. 什么是 Commitlint？

答案： Commitlint 检查 Git commit message 是否符合规范（通常是 Conventional Commits 规范：feat:, fix:, docs:, refactor:, chore: 等）。配合 Husky commit-msg 钩子使用，不符合规范的提交会被拒绝。规范化的 commit 便于：自动生成 CHANGELOG、语义化版本自动升级（semantic-release）、代码审查。

26. 🆕 Biome 是什么？和 ESLint + Prettier 组合如何取舍？

答案： Biome 从 Rome 项目 fork 而来，是 Rust 编写的单二进制 linter + formatter 一体化工具：一个 biome.json 同时完成 lint、格式化、import 排序，零第三方依赖、安装即用，速度比 ESLint + Prettier 链快一到两个数量级，也不存在两工具格式规则互相冲突的问题。Biome 2.0（2025 年末，代号 Biotype）首次提供不依赖 TypeScript 编译器的类型感知 lint，并引入 GritQL 插件系统、多文件分析；2026 年已迭代到 2.5，内置 500+ 条规则，改进了 Vue/Svelte/Astro 支持。 取舍建议：新项目、规则需求主流（推荐规则集 + 少量自定义）选 Biome 最省心，CI 提速明显；存量项目如果深度依赖 ESLint 插件生态（大量 React/无障碍/企业自定义规则），迁移要先核对规则覆盖率（格式化与 Prettier 约 97%+ 兼容，仍建议跑快照对比），可以继续用 ESLint 10（已强制 Flat Config），或关注 Oxlint——它走"兼容 ESLint 插件 API"路线，对大型 ESLint 代码库迁移更平滑。

测试

27. 🆕 Vitest 是什么？与 Jest 相比有什么优劣？

答案： Vitest 是 Vite 团队出品的测试框架，复用 Vite 的配置、插件和转译管线：开箱支持 TS/JSX/ESM、watch 模式按模块粒度极速重跑，API 与 Jest 高度兼容（describe/it/expect/vi.mock，开启 globals: true 后用例代码几乎不用改）。核心能力：① 环境可选 node/jsdom/happy-dom；② Browser Mode 在 Vitest 4 已稳定，可用真实 Chromium（Playwright/WebDriver provider）跑组件测试，验证真实浏览器 API，替代部分 Playwright Component Testing 场景；③ 多项目/workspace 模式（vitest.workspace.ts + defineWorkspace）可在 monorepo 中给不同包、不同环境（node 单测与 browser 组件测）分组并行执行（配置项 workspace 在 Vitest 3.2 更名为 projects）。版本：Vitest 4 要求 Vite 6+/Node 20+，4.1（2026-03）支持 Vite 8。与 Jest 对比：省去 ts-jest/babel-jest 配置、与 vite.config 同源、HMR 式反馈快；代价是绑定 Vite 生态——非 Vite 项目（重度自定义 webpack/Next 转换链）迁移前要评估，Vitest 4 的 V8 覆盖率重映射逻辑重写，升级后覆盖率数字会有变化。

CI/CD

28. 什么是 CI/CD？

答案： CI（持续集成）：代码提交后自动触发构建、测试，尽早发现集成问题。CD（持续交付/部署）：CI 通过后自动将代码部署到测试/预发/生产环境。核心价值：缩短反馈循环、减少手动操作错误、提高发布频率和可靠性。常用工具：GitHub Actions、GitLab CI/CD、Jenkins、CircleCI。

29. GitHub Actions 的基本结构是什么？

答案：

# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm run lint
      - run: pnpm run test
      - run: pnpm run build

核心概念：workflow（工作流）→ job（任务，可并行）→ step（步骤，顺序执行）。

30. 前端项目的 CI 流程通常包含哪些步骤？

答案： ① 代码检出（checkout）；② 安装依赖（pnpm install --frozen-lockfile，使用锁文件保证一致性）；③ 类型检查（tsc --noEmit）；④ Lint 检查（eslint）；⑤ 单元测试（vitest run/jest --ci）；⑥ 构建（vite build）；⑦ E2E 测试（Playwright/Cypress）；⑧ 产物部署/上传（OSS、CDN、Vercel、Netlify）；⑨ 性能检查（Lighthouse CI）。

31. 什么是语义化版本（Semantic Versioning）？

答案： 版本格式 MAJOR.MINOR.PATCH：MAJOR（重大版本）：有破坏性变更（Breaking Change），不兼容旧版；MINOR（次版本）：新增功能，向后兼容；PATCH（修订版）：Bug 修复，向后兼容。package.json 依赖版本前缀：^1.2.3（允许 MINOR 和 PATCH 升级）、~1.2.3（只允许 PATCH 升级）、无前缀（锁定精确版本）。

环境配置

32. .env 文件的使用规范是什么？

答案：

.env              # 所有环境通用的默认值
.env.local        # 本地覆盖（不提交 git）
.env.development  # 开发环境
.env.production   # 生产环境
.env.test         # 测试环境

Vite 中环境变量需以 VITE 开头才暴露给客户端（import.meta.env.VITEAPI_URL），避免泄露服务端机密。敏感信息（API 密钥、数据库密码）不应进入前端 bundle，只在服务端读取。

ℹ️ 补充（2026-09 核实）：Vite 6/7/8 的多模式（--mode）、envDir、VITE_ 前缀暴露规则均无实质变化，上述规范继续适用；只有不带前缀的变量通过 loadEnv 在 Node 侧（配置文件/SSR）可见。

33. Monorepo 下如何共享 TypeScript / ESLint 配置？

答案： 创建共享配置包（如 packages/tsconfig、packages/eslint-config），其他包通过 extends 引用：

// packages/web/tsconfig.json
{ "extends": "@company/tsconfig/base.json", "include": ["src"] }

// packages/web/.eslintrc.json
{ "extends": ["@company/eslint-config"] }

包管理器 workspace 让内部包可像普通 npm 包一样引用，无需发布到 registry。

⚠️ 版本更新（2026-09 核实）：示例中的 .eslintrc.json 写法在 ESLint 10 已失效。共享 ESLint 配置包现在直接导出 Flat Config 数组（export default [ ... ]），消费方在自己的 eslint.config.js 中 import companyConfig from '@company/eslint-config' 后展开即可；TS 配置的 extends 方式不变。

34. 🆕 Monorepo 中如何做跨包的构建缓存？

答案： Monorepo 的痛点是只改了一个包，CI 却全量 lint/test/build。Turborepo、Nx 这类任务编排工具按任务的输入哈希（源码、配置、锁文件、环境变量）决定是否命中缓存：声明 task 依赖图（如 build 依赖 ^build，即先建依赖包）、inputs 和 outputs（如 dist/、.tsbuildinfo），命中时直接还原产物、跳过执行。本地缓存让重复构建秒过；Remote Cache（Vercel Remote Cache、Nx Cloud 或自建 S3/MinIO 后端）让 CI 各任务甚至团队成员之间共享缓存，PR 上未改动的包不再重建。 与 Vite library 配合**：packages/* 各自用 Vite 库模式或 TypeScript project references 产出 dist，包间通过 workspace 协议引用；缓存 key 天然包含上游包的哈希，A 包变更才会让依赖它的 B 包缓存失效。注意事项：产物要确定性（固定 sourcemap/文件名策略）、把影响构建的 env 变量纳入 inputs、.vite 缓存目录与 dist 一起声明为 outputs。它与 pnpm 的内容寻址 store 是两层缓存（一个管依赖、一个管任务产物），互补不替代；超大规模仓库还可考虑 Rush、Bazel。

前端监控

35. 前端错误监控应该捕获哪些错误？

答案： ① window.onerror：JS 运行时错误（语法错误、引用错误等）；② window.addEventListener('unhandledrejection')：未处理的 Promise rejection；③ try/catch 手动捕获：业务关键路径错误；④ React ErrorBoundary / Vue app.config.errorHandler：组件渲染错误；⑤ Axios 响应拦截器：API 错误；⑥ 资源加载错误：window.addEventListener('error', handler, true)（捕获阶段）。

36. 如何实现前端性能数据上报？

答案：

// 用 PerformanceObserver 采集指标
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    // 上报到后端
    navigator.sendBeacon('/api/metrics', JSON.stringify({
      name: entry.name,
      value: entry.startTime,
      id: generateId()
    }));
  }
});
observer.observe({ type: 'largest-contentful-paint', buffered: true });

用 navigator.sendBeacon（不阻塞页面卸载）而非 fetch 上报，确保页面关闭时数据不丢失。

37. 什么是前端灰度发布？

答案： 灰度发布（Canary Release）是将新版本先发布给一小部分用户，观察指标（错误率、性能、业务转化），无问题再全量推进。前端实现方式：① CDN 版本控制（不同用户返回不同版本的 HTML/JS）；② Feature Flag（特性开关，通过配置服务控制功能开关，如 LaunchDarkly）；③ Nginx 按 Cookie/IP/比例路由不同版本。灰度发布降低发布风险，出问题可快速回滚。
