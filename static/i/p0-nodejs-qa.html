Node.js 常见面试题（附答案）

📌 版本说明（2026-09-16 核实）：文中标注版本的结论以当前 Node 24「Krypton」LTS（生产推荐）与 Node 26 Current（2026-10 将转 LTS）为准；Node 22「Jod」LTS 处于维护期，Node 20 已 EOL。

基础与运行原理

1. Node.js 是什么？核心特点有哪些？

答案： Node.js 是基于 Chrome V8 引擎的 JavaScript 运行时，让 JS 能在服务端运行。核心特点：

  • 单线程 + 事件驱动
  • 非阻塞 I/O（异步）
  • 高并发处理能力（适合 I/O 密集型）
  • npm 生态极其丰富
  • 前后端同语言，利于全栈开发

不适合 CPU 密集型任务（会阻塞事件循环）。

2. Node.js 的事件循环与浏览器有什么区别？

答案： Node.js 事件循环基于 libuv 实现，单线程运行，一轮循环按固定顺序经过六个阶段，每个阶段维护自己的宏任务队列：

阶段处理内容
1. timers到期的 setTimeout/setInterval 回调
2. pending callbacks被推迟到下一轮的系统级回调（如 TCP ECONNREFUSED）
3. idle/prepare内部使用
4. poll检索并执行 I/O 回调；队列空时在此阻塞等待新 I/O，若有到期 timer 则跳回 timers
5. check执行 setImmediate 回调
6. close callbacks关闭事件回调（如 socket.on('close')）

微任务（microtask）：每个回调执行完、以及每次阶段切换前都会清空微任务队列。微任务分两个子队列，nextTick 队列先于 Promise 队列，两者都清空后才继续：

  • process.nextTick 注册的回调（nextTick 队列，优先级最高）
  • Promise 回调、queueMicrotask、await 后续（V8 promise 队列）

与浏览器的区别：

  • 浏览器没有 libuv 六阶段划分，宏任务由不同任务队列调度；Node 特有 process.nextTick 和 setImmediate
  • setTimeout(fn, 0) 与 setImmediate 在主模块顶层执行时顺序不保证（取决于事件循环启动时序）；但在 I/O 回调内（poll 之后），setImmediate 总是先执行
  • Node 的 I/O 由 libuv 线程池/操作系统异步完成，完成后把回调投递到 poll 阶段

最小示例（微任务相对顺序固定）：

process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
queueMicrotask(() => console.log('microtask'));
console.log('sync');
// 输出：
// sync
// nextTick   ← nextTick 队列先清空
// promise    ← 再清空 promise 队列（按入队顺序）
// microtask

I/O 回调内 setImmediate 必先于 setTimeout：

const fs = require('node:fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
// 输出（固定顺序）：
// immediate
// timeout

实践建议：需要在当前操作完成后立即执行用 process.nextTick（但勿递归滥用，会饿死 I/O）；需要主动让出事件循环用 setImmediate。

3. process.nextTick 和 setImmediate 的区别？

答案： process.nextTick 在当前事件循环阶段结束时立即执行（在所有 I/O 和微任务之前），优先级最高，滥用可能饿死 I/O；setImmediate 在事件循环的 check 阶段执行，在 I/O 回调之后。执行顺序：process.nextTick > Promise 微任务 > setImmediate > setTimeout(fn, 0)（在 I/O 回调中 setImmediate 总是先于 setTimeout）。

❌ 更正（2026-09 核实）：两处表述需修正：① process.nextTick 本身就属于微任务（nextTick 微任务队列），并非"在所有微任务之前"；准确说法是每个回调结束/阶段切换时，先清空 nextTick 队列，再清空 Promise 队列。② setImmediate 并非总是先于 setTimeout(fn, 0)——该顺序仅在 I/O 回调内成立，主模块顶层两者顺序不保证。详见第 2 题。

4. Node.js 如何处理高并发？

答案： Node.js 用单线程 + 非阻塞 I/O + 事件循环处理并发：I/O 操作（文件、网络、数据库）交由 libuv 线程池或操作系统异步处理，主线程继续处理其他请求；I/O 完成后将回调加入事件队列。因此大量并发 I/O 请求不会互相阻塞。但 CPU 密集操作会阻塞事件循环，需用 worker_threads 或子进程处理。

5. Node.js 的模块系统有哪些？有什么区别？

答案：

  • CommonJS（默认，.js 文件）：require/module.exports，同步加载，运行时解析，require 有缓存（首次加载后缓存）
  • ES Module（.mjs 或 package.json 中 "type": "module"）：import/export，异步静态分析，支持 Tree Shaking，是未来标准

现代 Node.js（16+）支持 ESM，但与 CJS 互操作有限制（不能在 CJS 中 require ESM）。

⚠️ 版本更新（2026-09 核实）："不能在 CJS 中 require ESM" 已过时。Node 20.19.0 / 22.12.0 起 require() 可同步加载 ESM（此前需 --experimental-require-module，Node 23 默认开启，25.4.0 起标记稳定并回移植到受支持的 LTS 线）。限制条件：① 被加载的 ESM 及其整条依赖图中不能含顶层 await，否则抛 ERRREQUIREASYNCMODULE，这种情况仍需用动态 import()；② 不支持跨 CJS/ESM 边界的循环依赖（ERRREQUIRECYCLEMODULE）。详见第 28 题。

6. CommonJS 的模块缓存机制是什么？

答案： Node.js 在首次 require 一个模块时，将其导出对象缓存在 require.cache 中。后续 require 同一模块路径直接返回缓存，不重新执行模块代码。这意味着模块中的状态（变量、连接）是单例的，单元测试时可能需要清除缓存（delete require.cache[modulePath]）。循环依赖时会返回部分加载的对象。

核心模块

7. fs 模块有哪些常用 API？同步和异步如何选择？

答案： 常用 API：fs.readFile/writeFile/appendFile/unlink/mkdir/stat/readdir（异步回调版），加 Sync 后缀为同步版，fs.promises.* 为 Promise 版。选择原则：服务端代码用异步（避免阻塞事件循环）；脚本/CLI 工具可用同步（代码更简洁，无并发压力）。推荐 fs.promises + async/await 组合。

8. path 模块的常用方法有哪些？

答案：

  • path.join(...segments)：拼接路径（自动处理斜杠）
  • path.resolve(...segments)：解析为绝对路径（从右向左解析）
  • path.dirname(p)：获取目录部分
  • path.basename(p, ext)：获取文件名部分
  • path.extname(p)：获取扩展名
  • path.parse(p) / path.format(obj)：路径字符串与对象互转
  • __dirname（CJS）/ import.meta.dirname（ESM）：当前文件目录

9. stream 流有哪些类型？什么场景使用？

答案： 四种类型：

  • Readable（可读流，如 fs.createReadStream）
  • Writable（可写流，如 fs.createWriteStream）
  • Duplex（双工流，如 TCP socket）
  • Transform（转换流，如 zlib 压缩/解密）

适用场景：处理大文件（避免一次性加载进内存）、HTTP 请求/响应、管道数据处理（readable.pipe(transform).pipe(writable)）。stream.pipeline 比 pipe 更安全（自动处理错误和清理）。

10. EventEmitter 的使用和注意事项？

答案：

const EventEmitter = require('events');
const emitter = new EventEmitter();
emitter.on('data', handler);
emitter.emit('data', payload);
emitter.once('close', handler); // 只触发一次
emitter.off('data', handler);  // 移除监听

注意：

  • 默认最多 10 个监听器（超出警告，用 setMaxListeners 调整）
  • 必须监听 error 事件，否则会抛出未捕获异常
  • 同步触发（emit 时同步执行所有监听器）
  • 内存泄漏常见原因：监听器未移除

11. http 模块如何创建服务器？

答案：

const http = require('http');
const server = http.createServer((req, res) => {
  const { method, url, headers } = req;
  let body = '';
  req.on('data', chunk => body += chunk);
  req.on('end', () => {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify({ method, url, body }));
  });
});
server.listen(3000, () => console.log('Server running on port 3000'));

实际项目通常用 Express/Fastify/Koa 封装，而非直接使用原生 http。

12. 什么是 Buffer？什么时候用？

答案： Buffer 是 Node.js 处理二进制数据的核心类，类似 Uint8Array。用于处理 TCP 流、文件系统操作、加密、图片处理等二进制场景。常用：Buffer.from('hello', 'utf8')（字符串转 Buffer）、buf.toString('utf8')（Buffer 转字符串）、Buffer.alloc(size)（创建指定大小的零填充 Buffer）。注意 Buffer.allocUnsafe 速度快但不清零，不安全用于密码学。

框架与工程

13. Express 的中间件机制是什么？

答案： Express 中间件是函数，签名 (req, res, next) => void。请求到达时按注册顺序依次执行，每个中间件通过调用 next() 传递控制权，或直接发送响应终止链。错误中间件签名为 (err, req, res, next)，next(err) 触发。常见中间件：日志（morgan）、解析请求体（express.json）、鉴权、CORS、静态文件。洋葱模型：Koa 使用 async/await 的"洋葱圈"模型（中间件可以在请求前后执行代码）。

洋葱：请求从外层进入，经过所有中间件，响应从内层返回，再经过所有中间件（反向顺序）

14. Express 和 Koa 的区别是什么？

答案： Express：同步中间件（回调风格），内置路由和多种功能，生态最成熟，入门简单；错误处理需传 next(err)。Koa：由 Express 原班人马创作，精简内核（无内置路由等），中间件基于 async/await，洋葱模型（await next() 后可执行后续逻辑），错误处理更优雅（try/catch + ctx.app.emit('error')）。NestJS 是在 Express/Fastify 上的完整框架，提供 IoC、模块化、装饰器等能力，适合大型项目。

15. 什么是 NestJS？它的核心概念有哪些？

答案： NestJS 是基于 TypeScript 的渐进式 Node.js 框架，深受 Angular 启发。核心概念：

  • Module（模块，组织代码边界）
  • Controller（路由处理，@Get/@Post 等装饰器）
  • Service（业务逻辑，通过 DI 注入）
  • Provider（注入的任何服务/仓库）
  • Guard（权限守卫）
  • Interceptor（拦截器，类似 Axios 拦截器）
  • Pipe（数据转换和验证，class-validator）
  • Middleware（与 Express 中间件兼容）

16. 如何在 Node.js 中进行错误处理？

答案：

  • 同步代码：try/catch
  • 异步回调：回调第一个参数约定为 err
  • Promise：.catch() 或 async/await + try/catch
  • 全局未捕获：process.on('uncaughtException', handler)（严重错误，记录日志后应退出进程）
  • process.on('unhandledRejection', handler)（Promise 未捕获）
  • Express 错误中间件：(err, req, res, next)
  • 生产建议：用 PM2/cluster + 进程守护，异常时自动重启

17. Node.js 中如何使用环境变量？

答案： 通过 process.env.VAR_NAME 访问。开发时使用 .env 文件配合 dotenv 库（require('dotenv').config()）加载。生产环境通过系统环境变量、Docker ENV、Kubernetes ConfigMap 注入，不应将 .env 提交到版本库（加入 .gitignore）。@nestjs/config 封装了 NestJS 中的配置管理。

⚠️ 版本更新（2026-09 核实）：Node 20.6.0 起已内置 dotenv 能力，多数场景不再需要第三方 dotenv 包： - node --env-file=.env app.js 启动时加载；文件可能不存在时用 --env-file-if-exists=.env（不报错） - Node 22 起支持多个 --env-file，后者覆盖前者：node --env-file=.env --env-file=.env.production app.js - 也可编程式加载：process.loadEnvFile('.env')（20.12.0+） - 优先级：进程已存在的环境变量高于文件中的值；所有值均为字符串，不做布尔/数字转换 需要变量展开（${VAR}）、复杂校验等高级特性时仍可使用 dotenv/dotenv-expand。

性能与部署

18. 如何利用多核 CPU？

答案： Node.js 单进程单线程，默认只用一个 CPU 核。利用多核方案：

  • cluster 模块：主进程 fork 多个子进程（一般等于 CPU 核数），共享端口，各自处理请求
  • worker_threads：在同一进程内创建线程，共享内存（SharedArrayBuffer），适合 CPU 密集任务
  • PM2：生产环境常用进程管理器，pm2 start app.js -i max 自动按 CPU 核数启动集群

19. 如何排查 Node.js 内存泄漏？

答案：

  • 监控内存：process.memoryUsage() 或 PM2 监控面板
  • 生成堆快照：v8.writeHeapSnapshot() 或 Chrome DevTools（连接 --inspect）
  • 对比多次堆快照，找到持续增长的对象
  • 常见原因：全局变量积累、闭包引用、事件监听器未移除、定时器未清理、缓存无限增长
  • 工具：clinic.js（诊断）、heapdump、memwatch-next

20. PM2 有哪些常用命令和特性？

答案：

pm2 start app.js --name myapp   # 启动
pm2 start app.js -i max         # 集群模式（按 CPU 核数）
pm2 list                         # 查看进程
pm2 logs myapp                   # 查看日志
pm2 restart/stop/delete myapp    # 重启/停止/删除
pm2 monit                        # 实时监控
pm2 startup                      # 设置开机自启
pm2 save                         # 保存当前进程列表

特性：进程守护（崩溃自动重启）、日志管理、集群管理、热重载（pm2 reload，零停机更新）、监控面板。

⚠️ 版本更新（2026-09 核实）：注意区分 Node 自带能力与 PM2 的定位： - 多核利用：PM2 cluster 底层就是内置 cluster 模块，直接用 cluster（或 Fastify/NestJS 等框架的集群适配器）也能实现多进程共享端口 - 开发热重启：用内置 node --watch（Node 22 起稳定，文件变更自动重启），无需 PM2/nodemon - 生产守护：在裸机/虚拟机上 PM2 仍提供守护、日志聚合、ecosystem.config.js 声明式管理、监控面板等运维价值；但在 Docker/Kubernetes 环境中，主流做法是每容器跑单进程，由编排系统负责重启、水平扩展与滚动更新，通常不再引入 PM2。

21. 什么是 Node.js 的 --inspect 调试模式？

答案： 启动时加 --inspect 或 --inspect-brk（在第一行暂停）开启调试端口（默认 9229）。然后可以用 Chrome DevTools（chrome://inspect）或 VSCode 连接，进行断点调试、内存分析、CPU 性能分析。--inspect-brk 适合调试启动时的问题。生产环境谨慎开启，注意端口安全。

22. 如何实现 Node.js 的优雅退出（Graceful Shutdown）？

答案：

process.on('SIGTERM', async () => {
  console.log('Received SIGTERM, graceful shutdown...');
  server.close(async () => {      // 停止接受新连接
    await db.disconnect();         // 关闭数据库连接
    await redis.quit();            // 关闭 Redis 连接
    process.exit(0);
  });
  // 超时强制退出
  setTimeout(() => process.exit(1), 30000);
});

优雅退出：收到信号后停止接受新请求，等待进行中的请求完成，清理资源（DB 连接、消息队列），然后退出。Kubernetes 部署时 SIGTERM 是 Pod 终止信号，必须处理。

生态与工具

23. npm、yarn、pnpm 的区别？

答案： npm：Node.js 官方包管理器，v7+ 支持 workspaces，但 nodemodules 扁平化有幽灵依赖问题；yarn（v1）：并行下载更快，有 yarn.lock，目前维护模式；yarn（v2/3/4）：PnP（Plug'n'Play）模式，无 nodemodules，启动极快；pnpm：硬链接 + 符号链接共享依赖，节省磁盘，严格依赖隔离（无幽灵依赖），monorepo 支持好，现代项目首选。

⚠️ 版本更新（2026-09 核实）： - pnpm 现状：2026-04 发布 pnpm 11，要求 Node.js 22+，pnpm 自身转为纯 ESM；store 索引改用 SQLite 提升安装速度；默认开启供应链安全策略（新包发布满 1 天才解析 minimumReleaseAge、阻断异常子依赖等）；全局安装相互隔离；Node 24 LTS 配套的是 npm 11。 - Corepack 变化：Corepack 随 Node 14.19 起分发，但自 Node 25.0.0（2025-10）起已从官方发行包中移除（Node 25 已 EOL，Node 26 同样不自带）。在 Node 25+/26 上需 npm install -g corepack 单独安装；Node 22/24 LTS 仍内置，可继续用 corepack enable 按 package.json 的 packageManager 字段锁定 yarn/pnpm 版本。

24. 什么是 Monorepo？常用工具有哪些？

答案： Monorepo 是将多个项目/包放在同一 Git 仓库的管理方式。优点：跨包共享代码、统一构建流程、原子化提交（多包联动修改一次提交）、便于重构。常用工具：

  • pnpm workspaces（包管理）
  • Turborepo（任务编排、构建缓存，最快）
  • Nx（功能更丰富，有代码生成器、依赖图分析）
  • Lerna（较老，现配合 nx 使用）

25. Node.js 中如何处理大文件上传？

答案：

  • 流式处理：直接 pipe 到存储，不在内存中积累完整文件（multer 的 diskStorage、或自定义 busboy 流处理）
  • 分片上传：前端将文件切分为小块（File.slice()）分别上传，服务端接收后合并，支持断点续传
  • 直传云存储：服务端生成预签名 URL，前端直接上传到 OSS/S3，减轻服务器压力

注意设置请求体大小限制（express.json({ limit: '10mb' })）。

版本代号状态（2026-09）说明
Node 26—Current（最新 26.8.x）2026-05 发布，2026-10 将转 LTS

27. 🆕 Node.js 原生运行 TypeScript：什么是 type stripping？版本与限制？

答案： Node 内置了基于 Amaro 的 TypeScript 支持，无需 ts-node/tsx/预构建即可直接 node app.ts：

  • 22.6.0：新增 --experimental-strip-types（实验性）
  • 22.7.0：新增 --experimental-transform-types，支持需要转译的语法（enum、namespace、构造器参数属性等）
  • 23.6.0 / 22.18.0：类型擦除（type stripping）默认开启；24.3/22.18 起去掉实验警告
  • 24.12.0 / 25.2.0：类型擦除标记稳定
  • 26.0.0：移除 --experimental-transform-types 标志

原理与限制：

  • 只擦除、不转译：把类型注解原地替换为空白，因此极快且不需要 source map；不做任何类型检查，类型错误不会阻断运行，CI 仍应跑 tsc --noEmit
  • 不读取 tsconfig.json：不支持 paths 路径映射、不做语法降级（target），相对导入必须带 .ts 扩展名，默认不处理 node_modules 内的 TS
  • 仅支持"可擦除语法"（接口、类型注解、as、import type 等）；enum/namespace/参数属性/<T> 断言/import = 等带运行时语义的语法在 24/22 上需 transform-types flag

与 tsx/ts-node 的对比：tsx（esbuild）功能完整、支持 tsconfig 与各类边缘语法，仍是复杂项目首选；ts-node 已基本停止维护。原生方案零依赖、零构建，非常适合脚本、CLI、node:test 测试（node --test "**/*.test.ts"）与内部工具。

28. 🆕 require(esm) 同步加载 ESM 的规则与边界是什么？

答案： CJS 中用 require() 加载原生 ESM 的能力演进：早期需 --experimental-require-module → 20.19.0 / 22.12.0 默认开启 → 25.4.0（2026-01）标记稳定并回移植到受支持 LTS 线。规则：

  • 整个依赖图必须完全同步：被 require 的 ESM 及其任意依赖中都不能有顶层 await，否则抛 ERRREQUIREASYNC_MODULE（此时改用动态 import()）
  • 目标必须是明确的 ESM：.mjs 扩展名，或最近的 package.json 含 "type": "module"
  • 不支持跨 CJS/ESM 边界的循环依赖，抛 ERRREQUIRECYCLE_MODULE（纯 CJS 或纯 ESM 内部循环仍可）；常见解法是把其中一侧改为懒加载
  • 返回值类似 import() 的命名空间对象（具名导出 + default）；ESM 可导出名为 'module.exports' 的值来模拟 CJS 默认导出
  • 库作者可用 "module-sync" exports condition 同时支持 require 与 import；运行时用 process.features.require_module 检测能力

影响：曾长期存在的"ESM-only 包无法被 CJS require"痛点基本消除，越来越多新库（chalk、execa、nanoid 等）只发 ESM；但在包的 ESM 产物中引入顶层 await 对 CJS 用户仍是 semver-major 破坏。

29. 🆕 内置测试框架 node:test 怎么用？与 Jest/Vitest 对比？

答案： node:test 是内置测试运行器：18.7 实验性引入，Node 20 起核心 API（test/describe/it/before/after）稳定，用 node --test 自动发现并以子进程隔离执行测试文件。

import { describe, it, mock } from 'node:test';
import assert from 'node:assert/strict';

describe('math', () => {
  it('adds', () => {
    assert.equal(1 + 2, 3);
  });

  it('calls spy once', () => {
    const fn = mock.fn();
    fn();
    assert.equal(fn.mock.callCount(), 1);
  });
});
  • 断言用内置 node:assert/strict；mock.fn()/mock.method()/mock.timers 提供 spy 与假定时器（模块级 mock mock.module() 仍实验性，需 --experimental-test-module-mocks）
  • 覆盖率：node --test --experimental-test-coverage（Node 22 起支持 --test-coverage-lines 等阈值门禁）
  • 快照测试需 --experimental-test-snapshots；reporter 支持 spec/tap/dot/junit/lcov；支持 --watch 与 glob
  • Node 22.18+/24 可配合类型擦除直接跑 .ts 测试（不带扩展转换，需 tsc --noEmit 兜底）

对比：优势是零依赖、零配置、与运行时同速迭代，适合库、CLI、后端服务；短板是无 jsdom/DOM 环境、无 JSX 转换、快照与匹配器生态不如 Jest/Vitest 丰富。涉及 React/DOM 的前端测试仍选 Vitest/Jest。

30. 🆕 node:sqlite 内置 SQLite 客户端现状如何？

答案： node:sqlite 是内置的同步 SQLite 客户端（SQLite C 库直接编译进 Node 二进制，无需 node-gyp/native 依赖）：

  • 22.5.0 加入，需 --experimental-sqlite
  • 22.13.0 / 23.4.0 去掉 flag（仍为实验性）
  • 25.7.0 提升为 Release Candidate（Stability 1.2）；截至 2026-09，Node 26 当前文档仍标记为 RC（Node 24 LTS 各小版本以其随附文档标注的稳定性为准，24 早期版本仍显示实验性），API 基本冻结但尚未正式 stable
import { DatabaseSync } from 'node:sqlite';
const db = new DatabaseSync(':memory:');
db.exec('CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT)');
const insert = db.prepare('INSERT INTO users (name) VALUES (?)');
insert.run('Alice');
console.log(db.prepare('SELECT * FROM users WHERE name = ?').get('Alice'));
// { id: 1, name: 'Alice' }

核心 API：DatabaseSync、StatementSync 的 run()/get()/all()/iterate()（懒迭代大结果集）、用户自定义函数、Session 扩展等。注意它只有同步 API：SQLite 嵌入式场景简单快速，但高并发服务器中的慢查询会阻塞事件循环；适合 CLI、测试、local-first/边缘场景，成熟的服务端方案仍是 better-sqlite3（同步 native 插件）或异步驱动。Web 标准层面的 Origin-Private File System / Web SQLite 仍在标准讨论中。

31. 🆕 Node.js 内置了哪些 Web 标准 API（fetch / WebSocket / Streams）？

答案： 近年 Node 大量对齐浏览器 API（多数由 undici 提供），常见全局对象无需 require：

  • fetch/Request/Response/Headers：18 引入（实验性），Node 21 起稳定（LTS 20 后期去除实验警告）；同时有 FormData、Blob、File
  • WebSocket 客户端：21 开始增强，Node 22 默认启用、22.4 标记稳定，可直接 new WebSocket('wss://...')；注意只有客户端，WebSocket 服务端仍需 ws 等库
  • Web Streams（ReadableStream/WritableStream/TransformStream）：Node 18+ 可用、21 稳定，且与 Node Stream 可通过 Readable.fromWeb()/Readable.toWeb() 互转
  • 其他：structuredClone（17+）、URL/URLSearchParams、TextEncoder/TextDecoder、atob/btoa、AbortController、Web Crypto（globalThis.crypto）；EventSource 仍带实验 flag

意义：前后端可共享同一份 HTTP/流式代码，node-fetch、cross-fetch、客户端 ws 等依赖在新项目中大多可以去掉。可用 process.versions.undici 查看内置 undici 版本。

32. 🆕 权限模型（Permission Model）解决什么问题？怎么用？

答案： 权限模型是进程级的"安全带"机制，限制 Node 进程运行时可访问的资源，适合运行第三方脚本、CLI 插件、供应链风险代码时做最小权限收敛。20.0 实验性引入，22.13.0 / 23.5.0 起转为稳定；Node 24 起启用 flag 定名为 --permission（旧版为 --experimental-permission）。

node --permission \
  --allow-fs-read=/app,/tmp \
  --allow-fs-write=/tmp \
  --allow-child-process \
  --allow-worker \
  app.js
# Node 25+ 还支持 --allow-net 控制网络访问
  • 常用 flag：--allow-fs-read/--allow-fs-write（可按路径/glob 授权）、--allow-child-process、--allow-worker、--allow-addons、--allow-inspector、--allow-net（Node 25 新增）
  • 运行时 API：process.permission.has('fs.write', '/tmp') 查询；部分权限可在运行时 grant/revoke
  • Node 22.16+ 支持以 node.config.json 配置权限（经 --experimental-config-file/默认配置文件传入，配置文件能力本身仍在演进）

重要边界：官方明确它不防御恶意代码（恶意代码可绕过），定位是防止"受信任代码无意/被利用"访问未授权资源（seat belt），不能替代容器沙箱与 OS 级隔离。

33. 🆕 如何取消 fetch 与异步操作？AbortController / structuredClone 了解吗？

答案： AbortController 自 Node 15 起为全局对象，AbortSignal.timeout(ms) 在 17.3+ 提供，可统一取消各类异步操作：

// 给 fetch 设置 3 秒超时
const res = await fetch('https://example.com/api', {
  signal: AbortSignal.timeout(3000), // 超时自动 abort，抛 TimeoutError
});

// 手动取消多个操作
const controller = new AbortController();
const req = fetch(url, { signal: controller.signal });
controller.abort(new Error('user cancelled'));

signal 选项被广泛支持：fetch、timers/promises（setTimeout(..., { signal })）、child_process spawn、events.on(emitter, name, { signal })、异步迭代、Node 内置 http client 等，是比"布尔标志位"更标准的取消方案；监听方用 signal.addEventListener('abort', ...) 或 signal.reason 取取消原因。

structuredClone（Node 17+ 全局）则用于深拷贝结构化数据（对象、数组、Map、Set、ArrayBuffer、Date 等），支持 Transferable 转移所有权；不能拷贝函数、原型链、WeakMap 等。它比 JSON.parse(JSON.stringify()) 更正确（支持循环引用、类型不丢失），比 _.cloneDeep 零依赖。

34. 🆕 AsyncLocalStorage 如何在异步链路中透传请求上下文？

答案： node:async_hooks 的 AsyncLocalStorage（ALS）提供跨异步调用链的上下文存储，可在不层层传参的情况下，让整条请求链路（await、定时器、回调）取到同一份数据，是 Node 服务端做请求 ID、日志链路追踪、多租户隔离的标准方案（cls-hooked 的官方替代，OpenTelemetry 底层也依赖 async hooks）：

import { AsyncLocalStorage } from 'node:async_hooks';
const als = new AsyncLocalStorage();

// 中间件入口：为每个请求建立独立上下文
app.use((req, res, next) => {
  als.run({ traceId: req.headers['x-trace-id'] }, next);
});

// 任意深层函数中直接读取，无需透传参数
function log(msg) {
  const { traceId } = als.getStore() ?? {};
  console.log(`[${traceId}] ${msg}`);
}

注意事项：

  • 存储基于异步资源传播，als.run(store, fn) 内发起的所有 Promise/回调共享同一 store；误用 enterWith 易造成上下文泄漏，优先用 run
  • 有一定性能开销，勿在 store 中放大对象；Node 24 对 ALS 实现做了性能优化（基于 AsyncContextFrame 的新传播路径）
  • worker_threads 之间不共享；需要跨进程传播 traceId 时仍需通过 HTTP header / 消息体显式传递

35. 🆕 Node SEA（Single Executable Applications）打包单文件程序现状？

答案： SEA 把一个 JS 应用注入 node 二进制，生成无需目标机器安装 Node 的单个可执行文件（CLI/桌面工具/本地部署分发场景）。18.16/19.7 实验性引入，20.6 起支持 startup snapshot 与 V8 code cache 加速冷启动，25.5.0 新增 --build-sea 内置生成流程（免去手工 postject 注入）；截至 Node 26 仍标记为 Stability 1.1（active development）。

传统流程：esbuild 把应用打包成单文件 → 写 sea-config.json（main/assets/useCodeCache/useSnapshot）→ node --experimental-sea-config 生成 blob → 复制 node 二进制并用 postject 注入。运行时可用 node:sea 的 sea.isSea()、sea.getAsset() 读取内嵌资源。

局限与取舍：本质是"JS + 整个 Node 运行时"塞进一个文件，体积较大（数十 MB），并非编译成原生机器码；快照阶段触碰网络/文件系统/环境变量的代码会出问题；native addon（.node）需额外处理。与 vercel/pkg（已停止维护）、nexe 相比 SEA 是官方方案；Bun 的 bun --compile 产物更小；云服务/容器化部署场景下 Docker 镜像通常仍是更合适的分发方式。

36. 🆕 --watch、node --run 与原生 TS 带来了什么开发体验变化？

答案： Node 近年把常见开发工具链"收编"进运行时，新项目可以少装很多 devDependencies：

  • node --watch app.js：文件变更自动重启进程，Node 22 起稳定（可 --watch-path 指定监听目录），开发期可替代 nodemon/PM2 watch
  • node --run <script>（Node 22.0 实验性引入，22.10 起稳定）：直接执行 package.json scripts 中的命令，不必经过 npm run（不注入 npm 的额外环境变量，启动更快，参数用 -- 透传）
  • 原生 TypeScript：node --watch app.ts + 类型擦除 + node --test "**/*.test.ts" 组成零构建 TS 开发闭环；类型检查交给编辑器与 CI 的 tsc --noEmit
  • 内置 --env-file：开发环境变量也无需 dotenv（见第 17 题）
  • 其他便利项：fs.glob/globSync（Node 22）、import.meta.dirname/filename、V8 编译缓存（NODECOMPILECACHE，Node 22+ 可显著加速重复启动）

定位上仍有边界：--watch 只做重启不做热更新（HMR），复杂 bundling/转译（React、代码分割）仍需 Vite/esbuild/tsx。

37. 🆕 2026 年 ESM 现状如何？import attributes 是什么？

答案： ESM 在 2026 年已是 Node 生态的事实主流：

  • 大量新包（chalk v5、execa、nanoid v5、node-fetch v4 等）只发布 ESM；新库普遍以 "type": "module" 为默认。配合 require(esm)（见第 28 题）稳定，CJS 用户也能消费同步 ESM，"双发布（dual package）"的必要性大幅下降，同时避免了双包的单例不一致风险（dual-package hazard）
  • 仍建议库作者保持可被同步 require：ESM 产物的可达依赖图中避免顶层 await
  • Import attributes（导入断言）在 22.12 标记稳定，用于声明模块类型，最常见的是导入 JSON：
import config from './config.json' with { type: 'json' };
const mod = await import('./wasm/greet.wasm', { with: { type: 'file' } }); // WebAssembly 等
  • 其他成熟能力：顶层 await（Node 14.8+）、import.meta.dirname/import.meta.filename（20.11/21.2 起）、动态 import()、条件 exports（import/require/node/default conditions）
  • CJS→ESM 方向一直可用：ESM 中 import pkg from 'cjs-pkg' 直接拿到其 module.exports；createRequire(import.meta.url) 可在 ESM 中应急使用 require

总结

这些题目覆盖了 Node.js 运行原理、事件循环、核心模块、框架（Express/Koa/NestJS）、错误处理、性能优化、部署和生态工具，并增补了 2024–2026 年的热门新特性（原生 TypeScript、require(esm)、node:test、node:sqlite、Web 平台 API、权限模型、AsyncLocalStorage、SEA、ESM 生态等），适合作为 Node.js 后端面试系统复习资料。版本相关结论已于 2026-09-16 核实，实际使用时以对应大版本官方文档为准。
