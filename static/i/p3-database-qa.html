数据库 常见面试题（附答案）

SQL 基础

1. 什么是关系型数据库？

答案： 关系型数据库以表（行列结构）组织数据，表间通过主键/外键关联，使用 SQL 查询，遵循 ACID 事务特性。常见：MySQL、PostgreSQL、SQL Server、SQLite（轻量）。适合结构化数据、需要事务和复杂关联查询的场景。

2. 常见的 SQL 语句类型有哪些？

答案：

  • DDL（数据定义）：CREATE TABLE、ALTER TABLE、DROP TABLE
  • DML（数据操作）：INSERT、UPDATE、DELETE
  • DQL（数据查询）：SELECT
  • DCL（数据控制）：GRANT、REVOKE
  • TCL（事务控制）：BEGIN、COMMIT、ROLLBACK

3. INNER JOIN、LEFT JOIN、RIGHT JOIN 的区别？

答案：

-- INNER JOIN：只返回两表都有匹配的行
SELECT u.name, o.amount FROM users u INNER JOIN orders o ON u.id = o.user_id;

-- LEFT JOIN：返回左表所有行，右表无匹配则 NULL
SELECT u.name, o.amount FROM users u LEFT JOIN orders o ON u.id = o.user_id;
-- 可用来查找"没有订单的用户"：WHERE o.id IS NULL

-- RIGHT JOIN：返回右表所有行（可以用 LEFT JOIN 反写）
-- FULL JOIN：两表所有行（MySQL 不支持，需 UNION 模拟）

4. 什么是子查询？和 JOIN 如何选择？

答案： 子查询是嵌套在另一个查询中的 SELECT。相关子查询（依赖外层）每行执行一次，性能差；非相关子查询执行一次，可被优化器转为 JOIN。一般优先用 JOIN（优化器更容易优化），但子查询语义更清晰时也可用。复杂场景可用 CTE（公共表表达式）WITH 提升可读性。

5. 什么是聚合函数和 GROUP BY？

答案：

-- 聚合函数：COUNT、SUM、AVG、MAX、MIN
SELECT department, COUNT(*) as count, AVG(salary) as avg_salary
FROM employees
GROUP BY department
HAVING AVG(salary) > 5000  -- HAVING 过滤分组结果（WHERE 过滤行，HAVING 过滤组）
ORDER BY avg_salary DESC;

WHERE 在分组前过滤行，HAVING 在分组后过滤组，不可混用。

6. 什么是索引？有哪些类型？

答案： 索引是加速查询的数据结构（通常是 B-Tree），以额外存储和写入成本换取读取速度。类型：① 主键索引（唯一、非空）；② 唯一索引；③ 普通索引；④ 联合索引（多列）；⑤ 全文索引（FULLTEXT，搜索文本）；⑥ 覆盖索引（查询的所有列都在索引中，无需回表）。索引不是越多越好——过多索引增加写入开销和存储。

7. 什么时候索引会失效？

答案： ① 对索引列做函数运算（WHERE YEAR(created_at) = 2024，应改为范围查询）；② 隐式类型转换（列是 int，查询用字符串 WHERE id = '1'）；③ LIKE 以通配符开头（LIKE '%keyword'，改为 LIKE 'keyword%' 可用索引）；④ OR 连接非索引列；⑤ 联合索引违反最左前缀（(a,b,c) 索引，查询只有 b=? 不走索引）；⑥ 优化器认为全表扫描更快时（小表、选择性低的列）。

8. 什么是事务？ACID 是什么？

答案： 事务是一组操作的逻辑单元，要么全部成功，要么全部失败。ACID：

  • A（原子性）：事务中操作要么全做，要么全不做
  • C（一致性）：事务前后数据库从一个一致状态变为另一个一致状态
  • I（隔离性）：并发事务互不干扰
  • D（持久性）：事务提交后修改永久保存
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT; -- 或 ROLLBACK;

9. 什么是事务隔离级别？

答案：

隔离级别 脏读 不可重复读 幻读
READ UNCOMMITTED ✓ ✓ ✓
READ COMMITTED ✗ ✓ ✓
REPEATABLE READ（MySQL 默认） ✗ ✗ ✓（MySQL 通过 MVCC 解决）
SERIALIZABLE ✗ ✗ ✗

脏读：读到未提交的数据；不可重复读：同一事务两次读结果不同；幻读：同一事务两次查询行数不同。

10. 什么是数据库锁？乐观锁和悲观锁？

答案： 悲观锁：认为冲突概率高，操作前加锁（SELECT ... FOR UPDATE），其他事务等待。适合写多读少、冲突频繁场景。乐观锁：认为冲突概率低，不加锁，提交时检查数据是否被修改（通常通过版本号 version 字段）：

UPDATE orders SET status='shipped', version=version+1
WHERE id=1 AND version=5; -- 若影响行数=0则冲突，重试

适合读多写少、冲突少场景，性能更好。

MySQL

11. MySQL 有哪些存储引擎？InnoDB 和 MyISAM 的区别？

答案： MySQL 5.5 起默认引擎是 InnoDB，旧版本默认 MyISAM。核心区别：

特性 InnoDB MyISAM
事务 支持（ACID） 不支持
锁粒度 行锁（并发好） 表锁
外键 支持 不支持
崩溃恢复 支持（redo log） 不支持，易损坏
索引结构 聚簇索引（数据在主键索引叶子节点） 非聚簇（索引和数据分离）
COUNT(*) 需扫描统计 存了总行数，直接返回（无 WHERE 时）

结论：绝大多数场景直接用 InnoDB；MyISAM 只在极少数只读、无事务需求的场景考虑。

12. 什么是聚簇索引和非聚簇索引？什么是回表？

答案： InnoDB 中聚簇索引（主键索引）的叶子节点直接存整行数据；二级索引（非聚簇）叶子节点存的是主键值。通过二级索引查询时，先在二级索引找到主键，再到聚簇索引取整行，这个过程叫回表（两次 B+ 树查找）。 优化手段：① 覆盖索引——把查询需要的列都放进联合索引，避免回表（EXPLAIN 中 Extra 显示 Using index）；② 主键尽量短且自增（二级索引都存主键，UUID 主键会导致索引膨胀和页分裂）。

13. InnoDB 的 MVCC 是如何实现的？

答案： MVCC（多版本并发控制）让读写不互相阻塞，靠三部分实现：

  • 隐藏列：每行记录有 trx_id（最后修改的事务 ID）和 roll_pointer（指向 undo log 中的旧版本）
  • undo log 版本链：每次修改生成旧版本，串成链表
  • ReadView：事务快照读时生成，记录当前活跃事务 ID 列表，按可见性规则沿版本链找到对自己可见的版本

RC 级别每次 SELECT 都生成新 ReadView（所以能读到别人已提交的修改）；RR 级别只在第一次 SELECT 生成，之后复用（所以可重复读）。注意：MVCC 只作用于快照读（普通 SELECT），SELECT ... FOR UPDATE、UPDATE、DELETE 是当前读，走锁机制。

14. 什么是行锁、间隙锁、Next-Key 锁？如何避免死锁？

答案： InnoDB 行级锁有三种形态：Record Lock（锁住索引记录本身）、Gap Lock（锁住记录之间的间隙，阻止其他事务插入，防幻读）、Next-Key Lock（Record + Gap，左开右闭区间）。RR 级别下当前读默认加 Next-Key 锁；RC 级别只有 Record 锁。 注意：锁加在索引上，如果 UPDATE 的 WHERE 条件没走索引，会退化为锁全表（锁住所有行）。 避免死锁：① 多个事务按相同顺序访问表/行；② 事务尽量短小，尽快提交；③ 走索引缩小锁范围；④ 设置 innodb_lock_wait_timeout；⑤ 业务层捕获死锁错误（MySQL 错误码 1213）后重试。

15. 如何定位和优化慢查询？EXPLAIN 怎么看？

答案： 定位：开启慢查询日志（slow_query_log=ON，long_query_time=1），用 mysqldumpslow 或 pt-query-digest 分析。 EXPLAIN 关键列：

  • type：访问类型，从好到差 system > const > eq_ref > ref > range > index > ALL，出现 ALL（全表扫描）要警惕
  • key：实际使用的索引；rows：预估扫描行数
  • Extra：Using index（覆盖索引，好）、Using filesort（额外排序）、Using temporary（临时表，GROUP BY/DISTINCT 常见）需要优化

常见优化：加合适的联合索引（注意最左前缀）、避免 SELECT *、大分页用延迟关联（先查主键再 JOIN）、LIMIT 深分页改为游标方式（WHERE id > last_id LIMIT n）、必要时反范式冗余字段减少 JOIN。

16. MySQL 主从复制的原理？读写分离和分库分表怎么做？

答案： 主从复制：主库把变更写入 binlog → 从库 IO 线程拉取写入 relay log → 从库 SQL 线程重放。默认异步复制（主库不等从库确认），可配置半同步复制降低丢数据风险。复制延迟是读写分离的经典问题：写后立即读走主库，或用 GTID 判断从库是否追上。 读写分离：写走主库、读走从库，中间件（ProxySQL、MyCat）或应用层路由。 分库分表：单表过大（经验值千万级以上）或单库连接/IO 到瓶颈时考虑。垂直拆分（按业务拆库、按字段拆表）优先；水平拆分按分片键（如 user_id 取模/范围）路由，需解决跨分片 JOIN、分布式事务、全局 ID（雪花算法）、扩容迁移等问题。中间件：ShardingSphere。原则：先优化索引和架构，分库分表是最后手段。

PostgreSQL

17. PostgreSQL 和 MySQL 有什么区别？如何选型？

答案：

维度 MySQL（InnoDB） PostgreSQL
定位 简单可靠、互联网 OLTP 功能全面的对象-关系型数据库
SQL 标准 部分支持 遵循度高，窗口函数/CTE 支持早且完善
数据类型 常规类型 JSONB、数组、UUID、范围、几何、自定义类型
MVCC undo log 版本链 行多版本 + VACUUM 清理
默认隔离级别 REPEATABLE READ READ COMMITTED
扩展生态 插件较少 PostGIS（地理）、pg_trgm（模糊搜索）、TimescaleDB 等
复制 binlog 逻辑复制为主 流复制（物理）+ 逻辑复制

选型：互联网高并发简单读写、团队熟悉 MySQL 生态 → MySQL；复杂查询/分析、JSON 文档与关系混合、地理信息、需要丰富索引和扩展 → PostgreSQL。两者性能在多数场景差距不大，团队熟悉度往往比数据库本身更重要。

18. PostgreSQL 的 MVCC 和 MySQL 有何不同？为什么需要 VACUUM？

答案： PG 的 MVCC 是行多版本：UPDATE 实际是「标记旧行失效 + 插入新行」，每行有 xmin/xmax 记录创建/删除它的事务 ID，事务按快照判断哪个版本可见。旧版本（死元组 dead tuple）留在表文件中，不像 MySQL 存在 undo log 里可自动回收。 因此需要 VACUUM：① 回收死元组空间供复用；② 更新可见性映射；③ 防止事务 ID 回卷（wraparound，严重时会强制停库）。autovacuum 默认自动运行，但大批量写入/删除的表需要调参（autovacuum_vacuum_scale_factor）或手动 VACUUM。VACUUM FULL 会重写整表并加排他锁，生产慎用。这也是 PG 频繁 UPDATE 的表容易「膨胀（bloat）」的原因。

19. PostgreSQL 的 JSONB、数组等特有类型怎么用？

答案：

-- JSONB：二进制存储的 JSON，可建 GIN 索引，支持包含/存在查询
CREATE TABLE events (id serial PRIMARY KEY, payload jsonb);
SELECT * FROM events WHERE payload @> '{"type": "click"}';
SELECT payload->>'user_id' FROM events;  -- ->> 取文本，-> 取 jsonb
CREATE INDEX idx_payload ON events USING gin (payload);

-- 数组类型
CREATE TABLE posts (id serial, tags text[]);
SELECT * FROM posts WHERE tags @> ARRAY['nodejs'];

-- UUID / 生成列 / 枚举
CREATE TABLE users (id uuid DEFAULT gen_random_uuid() PRIMARY KEY);

JSONB vs JSON：JSONB 写入稍慢但查询快、支持索引，绝大多数场景选 JSONB。这让 PG 能「一库两用」：核心字段用关系列保证约束，灵活字段放 JSONB，兼顾 MySQL + MongoDB 的部分场景。

20. PostgreSQL 支持哪些索引类型？

答案：

  • B-Tree（默认）：等值、范围、排序，同 MySQL
  • GIN（倒排索引）：JSONB、数组、全文搜索（tsvector）、pg_trgm 模糊匹配
  • GiST / SP-GiST：几何、地理（PostGIS）、范围类型、最近邻搜索
  • BRIN：块级摘要索引，超大表且数据物理有序（如时间序列）时极省空间
  • Hash：仅等值查询

特色用法：

-- 部分索引：只索引满足条件的行，小而快
CREATE INDEX idx_active ON users (email) WHERE status = 'active';
-- 表达式索引：解决「对列做函数导致索引失效」问题
CREATE INDEX idx_lower_email ON users (lower(email));
-- 模糊搜索：LIKE '%keyword%' 也能走索引
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_name_trgm ON users USING gin (name gin_trgm_ops);

21. PostgreSQL 的事务隔离级别和 MySQL 有什么不同？

答案： PG 默认 READ COMMITTED（MySQL 默认 RR）。PG 实际只实现三种级别：RC、RR、SERIALIZABLE（声明 READ UNCOMMITTED 会按 RC 执行，因为 MVCC 天然不可能脏读）。PG 的 RR 基于事务级快照，幻读也不会出现。PG 的 SERIALIZABLE 用 SSI（可串行化快照隔离）实现：不加读写锁，通过检测读写依赖冲突，发现不可串行化时让其中一个事务报错回滚（错误码 40001），应用层需重试。对比 MySQL 的 SERIALIZABLE 把所有 SELECT 隐式加共享锁，PG 的 SSI 并发性能通常更好。另外 PG 支持事务内 DDL（CREATE TABLE 可回滚），MySQL 的 DDL 会隐式提交事务。

NoSQL

22. Redis 是什么？有哪些数据结构？

答案： Redis 是内存数据库，支持持久化，以高性能键值存储为核心。数据结构：

  • String：最基础，计数器、缓存、分布式锁（SET key value NX EX 30）
  • Hash：对象存储（HSET user:1 name Alice age 25）
  • List：消息队列、最近记录（LPUSH/RPOP）
  • Set：去重集合、共同好友（SADD/SMEMBERS/SINTER）
  • Sorted Set：排行榜（ZADD，按分数排序，ZRANGE/ZRANK）
  • Bitmap/HyperLogLog/Stream：特殊用途（统计日活、流式日志）

23. Redis 的缓存策略有哪些？

答案： 缓存击穿（热点 key 过期，大量请求直击 DB）：互斥锁（只允许一个请求重建缓存）或不设过期时间+主动更新。缓存穿透（查询不存在的数据，缓存永远不命中）：布隆过滤器拦截、缓存空值（短 TTL）。缓存雪崩（大量 key 同时过期）：过期时间加随机抖动、Redis 集群高可用。缓存更新策略：Cache-Aside（读缓存、缓存未命中查 DB 并写入）、Write-Through、Write-Behind。

24. MongoDB 和 MySQL 如何选择？

答案： MongoDB（文档型 NoSQL）适合：数据结构多变（Schema 灵活）、嵌套文档（评论、标签等）、大量非结构化数据、快速迭代原型、需要水平扩展。MySQL（关系型）适合：数据结构稳定、需要复杂关联查询、严格事务（金融）、数据一致性要求高。混合使用也很常见：MySQL 存核心业务数据，MongoDB 存日志/用户行为，Redis 做缓存。

25. 什么是 ORM？常见 Node.js ORM 有哪些？

答案： ORM（对象关系映射）允许用面向对象的方式操作数据库，自动生成 SQL，避免手写 SQL。常见 Node.js ORM：

  • Prisma：类型安全、自动生成 TypeScript 类型、Schema 优先、现代项目首选
  • TypeORM：装饰器风格、适合 NestJS
  • Sequelize：老牌，支持多数据库
  • Drizzle ORM：轻量、类型安全、更接近 SQL 语法

Prisma 示例：

const users = await prisma.user.findMany({
  where: { age: { gt: 18 } },
  include: { orders: true },
  orderBy: { createdAt: 'desc' },
  take: 10,
});

26. 什么是数据库连接池？

答案： 连接池预先创建并维护一定数量的数据库连接，请求时从池中借用，用完归还，避免每次操作都建立/断开连接（建立连接开销大）。关键参数：最小连接数、最大连接数（超过则等待或报错）、空闲超时。Node.js 中 Prisma/TypeORM/Sequelize 都内置连接池管理。生产环境需根据数据库和服务器性能调整池大小。

Node.js 中的数据库应用

27. Node.js 如何连接 MySQL / PostgreSQL？驱动如何选？

答案：

  • MySQL：mysql2（事实标准，支持 Promise、预处理语句、连接池）
  • PostgreSQL：pg（node-postgres，事实标准）
  • ORM 层：Prisma / Drizzle / TypeORM / Sequelize（底层也是这些驱动或自有实现）
// mysql2/promise
import mysql from 'mysql2/promise';
const pool = mysql.createPool({
  host: 'localhost', user: 'app', database: 'demo',
  connectionLimit: 10, waitForConnections: true,
});
const [rows] = await pool.query('SELECT * FROM users WHERE id = ?', [1]);

// pg
import { Pool } from 'pg';
const pool = new Pool({ host: 'localhost', database: 'demo', max: 10 });
const { rows } = await pool.query('SELECT * FROM users WHERE id = $1', [1]);

注意占位符差异：mysql2 用 ?，pg 用 $1, $2。Serverless 环境（连接数易爆）可加 PgBouncer 或 Prisma Accelerate 这类连接代理。

28. 如何防止 SQL 注入？

答案： 核心原则：永远不要拼接用户输入到 SQL 字符串，用参数化查询（预处理语句），驱动会把参数作为数据而非 SQL 代码传输：

// ✗ 危险：字符串拼接
pool.query(`SELECT * FROM users WHERE name = '${name}'`);
// ✓ 参数化
pool.query('SELECT * FROM users WHERE name = ?', [name]);      // mysql2
pool.query('SELECT * FROM users WHERE name = $1', [name]);     // pg

补充：① 表名/列名/ORDER BY 方向不能参数化，需用白名单校验；② ORM 的查询 API 天然参数化，但 $queryRaw / sequelize.query 等原始 SQL 接口仍要用参数绑定（Prisma 的 $queryRaw 配合模板字符串标签用法是安全的，$queryRawUnsafe 不安全）；③ 数据库账号遵循最小权限原则。

29. Node.js 中如何正确使用连接池和事务？

答案： 事务的关键：所有语句必须在同一个连接上执行，不能从池里随机拿连接。正确做法是取出一个连接，用完归还：

// mysql2
const conn = await pool.getConnection();
try {
  await conn.beginTransaction();
  await conn.query('UPDATE accounts SET balance = balance - ? WHERE id = ?', [100, 1]);
  await conn.query('UPDATE accounts SET balance = balance + ? WHERE id = ?', [100, 2]);
  await conn.commit();
} catch (e) {
  await conn.rollback();
  throw e;
} finally {
  conn.release(); // 必须归还，否则连接泄漏，池耗尽后所有请求挂起
}

// pg
const client = await pool.connect();
try {
  await client.query('BEGIN');
  // ... 同上
  await client.query('COMMIT');
} catch (e) {
  await client.query('ROLLBACK');
  throw e;
} finally {
  client.release();
}

ORM 封装了这套样板：Prisma 用 prisma.$transaction([...]) 或交互式 $transaction(async (tx) => {...})。常见事故：忘记 release、在事务里做耗时的外部 HTTP 调用（长时间占用连接和锁）。

30. 大量数据的查询和插入如何优化？

答案： 查询：① 分页避免深 OFFSET，用游标分页；② 流式读取避免一次性把百万行加载进内存：

// pg：pg-query-stream
import QueryStream from 'pg-query-stream';
const stream = client.query(new QueryStream('SELECT * FROM big_table'));
for await (const row of stream) { /* 逐行处理 */ }
// mysql2：pool.query(...).stream() 同样支持

插入：① 批量 INSERT（一条语句多组 VALUES）远快于逐条插入，mysql2 用 pool.query('INSERT INTO t (a,b) VALUES ?', [rows])，pg 可用 pg-copy-streams 走 COPY 协议（最快）；② 大批量分批提交（如每 1000 行一个事务）；③ 导入场景可先删索引、导入后重建。 其他：只 SELECT 需要的列；聚合尽量下推到数据库；Node 单线程不要在拿到大量行后做重 CPU 计算，会阻塞事件循环。

31. ORM 和原生 SQL 如何选择？

答案： ORM 优势：类型安全（Prisma/Drizzle 生成的 TS 类型）、迁移管理（migration）、防注入、开发效率高、切换数据库成本低。原生 SQL 优势：复杂查询（窗口函数、CTE、递归）表达力强、性能可精确控制、无抽象泄漏。 实践建议：CRUD 用 ORM，复杂报表/分析查询用原生 SQL（Prisma $queryRaw、Drizzle sql 模板），两者混用是主流。面试加分点：了解 ORM 的 N+1 问题——循环里逐条查关联数据，应改为 include/join 一次取回或 DataLoader 批量合并；以及 ORM 生成的 SQL 要用日志/EXPLAIN 验证，避免隐式全表扫描。

32. 数据库连接异常、超时和优雅关闭如何处理？

答案：

  • 错误处理：pg 的 Pool 要监听 error 事件（空闲连接被服务端断开时触发，不监听会导致进程崩溃）；mysql2 连接错误后池会自动重建连接
  • 超时：设置查询超时（pg：statement_timeout；mysql2：连接级配置），避免慢查询无限占用连接；获取连接也要有等待上限
  • 重试：只对可重试错误（死锁 1213/40001、连接闪断）做指数退避重试，且写操作重试要保证幂等
  • 优雅关闭：进程收到 SIGTERM 时先停止接收新请求，等在途请求完成，再 pool.end() / prisma.$disconnect()，最后退出；K8s 环境配合 preStop hook
  • 健康检查：就绪探针执行 SELECT 1，数据库不可用时摘除流量而不是让请求堆积
